## 1 · What's a vector (embedding)? — the core primitive ⭐

### 1.1 The definition

▸ **CRUX** — a **vector (embedding) is just an array of numbers that represents something** — a word, sentence, image, user, product, anything you can feed a model. ⭐ **The magic: similar things end up with similar vectors.**

```
"The cat sat on the mat"    → [0.12, -0.34, 0.78, ..., 0.45]   ┐ very
"A feline rested on a rug"  → [0.11, -0.32, 0.79, ..., 0.44]   ┘ similar
"The stock market crashed"  → [-0.89, 0.12, -0.45, ..., 0.23]  ← very different
```

- ⭐ **The whole point:** ⭐ **geometric closeness between vectors = semantic closeness between the things.** Distance in vector space _means_ similarity.

### 1.2 Dimensions

- ▸ Typical embedding = **128–1536 dimensions** (OpenAI `text-embedding-3-large` = 3072). Each dimension captures _some_ aspect of meaning; ⚠ **individual dimensions aren't human-interpretable.** What matters is the geometry, not any one number.

### 1.3 ⚠ What "similar" actually means — it depends on the model

> ⚠ **Don't gloss this — it's the one conceptual subtlety.** "Similar" isn't one fixed thing.

- ▸ **Pre-trained models** (OpenAI embeddings, Sentence Transformers, BERT for text; CLIP, ResNet for images) give a **vague "semantic" similarity.** To you the model is _"an expensive GPU function: data in, fixed-length vector out."_
- ⭐ **Custom-trained models define similarity precisely for the task.** Example: **diapers and bottles** are only vaguely similar semantically, but **profoundly similar as "things new parents buy together"** — a recommendation model trained on co-purchase makes their vectors close. ▸ **The embedding model decides what "similar" means.**

## 2 · Similarity metrics ▹

> ▹ **Working knowledge only.** ⭐ **The interview move:** say _"we'd use cosine similarity, or some appropriate metric"_ and you're **ahead of most candidates.** Metric choice rarely matters in an infra round; it matters in an **ML** round tied to your embedding model.

|Metric|Measures|Notes|
|---|---|---|
|**Euclidean (L2)**|straight-line distance (Pythagoras, many dims)|smaller = more similar; cares about **direction AND magnitude**|
|⭐ **Cosine similarity**|the **angle** between vectors, ignoring magnitude|1 = same direction, 0 = perpendicular, −1 = opposite. ⭐ **great when embeddings are normalized (most are)** — the default answer|
|**Dot product**|cosine × both lengths (no normalization)|slightly **faster** to compute; some systems prefer it|
|**Hamming**|# positions where two **binary** vectors differ|extremely fast (XOR + count) → popular in **LSH** (§4.3)|

## 3 · The nearest-neighbour problem ⭐

### 3.1 KNN — the exact version

▸ **K-Nearest Neighbours (KNN):** given a **query vector** (your "search term" — usually the embedding of the item you want neighbours for), return the **K most similar vectors.**

▸ **Naive exact KNN:** compare the query against **every** vector, score, sort, return top K. ⚠ **O(n)** in the number of vectors.

```python
def exact_knn(query, all_vectors, k):
    heap = []                                   # min-heap by similarity
    for v in all_vectors:
        s = compute_similarity(query, v)
        if len(heap) < k:            heapq.heappush(heap, (s, v.id))
        elif s > heap[0][0]:         heapq.heapreplace(heap, (s, v.id))
    return sorted(heap, reverse=True)
```

### 3.2 ⚠ Why exact doesn't scale

- ⚠ **1M vectors × 1536 dims ≈ 6 billion float ops per query.** Too slow for many apps.
- ▹ **It can be sped up** — SIMD on CPU (2–8 vectors at once), vectorized GPU ops (thousands at once). ▸ So exact KNN _is_ achievable if truly required — but **most apps tolerate slight inaccuracy for a lot of speed.**

### 3.3 ⭐ ANN — the foundation of every vector DB

▸ **CRUX** — **Approximate Nearest Neighbour (ANN):** find vectors that are _probably_ the nearest neighbours _most of the time._ ⭐ **Trade accuracy for speed** — don't always get the exact top-K, but get many close ones fast.

- ⭐ **The quality metric is recall:** _of the true top-K, what fraction did we find?_ **0.95 recall = found 95% of the true neighbours.** For most apps, plenty.

### 3.4 ⭐ The tradeoff triangle — what a vector DB _is_

> ⭐⭐ **This is the mental model to carry into any room.** A vector DB is a machine for making a **smooth tradeoff** between three things:

- **Recall** — how accurate are the results?
- **Latency** — how fast do we return them?
- **Memory** — how much RAM does the index eat?

▸ **Every indexing algorithm below, and every knob on it, is just a way to move around inside this triangle.** Push recall up → pay in latency or memory. That's the whole game.

---

> ▸ **Where we stand:** we have **vectors** (§1), a **similarity metric** (§2), and we know **brute force is O(n) and doesn't scale** (§3.2). ⭐ **The rest is one question: what clever data structure lets us skip most comparisons?** §4 covers the ANN indexes that do it; §5–§7 the practical concerns (filtering, writes, scaling).

## 4 · Indexing strategies (ANN algorithms) ⭐

> ⭐ **HI's explicit calibration:** _"most interviews will rarely approach this level of detail. The important thing is not that you can implement these, but that you have an intuition for how they work."_ ▸ **A key selling point of a vector DB:** it lets you **swap indexing strategies and tune parameters without rewriting your app.** You pick via an **eval set** (queries with known-good results) measuring recall/latency — not by proving one is best on paper.

### 4.1 ⭐ HNSW (Hierarchical Navigable Small World) — the one to know

> ⭐⭐ **HI: _"the most popular algorithm in production. If you remember one indexing strategy, make it this one."_**

▸ **The intuition = skip lists.** A linked list is O(n) to search. A **skip list** adds "express-lane" layers on top: the bottom has every element, higher layers keep a sparse random subset. Search **starts at the top express lane, zooms forward until it'd overshoot, drops a level, repeats** → **O(log n).**

```
skip list:
  L2:  A -----------------> M -----------------> (end)      ← sparse express lane
  L1:  A ------> F -------> M ------> S -------> (end)
  L0:  A -B-C-D-E-F-...-M-...-S-...-Z  (all elements)        ← dense base
```

▸ **HNSW applies this to a graph of vectors.** Each vector = a **node**; on insert, the index finds the most-similar existing vectors and **draws edges** to them. So "Taylor Swift" auto-connects to "Beyoncé," "Ed Sheeran" — not manually, but because their vectors are geometrically close. ⭐ **You can "walk" from any vector to similar ones by following edges, and similar vectors have a short path between them.**

▸ **Multi-layer, like the skip list:**

- **Layer 0** = _all_ vectors, densely connected to neighbours.
- Each vector has some probability of being **promoted** to higher layers.
- **Layer 1** = tens of thousands, **Layer 2** = hundreds… higher layers = **long-range "express" connections** to jump across the space.

▸ **Search — top-down:**

1. Start at the **top layer**, random entry point.
2. **Greedy step:** move to whichever neighbour is closest to the query.
3. Repeat until you can't get closer **at this layer.**
4. **Drop down** a layer (more nodes) and continue greedy search.
5. At **Layer 0**, do a thorough local search for the K nearest.

- ⭐ **Why it works:** top layers **zoom you into the right region** fast; by Layer 0 you're already in the right neighbourhood and only explore locally → **O(log n) with 95%+ recall.** That combo is why it's the **default.**
    
- ⚠ **The costs — this is what you mention as the tradeoff:**
    
    - ⚠ **Memory-hungry** — you store the graph (all edges) on top of the vectors → **~2× the raw vector memory.**
    - ⚠ **Slow to build** — constructing the graph is expensive.
    - ⚠ **Inserts are pricey** — each new vector must find its place and wire up connections at each layer (§6).
- ⭐ **The verbatim room-answer** (HI's): _"It builds a multi-layer graph where vectors are nodes. Search starts at a sparse top layer and greedily navigates toward the target, dropping to denser layers as it gets closer. It's like skip lists but for high-dimensional space."_
    

#### 4.1a ⚠ Confusion resolved — it's not a tree, and "dropping down" isn't an edge

> **Doubt (essence):** if nodes are connected, why need the skip-list layers — can't you just drill straight down through children? And how do you actually move _between_ layers?

- ⚠ **WRONG picture — a tree.** Top node → its children → their children, drilling vertically down. ⭐ **CORRECT — stacked per-layer graphs.** Each layer is its **own graph**; edges are **horizontal, within a layer** (Taylor Swift → Beyoncé is a Layer-0 sideways edge, not a link to a child). **There are no parent→child links.**
- ⭐ **Fix the direction:** ⚠ **Layer 0 has the MOST nodes; higher layers have FEWER.** Membership is **nested** — every node is in Layer 0; a shrinking random subset is _also_ promoted up. So `Layer 0 ⊇ Layer 1 ⊇ Layer 2`.
- ⭐ **How you move between layers — the crux:** a promoted node is the **same node** in every layer below, not connected _to_ a lower node. Each node keeps a **separate neighbour list per layer** (long-range edges up top, short-range at the bottom). ⭐ **"Drop down at node i" = stop reading i's Layer-1 neighbours, start reading i's Layer-0 neighbours.** Same node, different address book — **no downward edge to traverse.**
- ⭐ **You descend at wherever greedy search stalls**, not at a fixed wired point. Stuck at i in Layer 2 → continue at i in Layer 1 (nested membership _guarantees_ i is there) → stuck again → continue at i in Layer 0.
- ⭐ **Why the layers are necessary at all:** Layer 0 edges are **short-range only** → crossing the space there = thousands of tiny hops (the O(n) crawl). ⭐ **Upper layers are the ONLY source of long-range jumps** — few nodes, big edges → cross the space in a few strides, land near the target, _then_ drop to Layer 0 for precise local hops.
- ▸ **Analogy:** Layer 0 = **local roads** (every house, adjacent-only). Upper layers = **highway** (few on-ramps, cross the country fast). Highway to the right city → exit to local roads for the last mile. No highway → drive the whole trip on residential streets.

### 4.2 IVF (Inverted File Index) — the cluster-based alternative ▹

▸ **Different approach: partition vectors into clusters via k-means.** Each cluster has a **centroid**; each vector is assigned to its nearest centroid.

- ▸ **Query:** find the closest **centroids** to the query, then search **only within those clusters.** 1000 clusters, search 10 → **99% of comparisons eliminated.**
- ⭐ **The `nprobe` knob:** how many clusters you search. Higher `nprobe` → better recall, slower. ▸ **This is the triangle knob (§3.4) made concrete.**

#### 4.2a ⭐ The edge problem — this IS `04a`'s boundary problem

> ⭐ **HI says it outright:** _"the problem, like geospatial indexing, is the edges."_ ▸ Direct callback to `04a §5.1a`.

- ⚠ **Problem:** if the query sits **near a cluster's edge**, its true neighbours may be in the **adjacent** cluster → searching only the "right" cluster misses them.
    
- ⚠ **Worse in high dimensions:** in 2-D there's limited "edge"; in **1536-D there is enormous edge/surface** → far more boundary risk. ▸ Same as the geohash boundary (`04a §5.1a`) but amplified by dimensionality; the fix is the same shape — **search neighbouring cells/clusters too.**
    
- ▹ **Parallelism note:** probes parallelize, so a _single_ query needn't slow as `nprobe` rises — but a **loaded** system already saturates compute, so higher `nprobe` **does** raise average latency.
    
- ⭐ **vs HNSW:** IVF is **faster to build**, **handles inserts more gracefully** (just assign to a cluster), and uses **less memory** (store cluster assignments, not a full graph). ⚠ **Downside: typically lower recall for the same latency**, especially if data doesn't cluster naturally.
    

### 4.3 LSH (Locality Sensitive Hashing) `(⚠ below the interview waterline — knowledge only)`

> ⊕ **(not in HI) What's a hyperplane?** Just a **flat divider that cuts a space into two halves** — one dimension lower than the space it sits in: a **point** splits a line, a **line** splits a 2-D plane, a **flat plane** splits 3-D, and the 1536-D version (unpicturable) is the "hyperplane." ⭐ **Its only job: given a point, answer "which side are you on?"** — above or below. LSH turns that yes/no into a **hash bit**; Annoy (§4.4) turns it into a **tree branch**; k-d trees (`04a §4.2`) use axis-aligned ones. Same primitive, three wrappers.

▸ **The inversion of a normal hash:** regular hashing **avoids** collisions; **LSH is designed to _cause_ collisions for similar items** — similar vectors hash to the same bucket.

- ▸ **Mechanism (cosine):** draw **random hyperplanes** (a plane in high-D space). Each vector is "above" or "below" each plane = **one bit.** 8 planes → an 8-bit hash. Close vectors land on the same side of most planes → similar hashes.
- ▸ **Robustness:** use **multiple hash tables** with different random planes; the chance similar vectors share _at least one_ bucket rises sharply. Query = hash in all tables, collect candidates from matching buckets, **exact-distance the small candidate set** (⭐ same candidate-set discipline as everywhere, `04a`).
- ⚠ **Why it's below waterline:** popular **before** HNSW; simpler, good in high dims, nice theory — but **HNSW usually beats it on recall-for-latency.** Still useful when you need:
    - **Very fast index building** (just compute hashes)
    - **Streaming data** where vectors arrive continuously
    - **Hamming** distance similarity (LSH is natural here)
- ▸ **All you carry: "older, HNSW-beaten, natural for binary/Hamming."**

### 4.4 Annoy (Spotify) `(⚠ below the interview waterline — knowledge only)`

▸ **Random-projection _forest_.** Recursively split the space with random hyperplanes until each **leaf** holds few vectors; build **many trees** (10–100), each with different random splits (strong analog to **Random Forest**). Query = traverse all trees, union the candidate leaves, exact-distance them.

- ⭐ **Killer feature — memory mapping (`mmap`):** the whole index is one file `mmap`'d into memory → **multiple processes share it, index can exceed RAM (OS pages it in), loading is instant.**
- ⚠ **The cost — immutable.** Once built you **can't add/remove**; you rebuild the whole index. ▸ **Great for static datasets (Spotify's batch-updated catalog), unsuitable for real-time arrivals.** All you carry: "older, immutable, mmap-friendly, static data."

## 5 · Filtering and hybrid search ▹

> ▸ **The real-world wrinkle:** apps rarely want _"the 10 most similar"_ unconditionally — they want _"10 most similar **that are in stock / in budget / published this year.**"_ That's **filtered vector search**, and it's trickier than it sounds.

> ⭐ **First, separate two things §5 combines with similarity** — they're different operations, easy to conflate:
> 
> - **Filtered search (§5.1)** — similarity + a **hard boolean gate** (`in_stock`, `price<5000`). The filter **excludes** rows; it never changes ranking. Vector similarity does all the ranking.
>     
> - **Hybrid search (§5.3)** — similarity + **another relevance _score_** (usually keyword/BM25). Two rankings **blended** into one.
>     
> - ⭐ **Pre-filter vs post-filter is NOT a third option** — it lives _inside_ filtering, as the "**when do I apply the gate**" knob (before vs after the vector search). Hybrid has no pre/post — there's no gate to order, only two score-lists to merge.
>     
> - ⚠ They **compose**: a real query can be _"hybrid-ranked **and** filtered to in-stock."_ Orthogonal — one blends scores, the other gates rows.
>     

### 5.1 ⭐ Pre-filter vs post-filter — the decision

||How|⚠ Problem|
|---|---|---|
|**Post-filter**|find top-N similar (N ≫ K), then filter down to K|⚠ if the filter is **restrictive**, you may not get K results → must raise N → more work|
|**Pre-filter**|filter first, then search only the filtered set|⚠ you may **not be able to use the index** on an arbitrary subset|

- ⭐ **The honest room-answer:** _"This depends heavily on the data — I'd benchmark both on real data and see which wins."_ ▸ HI stresses you **can't** make sweeping claims here.
- ⭐ **The one coarse rule interviewers probe for:** if you're vector-searching only a **tiny subset** of your data, **pre-filtering is probably better.** ▹ Same flavour as FB Post Search, with a multi-dimensional twist.
- ▸ **Note the connection:** post-filtering = **candidate set then exact filter** — the identical _"index gives candidates, you finish exactly"_ discipline from `04a`.

### 5.2 How real systems handle it ▹

|System|Approach|Note|
|---|---|---|
|**pgvector** (`02g`)|leans on Postgres's **query planner** — one SQL with `WHERE` + `ORDER BY <vector distance>`|⚠ for highly selective filters it often **skips the vector index** and brute-forces the filtered rows (faster). ⚠ no _true_ filtered-HNSW → suboptimal in the awkward middle|
|**Elasticsearch kNN** (`02b`)|filter applied **during** HNSW traversal, not after → **guaranteed K results**|⚠ restrictive filters **slow** search (must traverse more graph). Native **hybrid** via `sub_searches`/`rescore`|
|**Pinecone**|metadata filtering **first-class** (inverted indexes on metadata alongside the vector index), applied **during** ANN|tunable "filter effort" knob|

### 5.3 Hybrid search — keyword + vector together

- ▸ **"red running shoes"** → keyword-match "red"/"running shoes" **and** vector-similarity for semantically related products. ⭐ **Often beats either approach alone.** Do both searches in parallel and **merge**, or use cleverer merge strategies. ▸ **Elasticsearch gives this out of the box** (BM25 + vector, `02b`).

## 6 · Inserts, updates, index maintenance ⭐

> ⭐ **The single biggest structural difference from a traditional DB — and a favourite interview probe.** Vector DBs are **read-optimized; writes are hard.**

### 6.1 Why writes are hard

- ⚠ **HNSW insert** = find the new vector's place + update connections at each layer → **compute-expensive**, and over many inserts the **graph degrades** (late vectors less well-connected than build-time ones).
- ⚠ **IVF** drifts too — clusters evolve, so you periodically **rebuild** or recall degrades.
- ⚠ ⭐ **The core contrast:** traditional DBs handle real-time writes by design; **vector DBs often can't.** ▸ So in a room you **deliberately discuss a rebuild strategy.**

### 6.2 ⭐ The hot/cold index pattern — the answer to "how do you handle writes?"

> ⭐ **HI flags this as a general pattern, not vector-specific — you'll reuse it.**

- ▸ Keep a **small "hot" index** for recent inserts + a **large "cold" index** for older data. **Queries hit both, merge results.** Periodically the hot index **merges into cold with a full rebuild.**
- ⭐ **The hot index needn't even be a real index** — it can be a **dumb list of un-indexed entries you exhaustively scan** (small, so cheap).
- ▸ **Same pattern, other uses (HI's example):** rare **deletions** → keep a small "deleted items" index you check before returning results, buying time to clean caches/precomputations later.

### 6.3 Deletes and rebuilds

- ▸ **Updates = delete + insert.** Most systems use **soft deletes** (mark, don't remove) → ⚠ deleted vectors still **consume space and slow queries** until a rebuild/compaction.
- ⚠ **Rebuilds are slow** — HNSW over millions of vectors can take **hours.** Strategies: **rolling rebuild** (build new alongside old, swap) · **partitioned indexes** (rebuild one partition at a time) · **background reindexing** (doesn't block queries).
- ⭐ **If embeddings change often** (model updates, fast-changing data) → prefer **batch updates + periodic rebuilds** over real-time.

#### 6.3a ⚠ Confusion resolved — the four write flows (and two separate mechanisms)

> **Doubt (essence):** how do insert / delete / update actually flow through hot vs cold, and what does compaction clean up?

- ⚠ **The trap:** fusing two _separate_ mechanisms into one. They're orthogonal:
    - **Mechanism 1 — deletes:** a delete is a **soft-delete (tombstone)** — flag the vector "deleted," queries skip it, it physically stays until compaction. Not removed in place.
    - **Mechanism 2 — writes:** every new vector lands in the small **hot** index (cheap); the big **cold** index is left alone. Queries hit **both, merge.**
- ⭐ **The four flows:**

|Operation|What happens|
|---|---|
|**Insert**|new vector → **hot** index|
|**Delete**|**soft-delete (tombstone)** the vector where it lives (usually cold)|
|**Update**|soft-delete old (where it lives) **+** insert new → **hot**|
|**Compaction / rebuild**|**purge all tombstones** (from deletes _and_ update's delete-half) **+ merge hot → cold**|

- ⭐ **Rebuild is the join point:** the tombstones (Mechanism 1) and the accumulated hot inserts (Mechanism 2) are **separate systems that meet at the same periodic rebuild** — one rebuild resolves both.
- ⚠ **One precision — the tombstone follows the vector, not "always cold."** Usually you're deleting old data (in cold), so "mark in cold" is right ~99% of the time. But a **very recently inserted** vector may still be in **hot** — the soft-delete happens **wherever the vector currently lives.** Don't hard-wire "delete ⇒ cold."
- ⭐ **To the user it looks like one atomic update;** under the hood it's a deferred soft-delete + a hot-index insert, reconciled at the next rebuild.

### 7.2 Purpose-built — when you need scale `(compress to one line)`

- ⭐ **Rule of thumb: consider a dedicated vector DB past ~100M vectors**, or when retrieval/recommendation _is_ the whole problem.
- ▹ **The lineup (name-drop tier — carry the one-liners, skip the rest):**

    - **Chroma** — lightweight, prototyping, popular in **LLM/RAG**.

## 8 · Using vector DBs in your interview ⭐

### 8.1 Common scenarios — where they're effectively mandatory

> ▸ You'll **know in advance** — it's an AI/ML team or an AI-focused company. These question shapes mandate a vector DB:

- **Semantic search** — _"design a document/code search system."_ Natural-language query → relevant docs. Classic embedding + vector search.
- **Recommendations** — _"design a product recommendation system / content feed."_ ⭐ **Meesho / Swiggy territory.** Often + collaborative filtering.
- **Image/video similarity** — _"reverse image search," "similar videos."_ Embed media, search embeddings.
- **RAG** — _"knowledge-base Q&A," anything LLM + custom data._ ⭐ **Your agentic-AI territory** — vector search retrieves docs, LLM synthesizes.
- **Deduplication** — near-duplicate detection (plagiarism, duplicate listings/tickets). Embed, find within a similarity threshold.
- ⭐ **Anomaly / fraud detection** — _"design a fraud detection system."_ ⭐ **Razorpay / CRED hook** — embed transactions, flag ones **dissimilar** to normal patterns.

### 8.2 ⭐ Architecture patterns

|Pattern|Shape|When|
|---|---|---|
|⭐ **1 · Vector DB as a separate service**|app gets an embedding → sends to vector service → gets back **IDs** → **fetches full details from your primary DB**|⭐ **the default — use this for almost everything.** Clean separation|
|**2 · Hybrid search**|query hits **both** a keyword index (ES) and a vector index → merge with a ranking function|search apps where exact + semantic both matter|
|**3 · Two-stage retrieval**|vector search returns a **large candidate set** (~top 1000) → a slower, richer model **reranks** to final K|recommendations where the reranker uses features the embedding misses|

- ⚠ **HI's warning:** unless the question is _specifically_ about this, extra patterns **rabbit-hole you into new hard problems** rather than impressing. ⭐ **Stick with Pattern 1.**

### 8.3 ⭐ Key design decisions to raise

- ⭐ **Consistency** — vector results are usually fine **slightly stale.** Say it explicitly: _"vector search can be eventually consistent; the embedding needn't be searchable the instant after insert."_
- ⭐ **Update strategy** — real-time as items are created, or hourly batch? Depends on latency needs (§6).
- ⭐ **Filtering strategy** — pre / post / hybrid, especially if filters are selective (§5).
- ▹ **Less common (ML-round) decisions:** embedding-model choice (_"a sentence transformer" / "OpenAI's API"_) · index type (_"HNSW unless write-heavy / huge / memory-bound"_) · embedding updates (model refresh = massive rebuild; ⭐ **tag stored vectors with which model produced them** so you never search across mismatched embeddings).

## 9 · Numbers to know ▹ _(ties to `01i`)_

- **Dimensions:** 128–1536 typical (OpenAI 1536; many OSS 384 or 768).
- **Memory/vector:** float32 = **4 bytes/dim** → a 1536-dim vector ≈ **6 KB raw** (bigger than you'd think).
- **1M vectors @ 1536:** ≈ **6 GB** for vectors alone; ⚠ **HNSW roughly doubles it** (~12 GB with index).
- **Query latency:** sub-10 ms achievable; **1–5 ms** common.
- **Recall:** **95%+** usually fine; 99%+ costs more latency/memory.
- **Throughput:** tens of thousands QPS/node for in-memory indexes.

---

## 10 · Gotchas and limitations ⚠

- ⚠ ⭐ **Not a transactional DB / not a source of truth.** Great at similarity, bad at everything else DBs do. ⭐ **Authoritative data lives elsewhere; the vector DB is an _index_.** (This is why Pattern 1 fetches details from the primary DB.)
- ⚠ **Embedding drift** — change the model and **all old embeddings are incompatible** → re-embed everything (expensive) or run multiple indexes during transition. Plan for it (§8.3's model-tag).
- ⚠ **Cold start** for personalization — a brand-new user has no behaviour to embed → need fallback strategies.
- ⚠ **Dimensionality vs performance** — higher dims capture more nuance but are **slower + heavier.** Don't reflexively pick the biggest embedding; 128 may be plenty.
- ⚠ **Index build takes time** — HNSW over 10M vectors can take an hour+; affects deploy speed and failure recovery.
- ⚠ **Not exact match** — need an exact doc by ID? Use a regular DB. Vector search finds **similar, not identical.** Sometimes you want both.

|⭐ Recall|the ANN quality metric: **fraction of true top-K actually found.** 0.95 = found 95%. **95%+ usually fine**|
|⭐⭐ The tradeoff triangle|⭐ a vector DB is a machine for smoothly trading **Recall ↔ Latency ↔ Memory.** Every algorithm + knob just moves inside this triangle|
|⭐⭐ HNSW|⭐ **the one to know.** **Skip-list idea on a graph of vectors:** sparse express-lane top layers + dense Layer 0; search **greedily top-down**, zoom into region, local search at bottom → **O(log n), 95%+ recall → the default.** ⚠ **~2× memory (stores edges), slow build, pricey inserts**|
|⭐ HNSW room-answer|_"multi-layer graph, vectors are nodes; search starts sparse-top, greedily navigates toward target, drops to denser layers as it closes in — skip lists for high-D space."_|
|IVF|**k-means clusters + centroids;** query nearest centroids, search those clusters; ⭐ **`nprobe` = how many clusters (the recall/latency knob).** vs HNSW: faster build, easier inserts, less memory, ⚠ **lower recall for same latency**|
|⭐ IVF edge problem|⭐ **IS `04a`'s cell-boundary problem** (HI says so) — query near a cluster edge → true neighbours in adjacent cluster → must search neighbours too. ⚠ **worse in 1536-D (huge surface)**|
|⚠ LSH / Annoy|⚠ **below waterline.** LSH = **hash so similar collide** (random hyperplanes → buckets), natural for **Hamming/streaming**. Annoy = **random-projection forest + `mmap`, immutable** (static data, Spotify). Both **older, HNSW-beaten**|

|⭐ Filtered search|⭐ **pre-filter** (filter then search — may not use index; best for **tiny subsets**) vs **post-filter** (search then filter — may miss K). ⭐ **"depends on data, I'd benchmark."** post-filter = `04a` candidate-set discipline|

|⭐ Writes are hard|vector DBs are **read-optimized**; HNSW inserts are costly + graph degrades; ⭐ **unlike traditional DBs — so discuss a rebuild strategy**|
