## 1 · The motivating example — why vanilla Postgres dies

▸ **The workload:** a cloud monitoring system — **100k servers × 5 metrics every 10 s = 50k metrics/sec = 4.3 billion points/day.** Users want dashboards, alerts, week-old debugging.

```sql
CREATE TABLE metrics (
    timestamp    TIMESTAMP,
    host         VARCHAR(255),
    metric_name  VARCHAR(255),
    value        DOUBLE PRECISION
);
```

⚠ **Four ways this collapses** (~30 billion rows/week):

- ⚠ **Reads** — "avg CPU for host-42 over the past hour" is painfully slow even with indexes.
- ⚠ **Writes** — more indexes → worse write throughput; **50k writes/s (bursts higher) crushes a single Postgres.**
- ⚠ **Storage bloat** — each row repeats the full host + metric name → **50–100 bytes/point** when the real information (a timestamp + a float) is **16 bytes.**
- ▸ **The gap this leaves:** TSDBs (InfluxDB, TimescaleDB, Prometheus) are **purpose-built for exactly this** — and the rest of the file is _how._

## 2 · The building blocks ⭐

> ⭐ **The interview-ready framing:** a TSDB is **seven simple patterns stacked.** ⭐ **None are TSDB-exclusive** — this is why the chapter is worth it even if you never touch a TSDB. Most you already own; I flag each as new or re-run.

### 2.1 Append-only storage `(re-run — cross-ref)`

▸ **The insight:** writing a lot → **don't update in place, append to the end of a file.** Turns **random I/O → sequential I/O.**

- ⚠ **Why in-place is slow:** update = find row → read → modify → write back → **random seeks** (spinning disk ~100–200 ops/s; even SSDs prefer sequential). Random I/O is the most common perf killer.
- ⭐ **Append flips it:** every point written to the end → no seek, no read-before-write → **sequential writes** (SSDs: hundreds of thousands/s; disks: tens of thousands/s).
- ▹ **You own this** from `02e` (Cassandra) and `02g §4.1` (WAL). ⚠ The open question append leaves — _"if we only append, how do we read it back organized?"_ — is answered by LSM (§2.2).

### 2.2 LSM trees `(re-run — cross-ref, do NOT re-learn)`

▸ **CRUX** — LSM turns random writes into sequential writes, then **reorganizes in the background** for read efficiency. ⭐ **You have this at depth in `01d` (indexing) and `02e` (Cassandra §…).** Do not re-study it here.

- ▸ **The three steps, as a reminder only:** write to in-memory **memtable** (sorted) → flush full memtable to an immutable sorted **SSTable** (sequential write) → **background compaction** merges SSTables, drops duplicates + tombstones.
- ⚠ **The tradeoff (also in `01d`/`02e`):** reads can touch **multiple SSTables** (slower reads) + **write amplification** (data rewritten during compaction). ⭐ **Reach for LSM when write-heavy and willing to trade read for write.**
- ▹ Your locked framing (`01d`): LSM earns its place next to B-trees because it solves the **same queryability problem** with write-optimized tradeoffs — a raw append log writes fast but has **no findability.** ▸ **"append-only + LSM ≈ Cassandra"** — HI notes it too.

### 2.3 Delta encoding & compression `(new — but mostly ⚠ below the interview waterline)`

▸ **CRUX** — time-series data has a unique property: ⭐ **adjacent values are similar** (CPU: 45.2, 45.3, 45.1, 45.4). That redundancy compresses **hard.** ⭐ **Carry the idea; skip the byte-counts.**

- ▸ **Delta encoding** — store the _difference_ between consecutive values, not absolutes: `[45.2][+0.1][-0.2][+0.3]`. Small numbers → fewer bits.
- ▸ **Variable-length (varint)** — small numbers take fewer bytes (1 vs 8), so tiny deltas cost 1–2 bytes instead of 8.

`(⚠ below the interview waterline — knowledge only, HI says don't memorize)`

- **Timestamps → delta-of-delta.** Regular intervals (every 10 s) → deltas constant → delta-of-deltas all **0** → Gorilla compresses timestamps to **~1 bit/value** ([Gorilla paper, VLDB 2015](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf)).
- **Floats → XOR compression.** XOR two similar floats → mostly leading zeros → run-length encode them → **~1.37 bytes/value** vs 8 for a raw double.
- ⚠ **Don't recite "1.37 bytes."** ⭐ **The only carry: strong compression on redundant data-at-rest, and time series is the poster child.**

### 2.4 Time-based partitioning (sharding by time) ▹

▸ **Organize data into partitions by time window** (one per day/week). ▹ **This is sharding (`01f`) with time as the shard key.** Partitions can live on one machine or spread across many for scale.

- ⭐ **Three payoffs — this is why it's powerful:**
    - **Writes localize** — all incoming data goes to the **"now" partition.** No "which of many partitions?" decision.
    - **Reads prune** — "last hour" → the DB knows **exactly which partitions**; never scans last month.
    - ⭐ **Retention is trivial** — keep 7 days = **drop partitions older than 7 days.** No expensive `DELETE` scanning a giant table — just delete old files.

```
Query: "Last 2 hours of CPU for host-42"
[Nov 22 skip][Nov 23 skip][Nov 24 skip][Nov 25 skip][Nov 26 ← SCAN]
```

- ▸ Nearly universal — TimescaleDB calls them **"chunks,"** Prometheus + custom systems do the same.

### 2.5 Bloom filters — read optimization `(new — but full depth lives in 04b)`

▸ **CRUX** — LSM means a value may be spread across **many SSTables**; checking each = a potential disk read. A **Bloom filter** answers **"definitely not here"** or **"maybe here"** with **zero disk I/O.**

- ▸ Each SSTable keeps a Bloom filter of its keys. Query → check the filter first → **"not here" = skip the file with certainty.**
- ⭐ **The asymmetry to remember:** ⭐ **false positives possible ("maybe" but absent); false negatives NEVER.** So "not here" is always trustworthy → safe to skip.
- ▹ **Numbers (`01i`):** ~10 bits/key → ~1% false-positive rate → turns dozens of potential disk reads into one or two.
- ⭐ **Forward ref:** the _mechanism_ (hash functions, bit array, why no false negatives) gets its full treatment in **`04b` (Data Structures for Big Data)** — carry only "definitely-not / maybe, no false negatives, near-zero cost" here.

### 2.6 ⭐ Downsampling & rollups — plus the interview tactic

▸ **Bloom filters help point lookups; rollups help aggregate queries over big ranges.** ⭐ **Downsampling reduces the resolution of _older_ data** — nobody needs 10-s granularity for last year.

```
Last 24h : full resolution (10-s)
Last 7d  : 1-min averages
Last 30d : 5-min averages
Last year: 1-hour averages
```

- ▸ The DB computes rollups in the background, storing pre-aggregated **min/max/sum/count**. "Avg CPU last month?" reads the 5-min rollup — **288× less data** than raw 10-s. ⭐ **Pre-computation trading storage + write-amplification for far faster historical reads.** (Ad Click Aggregator uses this.)

```
Raw data (10s):     [45.2] [45.3] [45.1] [45.4] [45.0] [45.5] ... (8,640 points/day)
1-min rollup:       [min:45.0, max:45.5, avg:45.25, count:6] ... (1,440 points/day)
1-hour rollup:      [min:44.1, max:47.2, avg:45.8, count:360] ... (24 points/day)
```

#### 2.6a ⭐ The requirements-negotiation move — a staff+ signal

> ⭐⭐ **Drill this — it's a concrete, repeatable room move HI explicitly rewards.**

- ▸ Interviewer: _"store 10-s samples for 1 year."_ You: _"that's a ton of data — I think we only need fine resolution for a week, and can downsample to 5-min averages for a month. Does that work?"_
- ⭐ **The scored structure:** (a) **anticipate** a future problem, (b) **explain** the challenge, (c) **offer** an alternative. ▸ **Even if they say no, you've shown you think past rigid requirements** — a staff+ hallmark. (Same muscle as `02h`'s "do we even need real-time?")

### 2.7 Block-level metadata `(re-run — = ES query planning)`

▸ **Each data block stores metadata about its contents** — especially **min/max timestamps**, sometimes min/max values → enables **block pruning.**

- ▸ Query wants CPU > 10%, a block's metadata says it holds only 0–5% → **skip the whole block unread.**
- ▹ ⭐ **This is `02b`'s Elasticsearch query-planning idea** — skip data you can prove is irrelevant before reading it. Stacks on top of time-partitioning (§2.4) as a **second pruning layer.**

## 3 · Putting it together — the storage engine

### 3.1 ⭐ The data model — measurement / tags / fields / timestamp `(new — the key distinction)`

> ⭐ **Master the tag-vs-field split — it's the setup for the cardinality problem (§4), the chapter's main scoring point.**

|Part|Is|Example|
|---|---|---|
|**Measurement**|like a table|`cpu_usage`, `memory`|
|⭐ **Tags**|**indexed** metadata for filtering|`host=server-1`, `region=us-west`|
|⭐ **Fields**|the **un-indexed** measured values|`value=45.2`|
|**Timestamp**|when it was measured|`1699999200000000000`|

```
cpu_usage,host=server-1,region=us-west value=45.2 1699999200000000000
└──────── measurement + tags ────────┘ └ field ┘ └──── timestamp ────┘
```

- ⭐⭐ **The rule that trips people up:** ⭐ **tags = metadata you filter by (indexed, fast); fields = the actual values (not indexed).** Get it wrong → poor query performance **or** the cardinality explosion (§4).

#### 3.1a ⚠ Confusion resolved — what a "block" is, and what the memtable sorts by

> **Doubt (essence):** is a block one data point? And since CPU, memory, network all pour into one memtable, what does "sorted" even mean before the flush?

- ⚠ **WRONG:** a block = one data point. ⭐ **CORRECT:** a **block = all the points of ONE series**, stored together. Hierarchy: **SSTable (file) → many blocks → each block = one series → each block holds many `(timestamp, value)` points.** The point is the atom; the block is the grouping unit.
- ▸ **Why group into blocks:** compression (§2.3) and pruning (§2.7) only work on **runs of same-series data** — CPU stays ~45% (compresses hard), but CPU-then-memory-then-network (45, 8000, 200) doesn't. So each series' points must be clustered before compressing. **The block IS that cluster.**
- ⭐ **What the memtable sorts by:** ⭐ **`(series key, then timestamp)`** — i.e. `(measurement+tags, timestamp)`. It does **not** split metrics into separate buffers; it keeps **one buffer**, ordered so all points of a series sit together, time-ordered within each series.

```
Arrivals (mixed):              Memtable sorted by (series, timestamp):
  cpu    host-1 t=10            cpu_usage,host-1 → [t=00, t=10]
  memory host-1 t=00            memory,host-1    → [t=00, t=10]
  cpu    host-1 t=00            network,host-2   → [t=00]
  network host-2 t=00
  memory host-1 t=10
```

- ⭐ **Why sort in RAM before flushing — the payoff:** because the memtable is already grouped-by-series and time-ordered, the **flush is a straight sequential write** and **each series' contiguous run becomes a block directly** — no reorganizing at flush time.

```
Sorted memtable        → flush →   SSTable
  cpu_usage,host-1 [pts]           Block 0: cpu_usage,host-1 (compressed)
  memory,host-1    [pts]           Block 1: memory,host-1    (compressed)
  network,host-2   [pts]           Block 2: network,host-2   (compressed)
                                   Index: series → block offset
```

- ⭐ **One-liner:** a **block = one series' many points** (not one point); the memtable sorts by **(series key, then timestamp)** so each series clusters in time order → the flush turns each series-run straight into a compressed block.

### 3.2 The storage engine — how the blocks combine `(mostly re-run)`

- **WAL** — data first to the write-ahead log for durability (crash recovery). ▹ `02g §4.1`.
- **In-memory buffer** — also written to a buffer organized by measurement+tag → ▹ **the memtable** (§2.2).
- **Flush to disk** — buffer full → immutable file with **compressed timestamps + values** (§2.3).
- **Background compaction** — merge small files → fewer to check, drop deleted data. ▹ §2.2.

▸ **File layout — the one new detail worth holding:** blocks of `[timestamps | values]` then an **index at the end mapping series → block offsets.** ⭐ **Looking up a series = seek to the index, then seek to the data — two disk ops regardless of file size.**

#### 3.2a ⚠ Confusion resolved — memtable vs SSTable, and where "blocks / index / metadata" live

> **Doubt (essence):** §2.7 says "each data block has min/max metadata" and §3.2 shows a "file layout with blocks + index" — are these the memtable or the SSTable?

- ⭐ **The one distinction that resolves both:** ⭐ **memtable = the in-RAM inbox** (small, temporary, where new writes land); ⭐ **SSTable = the finished file on disk** (immutable). ⭐ **Every "block," "min/max metadata," "file layout," "index → offsets" is the SSTable.** The memtable has none of that — it's just a sorted buffer waiting to be flushed.
- ▸ **Lifecycle:** write → **memtable (RAM)** → fills up → **flush** → becomes an **SSTable (disk)**, which is _internally_ organized into blocks + index + metadata. So ⭐ **a "block" is a sub-region _inside_ an SSTable file.**
- ⭐ **Rule of thumb:** the moment the notes say _block / on-disk / min-max / file structure / index→offset_, you're looking at an **SSTable.** You never prune or index the memtable — it's tiny, in RAM, just scanned.
- ⭐ **So §2.7 and §3.2 describe the _same_ SSTable file, two features of it:**
    - **§3.2 index (series → offset)** = _"**where** is series X?"_ → jumps you to the right block (a **lookup** aid).
    - **§2.7 block metadata (min/max)** = _"**can** this block match my filter?"_ → lets you **skip** blocks (a **pruning** aid).
- ⭐ **Why the index sits at the END of the file:** the file is written **append-only, front-to-back** (§2.1) → you don't know final block offsets until all blocks are written → so the series→offset index can only be written **after** the blocks. Common file-format pattern.
- ▸ **Three nested filters together:** time-partitioning skips whole **files** (§2.4) → block metadata skips **blocks** (§2.7) → the index **jumps** to the right block (§3.2). Each layer reads less from disk.

### 3.3 Query execution — tag-index intersection ▹

```sql
SELECT mean(value) FROM cpu_usage
WHERE host = 'server-1'
  AND time > now() - 1h
GROUP BY time(5m)
```

▸ **The engine exploits two localities:** ⭐ **time locality** (recent data in memory/recent files) + **series locality** (related points stored together) → minimal disk access.

▸ **The flow** for `WHERE region='us-west' AND env='prod' ... GROUP BY time(5m)`:

1. **Partitions** — pick only those overlapping the time filter (§2.4).
2. **Series** — look up tag filters in the **in-memory tag index** (▹ ⭐ **this IS an inverted index, `02b`** — HI says so: tag-value → series, like word → document).
3. **Intersect** the tag sets → the matching series.
4. **Block lookup** — series → block offsets via the file index; **read only those blocks**, skip the rest.
5. **Stream the aggregation** as data is read — no need to load everything into memory first.

```
region=us-west → [S1, S2]        env=prod → [S1, S2, S3]
intersect      → [S1, S2]        → read Block 0, Block 1 only (skip 2, 3)
```

- ⭐ **What made it fast:** the tag index found matching series **without scanning data**; series-oriented storage means the needed data is **physically co-located** → no scattered random reads. ⭐ **Writes are structured to serve reads** — vs Postgres, where matching rows sit scattered on disk and the scattered reads kill performance.

#### 3.3a ⚠ Confusion resolved — partitions vs shards, and what one SSTable actually holds

> **Doubt (essence):** is a partition a shard? And within a partition, does one SSTable track one metric (a CPU SSTable, a memory SSTable)?

- ⭐ **Partition = shard, with time as the shard key** (`01f`). "Reaching the right partition" = picking the shard(s) whose time window overlaps the query. ✅
- ⚠ **WRONG:** one SSTable tracks one metric — hunt for "the CPU SSTable." ⭐ **CORRECT:** an SSTable is **not organized by metric.** It's just a **time-slice flush of the memtable**, which holds **all metrics + all series mixed.** So one SSTable contains **many series** (CPU _and_ memory _and_ network, many hosts), each in its **own block.**

```
⚠ WRONG:                          ⭐ REALITY:
 Partition Nov-15                   Partition Nov-15
  ├ SSTable-A = only CPU             ├ SSTable-1 (09:00): cpu h1 | mem h1 | cpu h2 | net h3
  ├ SSTable-B = only memory          ├ SSTable-2 (09:20): cpu h1 | net h2 | mem h5
  └ SSTable-C = only network         └ SSTable-3 (09:40): mem h1 | cpu h4
```

- ⭐ **What separates metrics is the block _inside_ the SSTable, not the SSTable.** And because each flush writes whatever was in RAM, ⭐ **one series is smeared across multiple SSTables** (a bit at 09:00, a bit at 09:20…).
- ⭐ **So that's what bloom filtering is really for:** per SSTable, _"does this file hold series `cpu_usage,host-1` at all?"_ → "not here" skip the whole file, "maybe" open it. It's **"which SSTables hold a piece of my series,"** not "which SSTable tracks CPU."
- ⭐ **The corrected end-to-end walk:**
    1. **Time filter → pick partition(s)** (the shard).
    2. **Tag index (RAM) → resolve tags to series key(s)** (`host=server-1` + `cpu_usage`) — _in memory, before touching any SSTable._
    3. **Across the partition's many SSTables → bloom-filter each** for that series key → skip the misses.
    4. **In the "maybe" SSTables → use each file's index** (series → block offset) to jump to the block; **block min/max metadata** skips blocks outside the 1-hour window (§2.7).
    5. **Merge** the series' points from those SSTables **+ the memtable** (recent, unflushed), apply the time filter, **aggregate (`mean`)**, return.

## 4 · The cardinality problem ⭐⭐ — where things break

> ⭐⭐ **The single most important interview insight in the chapter.** HI: understanding this is a **staff+ hallmark.**

▸ **Cardinality = the number of unique tag combinations.** Each unique combination is a **series**, and ⭐ **the TSDB keeps an in-memory index of every series.**

- ▸ **Fine:** 1,000 hosts × 50 metrics = **50,000 series.** Manageable.
    
- ⚠ **Catastrophe:** add a tag `user_id` with 10M unique users → **up to 500 billion potential series** → ⭐ **the in-memory series index runs out of memory, and queries slow as the index balloons.**
    
- ⭐⭐ **The rule that falls out — and the scoring answer:** ⭐ **high-cardinality values (`user_id`, `request_id`, anything unbounded) must be FIELDS, not tags.** ▸ You can still **write** them, but you **lose the read/index benefits** for them — they're just stored values, not fast filters.
    
- ▸ **Ties back to §3.1:** this is _why_ the tag/field split exists and why getting it wrong is fatal. Tags are indexed → every distinct tag value costs index memory → **only low-cardinality things belong as tags.**

## 5 · The meta-lesson — data assumptions & when NOT to use a TSDB ⭐⭐

> ⭐⭐ **The takeaway that generalizes past TSDBs — the real reason to read the chapter.**

- ⭐ **A TSDB is a bet on strong data assumptions:** **low-cardinality tags · highly regular data · small deltas between points.** Hold all three → **10–100× better** than a general-purpose DB for the target workload. ⚠ **Violate any → you lose _all_ the benefits and it becomes _worse_ than Postgres.**
- ⚠ ⭐ **Where candidates stumble:** not understanding a database's data assumptions → proposing a solution that performs **worse (or not at all)** for the task. ⭐ **Understanding assumptions + hallmarks is the staff+ signal.**
- ⭐ **HI's safety advice, worth internalizing:** ⭐ **if uncertain, fall back to what you know rather than winging it with tech you don't.** A stretched Postgres you understand beats a TSDB you'll misuse.
- ▸ **The decision sequence:**
    1. ⚠ **Do you even need a TSDB?** → stretch **Postgres / DynamoDB** first. Stop here most of the time.
    2. **Hit a true write-throughput / retention / compression bottleneck** a general DB can't solve? → a TSDB is defensible.
    3. ⚠ **Check the assumptions first** — high-cardinality tags or cross-series sorting/aggregation (Top-K) → a TSDB is the **wrong** tool.

## 6 · End-to-end walkthrough — the series pipeline ⭐

> ⭐ **The whole chapter in one flow.** ⭐ **Series is the spine** — one `(measurement + all tag values)` combination = one series = the _identity_ of a stream. Three structures are all **keyed by series**, and the query walks through them in order:
> 
> - **Tag index** (RAM, global) — `tag value → series`. **Reverse lookup** (inverted index, `02b`): you query with one tag, it hands you the series carrying it. _Finds WHAT series._
> - **Bloom filter** (per SSTable) — `series → maybe / definitely-not`. _Finds WHICH files to open._
> - **File index** (inside each SSTable, DB-built at flush) — `series → block offset`. _Finds WHERE in the file._

**Query: "avg CPU for `host=server-1`, last 1 hour."**

```
STEP 1 — tags → series           [TAG INDEX, in RAM]
   host=server-1 → [Series: cpu_usage,host=server-1,...]
   ⭐ Why the tag index: you don't know the series yet — you only know one tag.
      The reverse lookup turns "one tag value" into "the series that carry it."
      Multi-tag (region=us-west AND env=prod) = intersect each tag's series-list.
   → Output: the exact SERIES KEY(s). No disk touched.

STEP 2 — pick partition(s)        [TIME = shard key]
   last 1h → only partitions overlapping that window.

STEP 3 — which SSTables?          [BLOOM FILTER, per SSTable]
   One series is smeared across many SSTables (flushed 09:00, 09:20, ...).
   Ask each file's bloom: "do you hold THIS series key?"
      maybe → open   |   definitely-not → skip (zero disk read)

STEP 4 — where in the file?       [FILE INDEX, series → offset]
   ⭐ Why the file index: once bloom says "maybe," you still need the exact spot.
      The file index (written once at flush, frozen with the immutable SSTable)
      maps your series key → its block offset → jump straight there.
      Block min/max metadata skips blocks outside the 1-hour window (§2.7).

STEP 5 — merge + aggregate
   Gather the series' points from each "maybe" SSTable's block
   + the memtable (recent, unflushed) → apply time filter → mean().
```

- ⭐ **The one chain:** **tags → (tag index) → series → (bloom) → which SSTables → (file index) → which block → points → aggregate.** Tag index finds _what_; file index finds _where_; bloom filter screens _which files_ in between.
- ⭐ **Cardinality hooks straight onto this:** cardinality = **how many series exist**, and **every series-keyed structure above scales with it** — especially the RAM tag index (one entry per series). A high-cardinality tag (`user_id`, 10M users) mints a new series per value → billions of series → the tag index can't fit in RAM → the system degrades. ⭐ **That's why `user_id` must be a field** (a value in the block, minting **no** new series) **and never a tag** (§4).
