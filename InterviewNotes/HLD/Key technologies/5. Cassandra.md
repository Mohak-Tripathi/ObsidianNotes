## 1 · What it is & the data model

▸ **CRUX** — Cassandra is an open-source, **distributed, partitioned wide-column NoSQL database** with **eventually consistent** semantics, built to horizontally scale on commodity hardware. Origin: Facebook, for inbox search. Now Discord, Netflix, Apple, Bloomberg.

- ▹ **Lineage:** Cassandra = **Dynamo** (partitioning, replication, availability) + **Bigtable** (wide-column storage model). If you know DynamoDB, you already know half of Cassandra — the primary key concept is shared **1:1**.
- ▸ **The one-line pitch:** massive write throughput + horizontal scale + high availability, purchased with **no JOINs, no ACID, no ad-hoc queries.**

### 1.1 The four data definitions

|Term|Relational analogue|What it actually is|
|---|---|---|
|**Keyspace**|database / schema|Top-level unit. Owns the **replication strategy** (§3.2) and any user-defined types (UDTs)|
|**Table**|table|Lives in a keyspace. Has a schema defining columns and the **primary key structure**|
|**Row**|row|One record, uniquely identified by its **primary key**|
|**Column**|column|Name + type + value **+ a write timestamp**. ⚠ Not every row needs every column|

### 1.2 What "wide-column" actually buys you

▸ **CRUX** — columns can **vary per row within the same table.** A relational DB stores an entry for every column on every row even when it's `NULL`; Cassandra simply omits it.

- ▸ **Payoff:** genuinely good fit for **flexible schemas** and **sparse schemas with many columns** — the case where a relational table would be 200 columns wide and 90% NULL.
- ▸ **Conflict resolution:** every column carries a write timestamp, so a write conflict between replicas resolves by **last write wins (LWW).** ⚠ LWW silently discards a concurrent write — this is the price of availability, and it's a legitimate thing to call out aloud in a design.

▸ Mental model — Cassandra's structure as a large JSON:

```json
{
  "keyspace1": {
    "table1": {
      "row1": { "col1": 1, "col2": "2" },
      "row2": { "col1": 10, "col3": 3.0 },
      "row3": {
        "col4": { "company": "Hello Interview", "city": "Seattle", "state": "WA" }
      }
    }
  }
}
```

- ▸ Column types include UDTs and JSON values → flat _and_ nested data are both first-class.
- ⚠ **Read this JSON narrowly — it illustrates exactly two things:** (1) **sparse columns** (`row1` has `col1,col2`; `row2` has `col1,col3` — no NULL padding), and (2) **nested column values** (`col4` holds a UDT). Nothing more.
- ⚠ **It elides the partition level.** `row1/row2/row3` appear as flat siblings under `table1`, as if a table were a bag of rows. The honest shape is **four levels**: `keyspace → table → PARTITION → row(clustering key) → column`. ▹ HI writes it flat because this section precedes the primary key (§1.3), so partition vocabulary isn't available yet — pedagogical sequencing, not an error. Accurate structure → §1.3a(k).
- ⚠ **Don't read `col4`'s nesting as a partition→rows relationship.** It is **one column whose value is structured** (a UDT), living _inside_ a single row. ▸ **Test that separates them:** you can **query by partition key**; you **cannot** query by a field inside a UDT — Cassandra returns the whole column value and your app unpacks it.
- ⚠ **Vocabulary:** there is no "secondary key." **Partition key + clustering key together _are_ the primary key.** (A _secondary index_ is an unrelated feature → §9, SAI.)

### 1.3 Primary key ⭐ (the single most important construct)

▸ **CRUX** — a Cassandra primary key is **two things stapled together**, and confusing them is the #1 modeling error:

- **Partition key** — one or more columns that determine **which partition (and therefore which node) the row lives on.** Hashed. (Same concept as the shard key in `01f`.)
- **Clustering key** — zero or more columns that determine the **sorted order of rows within that partition.** Not hashed — sorted.

▸ **Why this split is everything:** the partition key decides _how many nodes your query touches_; the clustering key decides _whether your range scan is free or impossible._ Every §8 decision flows from these two.

▸ CQL syntax — the parenthesization is load-bearing:

```sql
-- Partition key a, no clustering keys
CREATE TABLE t (a text, b text, c text, PRIMARY KEY (a));

-- Partition key a, clustering key b ascending
CREATE TABLE t (a text, b text, c text, PRIMARY KEY ((a), b))
WITH CLUSTERING ORDER BY (b ASC);

-- COMPOSITE partition key a + b, clustering key c
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY ((a, b), c));

-- Partition key a, clustering keys b + c
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY ((a), b, c));

-- Same as above, alternative syntax
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY (a, b, c));
```

- ⚠ **The gotcha:** `PRIMARY KEY (a, b)` means partition key `a`, clustering key `b`. `PRIMARY KEY ((a, b))` means a **composite partition key** of `a`+`b` with no clustering. The inner parentheses are the only difference and they change which nodes a query hits.

#### 1.3a ⚠ Confusion resolved — "wide-column" vs Mongo, and what the clustering key actually does

> **The doubt (verbatim):** _"whenever it is said that whenever you do not want, uh, you want flexible schema, when you do not know how many columns you need, at that point of time, you can use MongoDB and all, which is NoSQL. … broadly, the idea is flexible schema go with NoSQL and, like, MongoDB otherwise Postgres. … But what is this wide column? I want you to give me the example, uh, real world example and explain me why no SQL like MongoDB will not work and when Cassandra is needed."_
> 
> _"Partitioning key basically in the disk, the disk are circular, and in one particular space maybe pages are there in that disk is there. … Clustering key, also known as sort key, I don't know. If that's the case, then through message ID you are sorting it. So message ID could be anything. … but when you are saying, if it is just appending the new messages like Discord, then everything will be already sorted. Then what's the point? So, what is sort here, clustering key, and how it impact read?"_

**(a) The choice axis was wrong.**

- ⚠ **WRONG:** _flexible schema → NoSQL → Mongo; else Postgres_ — as a route to Cassandra. **Mongo already gives you flexible schema.** So "I need a flexible schema" cannot be the reason to pick Cassandra **over** Mongo; both satisfy it. Say it in a room and the next question is _"why not Mongo?"_ and you have no answer.
- ✅ **CORRECT:** Cassandra is chosen for **write throughput + masterless availability + physically pre-sorted partitions.** Flexible/sparse schema (§1.2) is a **byproduct** of the storage model, not the motivation — the fourth reason, never the first.

**(b) What "wide-column" actually means.** ⚠ The name is historically accurate and pedagogically terrible. It does **not** primarily mean "rows can have many/varying columns" (that's §1.2, the byproduct).

- ▸ **CRUX** — **the unit of storage is the partition, not the row.** All rows sharing a partition key are stored **physically contiguously, pre-sorted by clustering key.** A Discord channel-bucket with 40,000 messages is not 40,000 scattered records — it is **one contiguous, sorted run of bytes.**
- ▹ Underlying model (from Bigtable) is a map of maps: `row_key → { column_name → (value, timestamp) }`.

**(c) Mongo vs Cassandra — where the real difference lives.**

||MongoDB (document)|Cassandra (wide-column)|
|---|---|---|
|Retrieval unit|**the document** — fetch whole objects|**a range slice of a partition** — "next 50 rows in sorted order"|
|When sorting happens|**query time** (`.sort()`, via index)|⭐ **write time** — data lives on disk in clustering order|
|Topology|**primary + secondaries.** All writes funnel through each shard's primary|⭐ **masterless.** Every node accepts every write (§5)|
|Node failure|leader **election** → seconds of **write unavailability** for that shard|node convicted; writes continue via hints (§7.3). **No election, no gap**|
|Storage engine|**B-tree** (WiredTiger) → write must locate + modify a page = **random I/O**|**LSM tree** (§6) → writes are **sequential appends**|
|Query flexibility|⭐ rich — any field, secondary indexes, aggregation pipeline|⚠ partition key or nothing (§8)|

- ▸ **The two rows that carry all the weight:** **no leader** (a Mongo shard's write ceiling is one machine, and every failover is a write outage; a Cassandra node added = write capacity added, linearly) and **no random I/O on write** (structural, not a tuning matter).

**(d) The real-world evidence.** ▸ **Discord ran on MongoDB first and moved off it.** The failure was **not** schema: past roughly **100M messages**, the working set **plus the B-tree index** stopped fitting in RAM. Every read that missed RAM became a random seek through the index, then another to fetch the document → p99 latency went unstable, which for a chat app is the product.

- ▹ **Postscript worth knowing:** Discord later moved again to **ScyllaDB** — a C++ reimplementation of Cassandra, same data model and CQL — because of **JVM garbage-collection tail latency.** The _model_ was right; the _runtime_ was the remaining problem. ▸ **Use this as your answer to "any downside of Cassandra?"**

**(e) ⚠ Correction: the partition key does not pick a place on disk.** Two layers — don't collapse them:

- **Partition key → which NODE**, via consistent hashing (§2, `01g`). Nothing to do with platters or pages.
- **Clustering key → byte layout WITHIN that node's SSTable** — rows of one partition contiguous and sorted.
- ▹ Also drop the spinning-platter image ("disks are circular") — Cassandra typically runs on **SSDs**, which have no platter. Sequential still beats random there (fewer I/O ops, page-aligned reads, read-ahead prefetch works), but for different reasons.

**(f) ⭐ "Writes just append, so it's already sorted — what's the point?" — four reasons the premise is false.**

1. ⭐ **Writes are massively interleaved.** Traffic arrives as `ch42 · ch7 · ch99 · ch42 · ch1203 · ch7 · ch42 …` — chronological **globally**, but **never contiguous per partition.** Appending in arrival order would scatter channel 42's rows through the file with thousands of other channels between them. ▸ **What actually happens:** writes land in the **memtable**, a sorted in-memory structure keyed by `(partition key, clustering key)`. It maintains order in RAM, so the flushed SSTable comes out with channel 42's rows **grouped and internally sorted** despite arriving scattered across an hour of global traffic. **This is the whole point** — "already sorted" would only hold with exactly one partition and one file.
2. **A partition spans multiple SSTables** (10:00 flush, 11:00 flush, 12:00 flush). Reads must **merge** those pieces, and compaction must too (§6.3). Merging is a cheap single linear pass **only because each piece is independently sorted.** ⚠ The sort isn't paid once and forgotten — it's the **invariant** that keeps the read path and background maintenance affordable.
3. **`DESC` is a physical layout instruction with teeth.** `CLUSTERING ORDER BY (message_id DESC)` → newest stored **first** → "last 50" is one seek plus a forward read. With `ASC` the newest rows are at the **far end**, so the same query must locate the partition's tail and iterate in reverse — measurably slower. If insertion order alone determined layout, this declaration would be meaningless.
4. **Arrival order isn't reliably chronological anyway.** Snowflake IDs are minted on many servers with skewed clocks; retries land late; cross-DC replication delivers out of order. A message minted at `10:00:00.003` can arrive after one minted at `10:00:00.007`. ▸ With a clustering key it is **inserted into its correct sorted position**; append-by-arrival would leave it permanently misplaced and your "newest 50" would be quietly wrong.

**(g) What the sort actually buys on reads — three concrete things.**

- **Scroll-back becomes a seek, not a scan.** `WHERE channel_id = 42 AND bucket = 500 AND message_id < 8734512 LIMIT 50` — sorted order lets Cassandra **jump straight to that position** and read forward. Unsorted, every scroll event is a full partition scan.
- **The byte-offset index is only constructible against known order** (§6.4, `01d`). Random layout → nothing to index against.
- **No query-time sort step at all.** Postgres `ORDER BY` and Mongo `.sort()` do real work on **every request**; Cassandra's answer arrives pre-sorted because the disk is sorted. ▸ **The trade in one line: work moved from read time to write time.**

**(h) Proof that the sort is a decision, not a byproduct.** Change one thing:

```sql
PRIMARY KEY (channel_id, author_id, message_id)
```

- Same rows, same arrival order, same appends — but rows now sort by **author first.**
- "Last 50 messages in this channel" becomes **unservable efficiently** (newest rows scattered across every author's block → full partition scan).
- "All of Mohak's messages in channel 42" becomes **one contiguous read.**
- ▸ **Same data, different clustering key, completely different set of cheap queries.** This is precisely why modeling is **query-driven** (§8) — and it would be impossible if the sort were merely insertion order.

**(i) The clustering key's second job: uniqueness within the partition.** Independent of ordering.

- Ticketmaster's `PRIMARY KEY (event_id, seat_id)` (§8.4) uses `seat_id` **only** for uniqueness — the source comments explicitly that order doesn't matter, since users navigate by a venue map. Without it, every seat in an event would collide on the same primary key and overwrite.
- ▸ **So:** partition key = **which node**. Clustering key = **(a) uniqueness within the partition + (b) sort order on disk.** Discord's `message_id` does both jobs; Ticketmaster's `seat_id` does only (a).

**(j) ⚠ `message_id` is not "anything."** Discord uses a **Snowflake ID** precisely because it is **simultaneously collision-proof and chronologically sortable** — the two properties a clustering key needs here. A plain auto-increment or a random UUID breaks one or the other. Full reasoning → §8.3.

▸ **The one-line version:** _the clustering key doesn't record the order things arrived in — it declares the order they will be **stored** in, which decides which range queries are cheap._

**(k) The structure in one pass — the mental model to keep.**

```
KEYSPACE  discord                        ← database. Owns replication config (§3.2)
 └ TABLE  messages                       ← declares all columns + the primary key
    └ PARTITION  channel_id = 42         ← ⚠ physical grouping — one per distinct partition-key value
       ├ ROW  (42, 9003) → author 7 · content "hey"      ← sorted by clustering key
       ├ ROW  (42, 9002) → author 9 · content "yo"
       └ ROW  (42, 9001) → author 7 · content "hi"
             └ COLUMN → name + type + value + write timestamp
```

- ▸ You choose the **partition key column**, not individual partitions — Cassandra creates **one partition per distinct value** automatically.
- ▸ Rows within a partition are **sorted by clustering key** and stored **contiguously**.
- ⚠ **Sparse, not schemaless.** Every column must be declared in `CREATE TABLE`; what varies per row is **which declared columns are present.** A missing column occupies **zero bytes** (Postgres would store a NULL slot). Genuinely new fields still require `ALTER TABLE`. ⚠ **Interview trap:** _"Cassandra is schemaless so I don't need to plan the schema"_ is backwards — it needs **more** planning, since the primary key is frozen once chosen and dictates every query you can serve.
- ▸ **Timestamps are per-column, not per-row** — that's what makes last-write-wins work at **column granularity**: concurrent updates to _different_ columns of the same row both survive; only same-column conflicts trigger LWW (§1.2).
- ⚠ **"Partition" is absent from HI's four-term list** (keyspace / table / row / column) because that list is the **logical** model. The partition is the **physical** unit — what gets hashed to a node, replicated, stored contiguously, sorted, and compacted. ▸ **The list tells you how to declare data; the partition tells you how it behaves.** Every hard part of Cassandra lives in the level the list omits.

## 2 · Partitioning (how it scales horizontally)

> ▸ This is Cassandra's concrete instantiation of `01g`. If consistent hashing is already solid, read §2.2 (vnodes) and move on.

### 2.1 Why not plain `hash(value) % num_nodes`

▸ **Problem 1 — rebalancing storm.** Change the node count and _most_ keys remap → mass data movement across the cluster. ▸ **Problem 2 — uneven load.** An unlucky hash distribution piles many keys onto one node.

### 2.2 Consistent hashing + vnodes

▸ **CRUX** — hash the value to an integer on a **ring**; walk **clockwise** to the first node position; store there.

- ▸ **Fixes problem 1:** a node joining takes keys only from its clockwise neighbour; a node leaving hands keys only to its clockwise neighbour. **One adjacent node affected**, not the whole cluster.
- ⚠ **Does NOT fix problem 2** on its own — node positions on the ring can still be clustered.
- ▸ **Fix for problem 2 — vnodes (virtual nodes):** map **many** ring positions to each **physical** node. Ring positions are called **tokens** (t1, t2…). Load smooths out because each physical node owns many scattered slices of the ring.
- ▸ **Bonus payoff:** **heterogeneous hardware.** A bigger physical machine is simply assigned **more vnodes** → it takes proportionally more load. Plain consistent hashing can't express this.

### 2.3 What exactly gets hashed

▸ **CRUX** — Cassandra hashes the **partition key value** (all its columns concatenated, if composite) through **Murmur3**, producing an integer called a **token**. That token is the position on the ring.

```
hash("42")           → token → walk clockwise → vnode → physical node
hash("42" + "500")   → token → ...     (composite partition key: channel_id + bucket)
```

- ⚠ **The clustering key is never hashed and plays no part in placement.** It only orders rows _after_ they arrive. ▸ Two rows sharing a partition key always land on the same nodes regardless of clustering value — **that is exactly why a partition read hits one node** (§8.3).

#### 2.3a ⚠ Confusion resolved — immutable SSTables vs. moving data when a node joins

> **The doubt (verbatim):** _"from Memtable, it goes to SSTable and all, and then compaction happens and LSM tree. In the SSTable, the biggest point is that you cannot convert or you cannot change, right? It is immutable. Then if you are doing consistent hashing and all, and then if you have to, you know, do the migration of some because of the consistent hashing when you add a node, then you have to migrate, and migration you cannot do because it's immutable."_

**(a) The flaw is in what "immutable" means.**

- ⚠ **WRONG:** immutable = the file can never be changed **or removed**; data is stuck there permanently.
- ✅ **CORRECT:** immutable = **never modified in place.** Once written, no byte inside the file is ever edited. Files can absolutely be **created** and **deleted wholesale** — the rule constrains **mutation**, not **lifecycle**.
- ▸ **So every change in Cassandra takes one shape:** **read old files → write new files → delete old files.** Never "open a file and edit it."

**(b) How migration actually works.** Node D joins and takes ownership of certain token ranges from A, B, C:

1. **Streaming** — A reads its SSTables (sequentially, in sorted order) and streams the rows in the transferred ranges to D. ▸ **A pure read. A's SSTables are untouched.**
2. **D writes new SSTables** containing what it received. Brand-new files, written start-to-finish. **Nothing modified.**
3. **Cleanup** — A now holds data it no longer owns. It does **not** erase in place: it runs a compaction that reads its SSTables, writes **new** SSTables containing only the ranges A still owns, then **deletes the old files entirely.**

- ▸ **Notice this is just compaction (§6.3) with a "does this token still belong to me?" filter.** Same machinery, different predicate. Nothing was mutated at any point.

**(c) The pattern this reveals — one move, four problems.**

|Operation|Mutable DB (Postgres)|Cassandra|
|---|---|---|
|Update a row|modify the page in place|append a new version with a newer timestamp; compaction later discards the old|
|Delete a row|remove the row, free the space|append a **tombstone**; compaction later drops row **and** tombstone|
|Reclaim space|vacuum modifies pages|compaction writes **new** files, deletes old ones|
|Move data to a new node|update pages / reindex|stream out → write new files on target → **cleanup** rewrites the source|

- ▸ **The unifying principle:** Cassandra **never edits.** It **appends, rewrites in the background, then deletes whole files.** ⭐ Immutability isn't an obstacle it works around — it's the property that makes all four operations **cheap sequential I/O** instead of random page mutation.

**(d) Why migration is cheaper than you'd expect — and what it still costs.**

- **Data is already sorted** → streaming a token range is a **sequential read of a contiguous region**, not a scan-and-filter.
- **Vnodes shrink the blast radius** → a joining node takes many **small** ranges from **many** nodes in parallel, instead of one huge range from one neighbour. Work spreads across the cluster.
- ⚠ **The real cost, worth naming aloud:** streaming plus cleanup compaction is **heavy background I/O.** Adding nodes to a loaded cluster is a **planned operation, not a casual one.** ▸ Good answer to _"what's operationally hard about Cassandra?"_ alongside **JVM GC tail latency** (§1.3a(d)).

## 3 · Replication

### 3.1 How replicas are chosen

▸ **CRUX** — hash the key to a vnode, then **continue walking clockwise** collecting additional vnodes until you have RF (replication factor) replicas. RF=3 → the home vnode + the next 2.

- ⚠ **Critical detail:** Cassandra **skips any vnode that sits on a physical node already in the replica set.** Without this, three "different" vnodes could all live on one machine and a single hardware failure would take out all three replicas.

### 3.2 Replication strategies (recognition-tier)

|Strategy|Awareness|Use|
|---|---|---|
|**NetworkTopologyStrategy**|data-center **and** rack aware|⭐ **Production.** Spreads replicas across DCs (survives a DC outage) and across racks within a DC (survives a rack failure)|
|**SimpleStrategy**|none — pure clockwise scan|Simple deployments and testing only|

```sql
-- 3 replicas, naive placement
ALTER KEYSPACE hello_interview
WITH REPLICATION = { 'class' : 'SimpleStrategy', 'replication_factor' : 3 };

-- 3 replicas in dc1, 2 replicas in dc2
ALTER KEYSPACE hello_interview
WITH REPLICATION = {'class' : 'NetworkTopologyStrategy', 'dc1' : 3, 'dc2' : 2};
```

- ▸ **Interview use:** the only thing worth saying is _"NetworkTopologyStrategy so replicas span data centers and racks."_ Then move on. ⚠ The **multi-region** angle is the part that actually earns credit — per-DC replication factors are how Cassandra does active-active geo-distribution.

## 4 · Consistency ⭐ (tunable — the real interview surface)

> ▸ Continuation of `01h`. The point of this section is that Cassandra doesn't hand you a fixed CAP position — **you pick one per query.**

### 4.1 Consistency levels

▸ **CRUX** — a **consistency level** is _the number of replicas that must respond for a read or a write to be considered successful._ Set independently for reads and writes.

- Range spans **ONE** (a single replica responds — fastest, least consistent) through **ALL** (every replica must respond — slowest, unavailable if any replica is down).
- ▸ **Default posture:** Cassandra targets **eventual consistency** at all levels — given enough time with no new writes, all replicas converge.

### 4.2 QUORUM and the `R + W > N` rule ⭐

▸ **CRUX** — **QUORUM** = a majority of replicas, i.e. `N/2 + 1`.

▸ **Read at QUORUM + write at QUORUM ⇒ reads always see the latest write.** Why: the read set and the write set are each a majority, so they **must overlap in at least one node**, and that node has the newest data.

- ▸ **Worked example (N = 3):** `3/2 + 1 = 2`. A write must land on 2 of 3 nodes; a read must hear from 2 of 3. Any two 2-subsets of a 3-set share at least one member → that member saw the write.
- ▸ **The generalization to state aloud:** the guarantee is `R + W > N`. QUORUM/QUORUM is just the balanced instance of it.
- ▸ **The tuning lever this unlocks — say this, it reads as senior:**

|Config|`R + W > N`?|Profile|
|---|---|---|
|W=ALL, R=ONE|yes|Fast reads, slow/fragile writes. **Read-heavy** workloads|
|W=QUORUM, R=QUORUM|yes|Balanced. The safe default|
|W=ONE, R=ONE|**no**|Fastest possible both ways, **no read-your-write guarantee.** Only for genuinely tolerant data|
|W=ONE, R=ALL|yes|Fast writes, slow/fragile reads. **Write-heavy** — but ALL reads break on any node loss|

- ⚠ **The availability cost nobody mentions:** ALL means a **single unavailable replica fails the operation.** `R + W > N` is a _consistency_ guarantee bought with _availability_, which is the whole point of `01h`.

### 4.3 What tuning does NOT give you

⚠ **Even at QUORUM/QUORUM, this is not linearizability and not a transaction.** You get "a read sees the latest committed write for that row." You do **not** get multi-row atomicity, isolation across rows, or read-modify-write safety.

### 4.4 ⚠ No ACID — the fintech line in the sand

▸ **CRUX** — Cassandra has **no transaction support and no ACID guarantees.** The only atomicity/isolation it offers is at the level of a **single row within a single partition.**

- ▸ **Problem:** "debit A, credit B" needs multi-row atomicity.
- ▸ **Fix:** don't use Cassandra for it. Ledger/balance/order-state → Postgres. Cassandra holds the **event log** of what happened, not the authoritative mutable state.
- ⚠ This is the sentence that separates a candidate who has _read about_ Cassandra from one who would deploy it. Volunteer it before the interviewer asks.

## 5 · Query routing (the coordinator)

▸ **CRUX** — **any node can serve any query.** The client picks a node; that node becomes the **coordinator** for that request.

- ▸ **How the coordinator knows where data lives:** it runs the same **consistent hashing** calculation (§2) and knows the keyspace's **replication strategy** and the request's **consistency level** — so it can compute exactly which replicas to contact and how many responses it needs.
- ▸ **How it knows which nodes are alive:** every node maintains a view of the cluster, kept current by **gossip** (§7.1).
- ▸ **Why it matters architecturally:** **no leader, no single point of failure, no routing tier.** Contrast with a primary/replica system where writes must reach the leader. This is a large part of why Cassandra skews so hard toward availability.

## 6 · Storage model — the LSM tree (why writes are fast)

> ▸ Extension of `01d` (LSM vs B-tree). Most databases (relational, DynamoDB) index with a **B-tree**, optimized for reads. Cassandra uses an **LSM tree**, optimized for writes.

### 6.0 Framing: the storage _is_ the index ⭐

> ▸ Read this before the write path — it reframes everything that follows.

▸ **Postgres — storage and index are two separate structures.**

```
HEAP FILE (the table)                B-TREE INDEX on channel_id
row @ page 5, slot 2   ← unordered   42 → (page 5, slot 2)
row @ page 1, slot 9      insertion  42 → (page 1, slot 9)
row @ page 8, slot 4      order      88 → (page 8, slot 4)
```

- The heap is **unordered** — rows sit wherever there was free space. The B-tree holds sorted keys → **pointers into the heap.**
- A lookup traverses the B-tree, gets pointers, then **jumps to the heap** for each row. **Two structures, two I/O phases.**
- ⚠ Every index you add is **a whole new structure that must be maintained on every single write.**

▸ **Cassandra — there is no heap.**

```
SSTable
partition 42 → row (42,9003) · row (42,9002) · row (42,9001)   ← sorted by primary key
partition 88 → row (88,9500)                                      ON DISK
```

- ▸ **CRUX** — the data on disk is **already in primary-key order**, so there is no separate key→location structure. The sorted file is **both**. Correct term: a **clustered index**.
- ▹ Postgres cannot do this at all; MySQL/InnoDB clusters its primary key for exactly this reason.
- ⭐ **The precise framing:** Cassandra didn't optimize storage _instead of_ indexing — it **collapsed the two into one structure**, organized along a single axis: the primary key.
- ▸ Auxiliary structures **do** exist (bloom filter, partition summary, partition index — §6.2c), but ⚠ **they are not indexes in the Postgres sense.** They never enable querying a _different_ column; they only make the **same** primary-key lookup fast.

⚠ **The consequence that matters more than any internal in this chapter:** there is **nothing** for non-primary-key columns. Query by `author_id` and Cassandra has no idea where those rows live.

- **Postgres:** one `CREATE INDEX`, done.
- **Cassandra:** ⚠ **write a second table** partitioned by `author_id`, holding a duplicate copy.
- ▸ **This is the mechanical root of denormalization (§8)** — not a stylistic preference, a direct consequence of having exactly **one index axis.** Sole exception: **SAI** (§9), and note HI positions it as a fallback for _low-frequency_ queries, not the default.

||Postgres|Cassandra|
|---|---|---|
|Data on disk|**unordered heap**|⭐ **sorted by primary key**|
|Primary-key access|separate B-tree → pointer → heap|**the file itself** (clustered)|
|Auxiliary structures|none needed for the heap|bloom filter · partition summary · partition index — all serving the **same** access path|
|Index on another column|`CREATE INDEX`, done|⚠ **write a second table** (or SAI, §9)|
|Write cost|update heap **+ every index** — random I/O each|**append only.** Nothing to maintain|
|Balance|reads and writes balanced|⭐ **writes cheap; read flexibility sacrificed**|

### 6.1 The philosophy: everything is an append

▸ **CRUX** — Cassandra **never updates in place.** Every create / update / delete is a **new entry**. Row state is derived by replaying entries in **timestamp order**.

- ▸ A delete is just a "removal update" — Cassandra writes a **tombstone** marker rather than erasing anything.
- ▸ **Why this is fast:** sequential appends, no disk seeks to locate-and-mutate an existing record.
- ⚠ **The bill comes due on reads and on compaction** (§6.3), not on writes. Nothing is free — the tradeoff is _deferred_, not eliminated.

### 6.2 The three constructs

|Construct|Where|Role|
|---|---|---|
|**Commit log**|disk|Write-ahead log. Durability if the node dies before the Memtable is flushed|
|**Memtable**|memory|Sorted in-memory structure holding recent writes, **sorted by primary key**. Consolidates multiple writes to a key|
|**SSTable**|disk|"Sorted String Table." **Immutable** file, produced by flushing a Memtable|

### 6.2a Write path

1. Write arrives at a node.
2. Appended to the **commit log** (durability — survives a crash mid-processing or a crash while the data is still only in memory).
3. Written to the **Memtable**.
4. Eventually the Memtable is **flushed to disk as an immutable SSTable** — triggered by a **size threshold** or **elapsed time**. ▸ The SSTable's **bloom filter and partition index are built during this same pass** (§6.2c) — free, since the data is already being walked in order.
5. On flush, the corresponding **commit log entries are discarded** — now redundant, since the data is durably on disk in the SSTable.

▸ Note that steps 1–3 are all that the _client_ waits on. Steps 4–5 are background. That's the write-throughput story in one line.

- ⚠ **WRONG:** the memtable collects writes unordered, then **sorts them at flush time.**
- ✅ **CORRECT:** the memtable is a **continuously sorted structure** (a concurrent **skip-list**) keyed by `(partition key, clustering key)`. Every insert lands in its correct position **immediately.** At flush there is **no sort step at all** — Cassandra walks the structure in order and dumps it sequentially.
- ▸ **Why the design is this way:** sorting at flush would turn every flush into a CPU spike. Instead the cost is **amortized across every write** (an O(log n) insert on data already in RAM), and the flush becomes a **pure sequential write.** ▸ The SSTable is a byte-for-byte serialization of an already-ordered structure.

### 6.2b Read path

1. Check the **Memtable** first — it holds the newest data.
2. On a miss, consult a **bloom filter** per SSTable to determine **which SSTables might** contain the key. (Bloom filter = probabilistic set membership, no false negatives, some false positives → see `01d`.)
3. Read candidate SSTables **newest → oldest**, stopping at the latest version of the row.
4. Within an SSTable, data is **sorted by primary key**, so locating a key is cheap.

- ⚠ **Problem:** a key updated many times can be spread across many SSTables → a read touches many files. **Fix:** compaction (§6.3).

### 6.2c Read path in detail — and what the bloom filter actually does

▸ Trace `channel_id = 42 AND message_id < 8734512 LIMIT 50`, with **8 SSTables** on this node:

```
1. MEMTABLE                  → check first (newest data lives here)

2. For each of the 8 SSTables:
     BLOOM FILTER (RAM)  →  "definitely not here"  → SKIP, zero disk I/O
                         →  "possibly here"        → continue

3. For surviving SSTables (say 2 of 8):
     PARTITION SUMMARY (RAM)  → narrows to a region of the partition index
     PARTITION INDEX  (disk)  → exact byte offset for partition 42
     SEEK + sequential read   → rows already in clustering order; apply the range filter

4. MERGE across memtable + those 2 SSTables:
     per column, newest write timestamp wins (§1.2 LWW)
     tombstones suppress rows (§6.1)

5. Return 50 rows
```

▸ **The bloom filter's job in one line:** turn _"check 8 files on disk"_ into _"check 8 bit-arrays in RAM, then touch 2 files."_ That is the difference between a read that is viable and one that is not.

**The three accelerators — all serving the same access path:**

|Problem|Accelerator|Lives in|
|---|---|---|
|"Is this key in this SSTable **at all**?" — checking 20 files per read is fatal|**Bloom filter**|RAM|
|"**Roughly where** in this multi-GB file?"|**Partition summary** — a sampled index _of_ the index|RAM|
|"**Exactly which byte**?"|**Partition index** — key → byte offset (§6.4)|disk|

**How a bloom filter works.** A bit array plus _k_ hash functions:

- **Insert key K** — hash it _k_ ways, set those _k_ bits to 1.
- **Query key K** — hash it _k_ ways, check those bits.
    - **Any bit is 0** → the key was **definitely never inserted.** ⭐ **No false negatives, ever.**
    - **All bits are 1** → _probably_ present — other keys' bits may have collided. ⚠ **False positives are possible.**
- ▸ **Why that asymmetry is exactly what's needed here:** a **false positive** costs one wasted disk read. A **false negative** would mean **silently losing data** — telling a user their message doesn't exist when it does. The structure is engineered so that only the harmless error is possible.
- ⚠ **Tradeoff:** a lower false-positive rate needs a **bigger bit array** → more RAM **per SSTable**. Real tuning knob (`bloom_filter_fp_chance`), and one reason Cassandra nodes want a lot of memory.

**The whole picture:**

```
                    WRITE                              READ
                      │                                  │
              ┌───────┴────────┐                  ┌──────┴───────┐
         commit log        memtable  ◄────────────┤  1. memtable  │
        (durability)    (sorted, RAM)             └──────┬────────┘
                              │                          │
                         flush│ (sequential)       ┌─────▼─────────────┐
                              ▼                    │ 2. bloom filter   │ RAM
                    ┌──────────────────┐           │    per SSTable    │
                    │     SSTable      │ ◄─────────└─────┬─────────────┘
                    │  sorted by PK    │  maybe-present  │
                    │  + bloom filter  │           ┌─────▼─────────────┐
                    │  + partition idx │           │ 3. summary → idx  │
                    └────────┬─────────┘           │    → byte offset  │
                             │                     └─────┬─────────────┘
                   compaction│ merge sorted runs         │
                             ▼                     ┌─────▼─────────────┐
                  fewer, cleaner SSTables          │ 4. merge by ts,   │
                                                   │   drop tombstones │
                                                   └───────────────────┘
```

⚠ **Calibration — do not over-invest here.** The partition summary and bloom-filter tuning are **below the interview waterline.** What earns credit is the top-level sentence: ▸ _"Cassandra's storage **is** its primary index — there's no separate B-tree to maintain on write, which is why writes are cheap, and why any query outside the primary key needs a second table."_ That connects storage design to data modeling (§8), which is what an interviewer is actually listening for.

### 6.3 Compaction

▸ **CRUX** — background process that **merges many SSTables into fewer**, keeping only the consolidated current state of each row.

- **Fix 1 — read amplification:** fewer SSTables to check per read.
- **Fix 2 — space bloat:** superseded versions of a row are dropped.
- **Fix 3 — tombstone cleanup:** rows that were deleted are finally, physically removed along with their tombstones.
- ▸ **Why it's cheap:** every SSTable is already **sorted**, so this is an n-way merge of sorted runs — linear, sequential I/O.
- ⚠ **The cost to acknowledge:** compaction consumes disk I/O and CPU in the background. Heavy delete/update workloads generate tombstone pressure, and **tombstone-heavy partitions are a real production pain** (reads must scan past them until compaction runs).

### 6.4 SSTable indexing

▸ Cassandra keeps side files mapping **keys → byte offsets** in SSTable files (e.g. key `12` → offset `984`), so a read seeks directly instead of scanning. ▹ Conceptually the same job a B-tree's leaf pointers do — see `01d`.

### 6.5 Further reading

▹ **Deeper on the LSM tree specifically** — _"How Cassandra Stores Data: An Exploration of Log-Structured Merge Trees"_: [hackernoon.com/how-cassandra-stores-data-an-exploration-of-log-structured-merge-trees](https://hackernoon.com/how-cassandra-stores-data-an-exploration-of-log-structured-merge-trees)

- ⚠ **Calibration:** optional. §6.1–§6.4 above is already past interview depth — the payoff line is _"LSM tree, so writes are sequential appends instead of B-tree random I/O."_ ▸ Read this only if the write/read/compaction path still feels mechanical rather than intuitive, or post-offer out of interest. Foundations → `01d`.

## 7 · Cluster membership & fault tolerance (⚠ skim once)

> ⚠ **Calibration:** this whole section is recognition-tier. Know the _names_ and the _one-line purpose_. An SDE2 product round will not probe further, and volunteering Phi Accrual internals reads as noise.

### 7.1 Gossip

▸ **CRUX** — peer-to-peer protocol by which nodes exchange cluster state (who's alive, what the schema is). Universal cluster knowledge is **why any node can coordinate any query** (§5) and why there's no single point of failure.

- ▹ **Staleness handling:** each node tracks, for every node it knows about, a **generation** (timestamp of that node's bootstrap) and a **version** (logical clock, increments ~every second). Together these form a **vector clock**, letting a node discard stale gossip it receives.
- ▹ **Seed nodes:** nodes gossip with randomly chosen peers, **probabilistically biased toward "seed" nodes.** ▸ **Why:** seeds act as deliberate **choke points / guaranteed hotspots**, preventing the cluster from fragmenting into sub-clusters that information never crosses between. Seeds are always discoverable via standard service discovery.

### 7.2 Failure detection

▸ Nodes use a **Phi Accrual Failure Detector** during gossip — each node **independently** decides whether a peer is available. An unresponsive node is **"convicted"** and stops receiving writes; it rejoins when it heartbeats again.

- ⚠ **Notable design choice:** Cassandra **never treats a node as permanently down** unless an administrator decommissions or rebuilds it. ▸ **Why:** to stop transient network blips and routine restarts from triggering expensive cluster-wide rebalancing.

### 7.3 Hinted handoff

▸ **Problem:** a write arrives for a replica the coordinator believes is offline. ▸ **Fix:** the coordinator **stores the write locally as a "hint"** so the operation can succeed now, and **replays it to the node when it comes back online.**

- ⚠ **Scope limit:** hints are **short-lived**, a stopgap for brief outages only. A node down for a long time is **rebuilt** or repaired via **read repair** instead.

## 8 · How to use Cassandra — Data modeling ⭐⭐ (the highest-value section in this file)

### 8.1 Relational vs Cassandra modeling — the mental switch

||Relational|Cassandra|
|---|---|---|
|Driven by|**entities & relationships**|⭐ **queries / access patterns**|
|Data shape|**normalized** — one copy per entity|**denormalized** — duplicated across tables|
|Relationships|foreign keys, JOIN tables, referential integrity|⚠ **none of these exist**|
|Query scope|multi-table JOINs, ad-hoc aggregation|**single-table only**|

▸ **CRUX** — you do **not** design a Cassandra schema and then write queries against it. You **enumerate the application's queries first**, then create **one table per access pattern**, duplicating data as needed. If a new query appears, the answer is frequently **a new table**, not a new index.

### 8.2 The four levers

1. **Partition key** — which data determines the partition. _Goal: the common query is served from a **single partition**._
2. **Partition size** — how big does the partition get **in the worst case**, and **can it grow unbounded?**
3. **Clustering key** — how rows should be sorted within the partition (if order matters at all).
4. **Denormalization** — what data must be duplicated across tables to make each access pattern a single-partition read.

⚠ **Lever 2 is the one candidates forget, and it is the one that fails in production.** "Is this partition bounded?" is the question to ask out loud about every schema you propose.

### 8.3 Example: Discord messages ⭐ (bounding an unbounded partition)

▸ **Access pattern:** a channel is a big group chat; users read **recent** messages and scroll back a little → **reverse-chronological order**, queried **per channel**.

▸ **v1 schema:**

```sql
CREATE TABLE messages (
  channel_id bigint,
  message_id bigint,
  author_id bigint,
  content text,
  PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

- ▸ **Partition key `channel_id`** → all of a channel's messages live in **one partition** → the read is a single-partition query. ▸ **Why that matters:** it avoids a **scatter-gather** across many nodes, which is slow and resource-intensive.
- ▸ **Clustering key `message_id DESC`** → rows are pre-sorted newest-first on disk. The "latest 50 messages" query is a sequential prefix read, not a sort.
- ▸ **Why `message_id`, not `created_at`?** `message_id` is a **Snowflake ID** — a chronologically sortable UUID. It sorts like a timestamp but **cannot collide**, whereas `created_at` (even at millisecond granularity) can, which would silently overwrite a message via primary-key conflict.

⚠ **v1's fatal flaw — two problems, one root cause:**

- **Problem A:** very busy channels produce **enormous partitions**, and large partitions in Cassandra hit performance problems. Discord observed exactly this.
- **Problem B:** partitions grow **monotonically forever** — a long-lived channel eventually degrades no matter its traffic rate.

▸ **Fix — bucketing.** Add a **`bucket`** column to the **partition key**, where a bucket = a fixed **10-day window** aligned to a self-defined `DISCORD_EPOCH` (Jan 1 2015).

```sql
CREATE TABLE messages (
  channel_id bigint,
  bucket int,
  message_id bigint,
  author_id bigint,
  content text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

- ▸ **Fixes A:** even the busiest channel's 10 days of messages fits comfortably in one partition.
- ▸ **Fixes B:** partitions stop growing — time simply rolls over into a **new** partition.
- ▸ **Preserves the single-partition read** in the common case: recent messages are almost always within the current bucket. Multi-bucket reads happen only (1) right after a bucket rollover, or (2) for inactive channels — a small minority of queries.
- ⚠ **Generalize this — it's the reusable technique.** _Composite partition key = entity ID + time bucket_ is the standard answer to *_"this partition grows forever."_ Bucket width is a tuning knob: **narrower = smaller partitions but more cross-partition reads.** For your fintech framing: `PRIMARY KEY ((merchant_id, day_bucket), event_id)` for a transaction event log is the same shape.

### 8.4 Example: Ticketmaster seat browsing (denormalization)

▸ **Context & why Cassandra fits:** the ticket **browsing** UI does **not** need strict consistency — availability changes while the user is looking anyway, and the actual **checkout** flow re-checks a strongly consistent store. Meanwhile, _always_ rendering the browse UI matters, because most users browse and only a minority check out. **Availability > consistency ⇒ Cassandra.** ⚠ Note the shape: Cassandra serves the tolerant read path, a consistent store guards the transaction. Same split as §4.4.

▸ **v1 — one partition per event:**

```sql
CREATE TABLE tickets (
  event_id bigint,
  seat_id bigint,
  price bigint,
  -- seat_id is a clustering key purely for primary key uniqueness;
  -- order doesn't matter for the app's access patterns
  PRIMARY KEY (event_id, seat_id)
);
```

- ▸ Single-partition per event. ▹ Note the clustering key here exists **only to guarantee uniqueness**, not to provide ordering — users navigate by a venue map, so sort order is irrelevant.

⚠ **Problems:**

- **Problem A:** for events with 10,000+ tickets, the DB must do real work to **summarize** (seat totals, price floor) on every request.
- **Problem B:** popular events make that expensive summarization run constantly.

▸ **Fix 1 — narrow the partition using the UX.** The UI is two-tier: a venue map of **sections** first, then individual seats **within a chosen section.** So make `section_id` part of the **partition key**:

```sql
CREATE TABLE tickets (
  event_id bigint,
  section_id bigint,
  seat_id bigint,
  price bigint,
  PRIMARY KEY ((event_id, section_id), seat_id)
);
```

- Spreads one event across **many nodes** (one partition per section) instead of concentrating it.
- Each partition serves **less data**.
- Maps **exactly** to the "show me this section's seats" query.

▸ **Fix 2 — denormalize the summary into its own table** to serve the top-level venue view:

```sql
CREATE TABLE event_sections (
  event_id bigint,
  section_id bigint,
  num_tickets bigint,
  price_floor bigint,
  -- section_id is a clustering key purely for primary key uniqueness
  PRIMARY KEY (event_id, section_id)
);
```

- ▸ **Why this is correct rather than lazy:** rather than making the DB **aggregate** or **fan out across partitions**, you **precompute and duplicate** the numbers. Partitioned by `event_id`, and since events have **< 100 sections**, the whole venue view is **one partition read**.
- ▸ **Why the staleness is acceptable:** section stats don't need precision — Ticketmaster's UI doesn't even show exact counts, it shows **"100+"**. The NFR tolerates eventual consistency, so denormalization costs nothing real. ⚠ **Always justify denormalization by naming the staleness tolerance** — that's the reasoning an interviewer is listening for, not the schema itself.

▸ **The transferable lesson from both examples:** **the UX dictates the schema.** Access patterns → partition key → partition size check → clustering key → denormalize what's left.

#### 8.4a ⚠ Confusion resolved — "Ticketmaster isn't write-heavy. Why Cassandra at all?"

> **The doubt (verbatim):** _"Why for Ticketmaster, I am going to use Cassandra in the first place? … you can use Postgres and for fetching and all, and if you do proper indexing, it will work. Why I need Cassandra in the first place? It's not write-heavy. You're talking about UI fetching."_

▸ **The pushback is correct, and worth saying plainly: Ticketmaster is the weaker of HI's two examples.** Discord is airtight; this one is defensible but not obvious. ⚠ **Do not present it in an interview as self-evidently right** — present it the way §8.4a(d) does.

**(a) The case that genuinely exists — four arguments, in descending strength.**

1. ⭐ **The availability requirement is extreme.** Postgres primary dies mid-onsale → **election → seconds with no reads or writes**, on an event with hundreds of thousands of concurrent users. HI's line _"always showing the browsing UI is important"_ **is** the NFR. Same no-leader/no-election-gap property as §1.3a(c).
2. ⭐ **Read load spreads across nodes — and Postgres cannot do this for one event.** ▸ **Postgres:** all of event 9001's rows sit on one machine; 200k concurrent users hit that one primary, and read replicas only help if you accept lag _and_ add machines each holding the **entire** dataset. ▸ **Cassandra with `((event_id, section_id), seat_id)`:** event 9001's 40 sections become **40 partitions on 40 different nodes** — the hot event's read load is **physically distributed by the schema.** ⚠ **This is the real reason Fix 1 matters** — not just "smaller partitions."
3. **It's more write-heavy than "browsing" suggests.** What's being read is **seat availability**, which churns constantly: every selection creates a **hold**, most holds **expire** (abandoned carts), plus releases, re-holds, price-tier changes. During an onsale a 20,000-seat venue sees **far more state transitions per second than actual purchases.** ⚠ HI never spells this out — part of why the example reads thin.
4. **Isolating the browse path from the transaction path.** Browse traffic is ~100× checkout volume. Pointing it at the same Postgres causes lock contention and connection exhaustion **on the path where money is.** Cassandra as the read-serving layer keeps the transactional store quiet.

**(b) ⚠ Where the objection is right.**

- **At normal scale, Postgres wins.** Regional venue, moderate traffic → Postgres with an index on `(event_id, section_id)` plus Redis for section summaries is simpler, cheaper, and gives you joins and transactions free. **Cassandra there is over-engineering.**
- **Even at scale, Cassandra isn't the only answer.** Postgres + read replicas + aggressive Redis caching is a legitimate competing design — and the `event_sections` summary table is **especially Redis-shaped** (small, hot, staleness-tolerant, `01e`/`02a`). ▸ Cassandra wins on **availability** and on **not needing a separate cache tier.** It does not win by default.

**(c) Why HI includes it anyway — two levers Discord cannot teach.**

||Discord teaches|Ticketmaster teaches|
|---|---|---|
|Trigger for Cassandra|**write throughput**|⭐ **availability** (the second reason in §10.1, independent of write volume)|
|Partition sizing|**time bucketing** — partition grows unbounded|**entity sub-division** — partition bounded but too large / too hot|
|Second table|—|⭐ **denormalization** — precompute rather than aggregate|
|Clustering key|ordering matters (`message_id DESC`)|⚠ ordering **irrelevant** — key exists **only for uniqueness**|

- ▸ **That last row is unlearnable from Discord**, and it's the genuine gap this example fills.

**(d) How to actually present it in a room.** Don't defend it as obviously correct — reason through it:

> _"Browse tolerates staleness and must never go down; checkout needs strict consistency. So I'd split them — Cassandra serves browse, Postgres owns seat ownership and payment. Partitioning by `(event_id, section_id)` spreads a hot event's read load across nodes instead of concentrating it on one primary, which is the failure mode at onsale. **At smaller scale I'd just use Postgres with a Redis cache** — Cassandra earns its place here specifically because of the availability requirement during onsale spikes."_

- ⭐ **The final sentence is the highest-value part.** Naming **the scale at which you'd choose differently** is the difference between someone who knows a tool and someone who knows when not to use it.

## 10 · Cassandra in an interview

### 10.1 ✅ When to propose it

- **Availability > consistency** in the NFRs.
- **High scalability** needs — horizontal scale on commodity nodes.
- ⭐ **High write throughput** — the LSM storage layer (§6) is the specific reason, and naming it is what makes the answer credible.
- **Flexible or sparse schemas** — many columns, not all present per row (§1.2).
- **A few clear, known access patterns** the schema can be built around (§8).

### 10.2 ⚠ When NOT to (say this unprompted — it's the credibility move)

- **Strict consistency / ACID required** → heavy availability bias, no transactions (§4.4). Ledgers, balances, inventory-of-record.
- **Advanced query patterns** — multi-table JOINs, ad-hoc aggregation, "we'll figure out the queries later."
- **Unknown or rapidly changing access patterns** — a query-driven model is brittle when the queries aren't known; each new pattern potentially costs a new table.

### 10.3 The 30-second delivery template

> _"Writes are high-volume and append-only, and this read path tolerates staleness, so I'd use Cassandra. I'd partition on `<entity_id, time_bucket>` — the entity ID keeps the common read on a single partition and the bucket stops the partition growing unbounded — and cluster by `<sort column> DESC` so the recent-first query is a prefix scan. Reads and writes at QUORUM give me read-your-writes; I'd drop reads to ONE if latency matters more than freshness here. The authoritative `<money/state>` stays in Postgres because Cassandra gives me no transactions."_

- ▸ That paragraph hits partition key, partition sizing, clustering, tunable consistency, and the ACID boundary. It is worth more than every internal in §6 and §7 combined.

|Data model hierarchy|**Keyspace** (owns replication strategy + UDTs) → **Table** → **Row** → **Column** (name + type + value **+ write timestamp**)|
|⚠ Logical vs physical hierarchy|logical: keyspace → table → **row** → column. Physical: keyspace → table → **PARTITION** → row → column. ⚠ HI's four-term list **omits the partition** — the level everything else (hashing, replication, storage, sorting, compaction) actually operates on|
|⚠ Sparse ≠ schemaless|all columns must be declared in `CREATE TABLE`; absent columns cost **zero bytes** (Postgres stores a NULL slot); new fields still need `ALTER TABLE`. ▸ Cassandra needs **more** schema planning than Mongo, not less — the primary key is frozen once chosen|
|Why per-**column** timestamps|LWW resolves at **column granularity** — concurrent writes to _different_ columns of the same row both survive; ⚠ same-column conflict **silently discards** the loser|
|"Wide-column" means|columns **vary per row**; no NULL padding → good for **flexible / sparse** schemas|
|⭐ What "wide-column" **really** means|the **unit of storage is the partition, not the row** — rows of one partition sit **contiguous and pre-sorted** on disk. The varying-columns bit is the byproduct|
|⚠ Why Cassandra **over MongoDB**|**NOT** flexible schema — Mongo has that too. **Write throughput + masterless availability + pre-sorted partitions.** Evidence: Discord left Mongo at ~100M messages (B-tree index outgrew RAM → random seeks → unstable p99)|
|Mongo/Postgres write path vs Cassandra|**B-tree → random I/O on every write** (locate page, modify, write back) vs **LSM → sequential append** (§6)|
|⚠ Leader vs masterless|primary-per-shard ⇒ write ceiling = **one machine** + **election gap** (seconds of write unavailability) on failover. Cassandra: **no election, no gap**; adding a node adds write capacity linearly|
|"Any downside of Cassandra?"|**JVM GC tail latency** — why Discord later moved to **ScyllaDB** (C++ reimplementation, same model + CQL)|
|Write conflict resolution|**last write wins** via per-column timestamp. ⚠ silently drops a concurrent write|
|Primary key =|⭐ **partition key** (hashed → which node) **+ clustering key** (sorted → order within partition)|
|⚠ Vocabulary trap|there is **no "secondary key."** Partition key + clustering key together **are** the primary key. (_Secondary index_ = unrelated feature, §9 SAI)|
|⚠ HI's illustrative JSON|shows **only** sparse columns + nested column values. It **flattens away the partition level** and a **UDT's nesting is one column's value**, not a partition→rows relationship|
|CQL parenthesization gotcha|`PRIMARY KEY (a, b)` = partition `a`, clustering `b`. `PRIMARY KEY ((a, b))` = **composite partition key**|
|⚠ Two layers, don't conflate|**partition key → which NODE** (consistent hashing, `01g`) · **clustering key → byte order WITHIN that node's SSTable.** Partition key has nothing to do with disk placement|
|⚠ "Writes append, so why sort?"|writes are **interleaved across thousands of partitions** (`ch42·ch7·ch99·ch42…`) — chronological globally, never contiguous per partition. The **memtable sorts in RAM** so the flushed SSTable is grouped + ordered. Also: a partition spans **many SSTables** and cheap merging needs each sorted; `DESC` is a **layout instruction**; arrival order isn't reliably chronological (clock skew, retries, cross-DC)|
|What sort buys on reads|scroll-back (`message_id < X`) is a **seek not a scan** · **byte-offset index** only constructible against known order (§6.4) · **zero query-time sort** (vs Postgres `ORDER BY` / Mongo `.sort()` on every request)|
|Clustering key's **second** job|**uniqueness within the partition** — independent of ordering. Ticketmaster `seat_id` does **only** this; Discord `message_id` does both|
|Same as DynamoDB?|primary key concept shared **1:1**|
|Partitioning mechanism|**consistent hashing** on a ring, walk clockwise (`01g`)|
|What exactly gets hashed|the **partition key value** (composite columns concatenated) → **Murmur3** → a **token** = ring position. ⚠ **Clustering key is never hashed** — it only orders rows after arrival, which is why a partition read hits **one** node|
|⚠ "Immutable SSTables — so how does data ever move?"|immutable = **never modified in place**, NOT "never deleted." Every change = **read old files → write new files → delete old files**|
|Node join / rebalance|**stream** token ranges out (pure sequential read, source untouched) → target writes **new** SSTables → source runs **cleanup** (= compaction filtered by "do I still own this token?") and deletes old files|
|⭐ The unifying principle|Cassandra **never edits** — appends, rewrites in background, deletes whole files. Same move covers **update · delete · space reclaim · rebalance** → all cheap **sequential** I/O|
|⚠ Cost of adding nodes|streaming + cleanup compaction = **heavy background I/O**. A **planned** operation, not casual. ▸ Second-best "what's operationally hard?" answer after JVM GC|
|Why vnodes|plain consistent hashing fixes **remapping** but not **uneven load**. Many ring tokens per physical node → even spread **+ bigger machines take more vnodes**|
|Replica selection|continue **clockwise** for RF replicas; ⚠ **skip vnodes on a physical node already in the set**|
|Replication strategies|**NetworkTopologyStrategy** (⭐ prod — DC + rack aware, multi-region) vs **SimpleStrategy** (test only)|
|Consistency level =|how many replicas must respond. **ONE → ALL**, set separately for reads and writes|
|QUORUM|`N/2 + 1`. N=3 → 2|
|⭐ The rule|**`R + W > N` ⇒ read sees latest write** (read set and write set must overlap). QUORUM/QUORUM is the balanced case|
|Tuning shortcuts|read-heavy → **W=ALL, R=ONE**; write-heavy → **W=ONE, R=ALL**; ⚠ ALL fails if **one** replica is down|
|ACID?|⚠ **none.** Atomic + isolated only for a **single row within a partition**. No transactions|
|Query routing|**any node can coordinate**; it computes replica locations via consistent hashing + replication config, knows liveness via gossip. **No leader, no SPOF**|
|Why writes are fast|⭐ **LSM tree** (not B-tree, `01d`) — every write is an **append**; state derived by replaying in timestamp order|
|⭐ Postgres vs Cassandra indexing|Postgres: **unordered heap + separate B-tree** (maintained on every write). Cassandra: **the sorted file IS the index** (clustered) — no heap, nothing to maintain on write|
|⚠ Mechanical root of denormalization|Cassandra has **exactly one index axis** (the primary key). Non-key column query = **a second table**, not `CREATE INDEX`. Exception: **SAI** (§9), fallback for low-frequency queries|
|⚠ Memtable is **not** unordered|**continuously sorted skip-list**; **no sort step at flush**, just a sequential dump. Sort cost **amortized per write**, not spiked at flush|
|Built during flush, free|**bloom filter + partition index** are constructed in the **same ordered pass** that writes the SSTable|
|Three read accelerators|**bloom filter** (RAM — is it here at all?) · **partition summary** (RAM — roughly where?) · **partition index** (disk — exact byte offset). ⚠ All serve the **same** primary-key path; none enables a different column|
|Bloom filter guarantee|⭐ **no false negatives ever**; false positives possible. ▸ **Right asymmetry:** false positive = one wasted disk read; false negative = **silently losing data**. ⚠ Lower FP rate = more RAM (`bloom_filter_fp_chance`)|
|Delete mechanism|writes a **tombstone**; physically removed only at **compaction**|
|Write path|commit log (WAL) → **Memtable** (in-mem, sorted by PK) → flushed on size/time threshold to immutable **SSTable** → commit log entries dropped|
|Read path|Memtable → **bloom filter** picks candidate SSTables → read **newest → oldest** → sorted by PK within SSTable|
|Compaction|merges SSTables → cuts **read amplification**, reclaims **space**, purges **tombstones**. Cheap because inputs are sorted. ⚠ background I/O + CPU cost|
|SSTable indexing|key → **byte offset** side files (key 12 → offset 984); B-tree-leaf-like|
|Gossip|P2P cluster-state exchange. **generation** (bootstrap timestamp) + **version** (logical clock) = vector clock → discard stale info. Bias toward **seed nodes** to prevent sub-clusters|
|Failure detection|**Phi Accrual**, per-node independent decision → **convict** and stop routing writes. ⚠ never "permanently down" without admin action (avoids rebalance churn on blips)|
|Hinted handoff|coordinator stores the write as a **hint** for an offline replica, replays on recovery. ⚠ **short-lived only**; long outage → rebuild or read repair|
|⭐ Modeling philosophy|**query-driven, not entity-driven.** One table per access pattern; **denormalize** freely; no JOINs, no FKs, single-table queries only|
|The four levers|**partition key** · **partition size (worst case + unbounded?)** · **clustering key** · **denormalization**|
|Most-forgotten lever|⚠ **partition size.** Ask "is this partition bounded?" of every schema out loud|
|Discord v1|`PRIMARY KEY (channel_id, message_id)`, `CLUSTERING ORDER BY message_id DESC`. Single-partition read, avoids **scatter-gather**|
|Why Snowflake ID not `created_at`|chronologically sortable **and collision-impossible**; timestamps can collide → PK conflict|
|Discord v1's failure|huge partitions on busy channels **+ monotonic unbounded growth**|
|⭐ The bucketing fix|add a **time bucket to the partition key**: `PRIMARY KEY ((channel_id, bucket), message_id)`, 10-day window. Bounds size, stops perpetual growth, still single-partition for recent reads|
|Bucketing generalized|`((entity_id, time_bucket), sort_key)` = the standard answer to unbounded partitions. ⚠ narrower bucket = smaller partitions but more cross-partition reads|
|Ticketmaster — why Cassandra|browse UI tolerates staleness; **checkout re-checks a consistent store**; availability matters more (most users browse, few buy)|
|⚠ "But Ticketmaster isn't write-heavy"|**valid pushback — it's the weaker example.** Real case, strongest first: (1) **availability** — a Postgres election mid-onsale = seconds of total outage; (2) **read load spreads across nodes** — 40 sections = 40 partitions on 40 machines, which one Postgres primary cannot do; (3) holds/expiries/releases make it **more write-heavy than "browsing" implies**; (4) isolates browse traffic from the **money** path|
|⚠ When Postgres wins instead|normal scale → Postgres index on `(event_id, section_id)` + Redis for summaries. **Cassandra there = over-engineering.** Even at scale, Postgres + replicas + Redis is a legitimate competing design|
|⭐ The sentence that earns credit|naming **the scale at which you'd choose differently** — _"at smaller scale I'd just use Postgres with a Redis cache"_|
|What Ticketmaster teaches that Discord can't|trigger = **availability** not write volume · partition sizing by **entity sub-division** not time bucketing · **denormalization** · ⚠ clustering key for **uniqueness only**, ordering irrelevant|
|Ticketmaster fix 1|move `section_id` into the **partition key** → `PRIMARY KEY ((event_id, section_id), seat_id)` — spreads event across nodes, smaller partitions, matches the UX|
|Ticketmaster fix 2|**denormalized** `event_sections` table with precomputed `num_tickets` / `price_floor`; `< 100` sections → one-partition venue view|
|Justify denormalization by|⚠ **naming the staleness tolerance** (UI shows "100+", not exact counts) — not by the schema alone|
|Advanced (name-drop)|**SAI** (global secondary index — avoids denormalizing for _low-frequency_ queries) · **materialized views** (auto-denormalization) · ES/Solr plugins (`02b`)|
|✅ Use when|availability > consistency · high scale · ⭐ **high write throughput** · flexible/sparse schema · **known access patterns**|
|⚠ Avoid when|strict consistency / ACID · JOINs or ad-hoc aggregation · **unknown or shifting access patterns**|
