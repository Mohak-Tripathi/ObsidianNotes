## 1 · The motivating example — why coordination is hard

▸ **CRUX** — the chapter builds one problem up until only a coordination service can solve it. **Follow the escalation; each rung is a real pattern.**

### 1.1 The setup — a chat app that outgrows one server

▸ **One server:** Alice messages Bob, both connected to the same box. Everything in-memory, no coordination. ✅ Simple.

▸ **Two servers:** Alice on Server 1, Bob on Server 2. ⚠ **Server 1 must discover which server Bob is on** to route the message. **This is the whole problem** — service discovery — and every rung below is a failed attempt at it.

### 1.2 ⚠ The escalation ladder — four attempts, each breaks

|Attempt|Idea|⚠ Why it breaks|
|---|---|---|
|**1 · A database**|table mapping user → server|⚠ **single point of failure** · a **lookup per message** → latency · hammered at scale → **bottleneck**|
|**2 · Add a cache**|cache the mapping|⚠ **cache consistency** — Bob moves 2→3, Server 1's cache still says 2 → **messages lost**|
|**3 · Servers broadcast**|each server tells all others on change|⚠ **n² connections** — every server maintains a link to every other. Doesn't scale|
|**4 · Heartbeats**|servers ping to detect death|⚠ **network partition** — Server 2 is alive but unreachable from Server 1. Some see it up, some down → ⭐ **inconsistent view of system state**|

- ⭐ **The point of the ladder:** each of **service discovery, config sharing, failure detection, leader election, consensus** is individually hard, and **rolling your own gets partial failures wrong.** ▸ That inconsistent-view problem at the bottom is the one that needs a real answer.

### 1.3 ⭐ What ZooKeeper provides

▸ **A consistent, reliable source of truth all servers trust.** Servers register in it; user→server mappings live in it; it **notifies** interested servers of changes; it **auto-handles failures** via ephemeral nodes.

- ⭐ **The one-line mental model:** ⭐ **ZooKeeper is a synchronized metadata filesystem — every connected server sees the same tree.** ▸ That shared consistent view is the entire value proposition.
- ⚠ **It is a coordination service, not a database** (§3.5) — built to **notify of changes**, not serve high-volume traffic.
- ⭐ **What you get for free — without hand-building the algorithms:** reliable **service discovery**, **configuration management**, and **leader election.**

▸ **In the chat app, ZooKeeper is responsible for:**

1. **Registering new servers** as they come online.
2. **Telling servers where to route messages** (the user→server mapping).
3. **Tracking which servers are still alive** (ephemeral nodes, §3.2).
4. **Notifying servers of changes and failures** (watches, §3.3).
5. **Auto-cleaning up** a dead server's state — its ephemeral nodes vanish on session death (§5.4).

## 3 · ZooKeeper basics ⭐

> ▸ Three concepts carry the whole chapter: **the ZNode data model (§3.1–3.2)**, **the ensemble of servers (§3.4)**, and **watches (§3.3)**. Master these three and the rest is mechanism.

### 3.1 The data model — ZNodes

▸ **CRUX** — ZooKeeper stores data in a **hierarchical namespace like a filesystem**. The tree nodes are **ZNodes**, each identified by a path (`/app1/config`).

⚠ **Unlike filesystem folders, a ZNode both holds data AND has children.** But the data is **coordination data, kept small:**

- ⭐ **Small data, many nodes:** each ZNode typically **< 1 MB**; the number of ZNodes is **large (thousands)**.
- ⚠ **Not for bulk data** — no images, no documents. ▸ It's the _pointers and flags_ of your system, not the payload.

### 3.2 ⭐ The three ZNode types — the whole toolkit

> ⭐ **This is the most important table in the file.** Every capability in §4 is just a combination of these three.

|Type|Lifecycle|⭐ Used for|
|---|---|---|
|**Persistent**|exists until **explicitly deleted**|**config** — `max_message_size`, rate limits, feature flags|
|⭐ **Ephemeral**|⭐ **auto-deleted when the creating session ends** (disconnect or timeout)|**liveness** — which servers are alive, which users online|
|⭐ **Sequential**|name gets an **auto-appended monotonic counter**|**ordering** — and ⭐ **leader election + distributed locks** (§4.3–4.4)|

```bash
# Persistent — survives everything until deleted
create /chat-app/config/max_message_size "1024"

# Ephemeral — vanishes the instant Server 2's session dies
create -e /chat-app/servers/server2 "192.168.1.102:8080"
create -e /chat-app/users/bob "server2"
#   ↑ Server 2 crashes → BOTH nodes automatically disappear

# Sequential — counter appended by ZooKeeper
create -s /chat-app/channels/global/msg- "Alice: Hello!"
#   → creates /chat-app/channels/global/msg-0000000001
```

- ⭐ **Ephemeral is the killer feature.** ⭐ **"Alive" = "my ephemeral node exists."** No heartbeat logic to write — the session _is_ the heartbeat, and its death cleans up automatically. ▸ This is what §1.2's rung 4 (heartbeats) couldn't get right, solved by construction.
- ⭐ **Sequential + ephemeral together** = the leader-election and lock primitive (§4.3). **Hold that combination.**

#### 3.2a The chat-app tree — how the types compose

```
/chat-app
  /servers                    # who's alive
    /server1  (ephemeral) → "192.168.1.101:8080"
    /server2  (ephemeral) → "192.168.1.102:8080"
  /users                      # who's online, and where
    /alice    (ephemeral) → "server1"
    /bob      (ephemeral) → "server2"
  /config                     # survives restarts
    /max_users     (persistent) → "10000"
    /message_rate  (persistent) → "100/sec"
```

- ▸ **The routing payoff:** Server 1 reads `/chat-app/users/bob` → "server2" → routes there. Bob reconnects to Server 3 → the ZNode updates → routing stays correct. ▸ **§1.1's original problem, solved in one lookup.**
- ⚠ **The scale caveat HI adds — don't miss it:** a real chat app has **millions of users**; ⚠ **a ZNode per user doesn't scale.** ▸ **Fix: register only servers in ZooKeeper, map users → servers by consistent hashing (`01g`).** ZooKeeper tracks **thousands of servers**, not millions of users, and still gets fast failure detection via ephemeral **server** nodes. ⭐ **This is the interview-correct design.**

#### 3.2b ⚠ Confusion resolved — how the type is set, and what sequential is for

- ⭐ **The type is a `create` flag, not something premade.** No flag → **persistent** · `-e` → **ephemeral** · `-s` → **sequential** · `-s -e` → **both**. ▸ Whoever creates the node picks its behaviour; the tree looks structured only because the author chose the right type per node (durable config → persistent, liveness → ephemeral). **Path = where it lives; flag = how it behaves — independent.**
- ⭐ **Sequential = ZooKeeper stamps an ever-increasing unique number onto the name** (`/req-` → `/req-0000000001`, next `...002`). ▸ A distributed **"take a number" ticket machine** — even under a simultaneous race, no ties, numbers strictly ordered. ⭐ **That's what makes "lowest number wins" work** for leader election and locks (§4.3–4.4).

### 3.3 ⭐ Watches — knowing when things change

▸ **CRUX** — a **watch** notifies a client when a ZNode changes, killing the need for polling or server-to-server broadcast.

- ⚠ **Problem without watches:** a ZooKeeper query **per message** → latency + ZooKeeper becomes the bottleneck it was meant to prevent.
- ⭐ **Fix — the local-cache pattern:** each server keeps a **local cache** of the ZooKeeper state and **sets watches.** Reads hit the cache; ZooKeeper only speaks up **when something changes.**

```java
// Server 1 watches the users directory
zk.getChildren("/chat-app/users", true, null);

// Server 3 moves Bob
zk.setData("/chat-app/users/bob", "server3".getBytes(), -1);

// Server 1's callback fires — update local routing table
public void process(WatchedEvent event) {
    if (event.getType() == EventType.NodeDataChanged &&
        event.getPath().equals("/chat-app/users/bob")) {
        byte[] data = zk.getData("/chat-app/users/bob", true, null);
        routingTable.put("bob", new String(data));   // Bob now on Server 3
    }
}
```

- ⭐ **This kills the n² broadcast (§1.2 rung 3).** Every server connects to **ZooKeeper only**; when a user moves, **only servers that care** get notified. **n² → n.**
- ⭐ **Ties to ephemeral nodes:** Server 2 crashes → its session ends → its ephemeral nodes vanish → **watchers are notified** → mark those users offline. ▸ **Failure detection with zero custom heartbeat code.**
- ▹ ⚠ **(worth knowing) watches are one-shot** in classic ZooKeeper: a watch fires **once**, then you must **re-register** it to keep watching. ⊕ _(HI omits this; it's the single most common ZooKeeper gotcha, so I'm flagging it — not deep, just true.)_

### 3.4 The ensemble and server roles _(see the ensemble diagram in the Hello Interview writeup)_

▸ **CRUX** — ZooKeeper never runs on one node (that's the SPOF from §1.2). It runs as an **ensemble** — **3, 5, or 7 servers** (⭐ **odd, for clean majorities**).

|Role|Does|
|---|---|
|⭐ **Leader**|processes **all writes** — every update goes here|
|**Followers**|**serve reads** · follow the leader's updates|

- ⭐ **Fault tolerance = majority (quorum):** the ensemble works as long as **> half** are up. **3 servers tolerate 1 failure; 5 tolerate 2.** ▸ This is why **odd** — 3 and 4 both tolerate only 1, so 4 wastes a node.
- ▸ **Clients connect to the whole ensemble:** `new ZooKeeper("zk1:2181,zk2:2181,zk3:2181", ...)` — any one being down is fine.
- ▹ ⚠ **This is the same leader-based, quorum-write, read-from-any shape as Postgres replication** (`02g §5`) — one writer, many readers, majority durability. **Same pattern, coordination-service clothing.**

#### 3.4a ⚠ Confusion resolved — quorum on writes, not reads (and why that's safe)

- ⭐ **Writes = quorum-synchronous** — the leader waits for a **majority to persist** the change, then commits; the rest sync just after. ▹ **Cassandra-style** — sync to a majority, not to everyone (too slow) and not to nobody (unsafe).
- ⭐ **Reads = local, quorum-free, possibly stale** — any server answers from its own memory, so a lagging follower can return an old value. ⭐ **Why that's safe:** quorum-**on-write** means the data **never forks** — there's one true history, a follower is only ever _behind_ on it, **never holding a _different_ value.** So a stale read is **old-but-real, never wrong.** ▸ ⚠ Can't tolerate the lag? **`sync` before the read forces the follower current** (§5.2) — same as routing read-your-writes to the primary in `02g §5.2`.
- ⭐ **So "quorum is needed" always means the WRITE path.** Its job is **preventing split-brain:** majority-to-write means **only one partition can ever hold a majority → only one side is writable → data can't fork** (`01h`). ▸ **3 servers tolerate 1 failure** — with 1 down, the remaining 2 are still a majority; it only stops at 2 down.

### 3.5 ⭐ "Coordination service, not a database" — the framing to keep

- ⭐ Designed to **notify systems of change**, **not** serve high-volume reads. Small data, read-dominant, change-driven.
- ⚠ **If you're tempted to store real data in it, you've reached for the wrong tool.** ▸ The whole design (in-memory, < 1 MB nodes, watch-based) says _metadata and flags only._

## 4 · The four capabilities ⭐

> ⭐ **The interview-ready framing:** ZooKeeper does exactly four things — **Configuration Management · Service Discovery · Leader Election · Distributed Locks.** ▸ The first two are _reads + watches_; the last two are _the sequential-ephemeral trick._

### 4.1 Configuration management

▸ Store config in ZNodes; ⭐ **the power is push, not storage** — update one node, **every watcher is notified and adapts without restarting.**

```bash
set /chat-app/config/enable_reactions "true"
#  → all servers watching this node flip the feature live
```

- ▸ **Gives:** real-time propagation · versioning · atomic updates.
- ⚠ **Scope it right:** store **dynamic, runtime-changeable** config. ▸ **Static deploy-time config belongs in files / env vars**, not ZooKeeper.
- ⚠ **In a cloud shop, prefer the native option** — **AWS Parameter Store**, **Azure App Configuration**. ▸ Name that awareness in an interview (§7).

### 4.2 Service discovery

▸ **Service discovery** = automatically detecting services and endpoints in a distributed system. As services come online they **register**; as they go offline they **deregister** (or their ephemeral nodes expire). We saw this with the chat servers:

```bash
create -e /chat-app/servers/server2 "192.168.1.102:8080"
```

▸ This pattern enables **dynamic scaling, load balancing, and health checking.**

▸ Services **register** on startup (ephemeral node), **deregister** by session death. Consumers **read + watch** to find live instances.

```
/streaming/services
  /video-transcoder
    /instance1 → "10.0.0.1:8080"   (ephemeral)
    /instance2 → "10.0.0.2:8080"   (ephemeral)
  /recommendation-engine
    /instance1 → "10.0.1.1:9000"   (ephemeral)
```

- ▸ **Flow:** read children of `/…/video-transcoder` → pick an instance → **set a watch** for changes.
- ⚠ **Modern reality:** **Consul, etcd, Kubernetes Services, AWS Cloud Map** do this now — ▹ though many **implement ZooKeeper's patterns**, and some use ZooKeeper internally.

### 4.3 ⭐ Leader election — the sequential-ephemeral trick

> ⭐ **This is the black box from `02e`/`02f`/`02g §5.3` finally opened.** When those chapters said _"a leader is elected,"_ **this is the algorithm.**

▸ **Why elect a leader:** designate exactly **one** node for a critical job — process payments, schedule jobs, handle announcements — so it's done **once, coordinated.**

⭐ **The mechanism — four steps:**

1. Each server creates a **sequential ephemeral** node under one path.
2. ⭐ **Lowest sequence number wins** — that server is the leader.
3. Every other server **watches the node just below its own** (not the leader — the _next-lowest_).
4. ⭐ **Leader fails → its ephemeral node vanishes → the next server up is notified → it becomes leader.**

```bash
create -s -e /chat-app/leader/node-  "server1"   # → node-0000000001  ⭐ LEADER (lowest)
create -s -e /chat-app/leader/node-  "server2"   # → node-0000000002  watches node-...001
create -s -e /chat-app/leader/node-  "server3"   # → node-0000000003  watches node-...002
```

- ⭐ **Why watch the neighbour, not the leader:** if all watched the leader, its death wakes **everyone at once** — a **notification stampede** (the herd problem, §7 hot-spotting). Watching only your immediate predecessor means a death wakes **exactly one** server. ▸ **Elegant, and the detail that shows you actually understand it.**
- ▸ **Automatic failover, one leader at all times.** Used in **HBase** (schema coordination) and ⭐ **Kafka's pre-KRaft controller** (`02c`).

#### 4.3a ⚠ Confusion resolved — which systems this actually applies to

- ⚠ **Not Cassandra** — masterless, **no election at all** (`02e`).
- ⚠ **Not DynamoDB** — elects internally, but **hidden by AWS and not ZooKeeper-based** (`02f`).
- ⭐ **This trick is for an app electing among its OWN instances**, with ZooKeeper as referee. ▸ **Canonical case: Kafka brokers (pre-KRaft) electing a controller** (`02c`). Think "N identical app servers, one must lead" — **not** "database with read replicas."

### 4.4 ⭐ Distributed locks — the same trick, one more time

▸ **CRUX** — a distributed lock lets processes on different machines coordinate access to a shared resource. ⭐ **Same sequential-ephemeral pattern as leader election** — "holding the lock" _is_ "being the leader."

⭐ **The mechanism:**

1. Each **client** (⭐ any process holding a ZooKeeper session — typically an **app-server instance** or worker) creates a **sequential ephemeral** node under a lock path.
2. Sort by sequence number.
3. ⭐ **Lowest holds the lock.**
4. Each client **watches the next-lower node.**
5. **Release (or crash) → node removed → next client notified → it holds the lock.**

```bash
create -s -e /chat-app/locks/send_message-  "client1"  # → ...001  holds lock
create -s -e /chat-app/locks/send_message-  "client2"  # → ...002  waits, watches ...001
delete /chat-app/locks/send_message-0000000001         # client1 done
#   → client2 notified → now holds the lock
```

- ⚠ **The crash-safety win over a naive lock:** if the holder **crashes**, its ephemeral node **auto-vanishes** and the lock passes on. ▸ **No stuck locks, no manual timeout bookkeeping** — the thing you'd have to hand-build with a Redis lock.
- ⚠ **Not for high-frequency locking** (hundreds/sec) — ▸ use **Redis locks** (`02a`) or **DB transactions** (`02g §6.3`) there.

#### 4.4a ⭐ ZooKeeper locks vs Redis locks — the decision (fintech-relevant)

> ⭐ **This is the `02g §6.3` connection and the one genuinely quotable fintech line in the chapter.**

|Axis|**Redis lock** (`02a`)|**ZooKeeper lock**|
|---|---|---|
|Performance|⭐ **fast, simple** — hundreds/sec|⚠ slower — quorum write per acquire|
|Consistency|⚠ weaker (timeout/TTL-based)|⭐ **strong** — quorum-backed|
|Holder crash|⚠ **manual** — TTL + heartbeat bookkeeping|⭐ **automatic** — ephemeral node vanishes|
|Long-lived locks (hours)|⚠ awkward — TTL renewal|⭐ **robust** — session-based|
|Hierarchical / nested locks|⚠ no|⭐ **yes** (§7 durable locks)|

- ⭐ **HI's rule, worth quoting verbatim:** ▸ Redis for performance and simplicity (**Ticketmaster, Uber** breakdowns used Redis). ⭐ **ZooKeeper when correctness trumps performance — financial transactions — or for long-lived locks** where automatic crash detection beats Redis's timeout juggling.
- ⭐ **The Razorpay/CRED sentence:** _"For a payment-critical lock I'd take ZooKeeper's quorum-backed consistency and automatic crash cleanup over a Redis lock's speed — here correctness beats latency."_ ▸ Pairs directly with `02g §6.3`'s row-locking.

## 5 · How it works — under the hood ⚠

> ⚠ **HI is explicit: _"very unlikely you'll need this for interviews."_** ▸ Everything here is a **re-run of `02g`/`02h`** — I'm compressing hard and cross-referencing. **Read for recognition, not mastery.**

### 5.1 ZAB — the consensus protocol

▸ ZooKeeper coordinates _itself_ with **ZAB (ZooKeeper Atomic Broadcast)**. Two phases:

- **Leader election** — on startup or leader death, servers vote; ⭐ **most up-to-date transaction history wins** (ties → highest server ID).
    
- **Atomic broadcast** — writes go to the leader → leader proposes to followers → ⭐ **committed once a quorum persists it.**
    
- ⚠ **The delightful irony worth one sentence:** ZooKeeper solves everyone's coordination, but **first had to solve its own** — ZAB is that solution.
    
- ⚠ **The internal/external inversion HI flags:** ZAB's leader election prefers the **highest** ID; the **application-level** election you build on top (§4.3) picks the **lowest** sequence number. ▸ **Opposite conventions — don't conflate them.**
    
- ▹ ⭐ **ZAB ≈ Raft ≈ Paxos** — HI says so directly. **You've met this** (`01h` neighbourhood). Same goal: consensus under failure. **One line is enough.**
    

### 5.2 Consistency guarantees ⚠ (all re-runs)

|Guarantee|Means|You've seen it|
|---|---|---|
|**Sequential consistency**|one client's updates apply in send order|—|
|**Atomicity**|update fully succeeds or fully fails|`02g` ACID|
|**Single system image**|any server → same view (after sync)|`02g §5.2`|
|**Durability**|committed = persists across restarts|`02g §4.1` WAL|
|**Timeliness**|views updated within a bounded lag|—|

- ⚠ **The one that matters — stale follower reads:** reads come from a follower's **local memory**, which may **lag the leader.** ⭐ **This is `02g §5.2`'s read-your-writes problem exactly.** ▸ **Fix: the `sync` operation before a read** forces the follower current — ZooKeeper's version of "route to primary."
- ⚠ **Not for high-throughput** read/write; optimized for **read-dominant (~10:1), small data.** ▹ Same posture as every coordination store.

### 5.3 Read vs write paths

- **Reads** — served by **any server from in-memory** → high throughput, low latency, ⚠ **possibly stale.**
- **Writes** — **all through the leader** → ZAB → quorum. ⚠ **More expensive**, total-ordered.
- ▹ ⭐ **Identical to Postgres** (`02g §5.2`): reads scale on followers, writes funnel to one leader. **Third time you've seen this shape** (Postgres, and Flink's single JobManager).

### 5.4 Sessions — the heartbeat behind ephemeral nodes

▸ **CRUX** — a **session** is the client's connection with a **timeout (typically 10–30 s)**, kept alive by **heartbeats.** ⭐ **Ephemeral nodes and watches live and die with the session.**

- **Establish** → **heartbeat** to keep alive → **recover** by reconnecting to another server before timeout → ⭐ **expire → all the client's ephemeral nodes deleted + watches removed.**
- ⭐ **This is the machinery under §3.2's ephemeral magic:** "auto-deleted when the session ends" = _the session timed out with no heartbeat._
- ⚠ **The timeout is the key tuning knob:** **too short** → network blips cause false failovers; **too long** → slow to detect real deaths. ▹ **Exactly Flink's checkpoint-interval / heartbeat trade** (`02h §8.2`).

### 5.5 Storage — transaction log + snapshots ⭐ (you own this cold)

- **Transaction log** — every change **written to a WAL on disk before acknowledging.** ⭐ **This is Postgres's WAL** (`02g §4.1`) — same words, same guarantee: no acknowledged update is ever lost.
- **Snapshots** — periodic dumps of the in-memory DB; recovery = **load latest snapshot + replay the log.** ⭐ **This is Flink's checkpoint + replay** (`02h §8`) and Postgres's checkpoint.
- ⚠ **HI's one sharp note:** ⭐ **the transaction log is the most performance-critical part** — it's `fsync`ed before every response, so **give it a dedicated disk.** ▹ Same reason WAL flush gates Postgres commit latency (`02g §4.1`).

### 5.6 Handling failures ⚠

|Failure|Response|
|---|---|
|**Follower dies**|leader continues while **quorum holds**|
|**Leader dies**|⭐ **automatic re-election** (highest-ID follower promoted)|
|⭐ **Network partition, no majority**|⚠ **writes STOP until resolved** — ⭐ **prevents split-brain**|
|**Client dies**|ephemeral nodes removed after **session timeout**|

- ⭐ **The partition behaviour is the CAP identity (`01h`):** no quorum → refuse writes. ⭐ **ZooKeeper is CP — it sacrifices availability to never diverge.** ▸ **The one-word classification to remember: CP.**

## 6 · ZooKeeper in the modern world ⚠

> ⭐ **The most interview-relevant section after §4.** Knowing ZooKeeper's _decline_ is what stops you proposing a dated design.

### 6.1 Where it's still used

- ⭐ **Apache ecosystem:** HBase, Hadoop, SolrCloud, Storm, NiFi, Pulsar · **ClickHouse** (replication coordination).
- ⚠ ⭐ **Kafka LEFT it.** **KRaft** (Kafka Raft Metadata mode) replaced ZooKeeper to cut ops complexity, scaling bottlenecks, and failure points (`02c`). ▸ **A landmark signal** of the industry trend: **self-contained consensus over an external coordinator.**

### 6.2 The alternatives to name

|Tool|Niche|
|---|---|
|⭐ **etcd**|cloud-native; **powers Kubernetes**; strong consistency, HTTP/gRPC, small-data high-read|
|**Consul** (HashiCorp)|service discovery + health checks + KV + **network automation**|
|**Cloud-native**|**AWS Parameter Store**, **Azure App Configuration**, **Amazon MSK** (managed ZooKeeper), **AWS Cloud Map**|

- ⭐ **The interview move:** name **etcd/Consul/cloud** as the current defaults; mention ZooKeeper as **battle-tested but no longer the automatic pick.**

### 6.3 ⚠ Limitations — the deep-infra ammunition

|Limitation|Detail|
|---|---|
|⭐ **Hot-spotting / herd**|many clients watching **one node** (leader election, locks) → notification storms. ▸ **Why §4.3 watches the neighbour, not the leader**|
|**Write cost**|every write → leader → quorum. ⚠ **expensive**|
|**In-memory cap**|⚠ **< 1 MB nodes, dataset must fit in RAM**|
|**Ops complexity**|⭐ _"simple to use but complex to operate"_ — JVM tuning, disk layout, timeout monitoring|

---

## 7 · When to actually use ZooKeeper ⭐

> ⭐ **HI's blunt summary:** ⚠ **rarely your first reach.** Three places it's genuinely right:

### 7.1 Smart routing (⚠ Staff+ / deep-DS only)

▸ **Collocate related users on one server** — a chat room's, or a live stream's, websocket connections on the same box to cut cross-server chatter. ZooKeeper is the **API gateway's coordination point**: servers register capacity + rooms handled; the gateway queries ZooKeeper to place a new connection on the right server; full rooms expand to new servers coordinatedly.

- ▹ ⚠ **HI flags this as Staff+ / senior-DS-focused.** ▸ **Awareness-only for your target** — recognise the pattern (it's the `02c`/live-comments spine), don't lead with it.

### 7.2 ⭐ Certain infrastructure design problems

⭐ **The strongest legitimate use for an interview:** _"Design a distributed message queue"_ or _"distributed task scheduler."_ ZooKeeper is the **consensus brain** — exactly Kafka's pre-KRaft role:

- **Broker registration** (ephemeral) · **topic metadata** (partitions, replication) · ⭐ **per-partition leader election** (sequential ephemeral, §4.3) · **consumer-group membership + rebalancing** · ⭐ **broker failure detection** (session expiry → nodes vanish → reassignment).
- ▸ **If you draw a message queue or scheduler, this is where ZooKeeper belongs** — and where naming it is a **strength**, not a dated reflex.

### 7.3 Durable / hierarchical locks

▸ Beyond simple locks (Redis handles those), ZooKeeper wins for ⭐ **hierarchical locks with dependencies** — e.g. a **distributed filesystem** locking a **directory and its files** with **deadlock prevention.** Watches on multiple nodes let a client monitor the **whole lock hierarchy.** ▸ Extends §4.4a.

---

## 8 · Summary — the decision

⭐ **ZooKeeper is a coordination service** — config, service discovery, leader election, distributed locks — via a **synchronized metadata filesystem** of ZNodes with watches.

▸ **The decision sequence to run in a room:**

1. ⚠ **Do you even need a coordination service?** → Load balancers and built-in service discovery cover most product-app cases. **Stop here** most of the time.
2. **Need config push / service discovery / a lock?** → **In cloud, prefer etcd / Consul / Parameter Store.** Name them.
3. ⭐ **Designing deep infra (message queue, scheduler) or need quorum-strong / hierarchical / long-lived locks?** → **Now ZooKeeper is a defensible, battle-tested pick.**

- ⭐⭐ **The takeaway, mirroring `02h`:** the value is the **patterns** — ephemeral-node failure detection, sequential-node leader election, watch-driven config. ▸ **Know the patterns; name ZooKeeper as one implementation among current ones, and only where it fits.**

## Quick Recall (pass 3+)

|Use / Question|ZooKeeper answer|
|---|---|
|Calibration|⭐ **mid-tier** (like `02f`/`02h`). ⭐ **Opens the "a leader is elected" black box** from `02e`/`02f`/`02g §5.3`. Deep: **ZNode types (§3.2), leader election + locks (§4.3–4.4)**. ⚠ Cross-ref, don't re-learn: **ZAB=Raft, txn-log=WAL, stale reads=Postgres replication**|
|⭐⭐ The negative takeaway|⚠ **don't reach for ZooKeeper.** Modern = **etcd/Consul/cloud**; **Kafka removed it (KRaft)**; unprompted use reads **dated**. Know the **patterns**, name it as **one** implementation|
|⭐ One-line mental model|**a synchronized metadata filesystem — every connected server sees the same tree.** ⚠ **Coordination service, NOT a database** — notifies of change, doesn't serve bulk traffic|
|⚠ The escalation ladder|DB (**SPOF + bottleneck**) → cache (**consistency**) → broadcast (**n²**) → heartbeats (**partition → inconsistent view**). ▸ Each rung a failed service-discovery attempt|
|**ZNode**|node in a filesystem-like tree; holds **data AND children**. ⚠ **< 1 MB each, thousands of them** — coordination data, **not bulk**|
|⭐ Three ZNode types|**Persistent** (until deleted → **config**) · ⭐ **Ephemeral** (dies with session → **liveness**) · ⭐ **Sequential** (monotonic counter appended → **ordering, election, locks**)|
|⭐ How the ZNode type is set|a **`create` flag**, per node: none→**persistent**, `-e`→**ephemeral**, `-s`→**sequential**, `-s -e`→**both**. ⭐ **Sequential** = ZooKeeper appends a **unique ever-increasing number** → "take a number" ticket machine → makes **lowest-wins** election/locks work|
|⭐ Ephemeral = killer feature|⭐ **"alive" = "my ephemeral node exists."** Session death auto-deletes it → **failure detection with no heartbeat code.** Solves §1.2's heartbeat rung by construction|
|⚠ Millions of users|⚠ **don't create a ZNode per user.** ⭐ **Register servers only; map users→servers by consistent hashing (`01g`).** ZooKeeper tracks thousands of servers, not millions of users|
|⭐ **Watches**|notify a client on ZNode change → **no polling, no broadcast.** ⭐ **Local-cache pattern:** cache state + watch; ZooKeeper speaks only on change. **Kills n² → n.** ▹ ⚠ **one-shot — must re-register** (⊕ HI omits)|
|**Ensemble**|**3/5/7 servers (odd)**. ⭐ **Leader = all writes; followers = reads.** Tolerates **< half down** (3→1, 5→2). ▹ Same shape as Postgres replication (`02g §5`)|
|⭐ Quorum on write, not read (§3.4a)|**writes = quorum-synchronous** (majority persists, then commit; rest sync after — Cassandra-style). **reads = local, quorum-free, possibly stale.** ⭐ **Safe because** quorum-on-write means data **never forks** → a lagging read is **behind, never wrong.** ⚠ `sync` before read forces current (§5.2)|
|⭐ Why quorum exists (§3.4a)|**prevents split-brain:** majority-to-write → **only one partition can hold a majority → only one side writable → data can't fork** (`01h`). ▸ **3 servers tolerate 1 failure** (2 is still a majority; stops only at 2 down). ⚠ **Always a WRITE requirement — reads need none**|
|⭐⭐ **Leader election**|each server makes a **sequential ephemeral** node → ⭐ **lowest number = leader** → each watches the **node just below it** → leader dies → node vanishes → next up promoted. ▸ This **is** the `02e`/`02f`/`02g §5.3` black box|
|⭐ Why watch the neighbour|watching the leader → its death wakes **everyone (herd/stampede)**. Watching your **predecessor** → death wakes **exactly one**. ▸ The detail that proves understanding|
|⚠ Which systems use this trick (§4.3a)|⚠ **NOT Cassandra** (masterless, no election) · ⚠ **NOT DynamoDB** (hidden, non-ZooKeeper). ⭐ **It's an app electing among its OWN instances** — canonical: **Kafka brokers pre-KRaft** (`02c`). "N app servers, one leads" — not "DB with replicas"|
|⭐ **Distributed locks**|⭐ **same sequential-ephemeral trick** — lowest holds the lock, watch the next-lower, release/crash → next notified. ⚠ **crash auto-frees the lock** (ephemeral vanishes) — no stuck locks|
|⭐ ZK lock vs Redis lock|**Redis** = fast, simple, ⚠ TTL/heartbeat crash handling (Ticketmaster/Uber). ⭐ **ZooKeeper** = quorum-strong, **auto crash cleanup**, long-lived + hierarchical. ⭐ **"Correctness over performance → ZooKeeper (financial)"** — pairs with `02g §6.3`|
|Four capabilities|**Config management · Service discovery · Leader election · Distributed locks.** First two = read+watch; last two = sequential-ephemeral trick|
|Config management|update one ZNode → ⭐ **all watchers adapt live, no restart.** ⚠ **dynamic config only** (static → files/env). ⚠ In cloud prefer **Parameter Store**|
|Service discovery|register (ephemeral) on start, deregister on session death; consumers **read + watch**. ⚠ Modern: **Consul/etcd/K8s/Cloud Map** (often implement ZK's patterns)|
|⚠ **ZAB**|ZooKeeper's own consensus: elect leader (**most-up-to-date history**, tie→**highest ID**) + atomic broadcast (**quorum commit**). ▹ ⭐ **≈ Raft ≈ Paxos** — one line. ⚠ Internal election prefers **highest** ID; app-level election prefers **lowest** number — opposite conventions|
|⚠ Stale follower reads|reads from a follower's **local memory** can **lag the leader** → ⭐ **read-your-writes, same as `02g §5.2`.** ▸ **Fix: `sync` before read** (= route-to-primary)|
|Read vs write paths|reads **any server, in-memory, maybe stale**; writes **leader → quorum, expensive**. ▹ ⭐ Identical to Postgres (`02g §5.2`) — **third time this shape**|
|⭐ **Sessions**|connection + **10–30 s timeout** kept by heartbeats. ⭐ **Ephemeral nodes + watches die with the session.** ⚠ Timeout knob: too short → false failover, too long → slow detection (= Flink's trade, `02h §8.2`)|
|⭐ Storage|**transaction log = Postgres WAL** (`02g §4.1`) — `fsync` before ack, **dedicated disk**. **Snapshots + replay = Flink checkpoint** (`02h §8`). ▸ Third appearance of WAL+snapshot|
|⭐ **CP classification**|⭐ **network partition, no majority → writes STOP** (prevents split-brain). ⭐ **ZooKeeper is CP** (`01h`) — sacrifices availability to never diverge|
|⭐ Modern decline|Apache stack still uses it (HBase/Hadoop/Pulsar/ClickHouse); ⭐ **Kafka moved to KRaft.** Trend: **built-in consensus over external coordinator**|
|⚠ Limitations|⭐ **hot-spotting/herd** (many watch one node) · **write cost** (quorum) · ⚠ **<1 MB, in-RAM only** · _"simple to use, complex to operate"_|
|⭐ When to actually use it|1 **usually don't** (LB + built-in discovery) · 2 in cloud prefer **etcd/Consul/Parameter Store** · 3 ⭐ **deep infra (message queue / scheduler) or quorum-strong / hierarchical / long-lived locks** → defensible|
|⭐ Infra design fit|**distributed message queue / task scheduler** → ZooKeeper as **consensus brain** (Kafka's pre-KRaft role): broker registration, partition leader election, failure detection. ▸ **Naming it here is a strength**|
