## 1 · The motivating example (and why it's well chosen)

▸ A growing social platform — **not** Facebook scale. Requirements:

- Users create **posts** · comment on posts · **follow** other users · **like** posts and comments · create **DM threads**.

▸ **What makes it a good database exercise: the requirements pull in different directions.**

|Requirement|What it demands|Postgres answer|
|---|---|---|
|Creating a DM thread (thread + participants + first message)|**atomicity** across multiple steps|transactions (§6.1)|
|Comments and follows must reference real posts/users|**referential integrity**|foreign keys (§9.1)|
|Like counts|⚠ **eventual consistency is fine** — seconds of lag is acceptable|denormalized counter, or offloaded writes (§4.3)|
|Profile view: recent posts + follower count + metadata|**efficient multi-entity read**|indexes, covering indexes (§3)|
|Search posts, find users|**full-text search**|GIN (§3.3)|
|Growth|**room to scale**|replication, partitioning, sharding (§4.3, §5)|

- ⭐ **The transferable move:** notice that **different operations in one system have different consistency needs.** Saying that aloud — _"thread creation needs atomicity, like counts don't"_ — is worth more than a blanket "we'll use Postgres because it's ACID."

## 3 · Read performance

> ▸ Reads vastly outnumber writes in most systems — users browse far more than they post. ⚠ **Don't go into query planner internals.** Focus on **which index type for which access pattern**, and the practical limits (§3.7).

### 3.1 Basic indexing — B-tree

▸ **CRUX** — the default index type. Great for three things:

- **Exact matches** — `WHERE email = 'user@example.com'`
- **Range queries** — `WHERE created_at > '2024-01-01'`
- **Sorting** — `ORDER BY username`, ⚠ **only if the ORDER BY columns match the index column order**

```sql
-- Bread and butter
CREATE INDEX idx_users_email ON users(email);

-- Multi-column, for a common query pattern
CREATE INDEX idx_posts_user_date ON posts(user_id, created_at);
```

- ▸ Postgres creates a B-tree on the **primary key** automatically; everything else you declare.
- ▹ ⚠ **Contrast with `02e §6.0`:** here the index is a **separate structure** pointing into an unordered heap. Cassandra collapses index and storage into one. That contrast is why Postgres supports arbitrary indexes and Cassandra doesn't.

### 3.2 ⚠ The interview trap: indexing everything

▸ A common candidate reflex is to add an index per column. **Each index costs:**

- **Slower writes** — the index must be updated on every write (and gets its own WAL entries, §4.1).
    
- **Disk space.**
    
- ⚠ **Possibly nothing** — the query planner may decide a sequential scan is faster and never use it.
    
- ⭐ **The line to say:** _"I'd index `user_id` and `created_at` because those drive the profile query — I'd avoid indexing everything, since each index taxes every write."_
    

### 3.3 Beyond basic indexes ⭐ (where Postgres replaces other systems)

> ⭐ **This is the section that produces the strongest interview argument in the file** — see the calibration header.

**3.3a Full-text search — GIN**

▸ **GIN** (Generalized Inverted Index) works like the index at the back of a book: a mapping from **each word → every location it appears.**

```sql
ALTER TABLE posts ADD COLUMN search_vector tsvector;
CREATE INDEX idx_posts_search ON posts USING GIN(search_vector);

SELECT * FROM posts
WHERE search_vector @@ to_tsquery('postgresql & database');
```

▸ **Built in, and covers:** word **stemming** (finding/find/finds all match) · **relevance ranking** · **multiple languages** · complex **AND/OR/NOT** queries.

⚠ **When it is NOT enough — reach for Elasticsearch (`02b`) only if you need:**

- more sophisticated **relevancy scoring**
    
- **faceted** search
    
- **fuzzy matching** / search-as-you-type
    
- **distributed** search over very large datasets
    
- advanced **analytics and aggregations**
    
- ⭐ **HI's rule:** start with Postgres search; introduce Elasticsearch **only** when you hit a specific requirement it can't meet. **Simpler architecture, less operational complexity.**
    

**3.3a.1 ⚠ Confusion resolved — what a `tsvector` actually is, and how GIN differs from Elasticsearch**

> **The doubt (verbatim):** _"So I think you are doing vector and all embedding, and then you are adding gin over it, and then you are searching it. So, how it is different from Elasticsearch which kind of do, you know, keyword and the document ID, then the word and the document ID mapping and all. So, basically how adding one column, what exactly gets stored in that column and how it does full text search"_ _"'brown':3 'fox':4 'jump':6 'quick':2,7 These three four six seven two are these are the row row ID and all … So what is this two, comma, seven?"_

**(a) ⚠ WRONG: `tsvector` has anything to do with embeddings.** ✅ **CORRECT:** "vector" here is **1980s information-retrieval vocabulary meaning a list of terms.** No model, no training, no semantic similarity anywhere in this chapter.

```sql
SELECT to_tsvector('english', 'The quick brown foxes are jumping quickly');
-- 'brown':3 'fox':4 'jump':6 'quick':2,7
```

Four deterministic string-manipulation steps:

1. **Lowercased.**
2. **Stop words removed** — "the", "are" are gone; they match everything, so they're worthless for search.
3. **Stemmed** — foxes→fox, jumping→jump, quickly→quick. ▸ **This is why searching "find" matches "finding"** (§3.3a).
4. **Positions recorded.**

- ⚠ **Why the error matters:** claiming embeddings claims **semantic** search — matching "car" to "automobile". Postgres does **not** do that; it matches **stems**, and "car" will never match "automobile". You'd be misrepresenting a real capability limit. ▹ Semantic search in Postgres exists as the separate **pgvector** extension — different feature, not this chapter.

**(b) ⚠ The numbers are word positions within ONE document — not row IDs.**

```
The quick brown foxes are jumping quickly
 1    2     3     4    5     6       7
```

- `'quick':2,7` → the stem appears at word **2** ("quick") and word **7** ("quickly").
- ▸ **Two levels, don't conflate:** the **`tsvector` column** = word → **positions within this row**. The **GIN index** = word → **which rows**. ⭐ **Row IDs live in the index, not the column.**
- ▸ **Why positions exist:** they enable **phrase search** (`'quick' <-> 'brown'` = adjacent) and let ranking weigh matches near the start of a document.

**(c) Column vs index — two separate things.** The column stores each row's stems and positions; the **GIN index inverts that**:

```
COLUMN (per row)                  GIN INDEX (inverted)
row 1 → 'databas':4 'postgresql':2    'databas'    → [1, 2]   ← posting list
row 2 → 'databas':1 'mongodb':3       'mongodb'    → [2]
row 3 → 'index':5 'postgresql':1      'postgresql' → [1, 3]
```

- ⭐ **"Inverted" is the whole idea:** the **table** maps row → words; the **index** maps **word → rows.** That inversion is what makes "find documents containing X" fast.

**(d) Query execution** for `to_tsquery('postgresql & database')`: look up each stem → get its posting list → **intersect the sorted lists** → fetch surviving rows. ▹ Both lists are sorted, so intersection is a **linear merge** — same trick as `02e §6.3`'s compaction.

**(e) ⭐ So how is it different from Elasticsearch? Structurally, barely.**

||**Postgres GIN**|**Elasticsearch** (`02b`)|
|---|---|---|
|Core structure|inverted index|inverted index — ⭐ **same idea**|
|Analysis pipeline|fixed: `to_tsvector` config per language|⭐ pluggable analyzers, custom tokenizers, synonyms, n-grams|
|Relevance scoring|⚠ `ts_rank` computed **at query time**, re-reading the `tsvector` for each match|⭐ **BM25 with term-frequency and doc-length stats precomputed in the index**|
|Fuzzy / typo tolerance|⚠ needs the separate `pg_trgm` extension|built in (edit distance)|
|Search-as-you-type|⚠ awkward|built in|
|Facets / aggregations|⚠ plain SQL `GROUP BY`, no index support|⭐ purpose-built|
|Distribution|⚠ single node (or your own sharding)|⭐ natively distributed|
|Write cost|⚠ GIN updates are expensive|designed for it|

- ▸ **The one that actually bites: ranking.** **Finding** matches is fast in both. **Ordering by relevance** is where Postgres pays — it fetches and scores each match, while Elasticsearch has the statistics precomputed. ⭐ **Ten matches is fine; ten thousand needing ranking is where Postgres hurts.**
- ▸ **So HI's rule is well-founded:** the **matching is genuinely equivalent.** Reach for Elasticsearch when you need what **surrounds** it — scoring sophistication, fuzziness, facets, or distribution.

**(f) (⚠ below the interview waterline — knowledge only)** — GIN is structurally a **B-tree whose keys are the extracted terms**, each leaf pointing to a **posting list** of row identifiers (`ctid`s). ▹ A term appearing in very many rows gets its posting list promoted to its own B-tree, called a **posting tree**.

**3.3b Flexible metadata — JSONB + GIN**

▸ Posts have varying attributes: location, mentions, hashtags, attached media. Rather than a column per possibility, use **JSONB** — ⭐ **NoSQL-style flexibility inside Postgres.**

```sql
ALTER TABLE posts ADD COLUMN metadata JSONB;
CREATE INDEX idx_posts_metadata ON posts USING GIN(metadata);

SELECT * FROM posts
WHERE metadata @> '{"type": "video"}'
  AND metadata @> '{"hashtags": ["coding"]}';

SELECT * FROM posts WHERE metadata @> '{"mentions": ["user123"]}';
```

- ⭐ **The argument:** _"JSONB gives me schema flexibility for post metadata without introducing MongoDB."_ ▸ Compare `02f §2.2` — DynamoDB's schemaless model, available as **one column** inside a relational database.

**3.3b.1 ⚠ Confusion resolved — how JSONB is structured and what GIN does to it**

> **The doubt (verbatim):** _"I want to know type and hashtag. So it means that type is a key value in that JSONB. There will be one key is type and which has a value kind of a, you know, like video or audio whatever it is. And hashtag is also one of the key which has an array of string … how JSONB gets structured and how gin is getting involved. And if gin is getting involved then are you creating embedding the same way tsvector and all you are doing for that particular JSONB as well column?"_

**(a) ✅ Your reading of the query is correct.** `type` is a key with a **string** value; `hashtags` is a key with an **array** value. The stored document:

```json
{ "type": "video", "hashtags": ["coding", "backend"], "mentions": ["user123"] }
```

- ▸ **`@>` means "contains"** — _does this document contain this sub-document?_ ▸ For arrays that means **"contains this element"**, which is why `{"hashtags": ["coding"]}` matches a post tagged `["coding", "backend"]`.

**(b) ⚠ No embeddings here either** — same correction as §3.3a.1. GIN extracts **literal keys and values as index terms.** With the default `jsonb_ops`, each key and each value gets its own posting list:

```
"type"     → [rows having that key]
"video"    → [rows having that value]
"hashtags" → [...]
"coding"   → [...]
```

- ▸ **Execution:** `@> '{"type": "video"}'` looks up `"type"` and `"video"`, **intersects** the posting lists, then ⚠ **rechecks** the candidates to confirm the key and value are actually **paired** — guarding against a row that has `"type": "audio"` and separately the value `"video"` somewhere else.

**(c) ⭐ The unifying point: this is the same GIN machinery as full-text search.** GIN indexes anything that **decomposes into multiple searchable items per row** — text decomposes into **stems**, JSONB decomposes into **keys and values.** ▸ **One index type, two applications.**

**(d) Two things worth knowing about JSONB itself.**

- ▸ **JSONB is pre-parsed binary**, not text — that's the difference from the older `json` type, and **why it can be indexed at all.**
- ⚠ **The trade to voice aloud:** flexibility, but **no constraints, no foreign keys, no type checking** inside the document. Validation moves into your application — the same bargain as `02f §2.2`. ▸ **Use it for genuinely variable metadata, not as an excuse to skip schema design.**

**(e) (⚠ below the interview waterline — knowledge only)** — `jsonb_path_ops` is the alternative operator class: it indexes **hashes of complete key→value paths** rather than keys and values separately. Smaller and faster for `@>`, but supports fewer operators.

**3.3c Geospatial — PostGIS + GiST**

▸ Not in core; the **PostGIS extension** adds spatial types and indexing.

```sql
CREATE EXTENSION postgis;

ALTER TABLE posts
ADD COLUMN location geography(Point, 4326);

CREATE INDEX idx_posts_location ON posts USING GIST(location);

SELECT * FROM posts
WHERE ST_DWithin(
    location,
    ST_MakePoint(-122.4194, 37.7749)::geography,  -- SF
    5000                                          -- 5 km, in metres
);
```

▸ Handles spatial data types (points, lines, polygons) · distance calculations (great-circle, Euclidean) · spatial operations (intersection, containment) · multiple coordinate systems.

- ▹ **GiST** is a general-purpose index framework PostGIS uses for **bounding-box** lookups — so "within X km" or "inside this boundary" runs without checking every row.
- ⭐ **The credibility anecdote:** **Uber initially ran its entire ride-matching system on PostGIS**, moving to custom solutions only later, at scale. ▸ Good evidence that specialized geo databases are often premature.

**3.3c.1 ⚠ Confusion resolved — geometry types, and what GiST does under the hood**

> **The doubt (verbatim):** _"what I learned in earlier chapter is that there is a geohash, there is a quadtree, R-tree, these are the things available. So what basically Postgres use? … you are adding a column, column geography point. What is point? You talked about point, lines, and polygons, right? What is point, lines, and polygon is doing? And then you are adding an indexing of gist. So what does gist do under the hood?"_

**(a) The geometry types — what shape the column holds.**

|Type|Is|Example|
|---|---|---|
|**Point**|one coordinate|a post's location, a driver's position|
|**LineString**|ordered sequence of points|a road, a delivery route, a GPS trace|
|**Polygon**|closed ring enclosing an area|a city boundary, a delivery zone, a geofence|

**(b) Decoding `geography(Point, 4326)`:**

- **`Point`** → this column holds single coordinates.
- **`4326`** → the **SRID**, the coordinate system. 4326 is **WGS84** — ordinary GPS latitude/longitude.
- ⭐ **`geography` vs `geometry`** → **`geography` computes on a sphere** (metres, correct over long distances); **`geometry` treats coordinates as a flat plane** (faster, fine for small areas). ▸ **`geography` is why `5000` means 5 km** rather than 5000 degrees.

**(c) ⭐ Answering the question directly: PostGIS uses an R-tree — not geohash, not quadtree.**

- **GiST** = **Generalized Search Tree.** ⚠ It is **not one algorithm** — it's a _framework_ for balanced trees where you supply four operations (`consistent`, `union`, `penalty`, `picksplit`). **PostGIS plugs in R-tree behaviour.**

**(d) What's actually stored: the MBR — minimum bounding rectangle.** Every geometry is reduced to the smallest axis-aligned box containing it; a wiggly river becomes a box. Internal nodes hold boxes enclosing all their children's boxes.

```
                 ┌── big box enclosing everything ──┐
                 │                                  │
        ┌── box A ──┐                      ┌── box B ──┐
        │           │                      │           │
   [geom][geom]  [geom]                [geom]      [geom][geom]
```

▸ **Query — "everything within 5 km of this point":**

1. Compute the search box around the point.
2. Descend the tree, **pruning any subtree whose box doesn't intersect** the search box. ⭐ **This is where the speedup lives** — whole branches eliminated by one box comparison.
3. Collect candidate geometries.
4. ⚠ **Recheck exactly.** A bounding box is an approximation — a geometry's box can overlap your search area while the geometry itself doesn't. PostGIS computes the true distance on the survivors.

**(e) ⭐ "Lossy index" is the term to know.** The index gives a **superset** of candidates cheaply; the exact predicate filters them. ▸ **Same two-phase shape as GIN's recheck (§3.3b.1) and the bloom filter in `02e §6.2c`** — _cheap approximate filter, then exact verification._

**(f) (⚠ below the interview waterline — knowledge only)** — why R-tree over the alternatives:

||Approach|Why PostGIS doesn't lead with it|
|---|---|---|
|**Geohash**|encode lat/long into a string prefix; nearby points share prefixes|⚠ **Boundary problem** — two points metres apart can fall either side of a grid line and share no prefix. Also handles **points only**, not polygons|
|**Quadtree**|recursively subdivide space into four|Works, but ⚠ **rigid grid**, poor with unevenly distributed data. ▹ Postgres offers it via **SP-GiST**|
|⭐ **R-tree (GiST)**|boxes that **adapt to the actual data**|Handles **any geometry type**, adapts to clustering, no boundary artifacts|

- ▹ PostGIS has a `ST_GeoHash()` function, but it's for **encoding/output — not the index structure.**

**3.3d Combining them**

▸ All three compose in a single query — video posts within 5 km of SF, mentioning "food", tagged `restaurant`:

```sql
SELECT * FROM posts
WHERE search_vector @@ to_tsquery('food')
  AND metadata @> '{"type": "video", "hashtags": ["restaurant"]}'
  AND ST_DWithin(location, ST_MakePoint(-122.4194, 37.7749)::geography, 5000);
```

- ⭐ **Why this matters in a room:** that one query would otherwise require **Elasticsearch + MongoDB + a geo store**, plus the sync machinery between them. **Architectural simplicity is a design argument, not a cop-out.**

### 3.4 Covering indexes

▸ **Problem:** an index lookup normally does **two** things — find the row's location in the index, then **fetch the row from the table** for the other columns.

▸ **Fix:** put the needed columns **in the index itself.**

```sql
-- Common query:
SELECT title, created_at FROM posts
WHERE user_id = 123 ORDER BY created_at DESC;

-- Covering index — satisfies the whole query from the index
CREATE INDEX idx_posts_user_include
ON posts(user_id) INCLUDE (title, created_at);
```

- ▸ **Payoff:** the table is never touched. Significantly faster.
- ⚠ **Cost:** larger index, slightly slower writes.

#### 3.4a ⚠ Confusion resolved — why a covering index is actually faster

> **The doubt (verbatim):** _"covering index is also kind of a clear, you are saying, rather than go to the main table after finding the correct ID and correct location. Here you are indexing the whole thing. So basically it's like a B-tree search you are doing, log of n and then there only the answer also there. You don't need to go to the raw column and try to, raw row and try to find the answer from there. But how fast it is I don't know"_

**(a) ✅ Your reading is right — but the win is not the tree descent**, which is cheap either way.

- **Normal index scan:** traverse the index → get the **`ctid`** (physical row location) → ⚠ **fetch the heap page** for the remaining columns. That heap fetch is often a **random disk read, once per matching row.**
- **Index-only scan (covering):** everything needed is already in the index → **the heap is never touched.**
- ⭐ **Concretely, "50 posts by user 123":** normal = **1 index traversal + 50 random heap fetches**. Covering = **1 traversal + a sequential read of 50 adjacent index entries.** ▸ **That's the difference.**

**(b) (⚠ below the interview waterline — knowledge only)** — ⚠ **"index-only scan" is a slight lie.**

- Postgres's **MVCC** means the index doesn't record whether a row version is visible to _your_ transaction. So it consults the **visibility map** — a compact bitmap marking pages where all rows are visible to everyone.
- If the page is marked all-visible, the heap is skipped. ⚠ **If not, Postgres fetches the heap row anyway** just to check visibility.
- ▸ **Consequence:** covering indexes work best on tables that are **`VACUUM`ed regularly** and **not heavily updated.** On a write-hot table the visibility map goes stale and you **silently lose the benefit.**
- ▸ This is the honest answer to _"how much faster really."_

### 3.5 Partial indexes

▸ **Problem:** you index all rows but only query a subset — e.g. most queries want **active** users, not deleted ones.

```sql
CREATE INDEX idx_users_email ON users(email);            -- ALL users

CREATE INDEX idx_active_users
ON users(email) WHERE status = 'active';                 -- smaller, faster
```

▸ **Best when:** most queries need a subset · many "inactive"/"deleted" rows don't need indexing · you want to cut index size and maintenance overhead.

### 3.6 ⭐ Index types — the consolidated picture

|Index|Structure|Decomposes into|Lossy?|Use|
|---|---|---|---|---|
|**B-tree**|balanced tree of sorted values|**the whole value**|no|equality, ranges, sorting|
|**GIN**|B-tree of terms → **posting lists**|⭐ **many items per row** — stems, or JSONB keys/values|⚠ **yes** — rechecks|full-text, JSONB, arrays|
|**GiST**|balanced tree of **bounding boxes** (R-tree, for PostGIS)|**one MBR** per geometry|⚠ **yes** — rechecks|geospatial, ranges|
|**SP-GiST**|space-partitioned (quadtree, kd-tree)|—|yes|non-balanced / point data|

- ⭐ **The sentence that ties it together:** **B-tree indexes one value per row · GIN indexes many items per row · GiST indexes an approximation of a shape.** ▸ Which one you need follows entirely from **what "matching" means for your data.**
- ⚠ **Calibration:** posting trees, `jsonb_path_ops`, and the visibility map are all **below the waterline.** ▸ **What earns credit is the top line:** _"Postgres full-text search is an inverted index, structurally the same as Elasticsearch's — the difference is relevance scoring, fuzziness, and distribution. PostGIS indexes bounding boxes in an R-tree and rechecks exact geometry. Both are lossy indexes: filter cheaply, then verify."_

### 3.7 ⭐ Practical performance limits (the numbers → `01i`)

> ▸ **Why these matter:** if you quantified latency goals in the NFR phase, you need numbers to check the design against. ⚠ These are **rough** — real figures depend on hardware and workload — but they're enough for an interview.

**Query performance:**

|Operation|Throughput|
|---|---|
|Simple **indexed lookups**|**tens of thousands/sec per core** (often 50k+)|
|Multi-table **joins with indexes**|thousands to tens of thousands/sec|
|Complex **analytical queries** with aggregations|hundreds to low thousands/sec|
|**Full-table scans**|⚠ depends heavily on whether data fits in memory|

- ▸ **Reads vs writes:** simple writes top out around **5,000/sec per core** (§4.2). ▸ **Why reads are faster:** reads need **no WAL entry and no index updates.**

**Scale limits — the rules of thumb for "when do I need to do something":**

- Tables get unwieldy past **~100M rows**
    
- Full-text search works well up to **tens of millions of documents**
    
- Complex joins get challenging with tables **>10M rows**
    
- ⚠ Performance drops sharply once the **working set exceeds RAM**
    
- ⭐ **Memory is king.** Queries served from memory are **orders of magnitude** faster than disk. ▸ **Rule of thumb: keep the working set in RAM.**
    
- ▸ These aren't hard ceilings — Postgres goes much further with tuning. They're the **triggers** for considering partitioning, sharding, or alternatives.
    
- ⚠ **Interview value:** citing these shows you know **when Postgres stops being the answer** — which is exactly the judgment being tested.

## 4 · Write performance

> ▸ Writes matter more than their share of traffic suggests — they're **user-visible latency.** Nobody waits seconds after hitting "Post."

### 4.1 What actually happens on a write

|Step|Where|What|
|---|---|---|
|1 · **Buffer cache + WAL record**|memory|Modify data pages in the shared buffer cache (marked **"dirty"**) **and** generate a WAL record. Both in memory, during the transaction|
|2 · **WAL flush**|⚠ **disk**|At **commit**, WAL records are flushed to disk. **Sequential write** → relatively fast. ▸ Once on disk the transaction is **durable** — a crash can be recovered by replaying the WAL|
|3 · **Background writer**|memory → disk|Dirty pages are written to the real data files **asynchronously** — on a timer, under memory pressure, or at a checkpoint. ▸ Delayed writes let Postgres **batch** changes|
|4 · **Index updates**|memory & disk|Every index must be updated, and ⚠ **index changes go through the WAL too**|

- ⭐ **The one insight to keep:** **commit latency is gated by the WAL flush** — that's the only **synchronous disk** step. Everything else is deferred.
- ⚠ **Therefore: each additional index directly taxes write throughput** (its own WAL entries + memory updates). ▸ This is the mechanical justification for §3.2.
- ▹ ⚠ **This is your stop-point.** Naming WAL-flush-gates-commit is enough. Going further into MVCC, checkpoints, or vacuum is the over-depth failure mode from §2.

#### 4.1a ⚠ Confusion resolved — buffer cache, "dirty", the background writer, and why LSM beats this despite both having a WAL

> **The doubt (verbatim):** _"One is buffer cache. What this buffer cache does, that's not explained. … As you make it dirty so that you will not read from there and you always read from desk operation and all once it is made dirty, right? … if Val is also disc operation, that is also there in the LSM tree. So disc operation is expensive. Right? It is slow. Then how it is happening, it is fast in LSM tree, but it is slow here in in postgres and all. … why you are saying dirty pages are written to the real data files in the background writer asynchronously on time and memory pressure and all. … and then index updation also has happened in the disc and memory. Again, not able to understand why in the memory and why in the disc both."_

**(a) ⚠ WRONG — "dirty" means the opposite of what you assumed.** You had it as _"made dirty so you will not read from there and always read from disk."_

- ✅ **CORRECT: dirty = modified in memory, not yet written to disk.** ▸ A dirty page is **the only place the newest data exists** — disk still holds the **old** version. So you must read **from the buffer cache**; reading disk would return **stale** data.
- ⭐ **What the flag actually means:** _"this page owes a write to disk."_ A **to-do marker** for the background writer — **not** a do-not-read sign.

**(b) What the buffer cache is.** ▸ **CRUX** — a region of RAM holding **8 KB pages** copied from disk: pages of **tables and of indexes**. ⚠ **Everything goes through it — reads and writes both.**

```
READ:   page in cache?  yes → return from RAM          ← fast
                        no  → read from disk into cache, then return

WRITE:  load page into cache if absent
        modify it IN MEMORY
        mark it DIRTY                                  ← "differs from disk"
        done — the client's write never touches the data file
```

- ▸ **This is the mechanism behind "memory is king" (§3.7):** if the working set fits in the buffer cache, most queries never touch a data file.
- ⚠ **And why dirty pages must eventually be written back:** the cache is **finite.** Loading a new page may require **evicting** one — and evicting a dirty page without writing it would **destroy the only copy of that change.**

**(c) ⚠ The mapping you were reaching for: buffer cache is NOT the memtable.** Two of three map cleanly; the third doesn't, and that's the root of the confusion.

|Postgres|Cassandra (`02e §6.2`)|Same job?|
|---|---|---|
|**WAL**|**Commit log**|✅ **Yes — identical.** Sequential append, durability only, discarded once real data is safely on disk|
|**Buffer cache**|⚠ _nothing equivalent_|⚠ **No**|
|⚠ _nothing equivalent_|**Memtable**|⚠ **No**|
|**Heap pages + index pages**|**SSTables**|Both hold real data — ⚠ but **mutable vs immutable**|

- ▸ **The distinction that generates everything else:** the **buffer cache is a cache of existing on-disk pages** — pull a page in, edit it, push it back to **the same place**; the on-disk structure is **modified in place.** The **memtable is a staging area that becomes a brand-new file** — nothing on disk is ever edited (`02e §2.3a`: read old files → write new files → delete old files).
- ▹ To close your recall: the word you were reaching for is **memtable.** The three LSM constructs are **commit log → memtable → SSTable**, then **compaction.**

**(d) Why the background writer exists — three forces.**

|Force|Why dirty pages must reach disk|
|---|---|
|**Eviction**|Cache full, new page needed → a dirty victim must be written first|
|**Checkpoint**|Periodically declares "everything up to here is on disk" → lets Postgres **discard old WAL** and shortens recovery|
|**Crash recovery time**|More outstanding dirty pages = more WAL to replay after a crash|

- ▸ **Why asynchronous and batched:** a page may be modified **fifty times** before it's written. Writing it **once** instead of fifty times is the entire point — deferral lets Postgres **collapse many logical writes into one physical write.**
- ⭐ **The parallel:** the background writer does **compaction's job** (`02e §6.3`) — background I/O reorganizing on-disk state so the foreground write path stays fast. Different mechanism, **same architectural role: push work off the request path.**

**(e) "Index updates [Memory & Disk]" — why both.** ⚠ It isn't two separate things. It's **the same three-part story as table data:**

```
1. index page loaded into the BUFFER CACHE and modified   → MEMORY
2. a WAL record describing the change, flushed at commit  → DISK (durability)
3. the dirty index page written to the index file later   → DISK (background writer)
```

- ▸ Index pages live in the **same buffer cache** as table pages, with the same lifecycle.
- ⚠ **So why does HI single indexes out as costly? Because you have N of them.** One `INSERT` into a table with **3 indexes** touches **4 structures**: 1 heap page + 3 index pages modified · **4 sets of WAL records** at commit · 4 dirty pages to write back.
- ⚠ **And index pages are scattered** — a B-tree insert lands wherever the key **sorts**, unrelated to the heap page's location. So writeback is **random I/O across four locations**, not one.
- ⭐ **This is the mechanical reason behind §3.2 and §4.1** — not vague advice: **4× the WAL volume and 4× the scattered page writes.**

**(f) ⭐ The real question — both use a WAL, so why is LSM faster?**

▸ **The commit path is roughly the same cost.** Both do **one sequential append** at commit. ⚠ **The WAL is not the bottleneck you were imagining** — it's the cheap part in both systems. **The difference is what happens to the data.**

```
POSTGRES — one row insert            CASSANDRA — one row insert
─────────────────────────            ──────────────────────────
heap page    → modify in place       memtable → insert into sorted
index 1 page → modify in place                  in-memory structure
index 2 page → modify in place         ↓ thousands of rows later,
index 3 page → modify in place         ↓ ONE sequential file write
  ↓ all four written back later        ↓ NO separate index structures
  ↓ SCATTERED random I/O                 to maintain (02e §6.0)
```

⭐ **Two structural advantages, neither about the log:**

1. **Write amplification.** Postgres pays **1 + N** structure updates per row (N = indexes). Cassandra pays **one memtable insert** — because **the storage _is_ the index** (`02e §6.0`), there are no separate index structures.
2. **Random vs sequential.** Postgres's writeback is **scattered across the disk**; Cassandra's flush is **one contiguous file** written start to finish, **amortizing thousands of rows into a single sequential write.**

**(g) (⚠ below the interview waterline — knowledge only) ⭐ The honest nuance almost nobody mentions.** Part of the gap isn't structural at all — it's a **durability default**:

- **Postgres** defaults to **`fsync`ing the WAL on every commit.** Genuinely durable; that fsync is real per-transaction latency.
- **Cassandra** defaults to `commitlog_sync: periodic` — flushing roughly **every 10 seconds.** ⚠ Faster, but **a crash can lose the last few seconds of acknowledged writes.**
- ▸ Setting `synchronous_commit = off` in Postgres (§9.3) narrows the gap — and accepts **exactly the risk Cassandra accepts by default.**
- ⭐ **Why it's worth knowing:** it reframes the comparison honestly. Part of Cassandra's write advantage is **architectural** (write amplification, sequential I/O) and part is **a different default position on durability.** Saying that aloud is a genuinely sophisticated observation.

**(h) The one-sentence version for a room:**

> _"Both use a write-ahead log, so the commit path is comparable. The difference is **write amplification** — Postgres updates the heap plus every index in place, with random writeback, while Cassandra appends to a memtable and flushes thousands of rows as one sequential immutable file."_

- ⚠ **Calibration reminder:** buffer cache, dirty pages, and the background writer are exactly the territory §2 warns about over-explaining. **Know it so your answers are correct; don't volunteer it.** ▸ The two interview-visible facts remain: **commit latency is gated by the WAL flush**, and **each index taxes every write.**

### 4.2 ⭐ Throughput limits and what moves them

▸ A well-tuned instance on **good (not great)** hardware:

|Operation|Throughput|
|---|---|
|**Simple inserts**|⭐ **~5,000/sec per core**|
|**Updates with index modifications**|~1,000–2,000/sec per core|
|**Complex transactions** (multiple tables/indexes)|hundreds/sec|
|**Bulk operations**|tens of thousands of rows/sec|

- ▹ Assumes the default isolation level, **Read Committed** (§6.5). Changing it moves these numbers either way.

**What limits them:**

- **Hardware** — usually bottlenecked by **disk I/O for the WAL.**
- **Indexes** — each one reduces write throughput.
- **Replication** — ⚠ **synchronous** replication adds the replica's confirmation to every write (§5.1).
- **Transaction complexity** — more tables/indexes touched = slower.
- ⚠ **Connections** — Postgres **forks an OS process per connection**, so hundreds of connections burn memory and CPU on context switching. ▸ **Fix: a connection pooler (PgBouncer)** multiplexing app connections onto a small database pool. **Especially important with many app instances.**

⭐ **The framing that matters:** these are **single-node** numbers. ▸ _"We need more than 5k writes/sec"_ does **not** mean Postgres is off the table — it means **shard** (§4.3).

### 4.3 The write-scaling ladder (5 rungs, cheapest first)

**Rung 1 · Vertical scaling.** Faster **NVMe** disks (better WAL performance) · more **RAM** (bigger buffer cache) · more **cores**. ▸ **Why climb:** trivially simple, and ⚠ **rarely compelling in an interview** — but it's the honest first answer and there's always a ceiling.

**Rung 2 · Batch processing.** Collect operations and commit them together.

```sql
-- Instead of 1,000 separate inserts:
INSERT INTO likes (post_id, user_id) VALUES
  (1, 101), (1, 102), ..., (1, 1000);
```

- ⚠ **The risk, state it:** writes are buffered **in your server's memory** before commit — **crash mid-batch and you lose the batch.**

▸ **Why climb:** batching only helps where writes can be delayed and grouped. Some writes shouldn't be on the request path at all.

**Rung 3 · Write offloading.** Some writes don't need to be synchronous:

- Send writes to a **message queue (Kafka, `02c`)**
- **Background workers** process them in batches
- Optionally maintain a **separate analytics database**

▸ **Fits:** activity logging · analytics events · metrics aggregation · non-critical updates like "last seen." ▸ Back to §1: **like counts** are exactly this.

▸ **Why climb:** offloading removes _optional_ writes. The **core** writes remain, and the table keeps growing.

**Rung 4 · Table partitioning.** Split one large table into multiple physical tables — most commonly **by time.**

```sql
CREATE TABLE posts (
    id SERIAL,
    user_id INT,
    content TEXT,
    created_at TIMESTAMP
) PARTITION BY RANGE (created_at);

CREATE TABLE posts_2024_01 PARTITION OF posts
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

**Why it helps writes:**

- Different sessions write to **different partitions concurrently** → more concurrency.
- Index updates touch **only the relevant partition**, not the whole table.
- Bulk loading can proceed **partition by partition.**

**And it helps reads:** recent-post queries scan **only recent partitions** — no wading through years of history.

- ▸ **The storage-tiering pattern:** keep recent partitions on **fast storage (NVMe)**, migrate older ones to **cheaper storage.** Users get fast access to recent data, which is what they care about.
- ⭐ **Best fit:** data with a **natural lifecycle** — social posts, logs, events.
- ▹ ⚠ **Recognize the shape:** this is `02e §8.3`'s **time bucketing** in relational clothing. Same problem (a table/partition that grows forever), same fix (**split by time**).

▸ **Why climb:** partitioning splits the table but keeps it on **one machine.** Past a single node's ceiling, you need more machines.

**Rung 5 · Sharding.** ⭐ **The most common answer in an interview.** Distribute writes across multiple Postgres instances.

- ▸ **Be explicit about two things:** ⭐ **what you shard on**, and **how data is distributed.**
- ▸ **Example:** shard `posts` by **`user_id`** → all of a user's data on one shard. ▸ **Why that key:** the common read is "all posts by this user," so it stays on **one shard** and avoids a **scatter-gather** across many.
- ⭐ **The rule:** shard on the column **you query by most often** (`01f`). ▹ Identical logic to `02e §8.2`'s partition key selection.
- ⚠ **The costs:** cross-shard queries · keeping schemas consistent across shards · managing multiple databases. **Only introduce it when simpler rungs don't suffice.**
- ⚠ **The gap worth naming:** unlike DynamoDB (`02f §7.1`, auto-split), **Postgres has no built-in sharding** — you implement it manually, or use a managed layer like **Citus.**

## 5 · Replication

▸ Two distinct purposes, and candidates usually name only the first:

1. **Scaling reads** across replicas.
2. ⭐ **High availability** when a node fails.

### 5.1 Synchronous vs asynchronous

||**Asynchronous** (default)|**Synchronous**|
|---|---|---|
|Behaviour|primary confirms to the client **immediately**, replicates in the background|primary **waits** for ≥1 replica to acknowledge before confirming|
|Write performance|⭐ **best**|⚠ **added latency on every write**|
|Risk|⚠ replicas lag; **primary fails in that window → recent writes lost**|committed data is guaranteed on multiple nodes|

- ▸ **The trade in one line:** **synchronous buys durability and consistency with write latency; asynchronous buys performance with data-loss risk at failover.**
- ⭐ **The hybrid many organizations use:** a **small number of synchronous replicas** for consistency, **plus asynchronous replicas** for read scaling. Postgres lets you designate which are synchronous.

### 5.2 Scaling reads — and the caveat

▸ Read replicas serve reads; all writes go to the **primary.** Effective because most apps are read-heavy. ▸ In §1's terms: feed browsing and profile views hit replicas; creating a post hits the primary. **Read throughput multiplies by N replicas.**

⚠ **The caveat — replication lag.** A user makes a change, immediately reads it back, hits a lagging replica, and **doesn't see their own write.** ▸ This is the **read-your-writes** consistency problem.

- ▸ **The standard fix to name:** route a user's reads to the **primary** for a short window after they write.

### 5.3 High availability and failover

▸ If the primary fails, a replica is **promoted.** The process:

1. **Detect** the primary is down
2. **Promote** a replica to primary
3. **Update** connection information
4. **Repoint** applications to the new primary

- ⭐ **The line HI suggests:** _"We'll use replication not just to distribute read load, but to keep the service available if we lose a database node."_
- ▹ Most teams use **managed Postgres (RDS, Cloud SQL)** which automates failover. ⚠ **Knowing failover is possible and roughly how it works is enough** — manual configuration detail is over-depth.
- ⚠ **The contrast worth holding:** this is Postgres's **election gap** — the seconds of write unavailability that `02e §1.3a(c)` and `02f §6.3` both refer to. **Cassandra has no such gap; DynamoDB has one but hides it.**

## 6 · Data consistency ⭐⭐ (the highest-value section)

> ⚠ **HI names the exact failure:** saying _"we'll use PostgreSQL because it's ACID compliant"_ without being able to explain **how** you'd use those properties to meet the requirement. ▸ **This section is how you avoid that.**

### 6.1 Transactions

▸ A set of operations that **all succeed or all fail.**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

- ▸ Gives **atomicity.** ⚠ **But atomicity alone does not give you consistency under concurrency** — which is where the real questions live.

### 6.2 ⭐ The auction race condition (the worked example that matters)

▸ **Setup:** users bid on items; accept a bid only if it's higher than the current max.

```sql
BEGIN;
SELECT maxBid FROM Auction WHERE id = 123;

-- Application checks: is our bid ($100) higher than current maxBid?
INSERT INTO bids (item_id, user_id, amount) VALUES (123, 456, 100);

UPDATE Auction SET maxBid = 100 WHERE id = 123 AND maxBid < 100;
COMMIT;
```

⚠ **This is inside a transaction and it is still wrong** at the default isolation level (**Read Committed**). Two simultaneous bidders:

```
1. User A's transaction reads maxBid: $90
2. User B's transaction reads maxBid: $90
3. User A inserts a $100 bid, updates maxBid → $100
4. User A commits
5. User B, still seeing $90, inserts a $95 bid
6. User B's UPDATE ... AND maxBid < 100 matches 0 rows (A already set it)
   — but the INSERT already went through
7. User B commits
```

- ⚠ **Result:** a **$95 bid record exists** that should never have been accepted.
- ⭐ **The root cause, in the sentence to memorize:** **the check and the write aren't truly atomic — another transaction slips in between the read and the write.**
- ⭐⭐ **Why this is your most important example:** structurally identical to **double-spend**, **idempotency-key handling**, **inventory oversell**, and **seat booking.** ▸ Any Razorpay/CRED round that asks _"two payment requests arrive simultaneously"_ is asking this exact question. **Know both fixes and when to use each.**

### 6.3 Fix 1 — row-level locking (`FOR UPDATE`)

▸ Lock the row while checking and updating. Other transactions reading those rows **with `FOR UPDATE` must wait** until yours completes.

```sql
BEGIN;
SELECT maxBid FROM Auction WHERE id = 123 FOR UPDATE;   -- lock

INSERT INTO bids (item_id, user_id, amount) VALUES (123, 456, 100);
UPDATE Auction SET maxBid = 100 WHERE id = 123;
COMMIT;
```

- ⭐ **The delivery point HI stresses:** don't stop at _"we'll use transactions."_ Say **_"we'll use transactions and row-level locking on the auction row."_** ▸ **Naming the mechanism is what separates the answers.**

### 6.4 Fix 2 — a higher isolation level

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- same code as before
COMMIT;
```

- ▸ **Serializable prevents all consistency anomalies.**
- ⚠ **The cost:** on conflict, **one transaction is rolled back and must retry.** ▸ **Your application must implement retry logic.** Not free, and easy to forget to mention.

### 6.5 The three isolation levels

|Level|Guarantee|Notes|
|---|---|---|
|**Read Committed** (default)|sees only data committed **before each query began**|⚠ Later queries in the same transaction can see **new commits** → **non-repeatable reads**|
|**Repeatable Read**|a consistent **snapshot as of transaction start**|⭐ **Postgres is stronger than the SQL standard here** — it prevents **phantom reads too**, which other databases allow|
|**Serializable**|transactions behave as if executed **one after another**|Prevents everything. ⚠ **Requires retry logic**|

|Isolation level|Dirty read|Non-repeatable read|Phantom read|Serialization anomaly|
|---|---|---|---|---|
|Read uncommitted|⚠ allowed by standard, **not in PG**|possible|possible|possible|
|Read committed|not possible|possible|possible|possible|
|Repeatable read|not possible|not possible|⚠ allowed by standard, **not in PG**|possible|
|Serializable|not possible|not possible|not possible|not possible|

- ⭐ **The practical consequence:** because Postgres's Repeatable Read blocks phantom reads, ▸ **you may not need Serializable in cases where another database would require it.** That's a precise, non-obvious thing to know.
- ▹ The SQL standard defines **four** levels; Postgres accepts all four but implements **three distinct behaviours** — **Read Uncommitted behaves as Read Committed**, because **MVCC prevents dirty reads at every level.**

### 6.6 ⭐ Locking vs Serializable — which to choose

|Aspect|**Serializable isolation**|**Row-level locking**|
|---|---|---|
|Concurrency|⚠ lower — transactions may **retry** on conflict|higher — conflicts only on the **same rows**|
|Performance|more overhead — tracks all read/write dependencies|less overhead — locks specific rows|
|Use case|**complex transactions** where it's hard to know what to lock|⭐ **when you know exactly which rows** need atomic updates|
|Complexity|simple to write, ⚠ **but needs retry logic**|more explicit in code, **no retries**|
|Error handling|must handle **serialization failures**|must handle **deadlocks**|
|Example|complex financial calculations across multiple tables|⭐ **auction bidding, inventory updates**|
|Memory|higher — tracks entire transaction history|lower — only tracks locks|
|Scalability|doesn't scale as well with concurrency|scales better **when conflicts are rare**|

- ⭐ **The rule:** **row-level locking when you know which rows to lock; Serializable when the transaction is too complex to reason about locks.**

### 6.7 Optimistic concurrency control (OCC)

▸ **A third approach — no locks at all.** Read the data **plus a version number**, do your work, then at commit check whether the version changed. If it did, someone beat you — **retry.**

```sql
SELECT maxBid, version FROM Auction WHERE id = 123;
-- returns maxBid=90, version=5

UPDATE Auction SET maxBid = 100, version = 6
WHERE id = 123 AND version = 5;
-- 0 rows updated → someone else got there first → retry
```

- ⚠ **Postgres has no built-in OCC syntax** — you implement it at the application level with a **version column.**
- ✅ **Good when conflicts are rare** — most transactions succeed with no retry, and you never hold a lock.
- ⚠ **Bad when conflicts are frequent** — many transactions fail and retry, **wasting work.**
- ⭐ **The three-way summary to carry into a room:** **pessimistic locking** (`FOR UPDATE`) when contention is likely and rows are known · **Serializable** when the transaction is too complex to lock precisely · **OCC** when contention is rare and you want no locks held.

## 7 · When to use PostgreSQL (and when not) ⭐

### 7.1 ✅ The default position

⭐ **PostgreSQL should be your default choice unless you have a specific reason to use something else.** It:

- provides **strong ACID guarantees** while still scaling via replication and partitioning
    
- handles **structured and unstructured** data (JSONB)
    
- includes **built-in full-text search and geospatial** (§3.3)
    
- scales **reads** effectively through replication
    
- has excellent **tooling and a mature ecosystem**
    
- ⭐ **The strategic framing:** _"Start with PostgreSQL, then justify deviating."_ ▸ **Much stronger than starting with a niche solution and defending it against Postgres.**
    

**Shines when you need:** complex relationships · strong consistency · rich querying · a mix of structured and unstructured data · built-in full-text search · geospatial.

**Textbook fits:** e-commerce (inventory, orders, users) · ⭐ **financial systems (transactions, accounts, audit logs)** · content management · analytics up to reasonable scale.

### 7.2 ⚠ The three legitimate reasons to leave

**1 · Extreme write throughput.** Millions of writes/sec. ▸ **Why it struggles:** every write needs a **WAL entry and index updates** → I/O bottleneck even on the fastest storage. Sharding helps but adds coordination complexity and latency. ▸ **Alternatives:** **Cassandra** (`02e`) for event streaming · **Redis** (`02a`) for real-time counters.

**2 · Global multi-region, active-active.** ▸ **Why it struggles:** ⭐ **single-primary architecture.** One region must be the writer; others are read replicas. True active-active creates consistency and conflict-resolution problems Postgres was never designed for, and cross-region **synchronous** replication adds substantial latency. ▸ **Alternatives:** **CockroachDB** (global ACID) · **Cassandra** (eventual consistency at global scale, `02e §3.2`) · **DynamoDB Global Tables** (`02f §7.2`).

**3 · Simple key-value access.** ▸ **Why it struggles:** if you're only storing and fetching by key, **MVCC, WAL, and the query planner are overhead you're paying for nothing.** ▸ **Alternatives:** **Redis** (in-memory) · **DynamoDB** (managed scale) · **Cassandra** (write-heavy).

⚠ **The warning to internalize — HI states it flatly:**

> **Scalability alone is NOT a good reason to choose an alternative to PostgreSQL.** Postgres handles significant scale with proper design.

- ⭐ **So "it won't scale" is not an argument.** The argument must be **a specific number** (millions of writes/sec) or **a specific shape** (active-active multi-region, pure key-value).

## 8 · ⭐ The three-way decision — Postgres vs Cassandra vs DynamoDB

> ▸ Closes the loop across `02e`, `02f`, and this file. ⚠ **This table is the most useful artifact in Series 02 for a data-layer question.**

||**PostgreSQL** (`02g`)|**Cassandra** (`02e`)|**DynamoDB** (`02f`)|
|---|---|---|---|
|Default posture|⭐ **the default; deviate with a reason**|availability + write throughput|managed convenience|
|Consistency|⭐ **full ACID**, 3 isolation levels, row locks|⚠ **none** beyond single-row-in-partition|**serializable, ≤100 items**, per-request read consistency|
|Query flexibility|⭐ **joins, ad-hoc, aggregation, full-text, geo**|⚠ partition key or a second table|GSI/LSI, no joins|
|Write ceiling (single node)|**~5k/sec per core**|very high (LSM appends)|high, **auto-splits**|
|Scaling writes|⚠ **manual sharding** (or Citus)|⭐ add nodes, linear|⭐ automatic|
|Multi-region active-active|⚠ **cannot** — single primary|⭐ native|**Global Tables**|
|Failover|⚠ **election gap** (§5.3)|⭐ **none** — masterless|leader election, **hidden by AWS**|
|Ops burden|moderate (or managed RDS)|⚠ **high**|⭐ **near zero**|
|Cost at extreme write volume|machines|⭐ **machines — cheapest**|⚠ **capacity units — brutal**|
|Schema|relational **+ JSONB**|sparse but **declared**|**schemaless**|

▸ **The decision sequence to run in an interview:**

1. **Start at Postgres.** Complex relationships, transactions, or ad-hoc queries → **stop here.**
2. **Millions of writes/sec, or active-active multi-region?** → Cassandra or DynamoDB.
3. **Between those two:** ⭐ **the choice is economic** (`02f §11`) — DynamoDB for ops simplicity and transactions; Cassandra when capacity-unit cost or AWS lock-in rules it out.

⭐ **The fintech shape that uses all three, and is worth being able to draw:**

- **Ledger / balances / payment state** → **Postgres** (ACID, row locking §6.3)
- **Transaction event log / audit trail / webhook attempts** → **Cassandra** (append-heavy, `((merchant_id, day_bucket), event_id)`)
- **Idempotency keys / session state** → **DynamoDB or Redis** (key-value, single-digit ms)

## 9 · Appendix: SQL & ACID (⚠ skim — you know this)

> ⚠ **Compressed deliberately.** Only the two genuinely non-obvious points are expanded.

### 9.1 Relational basics — recall only

▸ **Tables** (relations) with typed **columns** and **rows** · **PRIMARY KEY** for uniqueness · **UNIQUE** constraints · **foreign keys** (`REFERENCES users(id)`) enforcing **referential integrity**.

▸ **Three relationship types:** **one-to-one** (user ↔ profile settings) · **one-to-many** (user → posts) · **many-to-many** (users ↔ liked posts, via a **join table** with a composite primary key).

▸ **Normalization** avoids duplicated data, maintains integrity, keeps the model flexible. ▸ ⚠ **Deliberate denormalization** (storing a post's like count on the post row) is a **performance trade worth discussing aloud** — the same move as `02e §8.4`.

### 9.2 ⚠ Non-obvious point 1 — ACID "consistency" ≠ CAP "consistency"

||Meaning|
|---|---|
|**ACID** consistency|the database always satisfies its **defined rules and constraints** — foreign keys, `UNIQUE`, `CHECK`|
|**CAP** consistency (`01h`)|a read always returns **the correct/latest result**, even at the cost of availability|

- ⚠ **These are different words that happen to be spelled the same.** Conflating them in an interview is a visible error.
- ▸ Example of the ACID sense: `balance DECIMAL CHECK (balance >= 0)` — a transaction that would go negative is **rejected entirely.** ⭐ In a NoSQL store you'd enforce that in **application code**.

### 9.3 ⚠ Non-obvious point 2 — durability is tunable

▸ **Durability** comes from WAL: changes written to the log → log **flushed to disk** → only **then** is the transaction committed (§4.1).

- ⚠ **But it's a dial, not a law.** `synchronous_commit = off` trades durability for speed: writes not yet flushed can be **lost on crash or power failure.**
- ▸ Worth knowing because it's a legitimate optimization for **non-critical** tables — and an obviously wrong one for a **ledger.**

### 9.4 ACID by requirement (the mapping to actually use)

|Data|Needs ACID?|
|---|---|
|**Financial transactions**|⭐ **absolutely** — prevents lost or double-spent money|
|**User authentication**|**yes** — inconsistency becomes a security issue|
|**Social media likes**|⚠ **no** — eventual consistency is fine|
|**Analytics data**|⚠ **no** — prioritize performance|

### 9.5 SQL command families — recall only

▸ **DDL — Data Definition Language** (`CREATE` / `ALTER` / `DROP TABLE`) — defines and modifies **structure**. ▸ **DML — Data Manipulation Language** (`SELECT` / `INSERT` / `UPDATE` / `DELETE`) — works with the **data inside** tables. ▸ **DCL — Data Control Language** (`GRANT` / `REVOKE`) — controls **access permissions**. ▸ **TCL — Transaction Control Language** (`BEGIN` / `COMMIT` / `ROLLBACK`) — manages **transactions**.

- ▹ ⚠ You will rarely write SQL in a system design interview. Expect **"how would you query this efficiently?"** and **"what indexes would you create?"** — concept questions, not syntax.

### 9.6 MVCC — Multi-Version Concurrency Control
When an **UPDATE** happens, PostgreSQL creates a new version of the row. Readers continue to read the older version until the update is committed. When a **DELETE** happens, PostgreSQL simply marks the existing row as deleted, but readers can still see it until that deletion is committed. 

▸ **CRUX** — Postgres never overwrites a row in place. An `UPDATE` writes a **new version** of the row and marks the old one as expired; each version carries the transaction IDs that created and deleted it. Every transaction sees **the version that was current when its snapshot was taken.**

- ⭐ **What it buys — the line to remember:** **readers never block writers, and writers never block readers.** A long-running `SELECT` reads an older version while an `UPDATE` proceeds on the same row; neither waits. ▸ This is why Postgres handles mixed read/write workloads well without heavy locking.
- ▸ **Why isolation levels fall out of it (§6.5):** an isolation level is essentially **when your snapshot is taken.** **Read Committed** = a fresh snapshot **per statement**. **Repeatable Read** = one snapshot at **transaction start**. ▸ And ⚠ **dirty reads are impossible at any level** — an uncommitted version is simply never visible — which is why **Read Uncommitted behaves as Read Committed** in Postgres.
- ⚠ **The cost:** old row versions accumulate as dead tuples and must be reclaimed by **`VACUUM`**. ▸ Neglected vacuuming causes **table bloat** and degrades performance. ▹ It's also why covering indexes depend on the **visibility map** (§3.4a(b)).
- ▹ ⚠ **Calibration: this is the exact topic §2 warns about over-explaining.** Know it so your answers are correct; **don't volunteer it.** One sentence — _"MVCC means readers don't block writers"_ — is a complete interview answer.
