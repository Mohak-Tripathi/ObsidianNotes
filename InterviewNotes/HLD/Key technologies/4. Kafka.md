## 1 · Motivating example (World Cup) — the intuition ladder

> ▸ Four scaling problems, each solved by one Kafka concept. This ladder _is_ the mental model — learn it and the terminology defines itself.

Setup: a live-stats website. Each goal/booking/substitution is an **event.** A **producer** puts events on a queue; a **consumer** reads them off and updates the site.

▸ **The four problems → the four concepts:**

- **P1 — one queue can't take the volume** (1,000 simultaneous games). _Fix:_ split the queue across servers.
- ⚠ **But random splitting destroys order** — goals appear before kickoff, bookings before the foul.
    - ▸ **P1 Fix → PARTITION by key.** Distribute events by **game ID** → all events for one game land on the **same partition** → processed in order. ⭐ _This is the single most important idea in Kafka: order is guaranteed only within a partition, and the key decides the partition._
- **P2 — one consumer can't keep up.** Add more. ⚠ But now how do we avoid processing each event twice?
    - ▸ **P2 Fix → CONSUMER GROUP.** Group consumers; each partition is assigned to **exactly one consumer** in the group → each event goes to a single consumer (no duplication under normal operation).
- **P3 — we added basketball; soccer consumers shouldn't see basketball events.**
    - ▸ **P3 Fix → TOPICS.** Each event belongs to a **topic**; consumers **subscribe** to the topics they care about. Soccer consumers subscribe to `soccer`, basketball to `basketball`.

▸ **The one-line takeaway:** _partition for ordered parallelism · consumer group for exactly-one-consumer delivery · topic for logical separation._

## 2 · Core terminology & architecture

### 2.1 The pieces

▸ **CRUX:**

- **Broker** — an individual server (physical/virtual) that stores data + serves clients. A **cluster** = many brokers. More brokers → more storage + more throughput.
    - ▹ "Physical or virtual" = bare-metal box or a **VM (e.g. an EC2 instance)** — Kafka doesn't care; a broker is a broker. ⚠ VMs often use network-attached disks (EBS), which matters only for I/O tuning, not the model.
- **Partition** — an **ordered, immutable, append-only** sequence of messages (think: a log file). ⭐ **Partitions are how Kafka scales** — they allow parallel consumption.
- **Topic** — a **logical grouping of partitions.** You publish/subscribe at the topic level. Always **multi-producer** (0, 1, or many producers write to it).
- **Producer** — writes messages to topics. **Consumer** — reads messages from topics.
- ▹ Kafka doesn't care what the data _is_ — it stores and serves bytes. Formatting/processing the message is **your** job as the developer.

### 2.2 Topic vs Partition — the distinction to state cleanly

||**Topic**|**Partition**|
|---|---|---|
|Nature|**logical** grouping|**physical** grouping|
|Purpose|**organize** data (publish/subscribe unit)|**scale** data (parallelism unit)|
|Relationship|one topic → many partitions|each partition lives on **one broker** (and can be on a different broker per partition)|

- ▸ **One-liner:** _topic = how you organize; partition = how you scale._

#### 2.2a ⚠ Confusion resolved — the architecture (broker/topic/partition/consumer group), on two axes

> **My doubt:** "There's a producer, consumer, producer group, consumer group. There's a server with a queue; to extend we add more servers and more queues per server. Now topic comes in, partition comes in, and I'm completely lost. There's a broker too, a partition too, a topic too, and a consumer group is assigned to one partition — I'm gone. I can't understand the architecture at all."

⚠ **Two wrong pieces to delete first:**

- **There is NO "producer group."** Consumers group; producers don't. Producers fire at topics independently. Only **consumer group** exists.
- **The consumer↔partition direction is backwards.** Not "a group is assigned to a partition" → it's **each partition is assigned to ONE consumer inside a group.** One partition → one consumer (not the reverse). This flip causes most of the pain.

▸ **The missing idea — STOP nesting these. They live on two perpendicular axes, meeting only at the partition:**

- **Physical axis (hardware):** `cluster → brokers → partitions`. A **broker = a server (machine)**; a **partition = an actual append-only log file on that machine's disk.** _(This is your "server has queues" intuition — and it's correct.)_
- **Logical axis (naming):** `topic → partitions`. A **topic = just a label** grouping a set of partitions. No hardware; it "contains" nothing physical.
- **Where they meet — the PARTITION:** every partition belongs to **exactly one topic** (logical) _and_ physically sits on **exactly one broker** (physical). The partition is the single crossing point. Topic and broker never nest inside each other.

▸ **Concrete (Meesho).** Topics `orders` (3 partitions) + `payments` (2 partitions). Cluster = 2 brokers. Kafka spreads partitions across them:

```
        BROKER 1  (a server)          BROKER 2  (a server)
        ┌──────────────────────┐      ┌──────────────────────┐
        │  orders-P0   [log]   │      │  orders-P1   [log]   │
        │  orders-P2   [log]   │      │  payments-P0 [log]   │
        │  payments-P1 [log]   │      │                      │
        └──────────────────────┘      └──────────────────────┘
```

- **A broker holds partitions from _multiple topics_** (Broker 1 has orders _and_ payments). A server doesn't "belong" to a topic — it hosts whatever log files Kafka placed there. ← your "one server, multiple queues," and the queues can be from different topics.
- **A topic is _smeared across brokers_** (`orders` = P0/P2 on Broker 1, P1 on Broker 2). A topic isn't "on a server" — it's scattered as partitions. ← the part nesting couldn't allow.
- A partition (`orders-P1`) has one topic (orders) + one home (Broker 2) → one clean point.

▸ **One message, producer side** (`order_id="A99"` → topic `orders`):

1. Which of 3 partitions? `hash("A99") % 3` → say `1` → `orders-P1`.
2. Which broker hosts `orders-P1`? Metadata says **Broker 2**.
3. Producer sends **straight to Broker 2**, appended to end of the `orders-P1` log. Every future `"A99"` event hashes to the same partition → same log → **stays ordered.** _(This is why key = ordering.)_

▸ **Consumer side** (the flipped part). Group `order-service` with 3 consumers:

```
consumer group "order-service":
   C1 ← orders-P0     C2 ← orders-P1     C3 ← orders-P2
```

- Each **partition → exactly one consumer** in the group → no double-processing + 3 work in **parallel.**
- ⚠ **4 consumers but 3 partitions → the 4th sits IDLE** (a partition can't split across two consumers in a group). So **useful consumers ≤ partitions** → partition count caps parallelism.
- **C2 dies → rebalance:** `orders-P1` reassigned to C1 or C3. Nothing dropped.

▸ **The stream / pub-sub twist** — a _second_ group `analytics` subscribes to the same `orders`:

```
group "order-service":  reads ALL of orders   (its own progress)
group "analytics":      reads ALL of orders   (its own separate progress)
```

- Different groups each get the **full stream independently** — same data, read twice, no interference. **One group = queue behaviour; many groups on one topic = stream/pub-sub behaviour.** _(→ §2.3, §4.)_

▸ **Your words → Kafka words:**

|Your word|Kafka word|What it actually is|
|---|---|---|
|server|**broker**|a machine|
|queue inside a server|**partition**|one append-only log file on that machine|
|— (missing)|**topic**|a _label_ grouping partitions scattered across servers|
|producer group|❌ doesn't exist|producers don't group|
|"group assigned to a partition"|**partition assigned to a consumer**|one partition → one consumer _within_ a group|

▸ **The one paragraph to hold:** _A **topic** is a name. Under it sit several **partitions**, each a log file. Those partitions are **scattered across brokers** (servers) so load spreads — and any one broker holds a mix of partitions from many topics. A **producer** hashes its message key to pick a partition, then sends straight to that partition's broker. A **consumer group** divides the topic's partitions among its consumers — one partition per consumer — so they process in parallel without overlap; add a second group and it gets its own full copy of the stream._

### 2.3 One platform, two modes: queue vs stream

▸ **CRUX** — same Kafka, two consumption patterns. Both track progress via **offset commits**; the difference is what happens to the data:

- **Message queue** — each message processed by **one consumer in a group**, then effectively "consumed."
- **Stream** — the log is **retained + replayable**; **multiple consumer groups** independently read the same data; consumers process continuously as data arrives.
- ▹ The distinction is "frankly minor" mechanically — it's a **usage pattern**, not two different systems. _(Redis streams/pub-sub comparison → `02a §6/§7`.)_

## 3 · How Kafka works

### 3.1 The message (record)

▸ Four fields, all technically optional: **value** (the payload) · **key** (decides the partition) · **timestamp** · **headers** (key-value metadata, like HTTP headers).

- ⚠ **Ordering within a partition is by OFFSET, not timestamp.** The timestamp only records creation/ingest time.

### 3.2 Partitioning — the heart of it ⭐

▸ **CRUX** — publishing is a two-step routing:

- **① Partition determination** — hash the **key** → assign to a partition. Same key → same partition → **order preserved per key.** No key → default partitioner spreads messages (modern clients use a **sticky** strategy: batch to one partition, then rotate).
- **② Broker assignment** — cluster metadata (maintained by the **controller**) maps partition → broker; producer sends **directly** to the broker hosting that partition.
- ▸ **The formula (memorize):** `partition = hash(key) % num_partitions` (default hash = **murmur2**).

Producer with keys (kafkajs):

```
const kafka = new Kafka({ clientId: 'my-app', brokers: ['localhost:9092'] })
const producer = kafka.producer()

await producer.connect()
await producer.send({
  topic: 'my_topic',
  messages: [
    { key: 'key1', value: 'Hello, Kafka with key!' },
    { key: 'key2', value: 'Another message with a different key' }
  ],
})
```

- ⭐ **Interview move:** in any large distributed design, **use keys deliberately** so related messages land on the same partition and stay ordered. **Choosing the key is the highest-leverage decision** (revisited in §5 and §8).

### 3.3 Partition = append-only log ("distributed commit log")

▸ Each partition is an **append-only log file** — messages appended at the end, never edited in place. Three benefits:

- **Immutability** — written messages aren't modified; they leave only via **retention** or **log compaction.** ▸ Simplifies replication, speeds recovery, avoids consistency bugs. _(Same immutability trade as LSM / `01d`.)_
- **Efficiency** — append-only means **minimal disk seeks** (the classic storage bottleneck).
- **Scalability** — simple append log → easy horizontal scaling (add partitions across brokers; replicate each for fault tolerance).

### 3.4 Offsets — how consumers track progress

▸ Each message gets a unique **offset** (sequential position in the partition). Consumers **commit** their offset back to Kafka after processing → on restart, resume from last committed offset.

- ⚠ **Default = at-least-once delivery.** Crash _after_ processing but _before_ committing → message is **reprocessed** on restart. ▸ **Exactly-once is possible but costs extra config** (idempotent producers + transactional APIs).
- ▸ **What "committed" means, precisely:** the consumer has finished processing up through offset N, and is now **telling Kafka** (writing to Kafka's internal `__consumer_offsets` topic, via the **group coordinator** — ⚠ NOT "the controller," a different, unrelated role) "resume from N+1 next time." ⚠ **The gap between processing and committing is where at-least-once reprocessing comes from:** crash after processing but before commit → restart resumes from the _old_ offset → **reprocesses the same message.**
- ⚠ **Consequence you must handle yourself:** at-least-once guarantees the message _reaches_ your consumer again — it says nothing about your handler's **side effect** happening only once. Reprocessing a "send email" or "charge card" message **redoes the side effect** unless you make it **idempotent** (e.g. check a dedup/idempotency key before acting). ⭐ Charging a card twice is exactly the fintech-relevant failure mode this protects against.

Consumer with a group (kafkajs):

```
const kafka = new Kafka({ clientId: 'my-app', brokers: ['localhost:9092'] })
const consumer = kafka.consumer({ groupId: 'my-group' })

await consumer.connect()
await consumer.subscribe({ topic: 'my_topic' })
await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    console.log({ value: message.value?.toString(), key: message.key?.toString() })
  },
})
```

### 3.5 Replication — leader/follower (▹ senior depth, know the shape)

▸ Each partition has a **leader replica** (handles writes, and by default reads) + several **follower replicas** on other brokers that passively copy the leader.

- **Followers sync continuously** with the leader → if the leader fails, a **fully-synced follower is promoted** → minimal downtime/loss.
- ▹ The **controller** manages this: monitors broker health, reassigns leadership on failure. _(Kafka 2.4+ allows follower reads for latency; staff+ trivia.)_

#### 3.5a ⚠ Confusion resolved — leaders, followers & replica placement (reading the cluster diagram)

> **My doubt:** "10 partitions for Topic A with replication of 2 followers → 30 total, where 10 are leaders and 20 are followers, 2 followers per leader on any server — correct? And with 3 partitions but only 2 brokers, one broker has one leader and the other has two leaders, as long as followers sit on the other broker — right? But the leader/follower diagram confuses me."

▸ **The arithmetic is right, with one word fixed:** 10 partitions at **RF 3** (RF counts _total_ copies → 1 leader + 2 followers) = **10 leaders + 20 followers = 30 replicas of 10 partitions** (not "30 partitions" — a partition is logical; it exists as 3 physical _replicas_). Reads/writes hit the **leader**; followers passively copy, ready for promotion.

▸ **The ONLY placement rule:** _no two replicas of the **same** partition on the same broker_ (else one machine dying loses both copies). That's it. Everything else your instinct feared is allowed:

- ⚠ **"One broker can't have two leaders" is FALSE** — a broker holds **many leaders**, as long as they're leaders of _different_ partitions. (In the diagram, Broker 2 holds Topic C's P2-leader _and_ P3-leader — perfectly legal.)
- **Partition count can exceed broker count** freely (3 partitions on 2 brokers: one broker gets 1 leader, the other 2 — fine, since followers go on the opposite broker).
- ⚠ **The real floor is `RF ≤ number of brokers`** — RF 3 needs ≥ 3 brokers (nowhere to put a 3rd distinct copy on 2). Partition count has no such floor.

▸ **Reading any Kafka cluster diagram:** each broker shows a _mixed bag_ of replicas from many topics in no clean order — so **group mentally by (topic, partition)**, find its 2–3 rows, and you'll see one leader + its followers, each on a different broker. Leaders are also spread across brokers on purpose (the controller balancing write load, §3.5).

### 3.6 Pull-based consumers

▸ Consumers **poll** the broker for new messages at their own pace (Kafka does **not** push).

- ▸ **Why pull is deliberate:** consumers control their consumption rate, slow consumers aren't overwhelmed, failure handling is simpler, and batching is efficient.

## 4 · When to use Kafka ⭐

> ⭐ **This section is pure interview payoff — the "should I reach for Kafka, and as queue or stream?" decision.**

### 4.1 As a message QUEUE — reach for it when:

- **Async processing** — do work later, off the request path. _(YouTube: serve SD video immediately, drop a Kafka message to transcode when the system has capacity.)_
- **Ordered processing** — events must be handled in arrival order. _(Ticketmaster virtual waiting queue: admit users in the order they arrived.)_
- **Producer/consumer decoupling** — so they scale independently and one service can't take down another (producer outpaces consumer). ⭐ Classic microservices pattern.

### 4.2 As a STREAM — reach for it when:

- **Continuous real-time processing** — treat data as a live flow. _(Ad Click Aggregator: aggregate clicks in real time.)_
- **Multiple independent consumers** of the same data. _(FB Live Comments: Kafka as pub/sub fanning comments to many consumers.)_

▸ **Decision one-liner:** _one consumer, process-and-done → queue · many consumers / replay / continuous → stream._

## 5 · Scalability ⭐ (still core for you, despite being "below the line")

### 5.1 Single-broker limits — decide if scaling is even needed

▸ **CRUX** — estimate throughput/volume _first_; you may not need to scale at all.

- **~1 TB storage** and **up to ~1M messages/sec** per broker on good hardware (hand-wavy, depends on message size/hardware). _(Capacity estimation → `01i`.)_
- **Message size:** no hard limit (`message.max.bytes`), but keep **< 1 MB** for performance.

### 5.2 ⚠ Anti-pattern — don't store big blobs in Kafka

▸ Kafka is **not a database / file store.** ⚠ Putting large files (e.g. raw videos) in Kafka is a classic interview mistake.

- ▸ **Fix:** store the blob in **S3 / distributed file store**, put a **small Kafka message pointing to the S3 location.** The message is a pointer, not the payload. _(Large-blob handling pattern → `03f`.)_

### 5.3 Scaling strategies

- **More brokers (horizontal)** — distributes load + adds fault tolerance. ⚠ **Only helps if topics have enough partitions** — under-partitioned topics can't use new brokers (parallelism is capped by partition count).
- **Partitioning strategy ⭐ — the main scaling decision in an interview.** You control distribution by choosing the **message key**: `partition = hash(key) % num_partitions`. ⚠ **A bad key → hot partitions.** Good keys spread evenly across the partition space.
- ▹ Managed services (**Confluent Cloud**, **AWS MSK**) automate much of this — but know the concepts. You usually scale **per topic** (different topics have different throughput needs), by **adding partitions.**

### 5.4 Hot partitions ⭐ ("interviewers love to ask this")

⚠ **Problem:** partition by `ad_id`; Nike drops a LeBron ad → that partition is flooded → **hot partition.** ▸ **Four fixes (Problem→Fix):**

- **No key (default partitioning)** — let Kafka spread messages evenly. ⚠ **Cost:** you lose per-key ordering. Fine _only if ordering doesn't matter._
- **Random salting** — append a random number/timestamp to the key → spreads load. ⚠ **Cost:** complicates consumer-side aggregation (related messages now scattered).
- **Compound key** — combine `ad_id` + another independently-varying attribute (region, user segment) → more even spread while keeping _some_ grouping.
- **Back pressure** — slow the producer down (check partition lag, throttle). Managed services may do this for you.

#### 5.4a ⚠ Confusion resolved — adding a partition, offsets, "filled" partitions, and indefinite storage

> **My doubt:** "Scaling is horizontal — add more partitions across servers. Say 10 partitions over 3 servers and you add one more. Do we reshuffle? If not, the key modulo changes and creates a ruckus. Also, a partition that's completely filled — you don't want to route there, so if you add more, routing changes, right? And is offset per-partition or not? And finally: do you just over-provision a bit and rely on retention clearing old logs — or does Kafka get used as indefinite storage?"

▸ **Offset is strictly PER-PARTITION.** Each partition has its own counter (P0: 0,1,2…; P1: its own 0,1,2…). A message = **(topic, partition, offset)**; consumers commit progress per partition (`__consumer_offsets`). **No global cross-partition offset** — which is _why_ ordering is guaranteed only within a partition.

▸ **Adding a partition — Kafka does NOT reshuffle existing data, and that's the whole problem:**

- Old messages in P0–P9 **stay put** — nothing moves. But `partition = hash(key) % num_partitions` now uses a **new divisor** (10 → 11).
- So a key's **old** messages sit on its old partition (`% 10`) while its **new** messages land elsewhere (`% 11`) → the key's stream **splits across two partitions → per-key ordering breaks from the resize point on.**
- ⚠ The danger isn't "past data gets scrambled" (it doesn't) — it's **future ordering breaks** because history is stranded on the old partition.
- ▸ **Why Kafka allows this:** default partitioner uses **plain `% num_partitions`, not consistent hashing.** This is the textbook case consistent hashing (`01g`) was invented to avoid (plain modulo remaps most keys on resize). ⭐ Great thing to name in an interview.

▸ **⚠ "Filled partition → reroute" is a MISCONCEPTION — two corrections:**

- A partition is an **append-only log**; it does **not "fill up"** like a bounded queue. It grows on disk, bounded only by **retention** (front trims) or **broker disk** (an ops problem → add brokers).
- Routing is **blind hash** — `hash(key) % n` **ignores** how big/busy/full a partition is. Kafka never load-reroutes (that would break the deterministic key→partition guarantee). ▸ This blind routing **is the root of hot partitions** (§5.4) — fixed by salting / compound key / no-key / backpressure, **not** by rerouting the busy one.

▸ **"Add a partition" ≠ "add a broker" — two different operations:**

|Operation|What happens|Existing data|
|---|---|---|
|**Add a partition** (to a topic)|new **empty** partition; `% num_partitions` changes → breaks key ordering|old partitions untouched, not moved|
|**Add a broker** (a server)|new empty machine joins|existing partitions **do NOT auto-move**; you run **partition reassignment** to migrate some onto it|

- ▸ Adding a _server_ rebalances nothing by itself — you explicitly reassign (ties back to §5.3: "more brokers only helps if enough partitions").

▸ **⚠ Two independent problems — don't fuse them (over-provision ≠ retention):**

- **Ordering problem** (adding partitions) → fixed by **over-provisioning partition count** at creation. Nothing to do with retention. ⚠ Kafka **can't decrease** partitions (must recreate the topic), so pick generously up front and rarely resize.
- **Disk-growth problem** (log grows forever) → fixed by **retention.** Nothing to do with the modulo or ordering.

▸ **⚠ The tempting-but-wrong synthesis (why over-provision ≠ retention):** _"short retention keeps partitions from filling, so I won't need to add partitions, so no reordering."_ The flaw: **you add partitions for THROUGHPUT (parallelism), not because they fill** — partitions don't fill (append-only, no cap). Retention bounds **disk**; it does nothing for throughput, so it can't reduce your need for partitions.

- **Over-provision (a bit)** → the actual ordering safeguard. ⚠ "a bit" because over-provisioning costs: more file handles, replication traffic, slower leader elections, higher latency.
- **Retention** → separate disk hygiene. Both good; **different jobs.**

▸ **Is Kafka indefinite storage? A deliberate knob, not a fixed rule:**

- **Default** — 7 days; old messages age out (log stabilizes if intake fits the disk budget). Clearing is the _default_, not a Kafka-imposed _must_.
- **`retention.ms = -1`** → keep **forever** (event-sourcing / log-as-source-of-truth). ⚠ Cost: unbounded disk.
- **Log compaction** → keep **latest message per key**, discard older same-key messages → grows with **distinct keys**, not total events ("infinite current-state retention," e.g. latest balance per account).
- ⚠ Still never store **large blobs** long-term (§5.2 S3-pointer). Small messages long-term = a legitimate configured choice.

#### 5.4b ⚠ Confusion resolved — choosing topic vs partition count vs key (and what scaling breaks)

> **My doubt:** "Tournaments with matches — we want ordering per match, not across matches. What's the partition key and why? Do we give one partition per match, keyed by match ID? And what's the topic then? And if we horizontally scale, ordering gets disturbed — how does that impact?"

⚠ **First, the misconception: do NOT create one partition per match.** You have (say) 10 partitions and **50 matches hash into them** — ~5 matches share each partition. Their events **interleave** in the log, and that is fine, because you never wanted cross-match ordering:

```
Partition 3 log:  [M17-goal] [M42-card] [M17-sub] [M42-goal] [M17-goal] ...
                       ↑ M17 in order              ↑ M42 in order  (interleaved, each key intact)
```

- ▸ **Ordering is preserved PER KEY, not per partition.** One partition carries thousands of keys, each internally ordered; the **consumer demultiplexes by key** (match ID) and applies each match's events in sequence.
- ⚠ One-partition-per-match would mean 50 partitions today, 200 tomorrow → constant resizing → the §5.4a modulo problem _every day._
- ▹ Precision: a partition is totally ordered **by offset = append order at the leader**, not wall-clock timestamps (§3.1).

▸ **Three separate decisions, three separate drivers — keep them apart:**

|Decision|Driven by|This scenario|
|---|---|---|
|**Topic**|_who subscribes independently_|`football-events`, `volleyball-events` (per **sport**)|
|**Partition count**|_how much consumer parallelism you need_|~10 (per-topic call: hot sport gets more, quiet sport fewer)|
|**Key**|_what must stay ordered_|`match_id`|

- ▸ **The universal key rule:** _the key is the entity whose ordering you need._ Per-match ordering → key on match → same match = same hash = same partition = same log = ordered.
- ▸ **Topic = a STABLE category; key = the EPHEMERAL entity.** Sports are few and permanent (good topic). Matches are thousands and temporary (good key, terrible topic — you'd be creating/deleting topics constantly).
- ▸ **Partition count is a per-topic decision** (§5.3) — you scale _topics_, not the cluster. Basketball busy → 5 partitions; cricket quiet → 2.

▸ **What scaling actually breaks (concretely).** Match `M123` in flight, 10 partitions:

- Events 1–40 → `hash("M123") % 10` = **P3**.
- Add a partition → 11. Event 41+ → `hash("M123") % 11` = **P7**.
- → M123 now **split across P3 and P7**, read by two uncoordinated consumers → the 89th-minute goal can be processed before the 12th-minute one → **the score goes backwards on your site.**

▸ **But the damage window is BOUNDED — only keys in flight at the moment of resize:**

- Matches **finished before** the resize → all `% 10` ✅ · matches **starting after** → all `% 11` ✅ · only **in-flight** matches straddle.
- **Fix 1 — over-provision at creation** (§5.4a): pick 20–30 partitions up front, never resize. Cheapest by far.
- **Fix 2 — resize at a natural quiet boundary:** between match days / off-season, when **no key is in flight** → zero breakage.
- **Fix 3 — drain deliberately:** pause producers, let consumers reach the end of the log, resize, resume.
- ▹ **Advanced (name it if pushed):** write a **custom partitioner** (stable mapping or consistent hashing, `01g`) instead of default modulo, so adding partitions doesn't remap existing keys.

▸ ⚠ **Sanity check that dissolves the whole worry:** 50 matches × ~10 events/sec = **500 events/sec**. A broker handles ~**1M/sec**. You are nowhere near a limit → you'd never add partitions for _volume_ here, only for consumer parallelism. **Pick the count once, generously, and never touch it.**

#### 5.4b ⚠ Confusion resolved — choosing topic vs partition-count vs key (and what scaling actually breaks)

> **My doubt:** "Tournament with 50 matches — we want ordering per match, not across matches. What's the topic, since you give one partition per match and key by match ID? And if we horizontally scale, ordering gets disturbed — how does that impact?"

⚠ **First correction — do NOT create one partition per match.** You have (say) 10 partitions and **50 matches hash into them** (~5 matches per partition). That's the design, not a bug. A partition-per-match would mean adding partitions daily → hitting the §5.4a modulo problem constantly.

▸ **Interleaving is fine — ordering is PER KEY, not per partition:**

```
Partition 3 log:  [M17-goal] [M42-card] [M17-sub] [M42-goal] [M17-goal] …
                       ↑ M17's events in order         ↑ M42's events in order
```

M17 and M42 **share** partition 3; their events interleave — harmless, because you never wanted cross-match ordering. Each key's own sequence is intact (same key → same partition → append-only log). ▸ The **consumer** holds per-match logic (routes each event by `match_id`, keeps per-match state). ⚠ Offsets _record_ this order; they don't _cause_ it.

▸ **Three separate decisions, three separate drivers — keep them apart:**

|Decision|Driven by|This scenario|
|---|---|---|
|**Topic**|_who subscribes independently_|`football-events`, `volleyball-events` (per **sport**)|
|**Partition count**|_how much consumer parallelism you need_|~10 (→ up to 10 parallel consumers)|
|**Key**|_what must stay ordered_|`match_id`|

- ▸ **Universal rule: the key is the entity whose ordering you need.** Need per-match order → key on match.
- ▸ **Topic = a STABLE category; key = the EPHEMERAL entity.** Sports are few and permanent; matches are thousands per season. A topic per match = constant topic churn + metadata overhead. ⚠ Keep topics **few and long-lived**.
- ▸ Partition count is **per topic** — a hot topic (basketball) gets more partitions than a quiet one (cricket). Driven by desired **parallelism**, not raw event volume.

▸ **What horizontal scaling actually breaks (concretely).** Match `M123` is **in progress**, 10 partitions:

- Events 1–40 → `hash("M123") % 10` = **P3**.
- You add a partition (→ 11). Event 41+ → `hash("M123") % 11` = **P7**.
- ⚠ M123 now **split across P3 and P7**, read by two uncoordinated consumers → the 89th-minute goal can process before the 12th-minute goal → **score goes backwards on the site.**

▸ **But the damage window is BOUNDED — only in-flight keys are affected:**

- Matches **finished before** the resize → all `% 10` ✅ · matches **starting after** → all `% 11` ✅ · only matches **mid-flight at the resize moment** get split.
- ▸ **The playbook:**
    - **Over-provision at creation** (§5.4a) — 20–30 partitions up front so you rarely resize. Cheapest fix.
    - **Resize at a natural quiet boundary** — between match days / off-season, when no key is in flight → zero breakage.
    - **Or drain deliberately** — pause producers, let consumers reach the end of the log, resize, resume.
    - ▹ _(Advanced: write a **custom partitioner** — stable mapping or consistent hashing (`01g`) — so adding partitions doesn't remap existing keys.)_
- ⚠ **Sanity check that dissolves the worry:** 50 matches × ~10 events/sec = **500 events/sec** vs Kafka's **~1M/sec per broker**. You'd never resize for volume here — so **pick the count once, generously, and never touch it.**

## 6 · Fault tolerance & durability (▹ senior depth)

### 6.1 Replication + acknowledgments

▸ Durability comes from **replication**: each partition replicated across brokers (1 leader + N followers). Write hits leader → replicated to followers.

- **`acks=all`** — leader acknowledges **the producer** only after **all in-sync replicas (ISR)** have the message → **strongest durability.**
- **Replication factor** — replicas per partition. **RF=3 is common** (1 leader + 2 followers) → survive one broker loss, promote a follower.

### 6.2 "Kafka is always available, sometimes consistent"

▸ Kafka leans **AP** (→ `01h`). ⚠ _"What if Kafka goes down?"_ is an unrealistic question — you can gently push back. The realistic failure is **a consumer going down.**

### 6.3 Consumer failure → offsets + rebalancing

- **Offset management** — consumer resumes from last committed offset → no messages missed (some may be **reprocessed** if it crashed pre-commit → at-least-once).
- **Rebalancing** — if a consumer in a group dies, Kafka **redistributes its partitions** to the survivors → all partitions stay covered.

### 6.4 ⚠ Offset-commit timing — the real tradeoff to discuss

▸ **When you commit matters.** _(Web Crawler: don't commit until the raw HTML is safely in blob storage.)_

- ▸ **Principle:** the **more work a consumer does before committing, the more gets redone on failure.** → **Keep consumer work small** (Web Crawler split into two phases: download HTML, then parse) so a crash re-does less.

## 7 · Handling retries & errors (▹ senior depth)

### 7.1 Producer retries

▸ Message may fail to _reach_ Kafka (network/broker/transient). Producers **auto-retry:**

```
const producer = kafka.producer({
  retry: { retries: 5, initialRetryTime: 100 },
  idempotent: true,
})
```

- ⚠ **Enable `idempotent: true`** so retries don't create **duplicates** (guards against "we thought it failed but it didn't").

### 7.2 Consumer retries — ⚠ not built in

▸ Kafka has **no built-in consumer retry** (SQS does). You roll your own:

- ▸ **Pattern:** move failed messages to a **custom retry topic**, processed by a **separate consumer** → retry without blocking the main consumer.
- ▸ Too many retries → **Dead Letter Queue (DLQ):** a parking topic for failed messages to investigate later.
- ▹ _(Web Crawler deliberately picks **SQS over Kafka** precisely to get built-in retry + DLQ for free.)_

## 8 · Performance optimizations (▹ mostly staff+, one line each)

- **Batching** — send multiple messages per `send()` (producers batch naturally); `sendBatch()` spans topics. Cuts network overhead.
- **Compression** — GZIP / Snappy / LZ4 via the `compression` option → smaller messages → faster transfer.

```
await producer.send({
  topic: 'my_topic',
  compression: CompressionTypes.GZIP,
  messages: [{ key: 'key1', value: 'Hello, Kafka!' }],
})
```

- ⭐ **Biggest lever is still the partition key** (§5.3) — even distribution = max parallelism. **In an interview, start with partition strategy.**

---

## 9 · Retention policies

▸ Topics retain messages per `retention.ms` / `retention.bytes`. **Default = 7 days.**

- ▸ Need longer storage? Raise retention — ⚠ but watch **storage cost + performance.**

## Quick Recall (pass 3+)

|Use / Question|Kafka answer|
|---|---|
|Calibration|⭐ **HIGH value, learn deeply.** Most-invoked queue/stream tech; heavy in fintech pipelines|
|The 4-concept ladder|**partition** = ordered parallelism · **consumer group** = one-consumer-per-partition · **topic** = logical separation · key = decides partition|
|⭐ The core invariant|**order is guaranteed only within a partition**, and the **key decides the partition** (`partition = hash(key) % num_partitions`, murmur2)|
|Broker / partition / topic|broker = server · partition = ordered append-only log (scaling unit) · topic = logical group of partitions (organizing unit)|
|Topic vs partition|topic = **logical** (organize) · partition = **physical** (scale, one broker each)|
|⚠ Producer group?|**No such thing** — only **consumer groups** exist; producers fire independently|
|⚠ Consumer↔partition direction|**each partition → ONE consumer in a group** (not group→partition). Useful consumers ≤ partitions (extras idle)|
|Two-axis mental model|**physical:** cluster→brokers→partitions (log files on disk) · **logical:** topic→partitions (a label). They meet ONLY at the partition|
|Broker vs topic scope|one **broker** holds partitions from **many topics**; one **topic** is **scattered across many brokers**. Never nested|
|Queue vs stream|queue = one consumer, process-and-done · stream = retained/replayable, many groups, continuous|
|Message fields|value · **key (→ partition)** · timestamp · headers. ⚠ order = **offset**, not timestamp|
|Append-only log|immutability + minimal disk seeks + easy scaling ("distributed commit log"); same trade as LSM (`01d`)|
|Offsets|consumer commits offset → resumes on restart. ⚠ **at-least-once** default (crash pre-commit → reprocess); exactly-once needs idempotent+transactional|
|⚠ Committed offset, precisely|consumer tells **Kafka** (`__consumer_offsets`, via **group coordinator** — NOT the controller) "processed through N." Gap before commit = reprocessing risk → **consumer-side idempotency required** (e.g. don't double-charge)|
|Replication|leader handles writes, followers sync; **`acks=all`** = wait for all ISR = strongest durability; **RF=3** common|
|Replica count math|N partitions at **RF k** = N leaders + N·(k−1) followers = **N·k replicas of N partitions** (RF counts total copies)|
|⚠ Only placement rule|no two replicas of the **same partition** on one broker. ✅ many leaders/broker (different partitions) · ✅ partitions > brokers · ⚠ but **RF ≤ brokers**|
|Reading a cluster diagram|group by **(topic, partition)** → one leader + its followers on different brokers; leaders spread for write-load balance|
|Pull vs push|consumers **poll** → control rate, no overwhelm, easy failure handling, batching|
|When to use — queue|async work (YouTube transcode) · ordered (Ticketmaster queue) · decouple producer/consumer|
|When to use — stream|continuous real-time (Ad Click Aggregator) · many consumers / pub-sub (FB Live Comments)|
|⭐ Scaling focus|**partitioning strategy** — the main interview scaling lever. More brokers only help if enough partitions|
|⭐ Topic vs partition-count vs key|**topic** = who subscribes independently (stable category) · **partition count** = desired consumer parallelism (per topic) · **key** = the entity that must stay ordered|
|⚠ One partition per entity?|**No** — many keys share a partition; their events **interleave harmlessly** because ordering is **per key**, not per partition. Consumer routes by key|
|Topic vs key granularity|**topic = stable category** (sport) · **key = ephemeral entity** (match). Topic-per-match = churn + overhead. Keep topics few and long-lived|
|Resize damage window|only **in-flight keys** split (old `% n` vs new `% n+1`); finished/future keys fine → **resize at a quiet boundary** or drain first|
|Offset scope|**per-partition** (own counter each); msg = (topic, partition, offset); no global offset → why order is per-partition only|
|⚠ Add a partition|**no reshuffle of old data** — but `% num_partitions` changes → key's future splits to a new partition → **per-key ordering breaks.** Plain modulo, not consistent hashing (`01g`)|
|⚠ Why add a partition?|for **throughput/parallelism** (consumers capped by partition count) — **NOT** because it "filled." → over-provision guards _ordering_; retention guards _disk_; don't fuse|
|⚠ Can't shrink partitions|Kafka **cannot decrease** partition count (recreate topic) → **over-provision at creation**, resize rarely|
|⚠ "Filled partition"?|**not a thing** — append-only log, no capacity limit; routing is **blind hash** (ignores size/load) → root of hot partitions, fixed by §5.4 not rerouting|
|Add partition vs add broker|add partition = new empty log, breaks ordering · add broker = no auto-move, run **partition reassignment**|
|Over-provision vs retention|**two separate fixes:** over-provision partitions = ordering · retention = disk growth. Don't fuse|
|Indefinite storage?|knob: default 7d · `retention.ms=-1` = forever · **compaction** = latest-per-key. ⚠ never big blobs (`03f`)|
|⚠ Big blobs|**never store in Kafka** — put blob in S3, send a **pointer message** (`03f`)|
|⭐ Hot partition fixes|**no key** (lose order) · **salting** (complicates aggregation) · **compound key** · **back pressure**|
|⭐ Topic vs partitions vs key|**topic** = who subscribes independently (stable category) · **partition count** = consumer parallelism (per-topic call) · **key** = what must stay ordered (ephemeral entity)|
|⚠ One partition per entity?|**No** — many keys share a partition, events **interleave**, each key stays ordered; consumer demultiplexes by key. Per-entity partitions = constant resizing|
|Scaling damage window|only keys **in flight at resize** split across old/new partition. Fix: over-provision · resize at a **quiet boundary** · drain · custom partitioner (`01g`)|
|Consumer failure|offset resume + **rebalancing** (partitions redistributed to survivors)|
|⚠ Offset commit timing|commit **after** work is safely done; keep consumer work **small** so less is redone on crash|
|Producer retries|auto-retry + **`idempotent: true`** to avoid duplicates|
|Consumer retries|⚠ **none built-in** → custom retry topic + **DLQ** (SQS has these free)|
|Performance|batching · compression (GZIP/Snappy/LZ4) · but **partition key is the biggest lever**|
|Retention|default **7 days** (`retention.ms`/`retention.bytes`); longer = more cost|
|Availability mantra|**"always available, sometimes consistent"** (AP, `01h`); "what if Kafka goes down" is an unrealistic Q|
