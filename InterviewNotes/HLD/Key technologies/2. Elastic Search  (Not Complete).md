## Why This Exists

▸ Search & retrieval — _"I have many things, find the right one(s)"_ — with sorting/filtering/ranking/faceting. Postgres full-text search covers many cases; at scale or sophistication you reach for a purpose-built engine. **Elasticsearch is that engine.** ▸ **This write-up has two parts:** (1) **how to use it** — the client-facing tool for search/product-architecture rounds; (2) **how it works under the hood** — the distributed-systems internals a gnarly/infra interviewer might make you rebuild from scratch.

## 1 · Part 1 — Using Elasticsearch (the half that pays off)

### 1.1 Core vocabulary

▸ **CRUX** — four client-facing concepts:

- **Document** — the unit you search over. Just a JSON object (a book, an order, a transaction). Don't overthink "document."
- **Index** — a collection of documents. ⚠ **Think "database table," but the word is overloaded** — an ES _index_ (the table) is a different thing from an _inverted index_ (the auxiliary lookup structure → `01d`). The article keeps clarifying which; so will these notes.
- **Mapping** — the **schema** of an index: which fields exist, their types, how each is processed/indexed.
- **Field** — a key-value pair inside a document. The mapping decides which fields are searchable and how.

⚠ **`keyword` vs `text` — the single most important mapping decision, and it maps onto two structures you already know:**

- **`keyword`** — the value is treated as **one whole atomic token.** Exact-match, sort, filter. → behaves like a **hash-table lookup** (`01d`). Use for IDs, statuses, enums, category tags, author names you filter on exactly.
- **`text`** — the value is **tokenized** (split into words, lowercased, analyzed) so you can ask "does this field _contain_ the word X." → backed by the **inverted index** (`01d`). Use for titles, descriptions, comments — anything free-text.
- ▸ **The mental test:** _do I look this up whole (hash) or search inside it (inverted index)?_ That answer picks `keyword` vs `text`. Getting it wrong is a classic bug — a `text`-mapped ID tokenizes weirdly; a `keyword`-mapped description can't do word search.

⚠ **Mapping bloat = memory cost.** Every mapped field carries index overhead. Map a 10-field User but only search 2 → you pay memory on 8 dead fields.

- **Fix:** map only what you actually search/sort/filter on. Keep the rest in `_source` (returned, not indexed) or out entirely.
- ▸ Most of your query-performance tuning is **mapping + cluster-param adjustments**, so a lean mapping is where control starts.

#### 1.1a ⚠ Confusion resolved — "document = whole object" vs "inverted index = term→docID": how do they coexist? (+ how to decide what goes in a document)

> **My doubt:** "How do I decide what exactly goes in the document? Take one case where Postgres fails so you must use ES — and show the schema, mapping, indices end-to-end. Also: when I learned inverted indexes, they map a key to which document contains it — that's what I understood. But here the document is one whole object. If I have a very large object, will it be divided into multiple objects? I can't reconcile the two."

**① The scenario where Postgres gives up.** Swiggy `restaurants` table, ~20 columns (`id, name, description, cuisines, lat, lng, avg_rating, price_for_two, is_veg, delivery_time, owner_id, gst_number, fssai_license, bank_account, …`). User types **"biriyani"** (misspelled) and expects, in <100ms over millions of rows:

- text match on name/description/cuisine, **typo-tolerant** ("biriyani"→"biryani")
- filter: within 4km, rating ≥ 4, veg-only, price < 500
- sort: relevance → rating → delivery time
- facets: per-cuisine counts ("Biryani (830)…")

⚠ **Why Postgres hits a wall:** `ILIKE '%biriyani%'` is a full scan, no typo tolerance, no ranking. Postgres full-text (`tsvector`/GIN) gives tokenized search + _some_ ranking — but blending **text relevance + geo + multi-field filter + faceted counts + fuzzy match + tuned score**, at low latency + high QPS, on a **write-heavy source-of-truth table**, is the wall. Facets and fuzzy matching especially fall over.

- ▸ **So:** Postgres stays system of record; **ES becomes a search projection fed by CDC** (canonical pattern → Part 2).

**② What goes in ES — and what you drop.** Index = `restaurants` (index ≈ table ✅). Mapping declares **only the fields search touches**, not all 20 columns:

```
PUT /restaurants/_mapping
{ "properties": {
    "restaurant_id": { "type": "keyword" },   // exact, joins back to Postgres
    "name":          { "type": "text" },       // tokenized → full-text
    "description":   { "type": "text" },
    "cuisines":      { "type": "keyword" },     // exact facet/filter
    "is_veg":        { "type": "boolean" },
    "avg_rating":    { "type": "float" },       // filter + sort
    "price_for_two": { "type": "integer" },
    "location":      { "type": "geo_point" }
}}
```

Dropped: `gst_number, fssai_license, bank_account, owner_id, created_at` — never searched → stay in Postgres. Mapping them = wasted memory (fat-mapping cost).

- ▸ **The rule for "what goes in a document":** whatever you **search on, filter on, sort on, or must display without a second DB hop.** Nothing else.

**③ A document = one restaurant as JSON:**

```
{ "restaurant_id": "R12345",
  "name": "Paradise Biryani",
  "description": "Authentic Hyderabadi dum biryani since 1953",
  "cuisines": ["Biryani","Hyderabadi","Mughlai"],
  "is_veg": false, "avg_rating": 4.4, "price_for_two": 600,
  "location": { "lat": 17.44, "lon": 78.44 } }
```

**One restaurant = one document. NOT split into multiple documents.** A large object stays one document — automatic splitting does not happen.

**④ The reconciliation — ES stores every document TWICE:**

- **`_source`** — the raw JSON blob, kept verbatim → the thing **returned** to the user (the search _hit_).
- **Search structures** — ES **shreds** the doc field-by-field into a **per-field inverted index:**
    - `name: "Paradise Biryani"` → text → tokenize → `["paradise","biryani"]` → `name` index: `"biryani" → [R12345, R888, …]`
    - `cuisines: [...]` → keyword → **not** tokenized, stored whole → `"Hyderabadi" → [R12345, …]`
    - `avg_rating`, `price_for_two` → **doc values** (columnar) for filter/sort
    - `location` → BKD tree for geo
- ▸ **So the inverted index is EXACTLY what you learned — `term → docs containing it`.** You had it right. The missing piece: it's built by **decomposing each document's fields into tokens.** The whole object stays _one document_ (returned); its _content_ explodes into `term→docID` entries across many per-field indexes.

▸ **What the two copies actually look like on disk.** Say we index **3 restaurants** — `R12345` _Paradise Biryani_, `R888` _Bawarchi_, `R777` _Sagar Veg_. ES now holds each restaurant in **two shapes at once:**

**COPY 1 — `_source` store** · one verbatim blob per docID · _used only to RETURN results:_

```
R12345 → { "name":"Paradise Biryani", "cuisines":["Biryani","Hyderabadi","Mughlai"],
           "avg_rating":4.4, "price_for_two":600, "is_veg":false, "location":{…} }
R888   → { "name":"Bawarchi",         "cuisines":["Biryani","Hyderabadi"],
           "avg_rating":4.2, "price_for_two":500, "is_veg":false, "location":{…} }
R777   → { "name":"Sagar Veg",        "cuisines":["South Indian"],
           "avg_rating":4.0, "price_for_two":300, "is_veg":true,  "location":{…} }
```

**COPY 2 — search structures** · built by shredding every doc · _used only to FIND docIDs:_

```
── inverted index: name        (text → tokenized) ────────────────────
     "paradise" → [R12345]        "biryani" → [R12345]
     "bawarchi" → [R888]          "sagar"   → [R777]      "veg" → [R777]

── inverted index: cuisines    (keyword → whole values, NOT tokenized) ─
     "Biryani"      → [R12345, R888]     "Hyderabadi"   → [R12345, R888]
     "Mughlai"      → [R12345]           "South Indian" → [R777]

── doc values: columnar        (one contiguous array per field → filter/sort) ─
     avg_rating     : R12345=4.4   R888=4.2   R777=4.0
     price_for_two  : R12345=600   R888=500   R777=300
     is_veg         : R12345=false R888=false R777=true

── BKD tree: location          (2-D spatial index over the 3 lat/lon points) ─
```

- ▸ **Read it as one dataset in two shapes:** the same three restaurants appear once as **whole blobs** (COPY 1) and again **exploded** into `term→docID` postings + columns + a geo tree (COPY 2).
- ▸ **A query — "Biryani cuisine, veg=false":** hit `cuisines` inverted index → `[R12345, R888]` → filter `is_veg` via doc values → rank → pull **COPY 1** for just those two IDs.
- ▸ **The one-liner:** **find via COPY 2, return via COPY 1.**

|Concept|What it is|Its job|
|---|---|---|
|**Document**|the whole object (one restaurant)|the **unit returned** — a search _hit_ (**noun**)|
|**Inverted index**|`term→[docIDs]`, built by shredding each doc's fields|the **machine that finds which docs to return** (**verb-machinery**)|

- ▸ **The docID is the bridge:** inverted index hands you IDs → IDs point back to whole `_source` documents.

⚠ **Precision fix — it's "term," not "key":** tokenization shreds field **values** into **terms**; field _names_ (keys) don't change. `name: "Paradise Biryani"` → terms `["paradise","biryani"]`.

⚠ **"Is a big object split into many documents?" → No.** 1 object = 1 document, always. Fields are indexed individually; the object is never auto-split. The only "splitting" is a **modeling choice you make** (reviews as `nested` vs separate index, driven by update frequency) — never automatic.

**⑤ How a search actually runs** (query: "biriyani", veg, within 4km, rating ≥ 4):

1. **Coordinating node** receives + plans it.
2. **Query phase (text):** "biriyani" → analyzer normalizes + fuzzy → term "biryani" → look up `name`/`description`/`cuisines` inverted indexes → **candidate docIDs.** The ~O(1) lookup replacing the O(n) scan — the whole reason ES exists.
3. **Filters:** rating/price via doc values; geo via BKD tree → **intersect** with candidates.
4. **Score/rank:** BM25/TF-IDF relevance blended with sort.
5. **Fetch phase:** pull `_source` for top-N docIDs → return whole documents.

▸ **Mental model (your analogy, corrected):** an ES index ≈ a **MongoDB collection** — a **document store, not columnar** (index≈collection · document=object · fields=key-values). CDC copies a **subset of Postgres columns** in; ES builds the inverted index to map term→docID. **Postgres = truth; ES = a searchable, shredded copy.**

### 1.2 CRUD — and the concurrency mechanic worth stealing

▸ REST API, JSON bodies. `PUT /books` creates an index (default **1 shard, 1 replica** — tunable later). `PUT /books/_mapping` sets the schema. `POST /books/_doc` adds a document and returns a generated `_id`.

▸ **The actual calls** (notes alone are abstract — here's the real sequence):

**1 · Create the index** — dynamic mapping, 1 shard, 1 replica (all tunable after):

```
PUT /books
{ "settings": { "number_of_shards": 1, "number_of_replicas": 1 } }
```

**2 · Set a mapping** — do this up front when most fields _aren't_ searchable, so you don't dynamic-map junk. Note `reviews` as a `nested` type:

```
PUT /books/_mapping
{ "properties": {
    "title":        { "type": "text" },
    "author":       { "type": "keyword" },
    "description":  { "type": "text" },
    "price":        { "type": "float" },
    "publish_date": { "type": "date" },
    "categories":   { "type": "keyword" },
    "reviews": {
      "type": "nested",
      "properties": {
        "user":    { "type": "keyword" },
        "rating":  { "type": "integer" },
        "comment": { "type": "text" }
      }
    }
}}
```

⚠ **Nested-vs-separate-index is a real design fork a picky interviewer will push on** — it's the **normalization/denormalization tradeoff** you know from SQL (`01c`). This is the decision you're making _right here_ by declaring `reviews` as `nested` above:

- **Nest** (reviews inside the book doc) → good when reviews are **frequently queried, infrequently updated.** One doc, one fetch.
- **Separate index** (reviews on their own) → good when reviews **change often** (remember: updates are expensive in ES — see segments below) or are queried independently.
- ▸ The deciding axis is **update frequency vs query pattern**, not "which feels cleaner."

**3 · Add a document** — POST to `/_doc`; ES extracts the mapped fields and indexes them:

```
POST /books/_doc
{ "title": "The Great Gatsby",
  "author": "F. Scott Fitzgerald",
  "description": "A novel about the American Dream in the Jazz Age",
  "price": 9.99,
  "publish_date": "1925-04-10",
  "categories": ["Classic", "Fiction"],
  "reviews": [
    { "user": "reader1", "rating": 5, "comment": "A masterpiece!" },
    { "user": "reader2", "rating": 4, "comment": "Beautifully written, but a bit sad." }
  ] }
```

**4 · The response** — returns the generated `_id` + how it persisted across the cluster. ⚠ **Note `_version`** (this is what powers the concurrency control below):

```
{ "_index": "books",
  "_id": "kLEHMYkBq7V9x4qGJOnh",
  "_version": 1,              // ← NOTE
  "result": "created",
  "_shards": { "total": 2, "successful": 1, "failed": 0 },
  "_seq_no": 0, "_primary_term": 1 }
```

⚠ **`_version` = built-in optimistic concurrency control.** Every doc carries a `_version`. Two ways to update:

- **Blind full-doc `PUT /books/_doc/{id}`** — overwrites everything. ⚠ **Risky**: a concurrent writer's changes get clobbered (last-write-wins).
- **Versioned `PUT ...?version=1`** — only applies if the version still matches; otherwise **errors** so the client can re-read and retry.
- **Partial `POST /books/_update/{id}`** — patch a few fields without fetching the whole doc.
- ▸ **Why explicit update semantics matter here specifically:** ES is distributed, async, concurrent — your request may hit many nodes and **arrive out of order.** `_version` is the same optimistic-concurrency pattern as `UPDATE ... WHERE version = X` (`01b` / `02a §2`). ⭐ **Interview-transferable:** this is a clean, real-world example to cite in an _API design_ round.

### 1.3 Search — SQL-like, JSON-shaped

▸ **CRUX** — queries are JSON and compose like SQL predicates:

- **`match`** — full-text search on a `text` field (`{"match": {"title": "Great"}}`).
- **`bool` + `must` / `should` / `filter`** — combine clauses (AND / OR / filter-without-scoring).
- **`range`** — numeric/date bounds (`price lte 15`).
- **`nested`** — query inside nested objects (reviews with rating ≥ 4 AND comment matching "excellent").
- Response returns matching `_id`s, a **`_score`** (relevance, below), and the `_source` doc unless you opt out.

▹ **A nested query + its response, end-to-end** (skim — the shape is the point). Find books with an "excellent" review rated ≥ 4:

```
// GET /books/_search
{
  "query": {
    "nested": {
      "path": "reviews",
      "query": {
        "bool": {
          "must": [
            { "match": { "reviews.comment": "excellent" } },
            { "range": { "reviews.rating": { "gte": 4 } } }
          ]
        }
      }
    }
  }
}
```

Response — note `hits.total.value` (match count), per-hit `_score` (relevance), and `_source` (the returned doc):

```
{
  "took": 7,
  "timed_out": false,
  "_shards": {
    "total": 5,
    "successful": 5,
    "skipped": 0,
    "failed": 0
  },
  "hits": {
    "total": {
      "value": 2,
      "relation": "eq"
    },
    "max_score": 2.1806526,
    "hits": [
      {
        "_index": "books",
        "_id": "1",
        "_score": 2.1806526,
        "_source": {
          "title": "The Great Gatsby",

}
```

### 1.4 Geospatial — where ES beats a relational DB

▸ **CRUX** — two field types:

- **`geo_point`** — a single lat/lon. Restaurants, drivers, check-ins, delivery addresses.
- **`geo_shape`** — arbitrary geometry (polygons, circles, bounding boxes). Delivery **zones**, city boundaries, coverage areas.
- **`geo_distance` query** — "within 5km of this point," combinable with `bool` filters ("Italian ∧ within 2mi ∧ sort by rating"). ⭐ That multi-faceted combo is exactly why ES fits Yelp/Uber/Swiggy-style prompts.

▹ **The actual calls** (skim — the shapes are the point):

**1 · Define the geo fields in the mapping:**

```
{
  "properties": {
    "name": { "type": "text" },
    "location": { "type": "geo_point" },
    "delivery_zone": { "type": "geo_shape" }
  }
}
```

**2 · Add a document with coordinates** — `geo_point` is a lat/lon; `geo_shape` here is a polygon:

```
// POST /restaurants/_doc
{
  "name": "Joe's Pizza",
  "location": { "lat": 40.7128, "lon": -74.0060 },
  "delivery_zone": {
    "type": "polygon",
    "coordinates": [[[-74.01, 40.71], [-74.00, 40.71], [-74.00, 40.72], [-74.01, 40.72], [-74.01, 40.71]]]
  }
}
```

**3 · Query — `geo_distance`, "within a radius of a point":**

```
// GET /restaurants/_search
{
  "query": {
    "geo_distance": {
      "distance": "5km",
      "location": { "lat": 40.7128, "lon": -74.0060 }
    }
  }
}
```

- ▸ Combine this inside a `bool` with `match`/`range`/`sort` → "Italian ∧ within 2mi ∧ by rating" in one query. That single-query multi-facet is the whole selling point.

▹ **WHY / internals (name-drop only):** `geo_point` indexes coordinates in a **BKD tree** (a block-storage-optimized k-d tree), letting ES prune in **two dimensions at once** — which a plain B-tree on lat and lon _separately_ can't do. Geohashes and R-tree-like structures also appear.

- ▸ **ES geo vs Redis geo (`02a §5`) — the interview-relevant contrast:**

||**Redis geo**|**Elasticsearch geo**|
|---|---|---|
|Structure|sorted set scored by **geohash**|**BKD tree** (+ geohash/R-tree)|
|Shape support|points only|points **and** polygons/shapes (`geo_shape`)|
|Combine with other filters|awkward — separate ops|native — one `bool` query does geo ∧ text ∧ range ∧ sort|
|Fit|"drivers near me," ultra-low-latency, already-have-Redis|rich multi-faceted search where geo is _one_ of several filters|

- ▸ **One-line hold:** Redis geo = _fast radius on points_; ES geo = _geo as one clause in a rich query, with real shapes._

### 1.5 Sort

▸ **CRUX** — `sort` param: single field, multi-field (tiebreak), ascending/descending.

- **Script sort** (`_script`, "Painless" language) — sort by a **computed** value. ⚠ **Expensive** — computes per-doc at query time. The article's own example (10%-off price) is deliberately pointless because it doesn't change order. Reach for it rarely.
- **Nested sort** — must specify the nested `path` + `mode` (e.g. `max`) so sort values come from the _same_ nested object.
- **Relevance (`_score`)** — the **default** when you don't specify sort. Ranks by how well the doc matches.

⚠ **`_score` ≈ TF-IDF** (Term Frequency–Inverse Document Frequency). ⭐ **Worth 10 minutes of your life** — it's the "why did this rank first" answer and it generalizes beyond ES. Rough intuition: a term matters more if it's **frequent in this doc** (TF) but **rare across all docs** (IDF). Common words ("the") get near-zero weight; distinctive words drive the score.

### 1.6 Pagination — the deep-pagination trap

▸ Three strategies, escalating in cost and consistency:

|Method|How|⚠ Cost / limit|Use when|
|---|---|---|---|
|**`from` / `size`**|skip `from`, take `size`|⚠ **dies on deep pages** (>10k) — cluster must fetch+sort _all preceding_ docs every request|shallow pages, "page 1–5" UIs|
|**`search_after`**|pass the **sort values of the last row** as the cursor|forward-only; no random page jump; can miss/dup rows if data shifts under you|infinite scroll, deep forward pagination|
|**PIT + `search_after`** (cursor)|open a **point-in-time** snapshot, paginate against it, close it|most overhead; snapshot must be kept alive|need a **consistent view** while the index is being written|

- ▸ **`search_after` is the workhorse** — it turns "skip N then read" into "read the slice _after_ this key," progressively narrowing the set. Same idea as **keyset/cursor pagination** in API design (`01b`): paginate by a **stable sort key**, never by offset.
- ▹ **PIT (point-in-time)** exists because `search_after` alone can shift under concurrent writes; PIT freezes a snapshot so pages stay consistent. Costs the snapshot's resources → only when consistency across pages actually matters.

## 2 · Part 2 — How it works (read once, don't memorize)

> ▹ **This whole part is ▹ WHY for your targets.** The two things to _actually retain_: **(a) segments are immutable → updates are expensive → ES is bad for rapidly-changing data**, and **(b) the CDC-from-Postgres pattern.** Everything else is infra-role trivia.

▸ **The one-sentence architecture:** Elasticsearch is a **distributed orchestration layer over Apache Lucene.** ES does the distributed-systems work (cluster coordination, APIs, aggregations, real-time); **Lucene** does the actual search. Mentally: _"a bag of Lucene indexes with scalability and availability bolted on."_

### 2.1 Cluster & node types

▹ **Name-drop tier — do not memorize all five.** A cluster is many nodes; a node can play multiple roles:

- **Master** — cluster admin (add/remove nodes, create/delete indices). Elected from master-eligible seed nodes via **leader election** (one active at a time).
- **Data** — stores documents + Lucene indexes. ⭐ where search actually happens.
- **Coordinating** — the **front door**: receives a query, fans it to the right shards, merges results.
- **Ingest** — transforms/prepares data on the way in.
- **ML** — machine-learning tasks.
- ▸ **The only three worth a sentence in an interview:** master (coordination), data (storage+search), coordinating (query fan-out/merge). Skip the rest unless asked.

### 2.2 Data nodes & the Russian dolls

▸ **Nesting (this hierarchy is worth knowing):**

```
index  →  shards (+ replicas)  →  Lucene index (1:1 with a shard)  →  Lucene segments
```

- **Shard** — how ES splits an index (and its search structures) across hosts → parallelism + scale (`01f`). Searches run across all relevant shards **in parallel**; the coordinating node merges/sorts.
- **Replica** — an exact **copy** of a shard. Two jobs: **high availability** + **read throughput** (X TPS/shard × Y replicas ≈ X·Y read TPS). ▹ Same read/write asymmetry as everywhere else (`02a` hot-key section): replicas scale **reads**, not writes.
- ▸ **`_source` is stored separately from the Lucene search structures** — like a document store sitting beside the index. Queries run in two phases:
    - **Query phase** — find matching doc IDs using the optimized index structures.
    - **Fetch phase** — pull the actual `_source` for those IDs.
    - ▸ **The ideal query never touches `_source`** — it's answered entirely from indexed/included fields. (This is why you sometimes _copy_ a field into the index.)

### 2.3 ⭐ Lucene segments are IMMUTABLE — the lesson to actually keep

▸ **CRUX** — a segment is an **immutable** container of indexed data. Writes are **batched into new segments and flushed to disk**; existing segments are never edited. This is the **same immutability trade as an LSM tree (`01d`)** — buffer writes, flush immutable sorted files, merge later.

▸ **How you do mutable CRUD on immutable files (Problem→Fix per operation):**

- **Insert** — add to a new segment. Cheap.
- **Delete** — ⚠ can't edit the segment → mark the ID in a **tombstone / deleted-set.** Queries **pretend it's gone**, but the bytes remain until cleanup.
- **Update** — ⚠ **no in-place update.** ES **soft-deletes** the old doc + **inserts a new one.** Old version lingers until merge.
- **Merge** — periodically combine segments into a new one, **physically dropping tombstoned/superseded docs.** This is the garbage collection.

⚠ **The consequence that matters for design: updates are strictly worse than inserts** (delete-bookkeeping + a lingering old copy + eventual merge cost). ▸ **This is the core reason ES is a poor fit for rapidly-updating data** — e.g. a per-post `like_count` or impression counter that increments constantly will churn segments and thrash merges. ⭐ **Interview move:** if someone proposes storing a hot mutable counter in ES, flag it — _"that's a write-heavy mutable field; segments are immutable so every increment is a soft-delete+insert. Put the counter in Redis/DB and CDC the periodic value in."_

▹ **Why immutability is worth the hassle** (the transferable lesson): safe caching (no consistency worries), simpler concurrency (reads never see mid-flight changes), easier crash recovery (known-good state), better compression, faster search on optimized static structures. ▸ **Same design philosophy you'd cite for LSM/append-only stores (`01d`)** — immutability at the right layer buys you caching, compression, and concurrency for free; the cost is merge/compaction.

### 2.4 Segment features — cross-reference, don't re-derive

▸ Two structures live inside every segment:

- **Inverted index** — token → list of docs containing it. Turns an O(n) scan into an O(1)-ish lookup for "which docs contain 'lazy'." **Full mechanics in `01d` — not repeated here.** This is what makes `text` search fast.
- **Doc values** — a **columnar, contiguous** store of a _single field across all docs_ in the segment. ▸ Needed because the inverted index tells you _which_ docs match, but **sorting/aggregating** needs the _values_ — and reading one column from row-oriented storage means reading whole rows. Doc values store the column contiguously (the same trick behind Redshift/Spark columnar analytics → data-layout discussion in `01c`).
    - ▸ **Split of labor:** **inverted index = find the matching docs · doc values = get the field you sort/aggregate on.**

### 2.5 Coordinating nodes & query planning

▹ **Infra-role tier — one paragraph, then move on.** The coordinating node parses the query, decides which nodes/structures to use, and **plans execution order.** The canonical example: searching `"bill nye"` where `"bill"` has millions of postings and `"nye"` has hundreds — you start from the **rare term** (`nye`) and intersect, not the common one. Orders-of-magnitude difference.

- ▸ **The transferable idea (this is the only reason it's here):** by keeping **statistics** (term frequencies, field types, doc lengths) and adding a planning **indirection**, the system adapts to the _actual data_ — the same reason query planners make databases powerful. Cite this in an _infra_ system-design round; ignore it otherwise.

## In Your Interview

> ⭐ **This section is the real payoff — the practical rules.**

▸ **The dominant pattern: ES is a CDC-fed read projection.** Elasticsearch almost always hangs off an authoritative store (Postgres, DynamoDB) via **Change Data Capture** (`01c` / CDC). Writes go to the source of truth; a CDC stream projects the searchable subset into ES.

- ▸ ⭐ **Fintech framing:** Postgres owns the transaction (money, ACID, durable). ES holds a **denormalized, searchable copy** for the merchant dashboard's "find transactions by ref / amount range / status / date" screen. If ES drifts or dies, you **rebuild it from Postgres** — no money is at risk. _Say this._

⚠ **Rules / boundaries (Problem→Fix framing):**

- **Don't use ES as your database.** It's a search engine; historically weak on consistency/durability. → **Persist truth elsewhere**, project into ES.
- **ES is read-optimized.** Write-heavy workloads (constant counters, high-churn fields) thrash it (immutable segments). → **Buffer writes / aggregate upstream**, or keep the mutable value in Redis/DB and sync periodically.
- **ES is eventually consistent** — results can be **stale, sometimes significantly.** → If your use-case can't tolerate staleness (e.g. "did my payment just succeed"), **read from the source of truth**, not ES. ⭐ This is the fintech line again.
- **ES is not relational — denormalize hard.** Aim for results from **1–2 queries**; push the join/transform work to the **write side** (in the CDC pipeline).
- **Not every search needs ES.** < ~100k docs or rarely-changing data → **a Postgres full-text index is often enough** (`01d`). Reach for ES only when a plain query against the primary store proves insufficient.
- **Sync is a bug source.** CDC drift between source and ES is a classic production failure. → Design the sync path deliberately (idempotent, replayable, reconcilable).
- ▸ **Always be ready to justify ES over the alternative** and to name its limits — picking it reflexively reads as junior.

### ⚠ When NOT to use Elasticsearch

|Situation|Use instead|
|---|---|
|System of record / anything that must durably persist|Postgres / DynamoDB (ES is a projection)|
|Money / correctness-critical reads that can't be stale|the source-of-truth DB (ES is eventually consistent)|
|Write-heavy or high-churn mutable fields (counters, likes)|Redis (`02a`) / DB; sync aggregates in|
|Small (< ~100k docs) or rarely-changing data|Postgres full-text index (`01d`)|
|Relational queries needing real joins|relational DB; denormalize before ES|

### Lessons worth stealing (even if you never use ES)

- ▸ **Immutability at the right layer** buys caching, compression, concurrency, recovery — cost is merge/compaction (`01d` LSM echoes this).
- ▸ **Separate query execution from storage** → optimize each independently (coordinating vs data nodes).
- ▸ **Indexing strategy = query pattern.** Inverted index for text-contains, doc values for sort/aggregate. Structure data for the queries you'll actually run.
- ▸ **Distributed = scale + fault-tolerance at the cost of consistency complexity** → the CAP tradeoff (`01h`). ES chose availability + eventual consistency, and every rule above falls out of that choice.
