## 1 · What it is & why it exists

▸ **CRUX** — an API Gateway is the **single entry point** for all client requests: it receives them, applies middleware, and **routes each to the right backend service.**

- ▹ **Analogy (HI's):** a hotel front desk. Guests don't hunt down housekeeping or maintenance — they ask the front desk, which handles check-in, room assignment, and requests. Clients shouldn't know your internal service layout either.
- ▸ **Why it appeared:** it's the child of **microservices.** Break a monolith into many services and something must give clients _one_ clean address instead of forcing them to know and call every service directly (tight coupling, bloated client code). The gateway is that clean separation between your **internal service layout** and your **external API surface.**

### 1.1 The core job everyone forgets: routing

⚠ **The classic candidate mistake:** introduce a gateway, then spend all your breath on auth / rate limiting / SSL — and **never mention routing**, which is the actual reason it exists.

- ▸ **Say routing first.** Middleware is the bonus, not the point. _(Determining which backend service handles each incoming request = the primary function.)_

## 2 · Tracing a request (the 6 steps)

> ▸ This is the meat of the chapter, but treat it as **recognition, not recitation** — you'd never walk all six on a whiteboard. Know steps **3 (routing)** and **2 (middleware)** cold; the rest are skim.

The flow, step by step:

1. **Request validation** — check the request is well-formed.
2. **Middleware** — apply auth, rate limiting, etc.
3. **Routing** — send the request to the appropriate backend service.
4. **Backend processing** — service handles it and returns a response.
5. **Response transformation** — gateway reshapes the response and returns it to the client.
6. **Caching** (optional) — cache the response for future requests.

### 2.1 Request validation

▸ Check the request is well-formed **before** it touches your backend: valid URL, required headers present, body matches expected format.

- ▸ **Why up front:** reject a malformed JSON payload or a missing API key **at the door** with a helpful error, instead of wasting backend resources on a request that was never going to succeed.

### 2.2 Middleware (cross-cutting concerns)

▸ The gateway centralizes work that would otherwise be duplicated in every service. Common tasks: authentication (JWT), rate limiting, SSL termination, logging/monitoring, response compression, CORS, IP whitelist/blacklist, request-size validation, timeouts, API versioning, throttling, service-discovery integration.

- ▸ **The only three worth naming in an interview:** **authentication**, **rate limiting**, **IP whitelisting/blacklisting.** _(Rate limiting itself → the Redis token/counter mechanics in `02a §4`.)_
- ⚠ **Discipline:** if you mention middleware at all, do it **with a purpose and briefly.** The recommended line is literally _"routing and basic middleware"_ — don't enumerate the whole list out loud.

### 2.3 Routing ⭐ (the actual core)

▸ The gateway keeps a **routing table** mapping incoming requests → backend services, keyed on some combination of: **URL path** · **HTTP method** · **query params** · **headers.**

```
routes:
  - path: /users/*
    service: user-service
    port: 8080
  - path: /orders/*
    service: order-service
    port: 8081
  - path: /payments/*
    service: payment-service
    port: 8082
```

- ▸ Look up the match (e.g. `/users/*` → user-service), forward the request. That's it — this is the whole "core responsibility."

### 2.4 Backend communication (protocol translation)

▸ Most services talk HTTP, but some use **gRPC** internally. The gateway can **translate protocols** — transform the incoming request into whatever the backend speaks.

- ▸ **Payoff:** services pick the most efficient internal protocol without clients ever knowing. ⚠ **Uncommon in practice** — mention only if relevant. _(Protocol choices → `01b`.)_

### 2.5 Response transformation

▸ Transform the backend's response into the format the **client** expects → internal services stay efficient/varied while clients see one clean, consistent API. Example — HTTP in, gRPC internally, JSON back out:

```
// Client sends an HTTP GET request
GET /users/123/profile

// API Gateway transforms this into an internal gRPC call
userService.getProfile({ userId: "123" })

// Gateway transforms the gRPC response into JSON and returns it over HTTP
{
  "userId": "123",
  "name": "John Doe",
  "email": "john@example.com"
}
```

### 2.6 Caching

▸ Optionally cache the response before returning it. ⚠ **Only for data that is (a) frequently accessed, (b) changes rarely, and (c) NOT user-specific** — i.e. the same input reliably returns the same output.

- **Full response caching** — cache whole responses for hot endpoints.
- **Partial caching** — cache only the slow-changing parts.
- **Invalidation** — TTL or event-based.
- ▸ Store in gateway memory or a distributed cache (Redis). _(Caching strategy/patterns, TTL-from-staleness → `01e`.)_

## 3 · Scaling an API Gateway

> ▸ Two dimensions: **more load** (horizontal) and **global users** (distribution). Both are one-liners in an interview.

### 3.1 Horizontal scaling

▸ **CRUX** — API Gateways are **stateless** → textbook horizontal scaling. Add instances behind a load balancer.

- ▹ Same reason any stateless tier scales cleanly: no per-instance state to coordinate, so requests fan across instances freely.

### 3.2 Global distribution

▸ For a global user base, deploy gateways near users (like a CDN):

- **Regional deployments** — gateway instances in multiple regions.
- **DNS-based routing** — **GeoDNS** sends users to the nearest gateway.
- **Config sync** — keep routing rules/policies consistent across regions.
- ▸ _(GeoDNS / edge-proximity mechanics → `01a` networking; the CDN parallel is the mental model.)_

### 3.3 Gateway vs Load Balancer — the distinction interviewers probe

⚠ Gateways _include_ load-balancing features, but two different jobs hide here:

- **Client → Gateway LB** — a **dedicated LB in front** of your gateway instances (AWS ELB, NGINX).
- **Gateway → Service LB** — the gateway itself balancing across **backend service** instances.
- ▸ **Interview shortcut:** you can **collapse both** into one box labeled _"API Gateway + Load Balancer."_ Don't get bogged down at the entry point — it's a distraction from the actual system. ⚠ Only split them if explicitly asked.

## 5 · When to propose one (and when NOT)

▸ **TL;DR — microservices → yes; simple client-server → no.**

- ✅ **Use it with microservices.** Almost essential — without it, clients must know and call many services directly (tight coupling, complex client code). The gateway is the clean internal/external boundary.
- ⚠ **Skip it for a monolith or single client type.** It adds **unnecessary complexity** with nothing to route between. Introducing it reflexively is itself a mistake.
- ▸ **The meta-rule (say it, then move on):** _"I'll add an API Gateway for routing and basic middleware."_ Understand the box, but know that **over-investing time here is the more likely error** than under-investing.
