## 1 · What it is

▸ **CRUX** — DynamoDB is a **fully-managed, highly scalable, key-value + document NoSQL service** from AWS. Descends from the same 2007 **Dynamo paper** as Cassandra (`02e §1`), which is why the data model feels familiar.

Unpacking the three marketing words, because each carries a real consequence:

|Claim|What it actually means|The consequence|
|---|---|---|
|**Fully-managed**|AWS handles hardware, config, patching, scaling|⭐ **Near-zero ops burden** — the single biggest advantage over Cassandra (`02e` needs repairs, compaction tuning, capacity planning)|
|**Highly scalable**|Auto-scales up and down, no downtime or degradation|Partitions **split and merge automatically** (§7.1) — you never run a rebalance|
|**Key-value**|NoSQL, not relational|Flexible storage; ⚠ but query flexibility is bounded by your key design (§4)|

⚠ **Not open source.** Unlike Kafka (`02c`), Redis (`02a`), or Cassandra (`02e`), internals are proprietary — HI's "under the hood" sections come from AWS docs and the Dynamo paper, not source code. ▸ **Interview consequence:** less scope for internals questions, more for **how you use it.**

### 1.1 ⚠ "Am I even allowed to use DynamoDB in an interview?"

▸ **HI's answer: ask your interviewer.** Many say yes and expect fluency. Others say no, wanting open-source alternatives that avoid **vendor lock-in.**

- ▸ **The move:** name it, ask, and have the alternative loaded. _"I'd reach for DynamoDB here — is managed AWS fair game, or would you prefer I stay vendor-neutral? If so, Cassandra with `((merchant_id, day_bucket), event_id)` gets me the same shape."_
- ⭐ Asking costs 5 seconds and demonstrates awareness of lock-in as a real architectural cost.

## 2 · Data model

### 2.1 The three definitions

|Term|Relational analogue|Detail|
|---|---|---|
|**Table**|table|Top-level structure. **Mandatory primary key.** Supports secondary indexes (§4)|
|**Item**|row|A collection of attributes. Must have a primary key. ⚠ **Max 400 KB** including all attributes|
|**Attribute**|column|Key-value pair. Scalars (string, number, boolean), **sets** (string set, number set), and **nested** structures|

```json
{ "PersonID": 101, "LastName": "Smith", "FirstName": "Fred", "Phone": "555-4321" },
{ "PersonID": 102, "LastName": "Jones", "FirstName": "Mary",
  "Address": { "Street": "123 Main", "City": "Anytown", "State": "OH", "ZIPCode": 12345 } },
{ "PersonID": 103, "LastName": "Stephens", "FirstName": "Howard",
  "Address": { "Street": "123 Main", "City": "London", "PostalCode": "ER3 5K8" },
  "FavoriteColor": "Blue" }
```

- ▸ Note item 103 has `FavoriteColor` and the others don't; item 101 has no `Address`. Attributes vary freely per item.
- ▹ JSON here is a **transport format only** — actual storage is proprietary. You model data without reasoning about physical layout (⚠ the opposite of `02e`, where physical layout _is_ the modeling exercise).

### 2.2 ⭐ Schemaless — and this is a real divergence from Cassandra

▸ **CRUX** — DynamoDB is **genuinely schema-less.** No schema definition before inserting. Items in one table can have entirely different attribute sets, and **new attributes can be added at any time without touching existing items.**

⚠ **Do not carry over `02e §1.3a(k)`'s "sparse, not schemaless" rule — that was specifically about Cassandra.** The two differ here:

||Cassandra|DynamoDB|
|---|---|---|
|New field|⚠ requires `ALTER TABLE` — must be **declared**|✅ just write it. **No DDL**|
|What varies per row/item|which **declared** columns are present|**anything**|
|Validation|schema enforces types|⚠ **none** — application-level validation is **your** responsibility|

- ⚠ **The cost of that flexibility:** DynamoDB enforces no attribute uniformity across items. Careless writes produce a table where half the items are missing a field your code assumes exists. **Validation moves into the app layer.**
- ▸ **What does NOT change:** the **primary key is still mandatory and still frozen at table creation.** Schemaless means _attributes_ are free — the access-pattern discipline of `02e §8` still applies in full.

#### 2.2a ⚠ Confusion resolved — "this JSON is wrong; DynamoDB stores exactly like Cassandra"

> **The doubt (verbatim):** _"in DynamoDB you are saying this is a one-to-one mapping, right? Then why this kind of a JSON structure has been given? Because later you are, when you are explaining global search index and local search index, you are still talking about, you know, chat ID, then message ID as a whole primary key … So these two keys are matching. So, I feel DynamoDB is also storing exactly the way Cassandra is storing, right? So this JSON is wrong. And so can I assume MongoDB is different, but Cassandra and DynamoDB is storing exactly the same way?"_

**(a) The JSON isn't wrong — it demonstrates three things.**

1. **A partition-key-only table.** `PersonID` is the **entire** primary key, no sort key. Legal in both systems — ≡ `02e §1.3`'s first CQL example, `PRIMARY KEY (a)`. It doesn't contradict the chat example that _does_ have a sort key.
2. **Schemaless attribute variation.** Item 101 has `Phone` and no `Address`; item 103 has `FavoriteColor` and the others don't. Nobody declared any of them.
3. ⭐ **Undeclared nesting.** `Address` is a nested object that simply exists.

- ▸ **Point 3 is the real Cassandra difference.** To store that `Address` in Cassandra you must first declare a **UDT**, or declare the column as `map<text,text>`. In DynamoDB you write the object and you're done (§2.2).
- ▹ Same pedagogical sequencing issue you caught at `02e §1.2` — the JSON appears **before** keys are introduced, so it can't show them. ▸ You spotted a real pattern in how HI writes; it just doesn't apply here.

**(b) Split the claim into two layers.** ▸ **Logical model: 1:1 — correct.** ⚠ **Physical storage: no, and the differences are consequential.**

||**Cassandra** (`02e`)|**DynamoDB**|
|---|---|---|
|Within a partition|rows **contiguous on disk, sorted**, in immutable SSTables|items in a **B-tree** keyed by sort key|
|Write path|memtable → SSTable → **compaction**|leader → **WAL** → B-tree|
|Update semantics|append a new version; **per-column timestamps**; conflicts resolve by **last-write-wins**|leader-ordered writes — ⚠ **no LWW, no per-column timestamps**|
|Nested data|requires a **declared UDT** or collection type|✅ just write it|
|Record identity|a **row of columns** — sparse but declared|an **item** — self-contained, ⚠ **400 KB cap**|

**(c) The framing to hold.** ⭐ **They share a key model, not a storage model.**

- **Cassandra** is genuinely **wide-column** — the **partition is the storage unit** (`02e §1.3a(b)`).
- **DynamoDB** is closer to **key-value + document** — each item is a self-contained unit the service understands.
- ⚠ **The 400 KB item cap has no Cassandra equivalent.** It follows **directly** from the document-style storage model, and it's a real design constraint (it's why §5.2's Yelp example pushes reviews out to their own table).

## 3 · Primary key: partition key + sort key

### 3.1 The 1:1 map to Cassandra

▸ **CRUX** — a DynamoDB primary key is one or two attributes:

- **Partition key** — hashed to determine the **physical location** (which partition/node). ≡ Cassandra's **partition key** (`02e §1.3`).
- **Sort key** (optional) — orders items **within** a partition; enables range queries and sorting. ≡ Cassandra's **clustering key**.

▸ Together = a **composite primary key.** ⭐ **The concept is shared 1:1 between the two databases** — everything in `02e §1.3a` about what each key does, and `02e §8` about choosing them, transfers unchanged.

- ▸ **Same selection rule:** pick a partition key that (a) matches your **most common query pattern** and (b) keeps data **evenly distributed.** Add a sort key when you need range queries or ordering.
- ▸ **Same worked example:** group chat → partition key `chat_id`, sort key `message_id`. All messages for a chat in one partition, chronologically ordered. (Identical to `02e §8.3`'s Discord v1.)

### 3.2 ⚠ Why a monotonic ID, not a timestamp — same trap as `02e §8.3`

▸ Timestamps look intuitive for sorting but **don't guarantee uniqueness** — multiple items can be created in the same millisecond. A monotonically increasing ID gives **both chronological ordering and uniqueness.**

Generation options HI names:

- **Auto-incrementing counters per partition**
- **UUID v7** — ▸ preferred over v1: timestamp-first layout makes it **naturally sortable as a string**, and it **doesn't leak the machine's MAC address**
- **Snowflake IDs** (what Discord uses, `02e §8.3`)
- **ULID**

### 3.3 ⭐ Under the hood — where DynamoDB genuinely differs from Cassandra

⚠ **This is the most important structural difference in the file. Do not assume Cassandra's internals apply.**

|Layer|Cassandra (`02e`)|DynamoDB|
|---|---|---|
|Finding the partition|**consistent hashing ring**, peer-to-peer, every node knows the topology via **gossip** (`02e §7.1`)|**hash partitioning + a centralized partition metadata service.** A **request router** consults it to map hashed key → storage node|
|Within a partition|**LSM tree** — sorted SSTables, memtable, compaction (`02e §6`)|⭐ **B-tree**, indexed by sort key|
|Growing|admin adds nodes; **streaming + cleanup** (`02e §2.3a`)|⚠ **automatic split and merge**, managed by the metadata service|

- ⭐ **The headline:** Cassandra is **peer-to-peer with an LSM tree**; DynamoDB is **centrally-routed with a B-tree.** ▸ **The consequence:** DynamoDB does **not** inherit Cassandra's write-optimization story. It's fast, but the "writes are pure sequential appends" argument (`02e §6.0`) is **Cassandra-specific — do not reuse it for DynamoDB.**
- ▸ **Composite key lookup:** hash the partition key → find the node → traverse the **B-tree** on sort key → find the item. Two tiers: **partitioning for horizontal scale, B-tree for efficient in-partition querying.**
- ▹ HI notes this is _conceptually similar_ to consistent hashing but uses a **centralized partition map and placement service** rather than the peer-to-peer ring of the original 2007 Dynamo paper. ⚠ So "DynamoDB uses consistent hashing" is approximately right and precisely wrong.

#### 3.3a ⚠ Confusion resolved — "B-tree, so DynamoDB can't take the write volume"

> **The doubt (verbatim):** _"it does not use compaction, it does not use LSM tree. So it is not that write-heavy optimized. So this is like a trade-off. If you are very, very write-optimized, then you go with Cassandra … But if you are not insanely write-optimized, because it is using B-tree and all, DynamoDB that means it is doing in-place modification and all, rather than update and delete which LSM tree does."_

**(a) ✅ The mechanism is correct.** B-tree modifies in place (locate page → modify → write back); LSM appends and compacts later (`02e §6.0`). ▸ **Cassandra is more write-efficient per machine.** That part is sound.

**(b) ⚠ But the conclusion reaches the right answer via the wrong reason.**

- DynamoDB **auto-splits partitions** (§7.1). Hit the throughput ceiling and it **silently adds capacity.** ▸ **Write throughput is not the wall** — you can push enormous write volume through DynamoDB.
- ⭐ **The wall is the bill.** 10M writes/sec ≈ **$156,000 per day** (§8.3).
- ▸ So you'd move to Cassandra at extreme write volume **not because DynamoDB can't, but because capacity units cost more than machines.**

**(c) ⚠ Why this matters in the room.**

- ❌ _"DynamoDB can't handle that write volume"_ → **wrong**, and an interviewer who knows DynamoDB will correct you.
- ✅ _"DynamoDB handles it, but at 10M writes/sec the capacity-unit bill is six figures a day, so self-hosted Cassandra wins on cost"_ → sounds like someone who has **operated both.**
- ▸ This is §11's rule in miniature: **the Cassandra-vs-DynamoDB decision is economic, not technical.**

## 4 · Secondary indexes ⭐ (GSI vs LSI — the real interview surface)

> ▸ **This is the section with no Cassandra analogue and the highest question density.** ⚠ Recall `02e §6.0`: Cassandra has **exactly one index axis** and answers "query by another column" with **a second table.** DynamoDB answers it with an **index** — this is a genuine capability gap in DynamoDB's favour.

### 4.1 Global Secondary Index (GSI)

▸ **CRUX** — an index with a **different partition key** (and optional sort key) from the base table.

- ▸ **Physical reality:** because the partition key differs, the data lives on **entirely different physical partitions**, replicated separately. ⭐ **A GSI is essentially a separate internal table.**
- ▸ **When to introduce one:** you need to query efficiently by an attribute that **isn't** the table's partition key.
- ▸ **Worked example:** chat table is `(chat_id, message_id)` → great for "all messages in a chat." But **"all messages this user sent across all chats"** has no efficient path. ▸ **Fix:** a GSI with partition key `user_id`, sort key `message_id`.

### 4.2 Local Secondary Index (LSI)

▸ **CRUX** — an index with the **same partition key** as the base table but a **different sort key.**

- ▸ **Physical reality:** same partition key ⇒ **stored on the same physical partitions** as the items it indexes. Maintains a separate **B-tree** within each partition, keyed on the LSI's sort key.
- ▸ **When to introduce one:** range queries or sorting **within a partition** on a different attribute.
- ▸ **Worked example:** already sorted by `message_id` within a chat — but you want _"messages with the most attachments in this chat."_ ▸ **Fix:** an LSI on `num_attachments`.
- ⚠ **Hard constraint:** LSIs can **only be defined at table creation** and can never be added or removed later. **Plan ahead.**

### 4.3 GSI vs LSI — the comparison table

|Feature|**GSI**|**LSI**|
|---|---|---|
|Definition|**different** partition key from the base table|**same** partition key, **different** sort key|
|When to use|query on attributes **outside** the primary key|additional **sort orders within** the same partition key|
|Size restrictions|none|⚠ **10 GB per partition key**|
|Throughput|**separate** read/write capacity from the base table|**shares** the base table's capacity|
|Consistency|⚠ **eventually consistent only**|✅ eventual (default) **or strongly consistent**|
|Creation|✅ add or remove **any time**|⚠ **table-creation only**, never removable|
|Deletion|dropping it doesn't affect base items|⚠ can't drop without dropping the table|
|Max count|**20** per table|**5** per table|
|Example use|global search across all partitions — e.g. **find user by email**|local search within a partition — e.g. **recent orders for this customer**|

- ⭐ **The one row interviewers actually probe:** **GSIs are eventually consistent, always.** If an access pattern needs strong consistency, it **cannot** be served by a GSI (§6.4).
- ▸ **Memory hook:** **G**lobal = **G**oes elsewhere (own partitions, own capacity, eventual). **L**ocal = **L**ives alongside (same partitions, shared capacity, can be strong).

### 4.4 Under the hood

**GSIs:**

- Each is effectively a **separate table with its own partition scheme.**
- On any write to the base table, DynamoDB updates the GSI **asynchronously** → hence eventual consistency.
- Same hash-partitioning mechanism, different partition and sort keys.

**LSIs:**

- **Co-located** with the base table's partitions, sharing the partition key.
- Maintain a **separate B-tree within each partition**, indexed on the LSI's sort key.
- Updates happen **synchronously** with the base table write → hence strong reads are possible.

**Index maintenance:**

- DynamoDB **automatically propagates** changes from the main table to **all** secondary indexes.
- ⚠ **GSIs — asynchronous** propagation (hence eventually consistent). **LSIs — synchronous**, happening with the base table write.
- The system manages the **additional write capacity** required for index updates.
- ⚠ **Indexes are not free** — every base-table write fans out into index writes **you pay for.**

**Query processing:**

- When a query uses a secondary index, DynamoDB **routes it to the appropriate index table** (for GSIs) or **index structure** (for LSIs).
- It then uses that index's **partition and sort key mechanics** to retrieve the requested data efficiently.
- ▸ Note the phrasing difference mirrors the physical reality of §4.4: a GSI is a **separate table** to route to; an LSI is a **structure** inside the partition you're already in.

#### 4.4a ⚠ Confusion resolved — "Cassandra can't do this, so Cassandra is very limited"

> **The doubt (verbatim):** _"These kind of thing can be done in Cassandra. If not, then Cassandra is very limited. Here the DynamoDB is giving that much flexibility because just imagine you cannot know everything beforehand, right? … global search index is also like that only because you are creating a different partition and, you know, sort key which is cluster key in Cassandra. So you are storing the same table but with a different key … because access pattern is different, you are repeating the same data, right?"_

**(a) ⚠ WRONG on capability — Cassandra has three answers**, all in `02e`:

1. **A second table**, written manually by your app (`02e §6.0`, `§8.1`) — **the default idiom.**
2. **Materialized views** (`02e §9`) — Cassandra maintains a derived table **automatically** under a different partition key. ⭐ **Functionally a GSI.**
3. **SAI / Storage Attached Indexes** (`02e §9`) — genuine **global secondary indexes** on columns.

**(b) ✅ The real difference is reliability and who carries the burden.**

||**Cassandra**|**DynamoDB**|
|---|---|---|
|Default idiom|⚠ **app-level dual-write** to a second table|⭐ declare a **GSI**; the service maintains it|
|Failure mode|⚠ app writes table A, **crashes before table B** → **silent divergence, no repair mechanism**|propagation is AWS's problem|
|Automatic option|**materialized views** — ⚠ historically buggy, often **banned** in production|**GSI** — production-standard|
|Consistency|⚠ **your problem**|eventually consistent, but **guaranteed to converge**|

- ▸ **The honest sentence:** _"Cassandra can do this, but the default answer is an app-level dual-write you have to keep correct yourself. DynamoDB makes it a declaration."_
- ⭐ **That is a managed-service advantage, not an architectural one** — the same axis as ops burden (§11), not a capability gap.

**(c) ⭐ "A GSI is denormalization" — correct, and it's the insight that ties `02e` and `02f` together.** A GSI is the same data, **re-keyed** by a different partition key, **physically duplicated** on separate partitions, to serve a different access pattern. That is **precisely** `02e §6.0`'s "second table partitioned by `author_id`." Same concept, different ergonomics.

**(d) ⚠ But one precise exception — do not anchor it to Ticketmaster's `event_sections`.**

||**Re-keyed copy**|**Precomputed aggregate**|
|---|---|---|
|Cassandra|second table by `author_id` (`02e §6.0`)|`event_sections` (`02e §8.4` Fix 2) — `num_tickets`, `price_floor`|
|DynamoDB|⭐ **GSI — exactly this**|⚠ **a GSI cannot do this**|

- ▸ **GSIs re-key. They do not aggregate.** To get `event_sections` in DynamoDB you'd still need application logic, or **Streams → Lambda** maintaining the aggregate (§9.2).
- ▸ **So the correct mapping is:** GSI ≡ Cassandra's **second table** (automated). `event_sections` ≡ a **different pattern that neither database does natively.**

**(e) ⚠ Terminology.** It is a **global secondary index**, not a "global search index." In a room that slip reads as unfamiliarity.

## 5 · Accessing data

### 5.1 Query vs Scan

||**Query**|**Scan**|
|---|---|---|
|Reads|only items matching the **key conditions**|⚠ **every item** in the table or index|
|Uses|primary key or secondary index key attributes; supports **range queries on the sort key**|reading everything|
|Verdict|⭐ **the default**|⚠ **avoid wherever possible** — inefficient on large datasets|

▸ **The design implication:** avoiding scans **is** the data modeling exercise. Choosing the right partition key and sort key is what keeps every access path a Query. ▸ Same discipline as `02e §8`, different vocabulary.

```js
// SQL:  SELECT * FROM users WHERE user_id = 101
const params = {
  TableName: 'users',
  KeyConditionExpression: 'user_id = :id',
  ExpressionAttributeValues: { ':id': 101 }
};
dynamodb.query(params, (err, data) => { /* ... */ });

// SQL:  SELECT * FROM users        ⚠ full scan
dynamodb.scan({ TableName: 'users' }, (err, data) => { /* ... */ });
```

- ▹ **PartiQL** — DynamoDB supports a SQL-compatible dialect (`SELECT`/`INSERT`/`UPDATE`/`DELETE`). ⚠ It translates to the **same underlying operations** — a convenience layer, **not** new capability. Don't present it as "DynamoDB has SQL."

### 5.2 ⚠ The `ProjectionExpression` trap

▸ **You read the entire item by default.** `ProjectionExpression` returns only chosen attributes — but ⚠ **it only reduces network bandwidth.** The full item is **still read from storage**, and you are **still charged the full RCU cost** based on total item size.

- ⚠ **This is NOT SQL column selection.** Believing it is will make you underestimate cost and latency.
- ▸ **Fix — normalize by access pattern.** HI's Yelp example: a `business` table with `business_id, name, address, city, state, zip, category, subcategory` **plus a list of reviews** means every read of basic business info drags the entire review list off storage. ▸ **Pull reviews into a separate table** keyed by business ID.
- ⭐ **Note the inversion worth saying aloud:** `02e` pushes you to **denormalize**; DynamoDB's per-item read cost pushes you to **normalize large sub-collections out.** Same goal (make the common access pattern cheap), opposite move.

## 6 · Consistency, CAP, and transactions ⭐

> ⚠ **Read this section as a correction to the belief `02e` installed.** "NoSQL means no ACID" is true for Cassandra and **false here.**

### 6.1 Per-request consistency

▸ **CRUX** — DynamoDB offers two read consistency models, and ⚠ **it is not a table-level setting.** You choose **per individual read request** via `ConsistentRead=true` on `GetItem` / `Query` / `Scan`.

|Model|Behaviour|Cost|Notes|
|---|---|---|---|
|**Eventual** (default)|may not see the most recent write|**0.5 RCU** per 4 KB|Highest availability, lowest latency. ▸ DynamoDB here behaves as an **AP system with BASE properties**|
|**Strong** (`ConsistentRead=true`)|reflects **all successful writes** that completed before the read|⚠ **1 RCU** per 4 KB — **double**|Slightly higher latency|

- ⭐ **Why per-request matters:** you can serve a **booking flow** with strong consistency while defaulting the **read-heavy, latency-sensitive browse path** to eventual — **in the same table.** ▸ Compare `02e §4.2`'s `R + W > N` tuning: same goal (buy consistency with availability/cost), but Cassandra tunes **replica counts** while DynamoDB flips **one boolean**.
- ⚠ **The lever does not exist everywhere.** Per-request tuning applies to the **base table and LSIs only** — **GSIs are eventually consistent, always**, and `ConsistentRead=true` is not an option there. ▸ So an access pattern needing strong consistency must be designed onto the base table or an LSI **up front** (§4.3, §6.4).

### 6.2 ⭐ ACID transactions — the belief correction

▸ **DynamoDB supports ACID transactions** via `TransactWriteItems` and `TransactGetItems`, providing **serializable isolation** across **up to 100 items spanning multiple tables.**

- ⚠ **`02e §4.4`'s rule does NOT transfer.** Cassandra: atomic only for a **single row in a single partition**, no transactions. DynamoDB: **real multi-item, multi-table transactions.**
- ⭐ **HI's framing:** this **neutralizes the biggest historical criticism** of DynamoDB. ▸ **Saying "NoSQL can't do transactions" in a 2026 interview is a dated answer** and a cheap way to look out of date.
- ▸ **What this unlocks for fintech:** idempotency-key stores, payment state machines, webhook dedup, per-merchant counters — workloads you would **never** put on Cassandra.
- ⚠ **The limit that still bites:** **100 items per transaction.** Fine for "debit A, credit B, write a ledger entry." Not a general-purpose OLTP substitute.

### 6.3 Under the hood — replication and where reads land

▸ Each partition is a **leader-based replication group of three nodes** using **Multi-Paxos** consensus.

- **Writes:** all go through the **leader.** It generates a **write-ahead log** entry and sends it to peers; the write is acknowledged once a **quorum (2 of 3) persists** the log record.
- **Strongly consistent reads:** routed **directly to the leader**, which by construction always holds the newest data.
- **Eventually consistent reads:** served by **any of the three replicas** — lower latency, possibly stale, because the leader replicates to followers **asynchronously after quorum ack.**

⚠ **The structural contrast with Cassandra worth naming:** DynamoDB **has a leader per partition**; Cassandra is **masterless** (`02e §5`, `02e §1.3a(c)`). ▸ That means DynamoDB _does_ have leader-election dynamics internally — AWS just hides them from you. **Cassandra's "no election gap" argument is not a DynamoDB argument.**

### 6.4 ⚠ The consistency gotcha to memorize

▸ **Strongly consistent reads are supported on the base table and LSIs only. GSIs are eventually consistent, always.**

- ▸ **Design consequence:** if an access pattern **requires** strong consistency, it must be served by the **base table or an LSI** — never a GSI. Plan the key design around that, not around it later.

## 7 · Architecture & scalability

### 7.1 Scaling

▸ **CRUX** — DynamoDB **auto-shards.** When a partition hits its capacity ceiling (size **or** throughput), DynamoDB **splits it automatically** and redistributes. Hash partitioning keeps distribution even.

- ⭐ **The contrast to state:** `02e §2.3a` required a planned operation — streaming, cleanup compaction, heavy background I/O. **Here it's invisible.** That is the fully-managed value proposition in one sentence.

### 7.2 Global distribution

- **Global Tables** — real-time **cross-region replication**, enabling local read/write worldwide. Reduces latency for a global user base.
- **Multi-AZ** — DynamoDB replicates across **three Availability Zones** within a region. ⚠ **Not user-configurable.** Each partition = 1 leader + 2 followers, entirely AWS-managed.
- ▸ Region/AZ choice matters for **latency** (user proximity) and **compliance** (data residency).
- ⭐ **HI's calibration:** for global designs, **"I'd enable Global Tables for cross-region replication" is usually sufficient.** Don't elaborate.
- ▹ Contrast `02e §3.2`: Cassandra expresses the same thing as **per-DC replication factors** in `NetworkTopologyStrategy`, which you configure yourself.

### 7.3 Fault tolerance & availability (brief)

▸ **CRUX** — durability and availability come from **automatic multi-AZ replication.** Data survives hardware failure and network disruption without any configuration from you.

- **3 AZs per region**, ⚠ **not user-configurable** · **3 replicas per partition** (1 leader + 2 followers), entirely AWS-managed.
- **Cross-region** → **Global Tables** adds replicas in further regions (§7.2).
- ▸ **Consensus mechanics** — Multi-Paxos, WAL, quorum 2-of-3, leader-routed strong reads → already covered at **§6.3**, not repeated here.
- ⚠ **The line to remember:** availability here is **AWS's problem, not yours** — the mirror image of `02e §7`, where gossip, Phi Accrual, and hinted handoffs are things you operate.

### 7.4 Security (⚠ name-drop only)

▸ **Encrypted at rest by default · TLS enforced in transit (no config) · IAM for fine-grained access control · VPC endpoints for private access.** One line each is the whole topic — see **§10.4** for HI's calibration.

## 8 · Pricing & capacity math ⭐ (the BOTE section)

> ▸ **Why pricing is in an interview file at all:** ⭐ **the cost model imposes real architectural constraints.** This is also the section that feeds `01i`.

### 8.1 The two models

|Model|Billing|Best for|
|---|---|---|
|**On-demand**|per request|**unpredictable** workloads|
|**Provisioned capacity**|specify read/write capacity units, billed hourly|⭐ **predictable** workloads — cheaper. ⚠ pay for idle capacity during troughs|

### 8.2 ⭐ The numbers to memorize

|Unit|Definition|Cost|
|---|---|---|
|**RCU** (read capacity unit)|**4 KB/sec** — one **strongly** consistent read/sec up to 4 KB, **or two** eventually consistent reads/sec|**$1.12** per million reads|
|**WCU** (write capacity unit)|**1 KB/sec** — one write/sec up to 1 KB|**$5.62** per million writes|

**Per-partition ceilings** — the numbers that actually matter for BOTE:

- **3,000 RCU** per partition → **12 MB/sec of reads** (3,000 × 4 KB)
    
- **1,000 WCU** per partition → **1 MB/sec of writes** (1,000 × 1 KB)
    
- ⚠ **The rounding trap:** every write consumes **at least 1 WCU regardless of size** — DynamoDB rounds up to the nearest 1 KB. ▸ A 50-byte counter increment costs the same as a 1 KB write. **This is what makes high-volume tiny writes brutally expensive.**
    

### 8.3 ⭐ The worked example (memorize the shape, not the digits)

HI's YouTube-views scenario:

```
10,000,000 views/sec, each write ≥ 1 WCU (rounded up)
1,000 WCU per partition        → ~10,000 partitions needed
10,000,000 WCU × $0.00065/WCU-hour × 24 hours  ≈  $156,000 PER DAY
                                                  (on-demand would be higher still)
```

- ⭐ **What to take from this:** at extreme sustained write volume, **DynamoDB's cost becomes the architectural constraint** — not its throughput, which is fine. ▸ **This is precisely the argument for Cassandra on your own machines** (§11).
- ▸ **The interview move:** use these to gut-check whether a design is economically viable. Saying _"that's roughly 10,000 partitions and six figures a day, so I'd move this to self-hosted Cassandra"_ is a **senior-sounding** observation grounded in arithmetic.

## 9 · Advanced features

### 9.1 DAX (DynamoDB Accelerator)

▸ **CRUX** — a **purpose-built in-memory cache** for DynamoDB delivering **microsecond** reads. ⭐ **Payoff: often no need to add Redis/Memcached to the architecture** (`02a`, `01e`).

- ▸ **Integration:** swap the DynamoDB client for the **DAX client SDK** (Java, .NET, Node.js, Python, Go). API-compatible, minimal changes — ⚠ but **not fully transparent.**
- ▸ **Mode:** **read-through and write-through** — caches reads, and writes go to **both** cache and DynamoDB.
- ⚠ **The invalidation gotcha:** DAX only auto-invalidates for writes that **go through DAX.** ▸ Update DynamoDB **directly** and those cached entries stay **stale** until TTL or eviction.
- ▹ Two always-active caches: an **item cache** (`GetItem`/`BatchGetItem`) and a **query cache** (`Query`/`Scan`). No configuration choice between them.
- ⚠ **DAX does not cache strongly consistent reads** — those pass straight through to DynamoDB, uncached.

### 9.2 Streams (CDC)

▸ **CRUX** — **DynamoDB Streams** provide built-in **Change Data Capture.** Every insert / update / delete is recorded as a **stream record** for downstream consumers in real time.

Uses HI names:

- **Search sync** — keep an **Elasticsearch** index in step with the table (`02b`).
- **Real-time analytics** — enable **Kinesis Data Streams** on the table, pipe into **Kinesis Data Firehose** → S3 / Redshift / OpenSearch. ⚠ **Firehose cannot read DynamoDB Streams directly** — you need Kinesis Data Streams or a Lambda as the intermediary.
- **Change notifications** — trigger **Lambda** on change: send notifications, update caches, etc.

▸ **The pattern to recognize:** this is the **CDC/outbox shape** from `02c` (Kafka) and `03a` (real-time updates) — **built in**, rather than assembled. ⭐ Strong answer to _"how do you keep your search index consistent with your database?"_

## 10 · DynamoDB in an interview

### 10.1 ✅ When to propose it

▸ HI's framing is unusually permissive: **you can justify DynamoDB for almost any persistence layer.** It is highly scalable, durable, supports **transactions**, and delivers **single-digit-millisecond** latency (**microseconds** with DAX). With DAX for caching and Streams for cross-store consistency, it covers a lot of ground. ▸ **If the interviewer allows it, it's usually a good option.**

### 10.2 ⚠ When NOT to — the four limitations

1. ⭐ **Cost efficiency.** Pricing is per read/write plus storage. ⚠ At **hundreds of thousands of writes/sec**, cost outweighs benefit (§8.3).
2. **Complex query patterns.** Joins, ad-hoc aggregations. ▹ Transactions exist (up to 100 items, multi-table) but that is **not** SQL's query flexibility.
3. **Data modeling constraints.** Optimized for key-value and document shapes. ⚠ **The tell: if you find yourself reaching for GSIs and LSIs constantly, PostgreSQL is probably the better fit.** ▸ Good self-check to voice aloud.
4. **Vendor lock-in.** Choosing DynamoDB locks you to AWS. ⚠ Many interviewers want vendor-neutral designs (§1.1).

### 10.3 The 30-second delivery template

> _"I'd use DynamoDB here — partition key `<entity_id>`, sort key `<time-ordered ID>`, so the common read is a single-partition Query. For `<the other access pattern>` I'd add a GSI on `<attribute>`, noting it's eventually consistent, which is fine for that path. The `<critical>` write goes through `TransactWriteItems` for atomicity. If write volume grows past a few hundred thousand per second I'd revisit — at that point capacity-unit cost favours self-hosted Cassandra. And is managed AWS acceptable here, or would you prefer vendor-neutral?"_

- ▸ That hits key design, index choice **with its consistency caveat**, transactions, a **cost-based revisit trigger**, and lock-in awareness.

### 10.4 ⚠ Security (skim — one sentence is a full answer)

▸ Encrypted **at rest by default**; **TLS enforced** for all API calls (no configuration). IAM for fine-grained access control; VPC endpoints for private access.

- ⭐ **HI's calibration verbatim:** for sensitive data, mention encryption at rest by default and TLS in transit. **"Beyond this, everything else is probably overkill."**

## 11 · ⭐ Cassandra vs DynamoDB — the decision

> ▸ **They are siblings** — both descend from the 2007 Dynamo paper, and the primary key model is shared 1:1. Feature lists overlap heavily. ⚠ **So the feature list is not what decides it.**

||**Cassandra** (`02e`)|**DynamoDB**|
|---|---|---|
|Ownership|⭐ **open source** — on-prem, any cloud|⚠ **AWS only** (lock-in)|
|Ops burden|⚠ **high** — repairs, compaction tuning, capacity, node additions|⭐ **near zero** — fully managed|
|Storage engine|**LSM tree** — write-optimized, sequential appends|**B-tree** within each partition|
|Topology|⭐ **masterless** — no election gap|**leader per partition** (Multi-Paxos, 2-of-3 quorum) — AWS hides it|
|Transactions|⚠ **none** — single row in a single partition only|⭐ **serializable, up to 100 items, multi-table**|
|Query outside the primary key|⚠ **write a second table** (or SAI)|⭐ **GSI / LSI**|
|Consistency control|per-query, full **ONE → ALL** spectrum|per-request **eventual or strong** (coarser, simpler)|
|Partition size|soft limit — degrades gradually|⚠ **hard 10 GB cap** on LSI partitions; auto-split otherwise|
|Multi-region|native active-active, per-DC replication factor|**Global Tables** (extra cost)|
|⭐ **Cost at very high write volume**|**machines** — much cheaper at scale|⚠ **capacity units** — brutal at millions/sec (§8.3)|

▸ **The honest decision rule — and it is economic, not technical:**

- **DynamoDB** wins on **operational simplicity** and now on **transactions**. Default choice for most designs _if AWS is acceptable_.
- **Cassandra** wins on **cost at very high sustained write volume**, **freedom from AWS**, and **masterless availability**.
- ⭐ **Why Netflix / Discord / Apple run Cassandra:** at their volume, the **machine bill beats the capacity-unit bill by an order of magnitude.** Not a technical superiority argument.

⚠ **Two beliefs from `02e` that must NOT transfer to DynamoDB:**

- **"NoSQL means no ACID"** — false here (§6.2).
- **"No leader, so no election gap"** — false here; DynamoDB has a **leader per partition** (§6.3).
