Bit.ly is a URL shortening service that converts long URLs into shorter, manageable links. It also provides analytics for the shortened URLs.
## 1 · Requirements

### 1.1 Functional (what it does)

▸ **CRUX** — the top 3–4 features only. 

1. ⭐ **Users should be able to submit a long URL and receive a shortened version.**
    - Optional **custom alias** (`short.ly/my-alias`).
    - Optional **expiration date**.
2. ⭐ **Users should be able to access the original URL by using the shortened URL.**

⚠ **Below the line (call out, then park):**

- Auth / account management.
- Click analytics (counts, geo).

▹ **WHY these are below-line:** they add complexity without being core to the _basic_ function. In the room, name them and ask the interviewer whether they're in scope — that itself signals scoping discipline.

### 1.2 Non-functional (how it behaves)

- ⭐ **Uniqueness** — each short code maps to exactly one long URL.
- ⭐ **Low-latency redirect** — < 100ms.
- ⭐ **Availability > consistency** — 99.99% up. ▹ A redirect that's briefly stale is fine; a redirect that's _down_ is not. This ordering justifies caching + replication later.
- ⭐ **Scale** — 1B URLs, 100M DAU.

⚠ **Below the line:** 1. real-time analytics consistency 
2. spam / malicious-URL filtering.

### 1.3 ⭐⭐ The design driver — read:write asymmetry

> ⭐⭐ **State this out loud in the first two minutes. HI treats leading with it as a staff signal.**

- ▸ **~1000 reads : 1 write.** Clicks vastly outnumber creations.
- ⭐ **Everything downstream falls out of this one fact:**
    - **Caching is not optional** — it's the primary read-scaling lever (§5.2).
    - **DB choice is almost free** — writes are trivial (~1/s), so any RDBMS works (§5.3).
    - **Read/write service split** — scale the read path independently and hard (§5.3).
- ⊕ **(not in HI)** This is the same "shape the architecture around the dominant access pattern" move as the read-hot vs write-hot asymmetry in your locked notes — here it's read-hot, so the answer is **duplicate/cache copies for reads**, not partition-for-writes.

## 4 · High-Level Design

> ▸ Build the single-node system that satisfies the FRs first; layer depth via deep dives after. Three components: **Client → Primary Server → Database.**

### 4.1) Users should be able to submit a long URL and receive a shortened version — create flow (`POST /urls`)

```
Client ──POST /urls──► Primary Server ──► Database
                          │
                          ├─ 1. validate long URL (is-url / regex)
                          ├─ 2. generate short code   (§5.1 — magic for now)
                          ├─ 3. insert {code, long_url, expiry} 
                          └─ 4. return short_url
```

1. **Validate** the long-URL format.
2. **Generate** the short code — abstracted here; the _how_ is DD1 (§5.1).
3. **Custom alias:** if supplied, validate it's free, use it directly as the code.
4. **Insert** the mapping, **return** the short URL.

⚠ **Custom-alias collision trap (staff-tier detail):** a user-chosen alias could collide with a future _counter-generated_ code.

- **Fix:** put generated codes and custom aliases in **separate namespaces**,
- **or** prefix generated codes with a character custom aliases can't use.

⊕ **(not in HI) — the fintech-relevant idempotency note:** HI mentions optional **dedup** (same long URL → return existing code) but flags that most shorteners _allow_ multiple codes per URL (different expiries/analytics/aliases). ⭐ The transferable lesson: dedup is a **deliberate tradeoff of storage-efficiency vs per-mapping independence** — the same call you make when deciding whether a payment/order create is idempotent on a natural key. Name it as a tradeoff, don't default either way.

### 4.2) Users should be able to access the original URL by using the shortened URL — redirect flow (`GET /{short_code}`)

1. Browser sends `GET /abc123`.
2. Server looks up `abc123` in the DB.
3. Found **and not expired** → retrieve long URL → send redirect.
4. **Expired** → `410 Gone` (§4.2b).

#### 4.2a ⭐ 301 vs 302 — the redirect status decision

> ⭐ A named, defensible choice here is easy points. HI: for a URL shortener, **prefer 302.**

|Axis|301 Permanent|⭐ 302 Found (preferred)|
|---|---|---|
|Browser caches it?|**Yes** — future hits skip our server|**No** — every hit returns to us|
|Control over the link|⚠ Lost once cached (can't expire/change)|Retained — can expire/update/delete|
|Analytics|⚠ Missed (hits bypass us)|Captured (every hit is seen)|
|Server load|Lower (browser shortcuts)|Higher (all traffic returns)|

- ▸ **Why 302 wins here:** control + expiry + analytics all depend on the request _coming back to us_. The extra load is exactly what caching/CDN (§5.2) exists to absorb.
- ▹ **The one-liner:** _"302, because we need to retain control over the link — expiry, deletion, click tracking — and 301's browser caching would take that away. The extra load is handled by our cache layer."_

#### 4.2b Expiration handling

- ▸ On read, compare `now` to the stored expiry → expired ⇒ **`410 Gone`** (semantically correct: it _existed_ and is deliberately gone, vs `404`).
- **Cleanup:** a periodic background job deletes expired rows (or just leave them — they're cheap).
- ⭐ **The detail that scores:** set **cache TTL ≤ URL expiry** so stale entries **self-evict** and you never redirect to an expired mapping from cache. Ties the cache lifecycle to the data lifecycle — an easy staff-flavored nod.

### 1) How can we ensure short urls are unique? ⭐⭐

> ⭐⭐ **The heart of the problem and the biggest new-content section for you.** The hash-vs-counter articulation _without prompting_ is the senior line.

**Constraints (they conflict — that's the whole dive):**

1. **Unique** — no two long URLs share a code.
2. **Short** — it's a URL _shortener_.
3. **Efficiently generated** — cheap, high-throughput.

⭐ **The tension to name aloud:** more entropy → fewer collisions → _longer_ codes. You can't max all three; every solution below sits somewhere on that tradeoff.

#### ⚠ Bad Solution — Long URL prefix

- **Approach:** take the first N chars of the long URL as the code.
- ⚠ **Challenges:** any two URLs sharing a prefix (`linkedin.com/in/evan…` vs `linkedin.com/in/stefan…`) collapse to the same code → the redirect is ambiguous → **fails uniqueness immediately. Dead on arrival.** (HI includes it only to motivate needing _entropy_.)

**Why climb:** the prefix has no entropy, so collisions are guaranteed. We need randomness — enter the hash.

#### Great Solution — Hash function (SHA-256 → base62)

- **Approach:** hash the (canonicalized) long URL with SHA-256 → base62-encode → take the first **N** chars (N≈8 → 62⁸ ≈ **218 trillion** codes).

```
canonical = canonicalize(long_url)   # lowercase host, strip default port, normalize trailing slash
h         = sha256(canonical)
code      = base62_encode(h)[:8]
```

> ⚠ **Confusion resolved — base62 doesn't shorten; truncation (`[:8]`) does. And why 8?**
> 
> - ⚠ **WRONG:** base62 is what shrinks the hash down to something short.
> - ⭐ **CORRECT:** base62 barely shrinks it — **truncation (`[:8]`) is what makes it short.** Walk the sizes:
>     - SHA-256 output = **256 bits** = 32 bytes = **64 hex characters**.
>     - base62-encoding the _full_ 256-bit number gives ≈ **43 characters** (256 ÷ log₂62 ≈ 43). So base62 only takes you 64 hex chars → ~43 chars. It's a **representation change** (into URL-safe characters), _not_ a big shrink.
>     - ~43 chars is a terrible "short" URL → so we **chop it: `[:8]`** — keep the first 8, discard the other ~35.
> - ⭐ **The consequence:** throwing away ~35 chars of entropy shrinks the namespace from 62⁴³ down to 62⁸ — and _that_ truncation is precisely why collisions become possible (hence the `UNIQUE` + retry below). ⭐ **base62 = url-safe representation; `[:8]` = the actual shortening, and also the source of the collision risk.**
> - **Why 8 (not 9)?** ⭐ **8 is a chosen knob, not a derived constant** — a balance between the two competing constraints:
>     - Each char = 1 of 62 → 8 chars → **62⁸ ≈ 218 trillion** codes. That's the namespace size.
>     - `[:9]` → 62⁹ ≈ 13.5 quadrillion (bigger namespace) but a **longer** URL. It's a _shortener_, so pick the smallest N with comfortable headroom.
>     - At ~1B URLs, 218T slots is ~200,000× what we'll fill → collisions stay rare. **7 is tighter (62⁷≈3.5T, still fine); 6 gets risky at 1B.** 8 = short enough, safe enough.

- ⭐ **Why base62?** a-z + A-Z + 0-9 = 62 chars. **Not** base64 because `+` and `/` are unsafe in URLs (`/` is a path separator, `+` decodes to a space in query strings).
- ▹ **Deterministic** — same URL → same code with no DB read. Good for **dedup**; bad if you _want_ multiple codes per URL or need to prevent guessability → then add a **secret salt / HMAC**.
- ⚠ **Challenges:**
    - **Collisions are still possible.** With code-space size `|S|` and `n` codes already used, the next code collides with probability **`n / |S|`** — grows with scale, eventually non-negligible.
        - ▹ **Notation:** `|S|` = the bars mean **"size of set S"** (cardinality) → total possible codes = 62⁸ ≈ 218T. `n` = codes **already used.** So `n / |S|` = used ÷ total = the chance a fresh random code lands on a taken one. _E.g._ n=1B, |S|=218T → ≈ **0.0000046** (tiny); as `n` → `|S|`, the fraction rises → collisions likely.
    - **Fix — the standard pattern:**
        - `UNIQUE` constraint on the short-code column (DB is the final arbiter).
        - On insert failure, **retry with a bounded cap** (3–5 attempts), adding a random salt each time.
        - Exceed the cap → error or fall back.
    - ⚠ **Cost:** each insert may now cost extra DB round-trips (collision check + retry) → latency + complexity on the _write_ path.

**Why climb:** the hash _tolerates_ collisions and pays for them with retries. Can we eliminate collisions entirely? Yes — with a counter.

#### ⭐ Great Solution — Unique counter with base62

- **Approach:** keep a global counter; each new URL takes the next value; base62-encode it. **Uniqueness is guaranteed by construction — zero collision checks.**
- ⭐ **Redis is the natural home:** single-threaded + atomic `INCR` (`02a`) → two concurrent creates _always_ get distinct values (one gets 1000, the other 1001). No race, no lock.

> ⚠ **Confusion resolved — the counter does NOT touch the long URL, does NOT hash, does NOT truncate.**
> 
> - ⚠ **WRONG:** long URL + counter → concatenate → SHA-256 → base62 → `[:8]`.
> - ⭐ **CORRECT:** the entire code-generation is just:
>     
>     ```
>     counter value:  1,000,000,000        (the next integer)base62_encode(1000000000) = "15ftgG"  (6 chars — done)
>     ```
>     
>     - **Is the long URL involved?** ⭐ **No.** It's only _stored in the DB_ as the value the code maps to — it is **not** an input to the generator. The generator's only input is the next integer.
>     - **Do we SHA it?** No. **Concatenate anything?** No.
>     - **Do we slice `[:8]`?** ⭐ **No — the elegant part.** We base62-encode the _raw counter integer_, which is **already short** (1B → 6 chars) and **already unique** (the counter never repeats). Nothing to truncate.
> - ⭐ **Why hash needs truncation but counter doesn't:** the hash starts _huge_ (a 256-bit digest → ~43 chars) so you must chop it and eat collision risk; the counter starts _small_ (a plain integer) so base62 alone is already short **and** unique. You pay instead with the need to **coordinate one global counter** across all write servers (→ DD3).
> 
> ||Hash approach|⭐ Counter approach|
> |---|---|---|
> |Input to generator|the long URL|just the next integer|
> |Transform|SHA-256 → base62|base62 only|
> |Size before shortening|~43 chars (huge, fixed)|already ~6 chars (grows slowly)|
> |Truncate `[:8]`?|**Yes** — 43 is too long|**No** — already short|
> |Collisions?|**Yes** (truncation kills entropy) → `UNIQUE` + retry|**None** — unique by construction|
> |Cost of the guarantee|—|needs one global counter (coordination)|

- ⚠ **Challenges:**
    - **Distributed coordination** — every write-service instance must agree on the counter. ⭐ **This is the real scaling problem → resolved in DD3** (Redis + batching).
    - ⚠ **Predictable codes** — a sequential counter → enumerable codes → an attacker walks `1,2,3…` and discovers every URL.
        - **Fix:** apply a reversible transform (XOR with a secret key) before base62.
        - **Or:** accept it — short URLs are usually meant to be shared publicly anyway. (State the tradeoff; don't silently ignore it — that's the staff move.)
    - ⚠ **Code length grows** as the counter climbs — but the math shows it's a non-issue:
        - **1,000,000,000 (1B) in base62 = `'15ftgG'` → just 6 characters.**
        - 62⁶ ≈ **56 billion** → 6 chars covers well past 1B.
        - Cross 56B → move to **7 chars** → 62⁷ ≈ **3.5 trillion**.
        - ⭐ **Carry `1B → 6 chars` and move on.** Length never bites the counter approach.

#### ⭐ Verdict — the room decision

|Axis|Hash (SHA-256 → base62)|⭐ Counter + base62|
|---|---|---|
|Uniqueness|Probabilistic → needs collision handling|**Guaranteed by construction**|
|Write-path cost|⚠ Collision check + retries|Cheap (one atomic `INCR`)|
|Distributed coordination|None needed (stateless)|⚠ Needs a shared counter (DD3)|
|Code predictability|Unguessable (good)|⚠ Sequential → enumerable (mitigate w/ XOR)|
|Dedup for free?|Yes (deterministic)|No|

- ▸ **Commentary:** neither is strictly better — they trade **coordination-free-but-collision-prone** against **collision-free-but-needs-coordination.** ⭐ **The counter is the more common interview answer** because it makes uniqueness trivial and the coordination cost is solvable cleanly with Redis (DD3). **Pick counter, name the enumeration risk + fix, and carry the coordination question into scaling** — that sequence _is_ the senior signal.

### 2) How can we ensure that redirects are fast? ⭐

> ⭐ Straight application of the **Scaling Reads pattern (`03d`)** — this whole dive is "you already know this."

#### Good Solution — Add an index `(re-run — 01d)`

- **Approach:** without an index, lookup = **full table scan** (O(n)) over billions of rows. Add a B-tree index on the short-code column → **O(log n)**. Better: make the **short code the primary key** → index + uniqueness in one. (You own B-trees from `01d`.)
- ⚠ **Challenges — why an index alone isn't enough (the capacity math to cite):**
    - 100M DAU × 5 redirects/day = **500M redirects/day**.
    - 500M ÷ 86,400s ≈ **~5,800 rps** average.
    - Traffic isn't flat → **×100 for peak** ≈ **~600k rps**.
    - ⚠ A single disk-backed DB (~100k IOPS on SSD) **can't serve 600k rps.** This is the number that motivates caching.

**Why climb:** disk I/O caps out well below peak. To go faster we have to leave disk — enter memory.

#### ⭐ Great Solution — In-memory cache (Redis / Memcached) `(re-run — 01e / 02a)`

- **Approach:** cache short-code → long-URL between server and DB. Hit → serve from RAM; miss → DB → populate cache.
- ⭐ **The latency ladder (`01i`) — why this works:**

|Tier|Access time|Throughput|
|---|---|---|
|Memory|~100 ns (0.0001 ms)|millions/s|
|SSD|~0.1 ms|~100k IOPS|
|HDD|~10 ms|~100–200 IOPS|

- ⭐ Memory is **~1,000× faster than SSD**, **~100,000× faster than HDD.** With a 1000:1 read ratio, the cache absorbs essentially all redirect traffic.
- ⚠ **Challenges:**
    - **Invalidation** — mostly a non-issue here (URLs rarely change), _except_ expiry → handled by TTL ≤ expiry (§4.2b).
    - **Cold start / warm-up** — early misses hit the DB until populated.
    - **Eviction** — bounded memory → **LRU** is the natural policy (hot links stay).

**Why climb:** a central cache is fast but still one round-trip from the user's region. For popular links we can go one hop further — to the edge.

#### ⭐ Great Solution — CDN + edge compute

- **Approach:** serve the short-URL domain via a **CDN** with global PoPs; cache mappings at the edge. Popular codes redirect **at the edge (Cloudflare Workers / Lambda@Edge)** — never reaching the origin server.
- ⭐ **Payoff:** for hot links, the redirect happens close to the user → big latency cut + origin offload.
- ⚠ **Challenges:**
    - Cache invalidation + consistency across all CDN nodes is complex.
    - Edge setup needs extra config + understanding of serverless functions at the edge.
    - Cost — CDNs and edge compute can be pricier, especially at high traffic volumes.
    - Edge functions have limits on execution time, memory, and available libraries → the redirect logic must be carefully optimized.
    - Debugging + monitoring a distributed edge environment is harder than centralized servers.
    - ▸ **Commentary:** you're trading cost + complexity for latency — worth it only if traffic/latency demands justify it. **Mention as the next lever; don't reach for it by default.**

### 3) How can we scale to support 1B shortened URLs and 100M DAU? ⭐

> ▸ Most of the work is done (cache handles reads). This dive is **write-side scaling + the counter coordination** deferred from DD1. ⚠ **Note:** HI writes this dive as **prose, not Bad/Good/Great** — there's no ladder of competing solutions here, just a sequence of scaling concerns. So no solution labels below.

#### Database size — is it even a problem? (spoiler: no)

- Row ≈ short code (8) + long URL (100) + created (8) + alias (100) + expiry (8) ≈ **~200 bytes** → round to **500 bytes** for metadata slack.
- 500 bytes × 1B rows = **500 GB.** ⭐ **Comfortably one modern SSD / one Postgres instance.** Shard _only_ if you hit a hardware wall (`01f`) — not now.

#### Which database? — almost free

- ⭐ Writes ≈ **100k/day ≈ ~1/s.** Reads offloaded to cache. So **any** RDBMS works — Postgres / MySQL / DynamoDB.
- ▹ **HI's advice:** pick what you know. No hands-on preference → **Postgres.** (For you: say Postgres — it's your stack.)

#### Availability — what if the DB dies? `(re-run — 02g)`

- **Replication** — Postgres replicas; failover to a replica if the primary dies. ⚠ Adds routing complexity (which replica, replication lag).
- **Backup** — periodic snapshots to separate storage. ⚠ Recovery, not live failover.
- ▹ Both from `02g`; name replication as the primary HA lever given the availability > consistency NFR.

> ⚠ **Confusion resolved — replication vs backup (they defend different failure modes).**
> 
> - **The one-liner:** ⭐ **replication = continuous _live_ synced copies** (real queryable DBs, seconds behind); ⭐ **backup = a _periodic point-in-time snapshot_** dumped to cheap storage (S3), cold + offline + not directly queryable — to use it you **restore** it (slow).
> - ⚠ **WRONG:** backup ≈ hot standby. ⭐ **CORRECT:** a **hot standby is a _replication_ concept** (a live replica ready to promote the instant the primary dies), not a backup one. Backup is the opposite of "hot" — a frozen snapshot in object storage.
>     - hot / warm standby, read replica → **replication family**
>     - nightly/periodic snapshot to S3 → **backup family**
> 
> ||Replication|Backup|
> |---|---|---|
> |What it is|live synced copies|point-in-time snapshot|
> |Freshness|seconds behind (or 0)|hours/days old|
> |Queryable directly?|yes (it's a live DB)|no — must restore first|
> |Recovery speed|fast (promote a replica)|slow (restore + replay)|
> |Node/hardware failure (server dies)|✅ yes|⚠ yes, but slowly|
> |⭐ Logical corruption (bad `DELETE`, buggy migration, ransomware)|❌ **NO**|✅ **yes**|
> |Also gives read scaling|✅ yes (serve reads off replicas)|❌ no|
> 
> - ⭐ **The killer row is logical corruption.** A bad `DROP TABLE` or migration is **replicated to every replica in milliseconds** → all live copies are equally broken. Only a **backup** lets you rewind to _before_ the mistake. ⭐ **That's why prod runs both:** replication protects against _machines_ failing; backup protects against _you / your code_ failing.
> - ▹ **Sync vs async is a knob _within_ replication** (not the replication-vs-backup axis):
>     - **Synchronous** — primary waits for the replica to confirm before acking → stronger durability, zero data loss on failover, higher write latency.
>     - **Asynchronous** — primary acks immediately, replica lags slightly → lower latency, but failover can lose the last few unreplicated writes.
> - ⭐ **For this system:** they're **not** either/or — replication is the **primary HA lever** (matches `availability > consistency` _and_ doubles as the read-scaling mechanism the whole design leans on), and since we ordered availability over consistency, **async replication** is the natural fit. Backup earns one sentence as the corruption/disaster backstop, but **lead with replication.**

#### ⭐ Read/write service split

- ▸ Given the asymmetry (§1.3), split the Primary Server into a **Read Service** (redirects) and a **Write Service** (creates). **Scale each independently** — the read tier scales hard, the write tier barely at all.
- ▹ Horizontal scaling = more instances, requests randomly routed. Standard.

#### ⭐⭐ The counter coordination problem (the DD1 cliffhanger)

- ⚠ **Problem:** horizontally-scaled write instances each generating codes → they need **one source of truth** for the counter, or two instances mint the same value.
- ⭐ **Fix:** a **centralized Redis** counter. Every write instance calls atomic `INCR` → guaranteed-distinct values across all instances (`02a`).

⚠ **"Isn't a Redis round-trip per write expensive?"** — no (network is fast, writes are ~1/s), **but** the clean optimization is **counter batching:**

```
Write instance ──INCRBY 1000──► Redis   (Redis atomically jumps counter +1000, returns range start)
Write instance uses 1000 values LOCALLY, no Redis contact
   └─ exhausted → request next batch
```

- ⭐ **Payoff:** ~1000× fewer Redis calls, uniqueness still guaranteed (ranges are disjoint).
- ⚠ **Accepted cost:** if an instance dies mid-batch, its unused values are **lost** (gaps in the sequence). **Fine** — we need _uniqueness_, not _continuity_.

#### ⭐ Multi-region + Redis failover (staff-tier, mention unprompted)

- ⭐ **Multi-region counters:** give each region a **disjoint range** (region A: 0–1B, region B: 1B–2B). Writes hit the local Redis; **no cross-region coordination.** Reads served globally via distributed cache/CDN (DD2).
- **Redis HA:** Redis Sentinel / Cluster with automatic failover. A single Redis does 100k+ ops/s — far beyond our write rate, especially with batching.
- ⭐ **The safety net:** even if Redis loses its latest counter on failover, we only lose _uniqueness-irrelevant_ values; the DB's **`UNIQUE` constraint on short_code is the ultimate backstop.** ⭐ **Naming this failover story unprompted is exactly the staff signal from the rubric.**
