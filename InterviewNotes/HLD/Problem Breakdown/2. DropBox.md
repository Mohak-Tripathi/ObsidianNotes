## 1 · Requirements

### 1.1 Functional (what it does)

1. ⭐ **Users should be able to upload a file from any device.**
2. ⭐ **Users should be able to download a file from any device.**
3. ⭐ **Users should be able to share a file with other users and view files shared with them.**
4. ⭐ **Users can automatically sync files across devices.**

⚠ **Below the line:**

- edit files
- view files without downloading
- (blob storage _itself_ is a separate design problem — out of scope)

### 1.2 Non-functional (how it behaves)

1. ⭐ **Highly available** — availability > consistency.
2. ⭐ **Support files up to 50GB.** (This single number drives the entire large-files deep dive.)
3. ⭐ **Secure + reliable** — recover files if lost/corrupted.
4. ⭐ **Low latency** — upload / download / sync as fast as possible.

⚠ **Below the line:**

- per-user storage limits
- file versioning
- virus/malware scanning

### 1.3 ⭐ The CAP call — why availability > consistency here

> ⭐ HI flags that **candidates struggle with this trade-off.** Nail the reasoning, don't just assert it.

- ▸ **The rule:** choose **consistency over availability _only_ when every read must see the most recent write**, or the system breaks.
- **Counter-example (needs consistency):** a stock-trading app — buy AAPL in Germany, then someone buys in the US → the first txn _must_ be replicated before the second proceeds.
- ⭐ **Dropbox (needs availability):** if a user in Germany uploads a file and a US user can't see it for a few seconds, **that's fine.** No correctness violation. → **availability wins** (`01h`).

## 3 · API

▸ One endpoint per functional requirement. ⚠ **Flag up front that these will evolve** — the upload/download APIs change significantly once presigned URLs enter (say so to the interviewer).

```
POST /files                          { File, FileMetadata }        # upload (evolves → presigned)
GET  /files/{fileId}                 -> File & FileMetadata        # download (evolves → presigned)
POST /files/{fileId}/share           { User[] }                    # share
GET  /files/changes?since={ts}       -> ChangeEvent[]              # sync: pull changes since last sync
```

- ▸ **`ChangeEvent`** = `{ fileId, changeType (created/updated/deleted), updated metadata }`. The `since` timestamp fetches only what changed → efficient sync.
- ⭐ **User info goes in headers** (session token / JWT), **never the request body** — body is client-manipulable. Auth + authz at the gateway.

## 4 · High-Level Design

### 4.1) Users should be able to upload a file from any device

▸ Two storage questions: **(1) where do the raw bytes go?** and **(2) where does the metadata go?**

- **Metadata → DynamoDB** (or Postgres — HI says don't agonize; loosely structured, few relations, query = "files by user"). ▹ `02f` / `02g`.

```
{ "id": "123", "name": "file.txt", "size": 1000, "mimeType": "text/plain", "uploadedBy": "user1" }
```

- **Bytes → the three-solution ladder below.**

#### ⚠ Bad Solution — Upload to a single server

- **Approach:** `POST /files` accepts the file, stores it on the server's local filesystem, saves metadata in the DB.
- ⚠ **Challenges:**
    - Doesn't scale — storage grows unbounded → constantly add disk / horizontally scale.
    - Not reliable — server dies → all files inaccessible.

**Why climb:** storage + reliability are already solved by blob storage. Use it.

#### Good Solution — Store file in Blob Storage (S3 / GCS)

- **Approach:** client uploads to backend → backend forwards bytes to **Blob Storage** (S3), saves metadata in DB. Virtually unlimited, reliable, gets lifecycle + versioning features for free.
- ⚠ **Challenges:**
    - More complex — must handle the **partial-failure** case (file uploaded but metadata not saved, or vice-versa) → use a transactional approach (only commit metadata if the upload succeeded). ▹ `03c`.
    - ⚠ **Uploads the file _twice_** — once client→backend, once backend→S3. Redundant + slow.

**Why climb:** kill the double-upload by letting the client hit S3 directly.

#### ⭐ Great Solution — Upload directly to Blob Storage (presigned URL)

- **Approach:** client uploads **straight to S3**, bypassing the backend for bytes. Backend only issues a **presigned URL** and records metadata. Faster + cheaper (no double transfer).
- ⭐ **Presigned URL** = a time-limited, permission-scoped URL to write to a specific S3 location. Generating it is a **purely local** operation — the backend signs with its AWS credentials, **no call to S3**.
- ▸ **The upload becomes a 3-step flow:**

```
1. POST /files/presigned-url  { FileMetadata }  -> PresignedUrl
   (backend saves metadata with status="uploading")
2. Client PUTs the file bytes directly to the presigned URL (→ S3)
3. S3 fires an S3 Event Notification → backend updates metadata status="uploaded"
```

- ⭐ **Challenges / pattern:** this is the **Handling Large Blobs** pattern (`03f (pending)`) — bypass app servers for data transfer, sign URLs for security, chunk for reliability (→ DD1).

### 4.2) Users should be able to download a file from any device

#### ⚠ Bad Solution — Download through the file server

- **Approach:** backend downloads the file from S3, then streams it to the client.
- ⚠ **Challenges:** downloads the file **twice** (S3→backend, backend→client) → slow + expensive. (Mirror of the upload double-transfer.)

**Why climb:** let the client pull straight from S3.

#### Good Solution — Download from Blob Storage (presigned URL)

- **Approach:** backend issues a **presigned download URL**; client GETs the bytes directly from S3.

```
GET /files/{fileId}/presigned-url -> PresignedUrl   → client downloads direct from S3
```

- ⚠ **Challenges:** S3 lives in **one region** → users far away get slow downloads. Fix with a CDN.

**Why climb:** cache the bytes near the user.

#### ⭐ Great Solution — Download from CDN

- **Approach:** put a **CDN** (CloudFront) in front. On first request (miss) the CDN fetches from S3; subsequent requests (hit) serve from the nearest edge → big latency cut. ▹ `01a`/`01e`.
- ▸ **Security:** issue a **CDN signed URL** (same idea as the S3 presigned URL) — time-limited access. (→ DD3.)
- ⚠ **Challenges:**
    - CDNs are expensive → be strategic about **what** is cached and for **how long**.
    - Use `Cache-Control` headers to bound TTL.
    - Use cache invalidation to evict updated/deleted files.
    - Net effect: only frequently-accessed files stay cached; rarely-accessed files don't burn money.

### 4.3) Users should be able to share a file with other users and view files shared with them

▸ Share by email (like Google Drive); users already authenticated. ⭐ **The interview angle: make "list files shared with me" fast.**

#### ⚠ Bad Solution — Sharelist on the file metadata

- **Approach:** add `"sharelist": ["user2","user3"]` to each file's metadata. Share → append; download → check membership.
- ⚠ **Challenges:**
    - "My own files" is easy (index on `uploadedBy`).
    - ⚠ "Files shared **with** me" is **slow** — you'd have to scan every file's sharelist to find the ones containing this user.

**Why climb:** we need the inverse mapping (user → files).

#### Good Solution — Cache the inverse mapping

- **Approach:** alongside the sharelist, cache `user → [fileIds shared with them]` so "shared with me" is a single key lookup.

```
user1 : ["fileId1", "fileId2"]
```

- ⚠ **Challenges:** the cache must stay in sync with the per-file sharelist → keep both in the **same DB** and update them in **one transaction**.

**Why climb:** normalize it away so there's nothing to keep in sync.

#### ⭐ Great Solution — Separate `SharedFiles` table

- **Approach:** a normalized table mapping `userId → fileId` (one row per share). "Shared with me" = query rows where `userId = me`. The per-file sharelist disappears entirely (nothing to sync). ▹ `01c`.

```
| userId (Partition Key) | fileId (Sort Key) |
| user1                  | fileId1           |
| user1                  | fileId2           |
| user2                  | fileId3           |
```

- ▸ **Composite primary key** `(userId, fileId)` — DynamoDB: partition key + sort key; SQL: composite PK.
- ⚠ **Challenges:** slightly less efficient than a pure key-value cache hit (index query vs single lookup), but the trade-off is worth it — **no sync burden.**

### 4.4) Users can automatically sync files across devices

▸ Keep a copy on each client **and** in the cloud (source of truth = remote). Two directions:

**Local → Remote** (a client-side **sync agent**):

- Watches the local folder via OS file-system events (FileSystemWatcher / FSEvents).
- On change, queues the file for upload locally.
- Uploads via the normal upload API + updated metadata.
- ⭐ **Conflict resolution = last-write-wins** (most recent edit saved). ▹ Versioning (out of scope) would add a new file/chunks + version pointer rather than overwrite.

**Remote → Local** (client must learn about remote changes):

|Approach|How|Trade-off|
|---|---|---|
|**Polling**|client periodically asks "changed since `t`?"|⚠ simple but slow to detect + wastes bandwidth when nothing changed|
|**WebSocket / SSE**|server holds an open connection, pushes change events|real-time but more complex|

- ⭐ **HI's answer = hybrid** (▹ `03a`): **one** WebSocket/SSE connection **per device/session** (not per file). Server pushes change events in real-time; the client **also polls every few minutes** (`GET /files/changes?since=t`) as a safety net for dropped connections / missed messages.
- ⭐ **Why hybrid:** push gives near-instant sync; polling guarantees **eventual consistency** even if the socket drops. Best of both.

### 4.5 Tying it together — the components

- **Uploader / Downloader** — the clients (web/mobile/desktop). Also run the sync agent (detect local changes, pull remote changes).
- **LB & API Gateway** — routing, SSL termination, rate limiting, request validation. ▹ `02d`.
- **File Service** — the **control plane**: reads/writes metadata, generates presigned URLs (locally, via the S3 SDK). ⭐ **Never touches file bytes.**
- **File Metadata DB** — file metadata + the `SharedFiles` table (permission enforcement).
- **S3** — the actual bytes; clients upload/download direct via presigned URLs.
- **CDN** — caches files at the edge; download uses a **CDN signed URL** (miss → fetch from S3, hit → serve from edge).

> ⭐ Same rhythm as `05a`: each dive walks **Bad → Good → Great** where HI does, every solution has **Approach + Challenges**, and the weaker solution's challenges motivate the next. DD1 is the meat.

### 1) How can you support large files? ⭐⭐

> ⭐⭐ **The heart of the problem.** Two UX insights drive everything:
> 
> - **Progress indicator** — users must see upload progress.
> - **Resumable uploads** — a dropped connection at 49/50GB must **not** restart from zero.

#### The limitations of a single POST (why we must chunk)

- ⚠ **Timeouts** — a 50GB file over one POST blows past server/client timeouts.
    - ⭐ **The math to do aloud:** `50GB × 8 bits/byte ÷ 100 Mbps = 4000 s`; `4000 ÷ 3600 ≈ 1.11 hours`. Way too long for one request.
- ⚠ **Payload limits** — browsers/servers cap request size. **Amazon API Gateway hard-caps at 10MB** (can't be raised). A 50GB POST is simply impossible.
- ⚠ **Network interruptions** — one drop → restart the whole 50GB.
- ⚠ **No progress visibility** — user stares at a spinner for an hour.

> ⚠ **Confusion resolved — the 10MB API Gateway cap does NOT gate file size. Bytes bypass the gateway entirely.**
> 
> - ⚠ **WRONG:** the 10MB limit is the decision boundary — under 10MB upload one way, over 10MB chunk.
> - ⭐ **CORRECT:** in the presigned design the **file bytes never pass through API Gateway** → the 10MB cap is **irrelevant to file size for every file.** Trace the flow:
>     - **Control-plane calls** (request presigned URL, PATCH chunk status, complete) → hit the backend/gateway → tiny JSON, always <10MB.
>     - **File bytes** → client `PUT`s **directly to S3** → ⭐ **does not touch API Gateway.** S3 has its own limits, not the 10MB one.
>     - So 10MB only ever mattered in the **Bad/Good** solutions (bytes routed through the backend). Direct-to-S3 removes it as a gate — a 4MB file and a 50GB file **both** go straight to S3.
> - ⭐ **The real decision axis is single-shot `PUT` vs S3 multipart — both direct to S3.** The threshold is set by **S3, not API Gateway:**
> 
> |S3 fact|Value|
> |---|---|
> |Max size for a single `PUT`|**5 GB**|
> |Multipart **required** above|**5 GB**|
> |AWS **recommends** multipart above|**~100 MB**|
> |Part size / count|5MB–5GB each, ≤ 10,000 parts|
> 
> - ⭐ **The 4MB file (concrete answer):** client → S3 via **one single presigned `PUT`.** No server hop, no chunking, no multipart. Chunking a 4MB file is pure overhead (no resumability worth having, no progress bar anyone needs). ⭐ **Small file = single-shot presigned PUT; large file = multipart.** The client knows the size upfront, so it picks the path.
> - ▸ **Two endpoints, or one that branches** — both seen in practice:
>     
>     ```
>     SMALL:  POST /files/presigned-url      -> one presigned PUT URL → client PUTs whole fileLARGE:  POST /files/multipart/initiate -> uploadId + per-part presigned URLs        ... client PUTs each part + PATCHes ETag ...        POST /files/multipart/complete -> backend calls S3 CompleteMultipartUpload
>     ```
>     
>     - **(a)** two distinct endpoints (explicit), or **(b)** one "initiate upload" endpoint that takes file size in metadata and **branches internally** (cleaner surface). Either is defensible — just say _"I'd branch on size."_
>     - ⭐ In practice the AWS SDK (`@aws-sdk/lib-storage` `Upload`, or Java `TransferManager`) auto-switches to multipart above a configurable threshold — **but be able to explain the mechanism yourself, don't just say "the SDK handles it."**
> - ⚠ **Terminology trap — two different "multipart"s:**
>     - `multipart/form-data` = an HTTP _content-type_ for browser form submissions. **NOT this.**
>     - ⭐ **S3 Multipart Upload** = S3's _chunked upload API_ (`CreateMultipartUpload` → `UploadPart` → `CompleteMultipartUpload`). **This** is "chunking." The small-file path is a single presigned `PUT` to S3 — not "multipart/form-data to the server."
> - ⭐ **The decision tree to carry:**
>     1. Bytes **always** go client → S3 direct (all sizes). Gateway 10MB cap never applies to bytes.
>     2. Pick the S3 path by size (known upfront): **small (≲100MB)** → single presigned `PUT`; **large (≳100MB, mandatory >5GB)** → S3 multipart + per-part presigned URLs.
>     3. Only the **large** path gets chunking / progress / resumability / per-chunk fingerprint.

▸ **The fix = chunking:** break the file into **5–10MB pieces**, upload them one at a time or in parallel.

- ⚠⚠ **Chunk on the CLIENT, never the server.** Chunking server-side means you already uploaded the whole file to reach the server — defeats the entire purpose. **HI calls this a very common fatal mistake.**
- ⭐ Progress bar = track per-chunk completion. Resumability = persist which chunks are done.

▸ **Persist chunk state in `FileMetadata`:**

```
{ "id":"123", ..., "status":"uploading",
  "chunks":[ {"id":"chunk1","status":"uploaded"},
             {"id":"chunk2","status":"uploading"},
             {"id":"chunk3","status":"not-uploaded"} ] }
```

On resume → read `chunks` → upload only the missing ones. **But how does `chunks` stay truthful?** → the Bad/Good ladder:

#### Good Solution — Update chunk status via client PATCH

- **Approach:** client uploads each chunk to S3, gets a success, then `PATCH /files/{fileId}/chunks` to mark it uploaded.

```
PATCH /files/{fileId}/chunks   { "chunks":[ {"id":"chunk1","status":"uploaded"} ] }
```

- ⚠ **Challenges:** you're **trusting the client.** A malicious user can PATCH all chunks "uploaded" without uploading → corrupt/inconsistent state (only their own file, but still hard to debug). **Security risk.**

**Why climb:** don't take the client's word — verify server-side.

#### ⭐ Great Solution — Server-side chunk verification (ETags, "trust but verify")

- **Approach:** each S3 chunk upload returns an **ETag**; client includes ETags in the PATCH; backend **verifies via S3's `ListParts` API** before marking the file complete.
- ▸ S3 event notifications only fire on the **completed** multipart object, not per part → `ListParts` is how you check part status mid-upload.
- ⭐ **Trust but verify:** accept client updates for **real-time progress** (good UX), but **verify server-side** before finalizing. ⭐ **This is the fintech-transferable pattern** — never let the client assert a state you can't independently confirm.

#### ⭐ Fingerprinting — dedup + resumability

- ▸ On resume, two questions: **(1) have I uploaded this file before?** and **(2) which chunks are done?**
- ⚠ **Can't use the filename** — two users (or one user twice) can upload different content with the same name.
- ⭐ **Use a fingerprint** — a **SHA-256 hash of the file's content** → a unique content identifier independent of name/source. ▹ **Same primitive as `05a §DD1`, opposite purpose:** there SHA-256 → _shorten_; here SHA-256 → _identify/dedup_.
- ⚠ **Fingerprint = content identity, not the record.** Two users uploading identical content get the **same** fingerprint. So: `fileId` = a UUID (the record); `fingerprint` = a **separate field** used for dedup + resumability.
- ▸ **Chunk-level fingerprints too** — fingerprint each chunk so you can tell exactly which parts already transmitted.

▸ **The full large-upload flow (tie it together):**

1. **Client** chunks the file into parts (5–10MB) + fingerprints each chunk **and** the whole file. ⭐ **The client splits the bytes** — the backend never sees file content.
2. Client asks: does a file with this fingerprint already exist for me? If yes + `status="uploading"` → resume by fetching existing chunk statuses.
3. If new → client POSTs to init a multipart upload (sends fingerprint + size + **part count**) → backend calls S3 `CreateMultipartUpload` (gets `uploadId`), **decides how many parts and issues one presigned URL per part number** (all N at once, default), saves metadata `status="uploading"`, returns `uploadId` + the N presigned URLs. ▹ Backend works with **part numbers**, not bytes.
4. Client uploads each chunk directly to S3 via its presigned URL → S3 returns an **ETag** per part → client PATCHes `{ partNumber, ETag }` → backend verifies via `ListParts` → marks that chunk "uploaded".
5. When all chunks "uploaded" → backend calls S3 `CompleteMultipartUpload` (part numbers + ETags) → S3 assembles the object and **responds success in that same synchronous call** → backend updates metadata `status="uploaded"` **on that response**, without needing to wait for the notification below.

> ⚠ **Confusion resolved — three multipart subtleties (division of labor · URL timing · how completion is learned).**
> 
> - ⭐ **Who chunks vs who counts:** the **client splits the actual bytes** into parts. The **backend only decides the part _count_** and issues that many presigned URLs (one per part number) — it works with **numbers + metadata, never file content** (it never receives the bytes). "Backend chunks" would be impossible since bytes bypass it.
> - ⭐ **All presigned URLs one-shot (default) vs on-demand:**
>     - **Default = one-shot** — at initiation the backend generates **all N part URLs at once** and returns them together (one round-trip; client then PUTs parts in parallel).
>     - ⚠ **But presigned URLs expire.** For a very large / slow upload (e.g. 50GB over a weak link) the later part URLs could **expire before you reach them.**
>     - **Fix for that case = on-demand** — issue each part's presigned URL just before its upload (or refresh expired ones). Also better when N is huge (tens of thousands of parts → a giant initiation response).
>     - ⭐ **The deciding rule:** upload finishes within the expiry window → one-shot is fine; might outlast expiry → on-demand.
> - ⭐⭐ **How completion is learned — a notification DOES exist, but the backend doesn't need it (correction to an earlier draft of this note):**
>     - ⚠ **WRONG (my earlier claim):** multipart has _no_ S3 event notification at all.
>     - ✅ **HI is correct, confirmed via web search:** S3 **does** fire an event (`s3:ObjectCreated:CompleteMultipartUpload`) — but **only once, when the full multipart upload completes** (all parts assembled into the final object). **Per-part `UploadPart` calls never trigger a notification**, regardless of upload model — that's why `ListParts` exists for progress tracking.
>     - ⭐ **Why our design doesn't need to _wait_ on it anyway:** our **backend is the one calling** `CompleteMultipartUpload` — a synchronous request — so it already gets success/failure **directly in that response**, at the same moment the notification would fire. It updates `status="uploaded"` off the response, not off the notification. The notification exists but is redundant for a caller who made the call itself.
>     - ⚠ **One extra nuance worth holding:** `CompleteMultipartUpload` can take **several minutes** to finalize server-side and can still fail even after an initial `200 OK` — production code should treat the response as needing confirmation, not pure fire-and-forget.
>     - ⭐ **The one-liner:** single-shot upload has **no synchronous signal** (the backend never made the S3 call) → it **must** rely on the notification. Multipart upload's backend **did** make the final call → gets the answer synchronously and doesn't need to listen for the notification, even though S3 still emits one.

- ⭐ **This is exactly S3 Multipart Upload.** Name-drop it (shows hands-on experience) **but be able to explain the mechanism** — HI says you can't get away with just "I'd use the S3 Multipart API."
- ▸ **Downloads don't need chunking** — once assembled, it's one object → one presigned/CDN URL. For big files, **HTTP Range requests** let the client parallelize or resume downloads without knowing chunk boundaries.

### 2) How can we make uploads, downloads, and syncing as fast as possible? ⭐

> ▸ Prose dive (no Bad/Good/Great). Recaps + two new levers: delta sync and compression.

#### Recap — what we already have

- **Download:** CDN caches near the user (§4.2).
- **Upload:** chunking → send **multiple chunks in parallel** + **adaptive chunk size** to saturate available bandwidth (the pipe is fixed; use all of it).

#### ⭐ Delta sync + content-defined chunking (CDC)

- ▸ **Only sync the chunks that changed**, not the whole file.
- ⚠ **The fixed-size-chunk trap:** with fixed 5MB boundaries, inserting **one byte near the start** shifts _every_ subsequent boundary → every later chunk re-fingerprints → delta sync becomes useless.
- ⭐ **Fix = Content-Defined Chunking (CDC):** boundaries are chosen by **content** via a **rolling hash** (Rabin fingerprinting). A small edit only changes the chunks **around** the edit; the rest stay identical. ⭐ **This is how Dropbox actually does efficient delta sync.**

#### ⭐ Compression (when it's worth it)

- ▸ Fewer bytes → faster transfer. Since uploads go **direct to S3**, compression is **client-side**: client compresses before upload, stores compressed in S3, decompresses after download. Backend stays out of the data path.
- ⚠ **Only compress when it pays** — the transfer saving must beat compress+decompress time:
    - **Media (png/jpg/video)** → already compressed → ratio ~few % → **skip.**
    - **Text** → high ratio (5GB → ~1GB) → **worth it.**
    - Decide client-side by file type + size + network conditions.
- ▸ **Algorithms:** Gzip (ubiquitous) · Brotli (better ratio, esp. text) · **Zstandard** (fast + tunable — strong client-side choice).
- ⭐⭐ **Always compress _before_ you encrypt.** Encryption randomizes bytes → randomized data won't compress. Compress-then-encrypt preserves the ratio.

### 3) How can you ensure file security? ⭐

> ▸ Prose dive. Three layers + the signed-URL mechanism.

- **Encryption in transit** — HTTPS between client and everything. (Table stakes.)
- **Encryption at rest** — S3 server-side encryption; S3 encrypts with a key stored separately from the file → stolen file is useless without the key.
- **Access control** — the `SharedFiles` table **is** the ACL; download links go only to authorized users.

⚠ **The real problem: an authorized user leaks a download link** (posts it to a forum). How do you stop an unauthorized downloader?

- ⭐ **Signed URLs** (S3 presigned / CDN signed) — the answer from §4:
    - **Generation:** server signs a URL embedding the path + an **expiry timestamp** (+ optional IP), using its private key.
    - **Distribution:** handed to the authorized user.
    - **Validation:** the CDN/S3 checks the signature (public key) + expiry + restrictions → serves only if valid + unexpired.
- ⚠ **Signed URLs are bearer tokens** — anyone holding a valid, unexpired URL can download. Short expiry (e.g. **5 min**) limits exposure but doesn't fully prevent sharing.
- ▸ **Higher-security options:** IP binding · require auth cookies alongside the signed URL.

|Calibration|⭐ HI "easy," but **DD1 (large files) is the real content.** Score: presigned URLs, client-side chunking + multipart, fingerprinting, delta sync (CDC), hybrid sync. **This = the Handling Large Blobs pattern (`03f`)**|

|⭐ CAP call|consistency only if **every read must see latest write** (stock-trading). Dropbox tolerates seconds of staleness → **availability wins** (`01h`)|
|Entities|File · FileMetadata · User|
|API|`POST /files` (→ presigned) · `GET /files/{id}` (→ presigned) · `POST /files/{id}/share` · `GET /files/changes?since=t`. ⭐ **user in headers, not body**|
|Metadata store|DynamoDB **or** Postgres — don't agonize (`02f`/`02g`)|
|⭐ Upload ladder|Bad: single server (no scale, no reliability) → Good: backend→S3 (⚠ double upload) → ⭐ **Great: presigned URL, client→S3 direct** (backend signs locally, no S3 call; S3 notification updates metadata)|
|⭐ Download ladder|Bad: through server (⚠ double download) → Good: presigned S3 (⚠ one region = slow far away) → ⭐ **Great: CDN** (edge cache, CDN signed URL). ⚠ CDN pricey → cache-control + invalidation|
|⭐ Share ladder|Bad: sharelist on file (⚠ "shared with me" = scan all) → Good: cached inverse map (⚠ sync burden) → ⭐ **Great: normalized `SharedFiles` table**, composite PK `(userId, fileId)`, no sync|
|⭐ Sync|**Local→Remote:** sync agent (OS file events) + **last-write-wins.** **Remote→Local:** ⭐ **hybrid** = 1 WebSocket/SSE per device (push) + periodic poll `?since=t` (safety net) → eventual consistency (`03a`)|
|Components|control plane = **File Service** (metadata + signs URLs, **never touches bytes**) · S3 (bytes) · CDN (edge) · Metadata DB (+ SharedFiles ACL) · LB/API Gateway (`02d`)|
|⭐⭐ Large files: limits|⚠ timeouts · **API Gateway 10MB cap** (⭐ applies to control-plane JSON only — **bytes bypass the gateway, so 10MB never gates file size**) · interruptions · no progress. Math: **50GB×8/100Mbps ≈ 4000s ≈ 1.11hr**|
|⭐ Small vs large upload path|⭐ **bytes ALWAYS go client→S3 direct (all sizes).** Branch by size: **small (≲100MB)** → single presigned `PUT`; **large (≳100MB, mandatory >5GB)** → S3 multipart + per-part URLs. 4MB → single PUT, no chunking. ⚠ "S3 Multipart Upload" ≠ HTTP `multipart/form-data`. SDK auto-switches but explain it yourself|
|⭐⭐ Chunking|5–10MB pieces, **on the CLIENT** (⚠ server-side chunking defeats the purpose). Enables progress + resumable. Persist `chunks[]` in FileMetadata|
|⭐ Chunk-status ladder|Good: client PATCH (⚠ trust client = security risk) → ⭐ **Great: server-side ETag verify via `ListParts`** ("trust but verify")|
|⭐ Fingerprinting|**SHA-256 of content** = dedup + resumability id. ⚠ identifies **content not record** (same content → same fp) → `fileId`=UUID, `fingerprint`=separate field. Chunk-level fps too. Mirror of `05a` hash (identify vs shorten)|
|Multipart flow|fingerprint → check-exists/resume → `CreateMultipartUpload` (uploadId + per-part presigned URLs) → upload parts + PATCH ETags (verify `ListParts`) → `CompleteMultipartUpload` → status "uploaded". Downloads: **HTTP Range requests** (no chunk knowledge needed)|
|⭐ Multipart subtleties|⭐ **client splits bytes; backend only decides part _count_ + issues N URLs** (never sees bytes). URLs **one-shot by default**, ⚠ but they **expire** → **on-demand** for very large/slow uploads. ⭐⭐ notification **does** fire once at full completion (`CompleteMultipartUpload` event) — ⚠ **never per-part** — but backend doesn't need it: it **made the completion call itself** and gets success **synchronously in that response**|
|⭐ Fast: delta sync|only sync changed chunks. ⚠ fixed chunks: 1-byte insert shifts all boundaries → ⭐ **Content-Defined Chunking (CDC) w/ rolling hash** (Rabin) → edit only touches nearby chunks|
|⭐ Fast: compression|client-side (direct-to-S3). worth it for **text** (5GB→1GB), skip **media** (already compressed). Zstandard = fast+tunable. ⭐⭐ **compress BEFORE encrypt** (encryption randomizes → kills ratio)|
|⭐ Security|HTTPS (transit) · S3 SSE (rest) · SharedFiles = ACL · ⭐ **signed URLs** = short-lived (5min) bearer tokens (sig + expiry + optional IP); leaked link expires fast. Higher sec: IP binding / auth cookies|
