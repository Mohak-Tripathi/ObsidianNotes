🎟️ **What is [Ticketmaster](https://www.ticketmaster.com/)?**

Ticketmaster is an online platform that allows users to purchase tickets for concerts, sports events, theater, and other live entertainment.

## 1 · Requirements

### 1.1 Functional (what it does)

▸ **CRUX** — "Users should be able to…" statements. ⭐ **Prioritize the top 3** and stay focused; you have limited time.

1. ⭐ **Users should be able to view events.**
2. ⭐ **Users should be able to search for events.**
3. ⭐ **Users should be able to book tickets to events.**

⚠ **Below the line (out of scope):**

- Users should be able to **view their booked events**.
- **Admins / event coordinators** should be able to add events.
- Popular events should have **dynamic pricing**.

### 1.2 Non-functional (how it behaves)

1. ⭐⭐ **Availability for searching & viewing; consistency for booking (no double booking).** ▹ **One system, two different CAP answers (`01h`) — this is the defining requirement.**
2. ⭐ **Scalable / high throughput for popular events** — **10 million users, one event.**
3. ⭐ **Low latency search — < 500ms.**
4. ⭐ **Read heavy — 100:1.**

⚠ **Below the line:** GDPR · fault tolerance · secure transactions · CI/CD · regular backups.

### 1.3 ⭐⭐ The design driver — the consistency split, and the human in the middle

> ⭐⭐ **Two things define this problem. State both early.**

- ⭐ **One:** the **availability/consistency split** inside one system — browse and search want availability; booking wants strict consistency. **Every architectural choice downstream is one side of that line.**

|Path|Need|Therefore|
|---|---|---|
|**View / search**|availability, <500ms, 100:1 reads|**cache aggressively, stateless services, horizontal scale, ES for search**|
|**Booking**|⭐⭐ **no double booking**|**Postgres transactions + OCC or row-level locking**|

- ⭐⭐ **Two — and this is what makes Ticketmaster harder than `05d` Gopuff:** between selecting a seat and paying for it, **a human spends minutes typing card details.** The contended thing must be held **across** that gap.
    - ▸ A DB transaction **cannot** span it (§5.1 rung 1 explains why).
    - ⭐ **So the hold must live outside the transaction — which is what forces a distributed lock with a TTL.**
- ⊕ **(not in HI) — the `05d` comparison worth carrying, it clarifies both problems:**

||`05d` Gopuff|⭐ `05e` Ticketmaster|
|---|---|---|
|Contended thing|**fungible count** (quantity ≥ n)|⭐ **a unique seat** (one specific row)|
|Hold period|none — checkout is immediate|⭐⭐ **~10 min, human typing**|
|Therefore|**one transaction suffices**|⭐ **transaction + an external hold with TTL**|

## 2 · Core Entities

▸ **CRUX** — broad nouns, no columns yet.

- **Event** — date, description, type, performer/team. The central record.
- **User** — the person interacting with the system.
- **Performer** — individual or group performing. ▹ Deliberately general — could be artist, company, collective.
- **Venue** — physical location: address, capacity, and ⭐ **a specific seat map.**
- **Ticket** — event ID, seat details (section, row, number), price, status (available / sold).
- **Booking** — user ID, list of ticket IDs, total price, status (in-progress / confirmed).

> ⭐ **Two modelling details that matter later:**
> 
> - ⭐⭐ **Tickets are generated per seat at event creation**, from the venue's seat map. The **seat map lives on the Venue entity** (e.g. a JSON structure or related table: sections, rows, seat numbers **plus coordinates for rendering**). ▸ **The client combines the seat map with each ticket's status to render the interactive seat-selection UI.** ⭐ **This is why the view API returns `Ticket[]` — the map is static, the statuses are not.**
> - ⭐⭐ **The split in one line: a venue seat map describes the physical layout _once_; a ticket represents that specific seat for _one specific event_.**
>     - Venue seat **A-1** → the seat map stores **where A-1 appears on screen**.
>     - Create a concert at that venue → the system creates a ticket: `eventId=concert123, seat=A-1, price=100, status=available`.
>     - The client **loads the map to draw the seat**, then **uses the ticket status to colour it** — available / reserved / sold.
>     - ⭐⭐ **The same physical seat has a different ticket per event** — A-1 can be **sold for Friday's concert and still available for Saturday's.**
> - ⭐ **Why Booking is separate from Ticket:** you _could_ fold booking data into Ticket, but a separate Booking entity **groups a multi-ticket purchase under one order** with a shared payment status and total price.

- ▸ **Simplest thing first:** a **Search Service** that connects to the DB and queries it by **filtering on the fields in the API request.**

**The search flow:**

1. Client makes a **REST GET** request with the search parameters.
2. ⭐ **Load balancer** accepts the request and routes it to the API gateway with the **fewest current connections.**
3. **API Gateway** handles basic **authentication and rate limiting**, then forwards the request to the **Search Service.**
4. **Search Service** queries the **Events DB** for events matching the search parameters and returns them to the client.

### 4.3) Users should be able to book tickets to events

- ⭐ **The thing to avoid, stated plainly:** two or more users **paying for the same ticket.** _"That would make for an awkward situation at the event."_
- ⭐ **So pick a database that supports transactions.** Anything with **ACID** is fine (MySQL → DynamoDB); **HI opts for PostgreSQL.** ⭐ **And say the next sentence, because it's the part candidates skip:** you also need **proper isolation levels and either row-level locking or OCC** to fully prevent double bookings (`02g §6`) — ⭐⭐ **"I chose Postgres" is not by itself a solution.**
- ▸ **Pattern: Dealing with Contention (`03b`)** — HI's own tag. Name it.

**New tables:** **Tickets** (event ID, seat, price, status, `bookingId` linking to Bookings) and **Bookings** (user ID, ticket IDs, total price, status).

**Booking Service** — owns the booking process, talks to Bookings/Tickets, and interfaces with **Stripe**. On payment confirmation it sets the ticket status to **sold**.

**The flow:**

1. User lands on a booking page, provides payment details, confirms.
2. `POST /bookings` with the selected ticket IDs.
3. The booking server opens a **transaction**: **check availability → set tickets to "booked" → create the Bookings record.**
4. Success → success response. ⚠ **Failed because someone else booked it meanwhile → failure response passed back to the client.**

▹ ⭐ **Note:** this means that **when a new event is created we need to create a new ticket for each seat in the venue.** Each of which will be **available for purchase until it is booked.**

> ⭐ **The shared-database argument (third time in the series — have it memorized).** _"The 'database per service' rule gets repeated a lot, but it's not a hard-and-fast rule."_ Shared is right here because: **data is tightly coupled** (bookings need tickets need events) · **ACID transactions are required for booking** · **splitting adds complexity for no real benefit.** ⭐⭐ **HI's closing line is the one to borrow: "weigh the tradeoffs and make a decision instead of parroting architectural dogma."** ▹ Same argument as `05c §4.3` and `05d §4.2`.

⚠⚠ **Flag the fundamental flaw yourself before the interviewer does:** a user can reach the booking page, **type in their payment details, and only then discover the ticket is gone.** ⭐ **"That's a real problem and I'll fix it in the deep dives"** → §5.1.

## 5 · Deep Dives

> ▹ HI's note on who drives: **mid-level — the interviewer may drive most deep dives. Senior/staff+ — agency and ownership are expected; you should "look around corners."**

### 1) How do we improve the booking experience by reserving tickets? ⭐⭐

> ⭐⭐ **The heart of the problem. Four rungs — walk all four.** ⚠ Nobody wants to spend 5 minutes on a payment form only to lose the ticket **"because someone else typed their credit card info faster."**

**Three things the solution must do:** lock the ticket while the user checks out · **release it if they abandon** · mark it sold and confirm the booking if they finish.

#### ⚠ Bad Solution — long-running DB locks ("interactive transactions")

- **Approach:** `SELECT … FOR UPDATE` in Postgres locks the ticket row as part of a transaction, **held until commit or rollback** (`02g §6.3`). Other transactions selecting the same row block. Finalize → commit, lock released, status "Booked". Abandon → rely on **subsequent actions or session timeouts.** ⚠ **Risk of tickets locked indefinitely.**
- ⚠ **Challenges — why it's bad:**
    - ⭐ **DB locks are meant for short, near-instant transactions.** Holding one for ~5 minutes **strains database resources** and raises **lock contention and deadlocks.**
    - **`lock_timeout` exists** but isn't graceful for a user-facing flow — ⭐ **users see an error rather than being queued.** Making it graceful needs **application-level management and extra complexity.**
    - **Doesn't scale under high load** — prolonged locks → longer waits, performance bottlenecks.
    - ⚠ **Crashes and network issues leave locks in an uncertain state.**

**Why climb:** the hold has to survive a human, and a transaction is the wrong lifetime for that. Move the state out of the lock and into the row.

#### Good Solution — status + expiration column, swept by cron

- **Approach:** add **status** and **expiration** to the ticket. Three states: **available · reserved · booked.** On select → **reserved** + timestamp. Purchase → **booked.** Abandon → back to **available** once expiry passes, via a **cron job** that finds `reserved` rows past the lock duration and resets them.
- ⚠ **Challenges:**
    - ⭐ **Delay in unlocking** — inherent lag between expiry and the cron run. **Tickets stay unavailable after they should be free, reducing booking opportunities** — worst exactly for high-demand events.
    - ⚠ **Reliability** — if the cron fails or lags, **booking is disrupted**; lost revenue.

**Why climb:** the cron is load-bearing, so its failure changes system behaviour. Make correctness independent of it.

#### Better Solution — short transactions, expiry in the predicate

- ⭐⭐ **The insight:** a ticket's effective status is **two attributes combined** — _available_ **OR** _reserved but the reservation has expired._ So use **short transactions** that check that condition and claim the row.

```
BEGIN
  check ticket is AVAILABLE or (RESERVED and expiration < now)
  update → RESERVED, expiration = now + 10 min
COMMIT
```

- ⭐ **Guarantees only one user can reserve or book**, _and_ lets users **claim tickets from expired reservations immediately.**
- ⚠ **Challenges:**
    - Reads are **slightly slower** — filtering on two values. ▹ Mitigate with **materialized views** and a **compound index.**
    - **The table is less legible** to other consumers (some "reserved" rows are actually expired). ▹ A sweep job still helps — ⭐⭐ **but the crucial difference: system behaviour is unaffected if the sweep is delayed.**
- ⭐⭐ **This rung _is_ `03b` rung 1 — a conditional write — and your note already has it nearly verbatim:** _"`reserved_by` + `reserved_until`; conditional `UPDATE … WHERE reserved_until IS NULL OR < NOW()`; rowCount 1 = won, 0 = taken; **expiry in the `WHERE` = no cleanup job**."_ ▹ **If you only remember one rung, remember this one — it needs no extra infrastructure.**

**Why climb:** correct, but Postgres still can't expire a row by itself, so "reserved" lingers as data and the read path has to reason about time.

#### ⭐ Great Solution — distributed lock with TTL (Redis)

- ⭐⭐ **Answer the obvious objection first — "Postgres is already strongly consistent, why add Redis?"** Because we need a **temporary reservation that expires by itself.** **Postgres has no native row-level TTL** — you'd need application-level expiration, i.e. the cron above. ⭐ **Redis has automatic key expiration built in**, and being in-memory, **acquire/release is extremely fast under high concurrency** (`02a`).
- **How it works:**
    - Select a ticket → **acquire a Redis lock keyed by ticket ID with a TTL.**
    - Purchase completes → DB status → **"Booked"**, and the app **releases the lock manually** before the TTL.
    - TTL expires → **Redis releases it automatically**, ticket becomes bookable with no intervention.
- ⭐⭐ **Consequence worth stating: the Ticket table now has only two states — available and booked.** Reservation lives **entirely in Redis.**
- ⭐ **Key = ticketId, value = userId** → so when a user confirms, you can verify **they are the one who reserved it.**
- ⭐ **No race on acquisition: `SET key value NX EX seconds` is atomic** — only one client succeeds (`02a`).
- ⭐ **Multi-ticket bookings:** acquire locks **sequentially per ticket**; ⚠ **if any fails, release the ones already acquired.** ▹ A **Lua script** makes multi-lock acquisition atomic **if the tickets hash to the same Redis node.**

> ⚠⚠ **Confusion resolved — your `03b` note says a Redis lock is "efficiency, not correctness… never for money." Tickets _are_ money. Contradiction?**
> 
> - ⭐⭐ **No — because Redis is not the correctness mechanism here. It's two layers:**
>     - **Redis = the _hold_.** A soft, self-expiring UX gate so users don't fill in a card for a seat someone else is taking.
>     - **Postgres = the _guarantee_.** The final write still goes through **OCC or row-level locking** (`02g §6`), so **two confirmations can never both succeed.**
> - ⭐ **HI says this explicitly:** if the lock goes down, _"we will still never have a double booking, since our database will use OCC or row-level locking."_ The only cost is **degraded UX** — some users get an error after entering payment details.
> - ⭐ **And the failure comparison is the thing to say:** a **Redis outage** means _some_ users hit an error late. A **cron failure** (the Good rung) means **every ticket appears unavailable.** ⭐⭐ **Degrading the hold is survivable; degrading the release is not.**
> - ▹ So your note's rule holds exactly as written: **never let Redis be the last word on money** — and here it isn't.

- ⚠ **Challenge 1 — read-path complexity. ⭐ HI says this is "worth calling out in an interview."** Reservations live in Redis, so how does the seat map show reserved seats as unavailable?
    - ⚠ **The tempting wrong answer:** a plain **Redis Set** of locked ticket IDs per event. ⭐⭐ **Set members don't expire when the lock keys do** → every abandoned checkout leaves a **ghost entry**, showing that seat reserved **forever.**
    - ⭐ **The fix — a sorted set scored by expiry:**

```
ZADD event:{eventId}:reserved <expiresAt> ticketId
```

```
- ▸ The seat-map read **only counts entries whose score is in the future**, so **expired holds disappear from the display on their own**; stale members get **lazily trimmed with `ZREMRANGEBYSCORE`** whenever the set is touched. ⚠ Costs one Redis round-trip on the read path — fast in practice.
- ▹ **Alternative:** **write through a "reserved" status to the DB** when acquiring the lock, treat the **Redis TTL as the source of truth for expiration**, and run a periodic sweep for stale DB rows.
```

- ⚠ **Challenge 2 — failure handling.** Lock down → degraded UX window; ⭐ **but never a double booking** (see the block above).
- ⚠ **Challenge 3 — ⭐ TTL expires _during_ payment.** A's lock expires at minute 10, their payment completes at minute 11, B grabbed the lock in between. ▸ **The DB transaction fails for one of them (OCC ensures only one write succeeds)** → ⭐ **issue an automatic refund via Stripe** for the failed booking. ⭐ **Mitigate: set the TTL generously, and better, extend the lock when payment is initiated.**

#### ⭐ The final booking flow (the reserve/confirm split, realized)

1. User selects a seat → `POST /bookings` with the `ticketId`.
2. API Gateway → **Booking Service**.
3. ⭐ **Booking Service locks the ticket in Redis with a 10-minute TTL.**
4. Writes a **Bookings** row with status **in-progress**.
5. Responds with the new `bookingId`; client routes to the payment page.
6. ▸ **If the user stops here, the lock auto-releases after 10 minutes.**
7. ⭐ **Payment:** client uses **Stripe.js to tokenize the card — your server never sees raw card numbers (PCI compliance).** Client sends the token + `bookingId`; server creates a **Stripe PaymentIntent**; Stripe processes and **notifies via webhook.**
8. ⭐ **Webhook** pulls the `bookingId` from Stripe metadata and runs **one transaction**: ticket → **"sold"**, booking → **"confirmed."**
9. ⚠⚠ **The webhook handler must be idempotent** — **Stripe retries on failure**, so processing the same event twice must not double-apply. ⭐ **Use `bookingId` as the idempotency key and check current booking status before updating** (`03g`).

### 2) How does the view API scale to tens of millions of concurrent requests? ⭐

> ▸ **Pattern: Scaling Reads (`03d`).** Event pages get **hammered** when tickets go on sale — thousands refresh the same page waiting for availability.

- ⭐ **Three levers: caching, load balancing, horizontal scaling.**
- ⭐ **Caching — what to cache:** data with **high read rate and low update frequency** — **event details** (name, date, venue info), **performer bios**, **static venue details** (location, capacity). ⭐ **"Cache it like crazy."** Key as **`eventId:eventObject`**; Redis or Memcached; **read-through** (miss → DB read → populate).
- ⭐ **Invalidation and consistency — two mechanisms:**
    - **Database triggers** notify the cache on changes (event dates, performer lineups) to invalidate entries.
    - ⭐ **TTL policy — tiered: long for static data (venue info), short for frequently-updated data (availability).**
- **Load balancing:** Round Robin or **Least Connections**. ▹ **You typically don't need to draw it, but mention it.**
- ⭐ **Horizontal scaling:** the **Event Service is stateless** → add instances and balance across them.
- ⚠ **Challenges:** cache/DB consistency under frequent updates (**not expected here**) · operational complexity of many instances, deployment and rollback.

### 3) How do we keep the UX good during high-demand events? ⭐⭐

> ⭐⭐ **Read HI's framing before the solutions, because it's the lesson, not an aside:** _"Sometimes the best solution is actually **not technically more challenging**. The mark of a senior/staff engineer is their ability to solve **business problems** — and sometimes that means thinking outside the box of presumed constraints."_ ⭐ **HI states that the Good vs Great below "are illustrative of a common delta between senior and staff candidates."**

- ▸ **The problem:** on popular events the **seat map goes stale within seconds.** Users repeatedly click a seat only to find it already taken.

#### Good Solution — SSE to push seat-map updates

- **Approach:** **Server-Sent Events** push updates to the client in real time, so the seat map updates as seats are booked or reserved **without a refresh.** ▹ **SSE is unidirectional, server → client** (`03a`).
- ⚠ **Challenge:** fine for **moderately popular** events. ⭐ **In the "Taylor Swift case" the seat map fills instantly** — a **disorienting, overwhelming** experience as seats vanish the moment they appear. ⭐⭐ **Solving the technical problem perfectly makes the user experience worse.**

**Why climb:** the problem isn't stale data, it's **too many people for the inventory.** Fix the flow, not the refresh rate.

#### ⭐ Great Solution — admin-enabled virtual waiting queue _(⭐ on revision: go deep here on how the Redis sorted set, the ordering and the `admitted` set actually work)_

- ⭐ **Approach:** an **admin-enabled** virtual queue that users enter **before they can even see the booking page.** It sits **in front of the Booking Service**, controlling the flow of users into the booking interface — preventing overload **and** improving experience.
- **How it works:**
    1. User requests the booking page → **placed in a virtual queue** over a **persistent connection (SSE or WebSocket)**. ⭐ **Queue backed by Redis — a sorted set with timestamps for ordering.** ▹ **SSE is simpler** (only server→client position updates); WebSocket if you anticipate bidirectional needs.
    2. **Dequeue periodically or on criteria** (e.g. tickets booked) and **notify** those users they can proceed.
    3. ⭐⭐ **Mark the user "admitted" in Redis** — session ID into an **`admitted:{eventId}` set with a TTL**. ⭐ **The Booking Service checks this set before allowing any reservation, rejecting anyone not admitted through the queue.** ▹ **This is the enforcement point — without it the queue is decorative.**
- ⚠ **Challenge:** long waits frustrate users, **especially if estimates are inaccurate.** ▹ Mitigate by **pushing real-time position and estimated wait** over the same connection.
- ▹ **Pattern: Real-time Updates (`03a`)** — note HI's phrasing: _"while we wouldn't pull the trigger on SSE for this use-case"_ — the queue is preferred over pure real-time seat updates.

### 4) How can you improve search to meet the low-latency requirement? ⭐

> ▹ ⭐ **Almost identical to `05c §5.3` — revise them together and save the time.** Three rungs.

- ⚠ **The problem:** keyword search needs a **full table scan** because of the leading wildcard.

```sql
-- slow query
SELECT * FROM Events
WHERE name LIKE '%Taylor%' OR description LIKE '%Taylor%'
```

#### ⚠ Bad Solution — standard indexes + query tuning

- **Approach:** index columns used in search — **event name, event date, performer name, venue location** — on Event, Performer, Venue. Plus query hygiene: **`EXPLAIN`** to read plans, avoid **`SELECT *`**, use **`LIMIT`**, and ⭐ **`UNION` instead of `OR`** for combining queries.
- ⚠ **Challenges:** ⭐ **standard indexes are weak at partial string matches** ("Taylor" vs "Taylor Swift") → you need full-text or `LIKE`, which is inefficient · indexes **increase storage and slow writes** · hard to balance index count against diverse query patterns.

#### Good Solution — full-text indexes in the database

- **Approach:** Postgres **`tsvector` + GIN** indexes (MySQL has its own full-text indexing) → far faster than `LIKE` scans for "Taylor" or "Swift". ⭐ **Note: neither uses Lucene, which is what powers Elasticsearch.**
- ⚠ **Challenges:** extra storage, **slower to query than standard indexes**, and **harder to maintain** — special handling in queries and in DB maintenance.

#### ⭐ Great Solution — Elasticsearch + CDC

- **Approach:** **Elasticsearch**, built on **inverted indexes** — each unique word maps to the documents containing it, so lookups are fast. ⭐ **Keep it in sync with Postgres via CDC** (inserts, updates, deletes replicated to the ES index).
- ⭐ **The payoff standard indexes can't give you: fuzzy search** — error tolerance for typos and spelling variants, **"Tayler Swift" → "Taylor Swift."** ⭐ **Very difficult with SQL alone.**
- ⚠ **Challenges:** sync needs a **reliable mechanism** for consistency · an ES cluster is **extra infrastructure complexity and cost.**

### 5) How can you speed up repeated search queries? ⭐

#### Good Solution — cache search results

- **Approach:** Redis/Memcached storing results of frequently executed queries, so repeats never touch the search engine.
- ⭐⭐ **Key design — the detail that matters: build the cache key from _every_ search parameter that can change the result.**

```json
{ "key": "search:keyword=Taylor Swift&start=2021-01-01&end=2021-12-31",
  "value": [event1, event2, event3],
  "ttl": 86400 }
```

- ⚠ **Challenges:** invalidation is hard — stale entries serve **wrong results**; ⭐ **worse when caching fuzzy results.** ▹ Use **TTLs plus invalidation triggers built around cache tags.** Frequent misses push load back onto search at peak.

#### ⭐ Great Solution — Elasticsearch's own caches + CDN

- ⭐ **ES has built-in caching:** **shard-level query caches for filter results**, plus a **separate shard-level request cache** for full search responses (**especially useful for aggregation-heavy queries**). ▹ Enables **adaptive caching** — the system learns and caches the most frequent queries over time.
- ⭐ **CDN** (e.g. CloudFront) to cache results **geographically closer to users** (`01a`). ⚠ **Only valid if search results are not personalized** — same query must return the same results for everyone.
- ⚠ **Challenges:** consistency needs real synchronization — you must invalidate when underlying data changes (a new event is announced), and ⭐ **that's hard because search queries and their potential results aren't connected.** Plus more infra to support.

Client

  │                       ▲
  │                      CDN  (non-personalized results)                01a

|API|`GET /events/:id → Event & Venue & Performer & Ticket[]` (**tickets to render the map**) · `GET /events/search?keyword&start&end&pageSize&page` · `POST /bookings/:eventId {ticketIds[], paymentDetails}`. ⭐⭐ **say upfront it will split into reserve + confirm**. ⚠ **don't enumerate fields** — poor use of time|
|⭐ Booking HLD|**pick an ACID DB** (MySQL→DynamoDB fine; HI picks **Postgres**) ⭐⭐ **and name the rest: proper isolation level + row-level locking OR OCC** — "I chose Postgres" is not a solution. Tables: **Tickets** (+`bookingId`) · **Bookings**. **Stripe** on payment → status "sold". ⚠ **flag the flaw yourself: payment typed, then ticket gone**|
|⭐ Shared DB|_"database per service is not a hard-and-fast rule"_ — tightly coupled (bookings→tickets→events) · **ACID needed** · splitting = complexity for no benefit. ⭐⭐ _"weigh the tradeoffs instead of parroting architectural dogma"_|
|⚠ DD1 Bad — long lock|`SELECT FOR UPDATE` held through checkout. ⚠ **DB locks are for short near-instant txns**; 5 min → **strains resources, contention, deadlocks**; `lock_timeout` ⇒ **users see an error, not a queue**; **doesn't scale**; **crashes leave locks uncertain**|
|DD1 Good — status + cron|3 states **available/reserved/booked** + expiration; cron resets expired. ⚠ **unlock delay** (tickets dead after expiry, worst for hot events) + ⚠ **cron failure disrupts booking**|
|⭐⭐ DD1 Better — expiry in predicate|status = **available OR (reserved AND expired)**. Short txn: check that → set RESERVED exp now+10 → commit. ⭐ only one winner **and** expired reservations are instantly claimable. ⚠ reads filter on 2 cols → **materialized view + compound index**; table less legible → optional sweep, ⭐⭐ **but behaviour is unaffected if the sweep lags**. ⭐ **= `03b` rung 1 conditional write — no extra infra**|
|⭐ DD1 Great — Redis TTL lock|⭐⭐ **why not Postgres alone: no native row-level TTL** → you'd need the cron. Redis = **built-in key expiry** + in-memory speed under high concurrency. ⭐ **Ticket table drops to 2 states (available/booked)**; reservation lives in Redis. **key=ticketId, value=userId** → verify the confirmer reserved it. ⭐ **`SET key value NX EX` is atomic** = no acquisition race. Multi-ticket: **sequential acquire, release all on any failure**; **Lua** for atomic multi-lock if same node|
|⭐⭐ Redis = hold, Postgres = guarantee|⚠ `03b` says Redis locks are **efficiency not correctness, never for money** — **not a contradiction:** Redis is the **soft self-expiring UX gate**; the **DB write still uses OCC/row-lock**, so **two confirms can never both succeed**. ⭐ **failure comparison: Redis down = some late errors; cron down = ALL tickets appear unavailable.** Degrading the hold is survivable; degrading the release is not|
|⚠ DD1 seat-map read path|reservations in Redis → how does the map show them? ⚠ **plain Set = ghost entries** (members don't expire with the lock keys) → seat reserved forever. ⭐ **sorted set scored by expiry: `ZADD event:{id}:reserved <expiresAt> ticketId`**; read **counts only future scores**; lazily trim with **`ZREMRANGEBYSCORE`**. ▹ alt: **write-through "reserved" to DB**, Redis TTL = source of truth, periodic sweep. ⭐ HI: **"worth calling out"**|
|⚠ DD1 TTL expires mid-payment|A's lock expires min 10, payment lands min 11, B took it → **DB txn fails for one (OCC: one write wins)** → ⭐ **auto-refund via Stripe**. ⭐ **generous TTL; better — extend the lock when payment starts**|
|⭐ Booking flow|select → `POST /bookings` → **Redis lock TTL 10min** → **Bookings row `in-progress`** → return `bookingId` → payment page → (stop ⇒ auto-release) → ⭐ **Stripe.js tokenizes, server never sees card (PCI)** → PaymentIntent → **webhook** → **one txn: ticket "sold" + booking "confirmed"**. ⚠⚠ **webhook must be idempotent** — Stripe retries; **key on `bookingId`, check status before updating** (`03g`)|
|⭐ DD2 scale views|**cache + load balance + horizontal scale** (`03d`). Cache **high-read/low-update**: event details, performer bios, static venue; key **`eventId:eventObject`**, **read-through**. ⭐ invalidation **two ways: DB triggers + tiered TTL** (long for venue, short for availability). LB: Round Robin / **Least Connections** (mention, don't draw). ⭐ **Event Service is stateless → scale out**|
|⭐⭐ DD3 the lesson|⭐ **"sometimes the best solution is not technically more challenging"** — solving **business** problems. ⭐⭐ **HI says Good vs Great here _is_ the senior→staff delta**|
|DD3 Good — SSE|push seat-map updates, no refresh; unidirectional (`03a`). ⚠ **Taylor Swift case: map fills instantly → disorienting.** ⭐ perfect tech, worse UX|
|⭐ DD3 Great — virtual queue|**admin-enabled**, users queue **before seeing the booking page**; sits **in front of Booking Service**. **Redis sorted set with timestamps** for ordering; **SSE simpler** than WebSocket for position updates. Dequeue periodically/on criteria → notify. ⭐⭐ **mark `admitted:{eventId}` set with TTL; Booking Service checks it before any reservation** — ▹ **without that check the queue is decorative**. ⚠ long waits frustrate → **push live position + ETA**|
|⚠ DD4 why search dies|`LIKE '%Taylor%'` on name **OR** description → **full table scan**|
