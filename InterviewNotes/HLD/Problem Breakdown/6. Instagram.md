## 0 · Understanding the problem

📸 **What is [Instagram](https://www.instagram.com/)?**

Instagram is a social media platform primarily focused on visual content, allowing users to share photos and videos with their followers.

---

## 1 · Requirements

### 1.1 Functional (what it does)

1. ⭐ **Users should be able to create posts** featuring **photos, videos, and a simple caption.**
2. ⭐ **Users should be able to follow other users.**
3. ⭐ **Users should be able to see a chronological feed of posts from the users they follow.**

⚠ **Below the line (out of scope):** like and comment on posts · search for users, hashtags or locations · **stories** (ephemeral content) · **go live** (real-time video streaming).

### 1.2 Non-functional (how it behaves)

> ⭐ **Ask for the scale _before_ you write the NFRs** — HI is explicit that it meaningfully changes the design. **Here: 500M DAU, 100M posts/day.**

1. ⭐ **Highly available, prioritizing availability of photos/videos over consistency** — ⭐ **eventual consistency is fine, up to 2 minutes** (`01h`).
2. ⭐ **Low-latency feed — < 500ms end-to-end** for feed requests.
3. ⭐ **Render photos and videos instantly** — low-latency media delivery (**< 200ms** on HI's whiteboard).
4. ⭐ **Scalable to 500M DAU.**

> ⚠ **Confusion resolved — aren't #2 and #3 the same thing?** No. They measure **two different parts of loading the feed.**
> 
> - **#2 = feed response latency (<500ms).** The backend returns the **list of posts and their metadata** — captions, media URLs.
> - **#3 = media delivery latency (<200ms).** Once the client has those URLs, the **actual image/video bytes** must load fast — usually from a **CDN near the user.**
> - ⭐⭐ **A feed can return in 200ms and still feel slow if its photos take 3 seconds to download.**
> - ⭐ **They also map to different deep dives:** #2 → **§5.1 (fan-out)** · #3 → **§5.2 (CDN + optimization).** ▹ Two NFRs, two separate problems.
> 
> ■ **— end of insert · HI write-up resumes below —**

⚠ **Below the line:** security (authn/authz/encryption) · fault tolerance / no data loss · analytics on user behaviour and engagement.

▹ ⚠ **The NFR discipline:** most systems are fault-tolerant and scalable — ⭐ **your job is to name the characteristics that make _this_ system unique.** Here that's **read-heaviness, media size, and a 2-minute staleness budget.**

### 1.3 ⭐⭐ The design driver — the work is in the wrong place

> ⭐⭐ **One sentence carries this entire problem, and it's HI's own:** _"The core issue is that we're **postponing the computational work until read time**, which is precisely when users expect immediate results."_ **Say this when you pivot into the deep dives.**

- ▸ **The asymmetry:** users **view** hundreds of posts a day and **post** only occasionally.
- ⭐ **So the naive design does the expensive work on the common operation**, and the fix is to move it to the rare one.
- ⊕ **(not in HI) — the economics in one line, since it makes the pivot concrete.** Assume ~200 followers on average (HI doesn't give this figure, so state it as an assumption):

||Work per day|
|---|---|
|**Fan-out on read**|2.5B feed generations × ~1,000 queries ≈ **~2.5 trillion reads**|
|**Fan-out on write**|100M posts × ~200 followers ≈ **~20 billion writes**|

- ⭐ **Roughly two orders of magnitude less total work**, and — more importantly — ⭐ **it moves off the latency-critical path.** ▸ **That's the trade: more work per post, almost none per read.**
- ▹ ⭐ **Same instinct as `05c`** — precompute `avgRating` on the rare write, keep the frequent read trivial. **Instagram is that idea at 500M DAU.**

## 2 · Core Entities

▸ **CRUX** — high-level overview first. ▹ HI notes there's **no single right approach** — if you prefer the full schema upfront, that's fine too.

- **User** — username, profile details. Keep it minimal.
- **Post** — a reference to the media file, a caption, and the creating user. ⭐⭐ **A single Post entity handles BOTH photos and videos** — don't split them.
- **Media** — the **actual bytes** of the file. **S3.**
- **Follow** — the relationship between two users: **follower → followee.** ⭐ **Unidirectional.**

## 3 · API

▸ One endpoint per core requirement. Start simple, add detail as you go.

### 3.1 Create a post

```
POST /posts -> postId
{ "media": {photo or video bytes}, "caption": "My cool photo!" }
```

- ⭐⭐ **The actual media upload is handled separately, via a pre-signed URL** (§5.2). ▸ This endpoint creates the **post metadata** and returns a `postId` the client uses afterwards.

### 3.2 Follow a user

```
POST /follows
{ "followedId": "123" }
```

- ⭐ **The follower's ID comes from the auth token (JWT or session)**, not the body — **more secure, and follows the principle of least privilege.** ▹ Including it in the body is acceptable in practice, **but then you must compare it against the session before following.**

### 3.3 Get the feed

```
GET /feed?cursor={cursor}&limit={page_size} -> Post[]
```

- ⭐ **Cursor pagination** plus a `limit` for page size; return the posts array **and a `next_cursor`** for the following page.

## 4 · High-Level Design

> ▸ Work one-by-one through the functional requirements.

### 4.1) Users should be able to create posts

▸ **Initial assumption: the media is small enough to upload in a single request.** (§5.2 removes it.)

```
Client ──► API Gateway ──► Post Service ──┬──► Database ── Post (id, userId, mediaS3Link, caption, createdAt…)
            routing · auth                └──► Blob Storage (S3) ── photos and videos
```

1. Client makes a **POST** to the API Gateway with the media and caption.
2. API Gateway routes to the **Post Service**.
3. Post Service stores the **metadata in the database** and the **bytes in the blob store**.
4. Post Service returns a **`postId`** to the client.

### 4.2) Users should be able to follow other users

- ⭐ **Unidirectional** — HI's example: _I follow @leomessi, he (sadly) doesn't follow me back._ ▸ **His posts appear in my feed; mine don't appear in his.**
- **Model it with a `Followers` table** storing `followerId` and `followedId`. Each `POST /follows` **inserts a single row.**
- ⭐ **A dedicated Follow Service**, separate from the Post Service: **following happens far less often than posting and viewing**, so separating lets you **optimize and scale each on its own needs.**

> ⭐ **The shared-database argument — 4th appearance in the series, and HI gives the fullest version here. Learn this table.**
> 
> ⭐ HI: _"We get a lot of comments from people concerned about two services writing to the same database… this is arguably **more academic than practical. Many production systems at FAANG and other large tech companies do have multiple services writing to the same database.**"_
> 
> ||✅ For|❌ Against|
> |---|---|---|
> |**Separate DB per service**|stronger **encapsulation/isolation** · **independent scaling** of DB resources · freedom to pick **different DB tech per service**|needs **distributed transactions or eventual consistency** for cross-service ops · **more operational complexity** · **higher infra cost**|
> |**Shared DB**|**simpler transactions** across domain boundaries · easier **referential integrity** · simpler **operationally and developmentally**|**tighter coupling** · one service's queries can **hurt another's performance** · **schema changes need coordination**|
> 
> - ⭐⭐ **The line to deliver:** _"Many organizations **start with shared databases and evolve toward more isolated data stores as specific needs arise.**"_ ▸ Here the two services deal with **related domain concepts**, so the coupling is natural.

### 4.3) Users should be able to see a chronological feed

▸ **The simplest approach — then we break it in the deep dives:**

1. **Get followees** — query the Follow table for the user_ids the current user follows.
2. **Get posts** — for each followed user, query the Post table for recent posts.
3. **Merge and sort** chronologically (by timestamp or postId).
4. **Return** the sorted posts.

▹ HI keeps this in the **Post Service** rather than adding a new one — ⭐ **"no right or wrong answer; you're trading off system complexity against the cost of the operations."**

#### ⭐ Database choice and indexing

- ⚠ **Without indexes these queries are full table scans** — every Followers row, then every Post row.
- ⭐ **HI picks DynamoDB** — given the **scale**, the **limited number of relationships**, and that **eventual consistency is acceptable.** ▹ **"PostgreSQL or most other databases would be equally valid — you just want to be able to justify your decision."**
- ⭐⭐ **The fun fact worth having ready:** **Instagram actually uses PostgreSQL** as its main post-metadata database. ▸ _"If you were following the SQL vs NoSQL debates of yesteryear you may be convinced a SQL DB could not scale to 500M DAU. Clearly not the case!"_ ⭐ **Use this if an interviewer pushes "surely SQL can't scale."**
- ⭐ **The key design (`02f`):**

|Table|Partition key|Sort key|Why|
|---|---|---|---|
|**Followers**|`followerId`|`followedId`|efficiently query **all users a given user follows**|
|**Post**|`userId`|⭐ **composite `createdAt` + `postId`**|most queries fetch **posts of a given user**; the composite gives **chronological ordering while keeping uniqueness**|

> 💬 **My question → HI Tutor (verbatim answer):** _"Tell me about Partition Key and sort key in DynamoDB. Also same Follower table — if I have to store in Postgres, how would I store it?"_
> 
> In DynamoDB, the partition key decides **where** data is stored, and the sort key **orders** related rows within that partition. For the Follow table, use `followerId` as the partition key and `followedId` as the sort key. Then this query is fast because DynamoDB goes directly to one follower's group.
> 
> ```
> followerId = user_1
>   followedId = user_2
>   followedId = user_9
>   followedId = user_15
> ```
> 
> In PostgreSQL, store the same relationship as a normal table and add an index. A **composite primary key prevents the same user from following someone twice.**
> 
> ```sql
> CREATE TABLE follows (
>   follower_id BIGINT NOT NULL,
>   followed_id BIGINT NOT NULL,
>   created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
>   PRIMARY KEY (follower_id, followed_id)
> );
> 
> SELECT followed_id
> FROM follows
> WHERE follower_id = 1;
> ```
> 
> PostgreSQL's primary key creates an index **starting with `follower_id`**, so this query is efficient. To find everyone following a posting user for feed fan-out, add the **reverse index.**
> 
> ```sql
> CREATE INDEX follows_by_followed_id
> ON follows (followed_id, follower_id);
> ```
> 
> ⭐⭐ **That reverse index is the PostgreSQL equivalent of the DynamoDB GSI on `followedId`.**
> 
> ■ **— end of insert · HI write-up resumes below —**

**The flow:**

1. Client **GET** with cursor and limit → API Gateway → **Post Service**.
2. Post Service queries the **Follow table** for the current user's followees.
3. Post Service queries the **Post table for each followed user**.
4. Combines, sorts, and returns — limited by cursor and limit.

⚠⚠ **Flag the problem yourself:** _"If I follow thousands of people this is crazy slow, even with indexes."_ ⭐ **HI: "And you're right!" — that's exactly the deep dive.**

## 5 · Deep Dives

### 1) Deliver feed content with low latency (< 500ms) ⭐⭐

> ⭐⭐ **The heart of the problem. Three rungs.** Our current **fan-out on read** could work for a small app; it will not scale to 500M DAU.

#### ⚠ Why fan-out on read fails — say this before proposing anything

- ▸ A user following **1,000+ accounts** needs **1,000+ queries** to the Posts table.
- ⭐ **DynamoDB batch operations are limited to 100 items and 16MB** → 1,000 accounts needs **at least 10 separate batch operations.** They can run in parallel, but three problems remain:
    1. ⭐ **Read amplification** — every refresh generates a large number of reads. **500M DAU × multiple refreshes/day** → unsustainable. **Expensive fast.**
    2. ⭐ **Repeated work** — two users following many of the same accounts means **querying the same posts over and over.** At Instagram's scale a popular post might be retrieved **millions of times.**
    3. ⭐ **Unpredictable performance** — latency varies with **how many accounts you follow and how active they are** → **consistent performance is nearly impossible.**
- ⭐⭐ **The numbers that settle it:**
    - Each refresh may process **10,000 posts** (1,000 accounts × 10 posts/day).
    - 500M DAU × **5 refreshes/day** = ⭐ **2.5 billion feed generations per day.**
    - Peak (evenings, major events) → ⭐ **150,000+ feed requests per second.**
- ▸ **So you'd have to either massively overprovision** (prohibitively expensive) **or accept higher latency at peak** (violating the requirement). ⭐⭐ **Neither is acceptable — and the flaw is architectural, not a tuning problem.**

▸ **Pattern: Scaling Reads (`03d`).** Users view hundreds of posts daily and post occasionally. ▹ HI's pattern note also mentions **sharding by user ID**, **vertical partitioning** by data type (profiles, posts, analytics) and **hierarchical storage** for older content.

#### ⚠ Bad Solution — a cache in front of the Posts table

- **Approach:** Redis in front of Posts, caching each user's recent posts. Check cache → return; miss → query DB → populate. ⭐ **Key: `feed:{user_id}:{cursor}`** (so you can fetch a specific _page_), **value: a list of postIds.**
- ⚠ **Challenges:** ⭐⭐ **"treating the symptom rather than addressing the root problem."** The cache must be **massive** to get a meaningful hit rate at this scale, **and you still perform the expensive fan-out read** to aggregate posts from all followed users on every feed request.

**Why climb:** caching the result of an expensive read still leaves the expensive read. Stop computing at read time.

#### Good Solution — precompute the feed (fan-out on write)

- ⭐ **Approach: generate the feed when a user _posts_, not when a user _reads_.**
- ⭐⭐ **The index that makes it possible — a GSI reversal on Follows:** partition key **`followedId`**, sort key **`followerId`**. ▸ The base table answers **"who do I follow"**; ⭐ **the GSI answers "who follows me"** — which is the query fan-out needs. ⚠ **Without this index, fan-out on write cannot be done.**
- For each follower, **prepend the new postId to their precomputed feed.** Store in a dedicated **Feeds table** (DynamoDB) **or a cache like Redis** — ⭐ **HI uses Redis**, for very fast read and write access.
- ⭐ **The data model (`02a`):**

|||
|---|---|
|**Key**|`feed:{user_id}`|
|**Type**|**Sorted Set (ZSET)**|
|**Members**|`postId`|
|**Scores**|**timestamp** (or `postId`, if chronologically sortable)|

> 💬 **My question → HI Tutor (verbatim answer):** _"Why a GSI, and how is it helpful in this example? Also explain the Redis sorted set (ZSET)."_
> 
> A GSI gives DynamoDB a **second lookup direction.** Your main Follows table is organized as `followerId -> followedId`, which answers **"Who does user A follow?"** But after user A posts, you need the reverse question, **"Who follows user A?"**
> 
> ```
> Main table                      GSI
> PK = followerId, SK = followedId    PK = followedId, SK = followerId
>   user_1 -> user_9                    user_9 -> user_1
>   user_2 -> user_9                    user_9 -> user_2
> ```
> 
> Now, when `user_9` creates `post_123`, query the GSI with `followedId = user_9`. It quickly returns `user_1` and `user_2`, so the fan-out service knows whose feeds need `post_123`. ⚠ **Without the GSI, DynamoDB would need to scan the whole table to find those rows.**
> 
> A Redis sorted set, or **ZSET**, is a collection where every item has a **numeric score** and Redis keeps items **ordered by that score.** For one user's feed, the key is `feed:user_1`, each member is a `postId`, and its score is the post timestamp.
> 
> ```
> feed:user_1
>   post_123  score 1730000100
>   post_122  score 1730000000
> ```
> 
> ⭐ When a new post arrives, add it with its timestamp. When the user opens their feed, ask Redis for the **highest-scored 20 items.** That returns the newest post IDs **in order** — which is exactly what a chronological feed needs.
> 
> ▸ **Follow-up — "is a ZSET a nested dictionary?"** A Redis ZSET is **one Redis value type. It is not a nested dictionary.** You have one Redis key, such as `feed:user_1`, which points to a sorted set. Inside it, **each postId is a unique member and each member has one numeric score**, usually the creation timestamp.
> 
> ```
> Redis key: feed:user_1
> 
> ZSET members
>   post_501  score 1730000200
>   post_498  score 1730000100
>   post_470  score 1729999000
> ```
> 
> Redis uses the score to keep members ordered, so fetching the newest 20 posts is fast. ⭐ **Conceptually it feels like `postId -> timestamp`, but Redis also maintains the ordering by timestamp for you.**
> 
> ▹ For fan-out on write the **GSI** is the important lookup; the **original table** is still used for the opposite question — who does `user_1` follow.
> 
> ■ **— end of insert —**

> ⊕ **(not in HI) — what a sorted set actually IS, since this one keeps tripping you up.**
> 
> ⭐⭐ **A ZSET is two structures kept in sync over the same data:**
> 
> |Structure|Holds|What it buys|
> |---|---|---|
> |**Hash table**|`member → score`|⭐ **O(1)** — "what is `post_501`'s score?" (`ZSCORE`)|
> |**Skip list**|members ordered **by score**|⭐ **O(log N)** — range and rank queries (`ZREVRANGE`, `ZRANK`)|
> 
> - ⚠ **It is NOT a set of tuples.** Two facts settle that:
>     - ⭐ **The member is the identity; the score is a mutable attribute.** `ZADD` with a member that already exists **updates its score** — it does not add a second entry. A set of tuples would happily hold both `(post_501, 100)` and `(post_501, 200)`.
>     - You can fetch **one member's score directly** in O(1). A set of tuples would have to scan.
> - ⭐⭐ **The mental model: a dict (`member → score`) that also keeps a sorted view of its keys, ordered by value.**
> 
> |Python|Redis|Stores|Ordered?|
> |---|---|---|---|
> |`set`|**SET**|members only|no|
> |`dict`|**HASH**|field → value|no|
> |—|⭐ **ZSET**|member → score|⭐ **yes, by score**|
> 
> - ⭐ **Ties:** members with **equal scores are ordered lexicographically by member**, so the ordering is always deterministic.
> - ⚠⚠ **The gotcha that bites in exactly this design: a score is a 64-bit double, so integers above 2⁵³ (≈9×10¹⁵) lose precision.** ▸ A **timestamp** in seconds, ms or µs is safe. ⚠ **A 64-bit snowflake-style `postId` (≈10¹⁸) is not** — it gets silently rounded, and two posts can collide. ⭐ **So "scores are timestamps (or postId if chronologically sortable)" only holds for small ids — prefer the timestamp.**
> - ▹ Small sorted sets are stored as a compact **listpack** and only convert to skiplist + hashtable past a threshold (default 128 members). Irrelevant at feed scale, but it's why ZSETs are cheap for tiny sets.
> - ⭐⭐ **Why you keep meeting this structure — it's the leaderboard, e.g. a LeetCode contest scorecard:**
> 
> ```
> ZADD      contest:123 <score> <userId>    -- submit / update        O(log N)
> ZREVRANGE contest:123 0 99 WITHSCORES     -- top 100                O(log N + 100)
> ZREVRANK  contest:123 <userId>            -- ⭐ "what is my rank?"   O(log N)
> ZINCRBY   contest:123 <delta> <userId>    -- a problem passes       O(log N)
> ```
> 
> - ⭐ **`ZREVRANK` is the reason a ZSET beats SQL for leaderboards:** finding _your own_ rank is **O(log N)**, where `ORDER BY score LIMIT …` would have to count every row above you.
> - ▹ ⭐⭐ **Same structure, three different meanings of "score" across the series:** **recency** (this feed) · **expiry** (`05e §5.1` seat-map reserved set, trimmed with `ZREMRANGEBYSCORE`) · **position** (`05e §5.3` virtual waiting queue, scored by timestamp).
> 
> ■ **— end of insert · HI write-up resumes below (Good Solution continues: hydration) —**

- ⭐⭐ **Hydration — reading the feed gives you postIds, not posts. Three options, and you should name all three:**

||Approach|Verdict|
|---|---|---|
|**1**|For each postId, **fetch metadata from the Posts table**|**Simple**, but ⚠ **an extra DB query on every feed request**|
|**2**|**Cache entire post metadata in Redis** (not just ids)|**Faster**, but ⚠ **more memory + data consistency challenges**|
|**3**|⭐ **Hybrid — two Redis structures: a ZSET for feed postIds + a short-lived post-metadata cache (HASH)**|⭐⭐ **Best balance of performance and resource usage**|

- ⭐ **Option 3, concretely:** try the Redis post cache for all metadata → **batch-fetch cache misses from DynamoDB with `BatchGetItem`** → **update the Redis post cache** → return combined results. ▸ **Tune the TTL** against memory constraints and consistency needs. ⭐ **Caption edited? Invalidate that post's cache entry and it refreshes on the next feed request.**

**Write flow (post creation):**

1. Store post metadata in Posts and media in the blob store, as before.
2. ⭐ **Put the postId on a queue** for asynchronous processing by the **Feed Fan-out Service** (`03g`).
3. Fan-out service queries the **Follows GSI** for everyone who follows the poster.
4. For each follower, **prepend the postId to their precomputed feed.**
5. Store the updated feed in Redis.

**Read flow (feed request):**

1. **Read the top N postIds from the user's ZSET** — a single, fast operation.
2. **Hydrate** — Redis post cache first, `BatchGetItem` from DynamoDB for misses.
3. Combine and return.

- ⚠ **Challenges:** ⭐⭐ **we traded read-time complexity for write-time complexity and increased storage.** The primary problem is **write amplification — the "celebrity problem."** ▸ **One post by a user with millions of followers triggers millions of Redis writes**, potentially overwhelming the system and **increasing write latency for popular users.**

**Why climb:** the model is right for almost everyone and catastrophic in the tail. Don't abandon it — exclude the tail.

#### ⭐ Great Solution — hybrid (fan-out on write + fan-out on read for celebrities)

- ⭐ **Approach: a follower-count threshold — say 100,000.**
    - **< 100,000 followers** → **precompute** into followers' feeds, as above.
    - ⭐ **> 100,000 followers ("celebrities")** → **do NOT precompute.** The post goes into the Posts table and **no asynchronous feed update is triggered.**
- ⭐ **On a feed request:**
    1. Fetch the **precomputed portion** from Redis (posts from sub-threshold users).
    2. **Query the Posts table for recent posts from the celebrities they follow.**
    3. **Merge the two chronologically** and return.
- ▸ So: ⭐ **fan-out on write for the majority · fan-out on read for the few celebrities.**

> 💬 **My question → HI Tutor (verbatim answer):** _"How does the system know which accounts are celebrities on the read path?"_
> 
> You are right that the system **cannot discover celebrities from the Posts table alone.** It needs a separate way to know which accounts the requesting user follows and which of those are **marked as celebrities.**
> 
> For `user_1` opening their feed, the flow is:
> 
> ```
> 1. Read feed:user_1 from Redis
>    This contains posts already fanned out from normal accounts.
> 
> 2. Query Follows where followerId = user_1
>    This returns accounts user_1 follows, such as user_9, user_20, user_30.
> 
> 3. Keep only celebrity accounts
>    Use a `User` profile field like followerCount, or a flag like isCelebrity.
>    user_9 has followerCount = 2M, so include user_9.
> 
> 4. Query Posts for each followed celebrity
>    Query by userId = user_9 and fetch their newest posts.
> 
> 5. Merge celebrity posts with the Redis posts by createdAt
>    Return the newest page to user_1.
> ```
> 
> ⭐⭐ **The main Follows table with `followerId` as the partition key is still needed here.** It answers, **"Who does `user_1` follow?"** The **GSI** with `followedId` as the partition key is used on the **write path.** It answers, **"Who follows `user_9`?"**
> 
> ⭐ **So celebrity status usually lives on the `User` record or in a small cache. It does not live in the Posts table.**
> 
> ■ **— end of insert · HI write-up resumes below —**

- ⚠ **Challenges:**
    - ⭐⭐ **The threshold needs careful tuning — too low and you don't solve write amplification; too high and you hurt read performance for too many users.**
    - ⭐ **Users following many celebrities get slower feeds → an inconsistent experience.** ▹ Mitigate by setting **clear SLAs for different user segments** and possibly **additional caching specifically for celebrity posts.**
    - **Two separate systems** (precomputed Redis feeds + real-time celebrity queries) → **storage and operational complexity**, needing **careful monitoring of both.**
- ⭐⭐ **"Instagram actually uses a similar approach in production"** — the benefits outweigh the complexity. ▹ Say that; it converts your answer from theory into practice.

▸ **Pattern: Managing Long-Running Tasks (`03g`).** Fan-out on write is the textbook case — **updating millions of followers' feeds is long-running and must happen asynchronously.**

> ⭐⭐ **Confusion resolved — "what if Redis goes down?" HI explicitly tells you to raise this _before_ being asked.**
> 
> - ⚠ **The risk:** without persistence configured, **a Redis failure loses all cached feed data** → service degradation and poor user experience. ⚠ **Don't present Redis as "a magical black box."**
> - ⭐ **The three things to name:**
>     - **Redis Sentinel** → high availability with **automatic failover.**
>     - **Redis Cluster** → **data sharding** across multiple nodes.
>     - **Persistence** → **AOF (Append-Only File)** or **RDB snapshots** to recover after failures.
> - ⭐⭐ **HI's suggested sentence, worth memorizing nearly verbatim:** _"We'd implement Redis with **AOF persistence and Sentinel for failover** to handle node failures with minimal data loss."_
> - ⊕ **And the fallback worth adding:** feeds are **derived data** — if Redis is lost entirely, they can be **rebuilt** from the Posts and Follows tables. ⭐ **A lost cache means degraded latency, not lost content.** ▹ Same two-layer thinking as `05e` (Redis is the hold, the DB is the guarantee).
> 
> ■ **— end of insert · HI write-up resumes below —**

### 2) Render photos and videos instantly — photos to 8MB, videos to 4GB ⭐

> ▸ **Two distinct challenges: upload efficiency, and download/viewing latency.** ⭐ **The upload half is a direct re-run of `05b` Dropbox — revise them together.**

#### Upload — presigned URL + S3 multipart

- ⭐ **Why chunking is mandatory, with the number:** a **single HTTP request is usually constrained to a max payload under 2GB.** ▸ So a **4GB video needs at least 2 requests** — in practice more, given metadata.
- ⭐ **S3 multipart upload API, three steps:**
    1. `POST /posts` creates the metadata and returns the **`postId`** _and_ ⭐ **a pre-signed URL**, valid for a limited time (e.g. **1 hour**), letting the client **upload directly to S3 without going through our servers.**
    2. The client uses the **multipart upload API** to upload the file **in chunks** to that URL.
    3. ⭐ **S3 automatically reassembles the chunks** and stores the final file.
- ▸ **Pattern: Handling Large Blobs (`03f`)** — presigned URLs + chunked uploads + CDN distribution recur across file-storage and video systems.
- ⭐ **The `uploadStatus` field:** metadata starts as **`pending`**; once the media is uploaded, update the post with the **S3 `object_key`** and set status **`complete`.**

> ⭐⭐ **Who reports completion? Two options — and HI has a clear preference.**
> 
> ||Approach|Verdict|
> |---|---|---|
> |**1. Client-driven**|client sends a **PATCH** with the `object_key` + status once multipart finishes|**Simpler**, but ⚠ **less reliable — you must trust clients to report completion honestly**|
> |**2. ⭐ Server-driven**|**S3 event notifications** trigger a **Lambda or background job** on multipart completion, which updates the metadata|**More complex**, but ⭐ **better data consistency — the backend keeps full control**|
> 
> - ⭐⭐ **"Most production systems opt for Option 2 despite the added complexity."** ▹ Same "never trust the client's word" instinct as `05b`'s server-side ETag verification.

#### ⚠ Bad Solution — serve media directly from S3

- **Approach:** return the S3 URL; the client downloads straight from S3.
- ⚠ **Challenges — three:**
    - ⭐ **Latency by geography** — a user in **Singapore** hitting a bucket in **us-east-1 might wait seconds** for images.
    - **Every request hits S3** → **expensive at scale** and **no caching benefit.**
    - ⭐ **Same high-resolution file for everyone**, regardless of device or network → **wasted bandwidth**, slower experience.

**Why climb:** the bytes are too far from the user. Move them closer.

#### Good Solution — CDN in front of S3

- **Approach:** a **CDN (CloudFront)** with a global network of **edge locations** caching media closer to users. Requests route to the **nearest edge**; a miss fetches from S3 and caches for next time.
- ⭐ **Configure caching by type and popularity** — e.g. **cache images 24 hours at the edge**, since they rarely change once uploaded. ▸ Dramatically cuts latency **and** origin load. ⭐ **CDN built-in compression** reduces transfer sizes.
- ⚠ **Challenges:**
    - ⭐ **Still serving identical files to everyone** — a mobile user on a slow connection gets the same high-resolution image as a fast desktop.
    - **Limited control over the caching strategy** → ⚠ **popular media can be evicted due to edge cache size limits**, causing unnecessary origin fetches.

**Why climb:** distance is solved; **fit** isn't. One file can't be right for every device.

#### ⭐ Great Solution — CDN + dynamic media optimization

- ⭐ **Approach:** on upload, a **media processing service (Cloudinary, Imgix)** generates **multiple variants** per file:
    - **Images** — different **resolutions** and formats like ⭐ **WebP** for supported browsers.
    - **Videos** — multiple **quality levels** plus ⭐ **adaptive streaming** (detail lives in HI's YouTube breakdown).
- ⭐ **The CDN serves the right variant based on requesting device and network conditions** — mobile gets appropriately sized images, desktop gets higher resolution. ▸ **The client includes device info and network conditions in its requests.**
- ⭐ **Intelligent caching:** cache **popular media more aggressively** at the edge, **shorter TTLs** for less-accessed content. ⭐⭐ **For viral content, proactively warm caches in regions where you predict high viewership.** ▹ **Say this one — predictive warming is a strong detail.**
- ⚠ **Challenges:** **multiple versions per file** → more **storage cost and complexity**; the **processing pipeline adds latency to uploads** and needs careful monitoring. ⭐ **Still what most large-scale media platforms do** — best balance of performance and manageability.

### 3) Scale to 500M DAU ⭐

> ▸ **Mostly a recap plus the storage math.** The four choices that carry the scale: ⭐ **hybrid precomputed feeds** (the cornerstone) · **CDN** with dynamic optimization · **chunked uploads** · **DB choice + careful PK/SK design.**

- ⭐ **The math:**

||Calculation|Result|
|---|---|---|
|**Media/day**|100M posts × ~2MB|**200TB/day**|
|**Media/10 years**|—|⭐ **~750 PB** — S3 handles it, ⚠ **but it's not cheap**|
|**Metadata/day**|100M × 1KB|**100GB/day**|

- ⭐ **Cost management: move cold data down a tier.** Media not accessed in a long time → **Glacier.** Infrequently accessed metadata → out of DynamoDB and into **S3.**
- ⭐⭐ **The reusable principle — worth memorizing:** _"The **warmer the storage, the more expensive** it is. Working back from **CDN → Cache/Memory → SSD → HDD → Tape**, we can always take data that is infrequently accessed and **move it down a level** to save money."_
- **Throughput:** horizontally scale the microservices dynamically — **automatic with most cloud providers, triggered on CPU or memory thresholds.** ▹ ⭐ **Each horizontally scaled set implicitly has a load balancer in front of it.**

  │                   ├──► Blob Storage (S3) ──┬── presigned-URL multipart upload
  │                   │                        ├── s3 notification ──► metadata update
  │                   │                        └── s3 notification ──► Image Processing
  │                   │                                                (Cloudinary/Imgix)
  │                   │                                                 → variants, WebP
  │                   └──► Message Queue (new postIds)
  │                             │
  │                             ▼
  │                      Feed Fan-out Service  ──► Precomputed Feed Cache (Redis)

                   hydrate: Redis HASH → BatchGetItem for misses
