## 1 · Requirements

### 1.1 Functional (what it does)

▸ **CRUX** — three features. HI leads candidates to exactly this set.

1. ⭐ **Users should be able to search for businesses** by **name**, **location (lat/long)**, and **category**.
2. ⭐ **Users should be able to view a business and its reviews.**
3. ⭐ **Users should be able to leave a review** — mandatory **1–5 star rating**, optional **text**.

⚠ **Below the line (name them, then park):**

- **Admins should be able to add, update, and remove businesses** — we focus just on the user, not the admin.
- **Users should be able to view businesses on a map.**
- **Users should be recommended businesses relevant to them.**

▹ **WHY these are below-line:** each one is a whole system (admin auth + moderation, map tiling, a recommender). Naming them and parking them is the scoping signal; silently designing them is how you run out of time.

### 1.2 Non-functional (how it behaves)

- ⭐ **Low-latency search — < 500ms.** ▹ This is the NFR that forces the entire DD3 search design. Note it's a _generous_ budget compared to `05a`'s <100ms redirect — search is allowed to be slower than a redirect.
- ⭐ **High availability; eventual consistency is fine** (`01h`). ▹ A review appearing a second late is harmless. This ordering is what licenses replicas, caches and an async-synced search index.
- ⭐ **Scale — 100M DAU, 10M businesses.**

⚠ **Below the line:** GDPR / user-data protection · fault tolerance · spam & abuse protection.

▹ ⚠ **The NFR discipline (worth re-reading):** every system is "fault tolerant" and "scalable" — listing those scores nothing. Your job is to name the **unique** characteristics that make _this_ system challenging. Here that's exactly two things: **search latency** and **the read:write asymmetry**.

### 1.3 Constraint the interviewer will add

- ⭐ **Each user can only leave one review per business.** HI's stated interviewer-introduced constraint. Framed as basic spam/abuse defense — it stops a competitor carpet-bombing a rival with 1-star reviews.
- ▹ Don't solve it in the HLD. Acknowledge it and **defer to deep dives** (§5.2) — that's HI's own sequencing.

### 1.4 ⭐⭐ The design driver — the asymmetry, and what it _removes_

> ⭐⭐ **State this in the first three minutes, and then keep returning to it.** In `05a` the asymmetry justified _adding_ caching. Here it justifies **not adding** three different things. That inversion is the whole problem.

- ▸ **~1000 reads : 1 write.** Everyone searches; almost nobody reviews.
- ⭐ **Derive it out loud:** 100M DAU at 1000:1 → **~100k writes/day → 100,000 ÷ 86,400 ≈ ~1 write/sec.** Modern Postgres handles **thousands** of writes/sec. **We are three orders of magnitude below the floor.**
- ⭐ **Data volume, same story:** 10M businesses × ~100 reviews each = **~1B reviews ≈ 1TB.** A single modern instance holds this. **No sharding** (`01f`) — don't even open the topic except to say you've checked.
- ⭐⭐ **What the asymmetry therefore kills:**

|Reflex answer|Why it's wrong _here_|What to say instead|
|---|---|---|
|Message queue for rating updates|⚠ ~1 write/sec. The queue adds a moving part to absorb nothing|**"Update it synchronously in the same transaction"** (§5.1)|
|Shard the database|⚠ 1TB on one box|**"One instance, replicas for reads"** (`03d`)|
|Separate DB per microservice|⚠ reviews and businesses are tightly coupled; you'd join across a network|**"Same DB, separate services"** (§4.3)|
|CQRS / write-optimized store|⚠ there is no write problem to optimize|**"The write path is trivial; all the pressure is on reads"**|

- ⊕ **(not in HI) — the meta-lesson to carry into every interview:** the asymmetry is the same tool as in `05a`, used in the opposite direction. **Read-hot → duplicate copies for reads** (replicas, cache, search index). The thing that changes between problems is only whether the _write_ side also needs help. Here it emphatically doesn't, and noticing that is the senior/staff split.

## 4 · High-Level Design

> ▸ Build one system that satisfies the three FRs; layer depth after. ⚠ **No Bad/Good/Great ladders in this HLD** — unlike `05b`, there are no competing architectures at this stage. It's a linear build. The ladders appear in the deep dives.

### 4.1) Users should be able to search for businesses

```
Client ──GET /businesses?query&location&category&page──► API Gateway ──► Business Service ──► Database
                                                          │                                     │
                                                    auth · rate limit · routing          Business
                                                          (02d)                          - id
                                                                                         - name
                                                                                         - description
                                                                                         - location (lat/long)
                                                                                         - address
                                                                                         - category
```

1. Client sends `GET /businesses` with search params.
2. **API Gateway** (`02d`) — authentication, rate limiting, routing.
3. **Business Service** — parses query params, builds the DB query.
4. **Database** — returns matching businesses → back through the gateway.

⚠ **Park the elephant explicitly:** this query is _catastrophically slow_ as drawn — a full table scan. ⭐ **Say so now and defer it:** _"This works functionally; the lat/long and name-term lookup needs a real index, which I'll take in deep dives."_ ▹ That one sentence buys you the whole HLD without the interviewer thinking you missed it.

### 4.2) Users should be able to view businesses (and their reviews)

- ▸ **No new service.** Gateway → Business Service → DB for business details, then reviews. Same DB, **join the two tables** for now.
- ⭐ **Pattern: Scaling Reads (`03d`).** With a 1000:1 ratio this is the canonical application — read replicas + cache, straight from the pattern file. Nothing new to derive; **name the pattern and cite it.**

```
Reviews
- userId
- businessId
- rating
- text
```

1. Client sends `GET /businesses/:businessId`.
2. **API Gateway** routes it to the **Business Service**.
3. **Business Service** retrieves business details **and** reviews from the Database.
4. The **combined** information is returned to the client.

> ⭐ **The reusable rule — when do you split a service?** Two criteria, and only two:
> 
> 1. **Is the functionality closely related?**
>     
> 2. **Do the parts need to scale independently** because of **vastly different read/write patterns**?
>     
> 
> - ▸ **Here:** searching and viewing are closely related _and_ both read-heavy → **same service.** Reviewing is a fundamentally different (write) pattern → **its own service** (§4.3).
> - ⭐ Carry this rule verbatim into every design interview. It converts "how many microservices?" from taste into a derivation.

### 4.3) Users should be able to leave reviews on businesses

- ▸ **One new service: Review Service.** Handles review creation and management.

```
Client ──POST /businesses/:id/reviews──► API Gateway ──► Review Service ──► Database
                                                                            (same DB)
```

1. Client sends `POST /businesses/:businessId/reviews` with the review data.
2. **API Gateway** routes it to the **Review Service**.
3. **Review Service** stores it in the Database.
4. A **confirmation** is sent back to the client.

- ⭐ **Why a separate service — the criteria from §4.2:** the usage pattern is _vastly_ different. Users search and view constantly; they almost never write. ⭐⭐ **HI flags that this insight "becomes fairly crucial later" — it is the same asymmetry that kills the message queue in §5.1.** Separating the services is what lets you scale the read tier hard and leave the write tier at one small instance.

> ⚠ **Confusion resolved — "shouldn't every microservice own its own database?"**
> 
> - ⭐ **HI's answer: "a resounding maybe."** The purist position is a real position, but many production systems share a database and that is often **the simpler and arguably correct** answer.
> - ⭐ **Why shared wins here, concretely:**
>     - **Tiny data** — 10M businesses × 100 reviews = **1TB**. One instance, no sharding needed.
>     - **Tight coupling** — businesses and reviews are read together constantly. Separate DBs → **join across a service boundary**, which is slow, chatty and awkward.
> - ⚠ **The honest counter-argument (name it):** **fault isolation** and **operational ownership** — if the review DB dies you don't want search and view to die with it. ▹ **Mitigation without splitting:** replication (`02g`).
> - ⭐ **The line to deliver:** _"I bias toward simplicity unless I can articulate a clear benefit to the added complexity."_ ⭐ **This is the same instinct DD1 tests. Stating your bias explicitly reads as principle rather than ignorance.**

## 5 · Deep Dives

> ▸ Four dives. ⭐⭐ **DD3 is "the crux of the interview" in HI's own words — budget your time so you reach it with 12+ minutes left.** DD1 and DD2 should each take ~3 minutes; they have short, confident answers. DD4 is the staff-tier extension.

### 1) How do you efficiently calculate and update average ratings? ⭐⭐

> ⭐⭐ **The highest-value section in the file, and the answer is "don't build the thing you're about to build."**

- ▸ **The requirement:** search results show partial business data — name, location, category — **and the average rating**, because that's the first thing users look at. Computing `AVG(rating)` across a business's reviews **on every search query** is hopeless: it's an aggregate over a large table, per result, per request.

#### ⚠ Bad Solution — calculate the average on the fly

- **Approach:** the simplest thing — no extra data, no extra infrastructure. Join businesses to reviews and aggregate at query time.

```sql
SELECT b.business_id, b.name, b.location, b.category,
       AVG(r.rating) AS average_rating
FROM businesses b
JOIN reviews r ON b.business_id = r.business_id
GROUP BY b.business_id;
```

- ⚠ **Challenges — three distinct ones; name all three, they're separate failures:**
    1. **Performance degradation** — cost grows with the review count. The **JOIN** is especially expensive for popular businesses with thousands-to-millions of reviews.
    2. **Unnecessary recalculation** — recomputed on **every search query**, even when no review has been added since the last run. Computationally wasteful by construction.
    3. ⭐ **Impact on unrelated read operations** — this heavy query runs constantly and **slows every other read** on the database. The blast radius is the whole system, not just search.
- ▸ **At 100M DAU and 10M businesses this leads to unacceptable performance and UX.** Dead on arrival.

**Why climb:** the work is redone per request although the answer only changes on a write. Get the computation off the read path.

#### Good Solution — pre-compute with a cron job

- **Approach:** add an **`average_rating`** column to the business table. A **cron job** runs periodically (once an hour, once a day) over the reviews table, computes each business's average, and writes it back. Search and view then just **read the column** — no join, no aggregate.
- ✅ Read path becomes trivial; the expensive work happens once per period instead of once per request.
- ⚠ **Challenge — staleness. Note this is a UX failure, not a performance one:** the rating doesn't account for real-time changes. ⭐ **HI's example is the one to carry into the room:** a business with **very few reviews** and a **currently low average**. You leave a **5-star** review and reasonably expect the average to rise to reflect your vote. With periodic recalculation it **may not move for hours or even days** → stale rating, confused user who thinks their review vanished.
- ▹ ⭐ **The generalizable lesson:** a staleness window is fine for an aggregate nobody is watching, and **unacceptable for one the user just changed themselves.**

**Why climb:** the user's own write has to be visible immediately. So update the aggregate **as reviews arrive**, not on a timer.

#### ⭐ Great Solution — synchronous update at write time

- **Approach:** add **`num_reviews`** alongside `avgRating`. On each new review the Review Service does two things: **insert the review row** _and_ **update the business's average**.
- ⭐ **The incremental formula — the reason this is affordable:**

```
new_avg = (old_rating × num_reviews + new_rating) / (num_reviews + 1)
num_reviews += 1
```

- ⭐ **It's a few CPU cycles**, so it runs **synchronously for every new review.** No background job, no timer, no staleness. ▹ Denormalization (`01c`) paid at the write — the right trade when reads outnumber writes 1000:1.

#### ⚠⚠ The problem the Great Solution introduces — concurrent updates

> ⭐⭐ **This is the real technical content of DD1 and the part most candidates skip. Walk the timeline out loud — it's the clearest possible demonstration that you understand the failure mode.**

- ⚠ **What if multiple reviews arrive for the same business at the same time?** One overwrites the other and the state goes inconsistent.
- ⭐ **The timeline to reproduce:**

```
Business A: num_reviews = 100, avg_rating = 4.0

User 1 reads state:          num_reviews = 100, avg = 4.0
User 2 reads state:          num_reviews = 100, avg = 4.0
User 1 submits 5★, computes: (4.0 × 100 + 5) / 101 ≈ 4.01
User 2 submits 3★, computes: (4.0 × 100 + 3) / 101 ≈ 3.99
User 1's update completes:   num_reviews = 101, avg = 4.01
User 2's update overwrites:  num_reviews = 101, avg = 3.99   ⚠
```

- ⚠ **The final state is wrong in two ways:** `num_reviews = 101` when **102** reviews exist, and the average **doesn't account for User 1's 5★ at all**. ⭐ **The correct value is `(4.0 × 100 + 5 + 3) / 102 ≈ 4.00`.**
- ▹ **Name it:** this is a **lost update** — the classic read-modify-write race (`02g §6`).

#### ⭐ The fix — optimistic locking

- **Approach:** read the current state, then attempt the update **conditional on nothing having changed since that read**. If it changed, **the update fails** → re-read, recalculate, retry.
- ⭐ **The neat detail:** OCC normally needs a dedicated **`version`** column — but here **`num_reviews` already behaves as one.** It increments on every write, so checking it hasn't moved _is_ the version check. No extra column.

```sql
UPDATE businesses
SET    avg_rating = :new_avg, num_reviews = :read_num + 1
WHERE  business_id = :id
  AND  num_reviews = :read_num;   -- 0 rows updated ⇒ someone wrote first ⇒ retry
```

- ▸ In the timeline above, **User 2's update now fails** (num_reviews moved 100 → 101). User 2 re-reads (4.01, 101), recalculates, and the final state is correct. ⭐ **HI labels the resulting diagram "Synchronous Update with Optimistic Locking"** — the locking is part of the answer, not a footnote.
- ⭐ **Why _optimistic_ and not pessimistic — say the reasoning, not just the name:** conflicts are almost nonexistent (~1 write/sec across **all** businesses, so two reviews landing on the **same** business in the same instant is vanishingly rare). ⭐ **OCC is correct precisely when conflicts are rare: you pay nothing in the common case and retry in the rare one.** A row lock (`SELECT … FOR UPDATE` → `02g §6.3`) would serialize writers for no benefit.

> ⊕ **(not in HI) — the alternative worth knowing, and when to offer it:** the race exists only because the _application_ does read → compute → write. A **single atomic SQL statement** eliminates the read, and with it the race and the retry loop:
> 
> ```sql
> UPDATE businesses
> SET    avg_rating  = (avg_rating * num_reviews + :new_rating) / (num_reviews + 1),
>        num_reviews = num_reviews + 1
> WHERE  business_id = :id;
> ```
> 
> - ⭐ The DB computes in place under its own row lock → concurrent reviews serialize correctly, **no version column, no retry, no lost update.**
> - ⚠ **But read the room:** HI's expected answer is **OCC**, and an interviewer asking this is usually fishing for the concurrency vocabulary — lost update, optimistic vs pessimistic. ⭐ **Best move: give OCC as the answer, then offer the atomic `UPDATE` as a simplification.** Leading with the atomic version can look like you're dodging the concurrency discussion rather than solving it.

#### ⚠ The over-engineered answer to refuse — a message queue

- **Approach (what most senior candidates propose):** write incoming reviews to a **message queue**; a consumer updates the average in a separate service.
- ▸ **It's a decent answer, not a wrong one** — it just introduces complexity that isn't necessary at this write volume, and reaching for it shows you skipped the arithmetic.
- ⭐ **The arithmetic — say these numbers out loud:**
    - 1000:1 read:write at 100M DAU → **~100k writes/day**
    - 100,000 ÷ 86,400 ≈ **~1 write/sec**
    - Modern databases handle **thousands/sec** → even accounting for surges, this will almost never be a problem.
- ⭐ **HI's verdict:** _"Calling this out is the hallmark of a staff candidate and is a perfect example of where simplicity actually demonstrates seniority."_
- ▹ **The line:** _"At one write per second a queue adds a moving part and an eventual-consistency surface to absorb load that doesn't exist. I'll update the aggregate synchronously, with optimistic locking for the concurrent-review case. If write volume grew three orders of magnitude — or the aggregate became expensive, like a recommendation score — I'd move it behind a queue."_ ⭐ **Naming the condition under which you'd change your mind is what separates "simple" from "naive."**

> ⚠ **Confusion resolved — why store `numRatings`? Isn't `avgRating` enough?**
> 
> - ⚠ **WRONG:** keep only the average and somehow nudge it on each new review.
>     
> - ⭐ **CORRECT:** an average is **not incrementally updatable from itself.** You need the count:
>     
>     ```
>     newAvg = (avgRating × numRatings + newRating) / (numRatings + 1)
>     numRatings += 1
>     ```
>     
> - ⭐ **Both fields are mandatory, and `numRatings` is independently useful** — "4.5 ★ (2,431 reviews)" is what users actually judge on; a 5.0 from one review is worthless.
>     
> - ⊕ **(not in HI) — the general primitive:** this is a **running aggregate maintained transactionally with the event that changes it** — the same shape as a like count, a view count, a follower count or an inventory total. ⭐ **The rule generalizes: store the components, not just the derived figure.**
>     
> - ⚠ **One honest wrinkle (worth raising if asked about edits/deletes):** with only `(avg, count)` you can add a review cleanly, but **editing** a rating requires the old value (`newAvg = (avg×n − oldRating + newRating)/n`) — fine, since the review row has it. **Deletion** similarly. ▹ If the interviewer pushes on correctness drift, the answer is a **periodic reconciliation job** that recomputes the aggregate from the source rows — the standard backstop for any denormalized counter.
>     

### 2) How do you ensure a user can only leave one review per business? ⭐

- ▸ **The requirement:** one review per (user, business). Basic spam/abuse defense — stops competitors repeatedly 1-starring rivals.
- ⭐⭐ **HI's governing principle, verbatim in substance:** _"Whenever we have a data constraint we want to enforce that constraint as close to the persistence layer as possible."_ ▸ **Why:** it guarantees business logic is **always** consistent regardless of which service or code path writes, and it avoids extra application-layer work.

#### ⚠ Bad Solution — check in the application layer

- **Approach:** service checks before writing. ⚠ **What mid-level — and often senior — candidates propose first.**

```python
def leave_review(user_id, business_id):
    reviews_for_business = db.get_reviews_for_business(business_id)
    if user_id in reviews_for_business:
        return "User has already reviewed this business"
    db.leave_review(user_id, business_id)
```

- ⚠ **Main challenge — not robust to change.** As the company grows: **other services** start writing reviews, **data engineers run backfills**. None of them know your application-layer constraint → they violate it.
- ⚠ **Secondary (HI's own ranking — raise it second):** **race condition.** Same user submits twice concurrently → both pass the check → two reviews.

#### ⭐ Great Solution — a database constraint

- **Approach:** enforce at the **database engine level**.

```sql
ALTER TABLE reviews
ADD CONSTRAINT unique_user_business UNIQUE (user_id, business_id);
```

- ✅ **Now impossible to violate** — the DB throws on a duplicate insert. Service **handles the error gracefully** and returns it to the client (`409`).
- ✅ **The race resolves itself:** there is always **one winner** (as long as the data sits on one DB instance, which it does here); the write processed second throws the unique-constraint error.
- ▹ Edits allowed ⇒ **upsert** (`ON CONFLICT … DO UPDATE`), and the aggregate update uses the edit formula from §5.1.
- ⊕ ⭐ **Transfer:** same primitive as a **dedupe / idempotency key** on any retryable create — one action per key, enforced by the schema, not the application.

### 3) How can you improve search to handle complex queries more efficiently? ⭐⭐

> ⭐⭐ **"This is the crux of the interview and where you'll want to be sure to spend the most time."**

#### The problem

```sql
-- This query sucks. Very very slow.
SELECT *
FROM businesses
WHERE latitude > 10 AND latitude < 20
  AND longitude > 10 AND longitude < 20
  AND name LIKE '%coffee%';
```

- ⚠ **Lat/long inequality comparisons without proper indexing** → **full table scan**, every record checked against all four conditions.
- ⚠ **Name/description terms** → wildcard `LIKE` search across the whole table → same full scan.

#### ⚠ Bad Solution — a composite B-tree on (latitude, longitude)

- **Approach:** the obvious first move — index the two columns, hope bounding-box lookups get fast.

```sql
CREATE INDEX idx_latitude_longitude ON businesses (latitude, longitude);
```

- ⚠ **Challenges — a B-tree is not optimized for 2-D data. Two named reasons:**
    1. **Range queries** — a geographic area is a range query on **both** lat **and** long. B-trees are efficient for **single-dimension** ranges and **struggle with multi-dimensional** ones.
    2. ⭐ **No spatial awareness** — the index treats lat and long as **independent values**; it doesn't capture the 2-D nature of coordinates. ▹ Mechanically: it sorts by `lat` and only breaks ties on `long`, so you get a strip of millions of unranked rows (`04a`).
- ▸ **Conclusion:** need purpose-built spatial structures — **R-trees, quadtrees, geohash-based indexes** (`04a`).

**Why climb:** location is only one of three filters, and each of the three needs a _different_ kind of index.

#### Good Solution — Elasticsearch (`02b`)

- ⭐ **The framing that scores — three filter types, three index strategies:**

|Filter|Index needed|
|---|---|
|**Location**|**geospatial index** — geohash / quadtree / R-tree|
|**Name**|**full-text search index** — inverted index over terms|
|**Category**|**simple B-tree**|

- **Approach:** **Elasticsearch** supports all three. A search-optimized database purpose-built for fast search queries, handles large datasets and complex queries traditional DBs struggle with. Supports geohashing, quadtrees **and** R-trees for the geospatial part.
- ⭐ **One query combines all filters and returns a ranked list:**

```json
{ "query": { "bool": { "must": [
    { "match": { "name": "coffee" } },
    { "geo_distance": { "distance": "10km",
        "location": { "lat": 40.7128, "lon": -74.0060 } } },
    { "term": { "category": "coffee shop" } }
] } } }
```

- ⚠ **Challenge 1 — ⭐⭐ never use Elasticsearch as your primary database. This is "a no-no."**
    - Not optimized to maintain **transactional data integrity with full ACID** compliance, nor to handle **complex transactions**.
    - Its **fault tolerance works but needs careful configuration** to avoid data loss on node/network failure.
    - ⭐ Use it for what it's designed for: **search and analytics over large datasets**, not primary storage.
- ⚠ **Challenge 2 — therefore it must be kept in sync with the primary DB → CDC (Change Data Capture).** DB changes captured as **events → queue/stream → consumer applies them to Elasticsearch.**

> ⚠ **Confusion resolved — why CDC, and not just write to both from the service?**
> 
> - ⚠ **The trap: the dual-write problem.** If the service writes to Postgres _and_ to Elasticsearch itself, the two writes aren't in one transaction. The second can fail (ES down, network blip) → **the index silently diverges from the source of truth** with no record that it happened.
> - ⭐ **CDC fixes this by construction:** the service does **one** write, to the DB. The change log (WAL) is the single ordered source driving the index — replayable, and divergence is detectable.
> - ▹ Our NFRs make the lag free: **eventual consistency is explicitly fine** (§1.2).
> - ⊕ ⭐ **The general rule:** same reasoning wherever a secondary store shadows a primary one — search indexes, analytics stores, caches, read models. **Never dual-write a system of record.**

**Why climb:** the whole consistency problem exists only because we added a second store. Can we avoid it entirely?

#### ⭐ Great Solution — Postgres with extensions (no new service)

- ⭐ **Approach: get around the consistency issue altogether** — keep one database and enable two extensions.

```sql
CREATE EXTENSION IF NOT EXISTS postgis;    -- geospatial index + queries
CREATE EXTENSION IF NOT EXISTS pg_trgm;    -- full text index + queries
```

- ✅ Geospatial index on lat/long **and** full-text index on name/description — **without introducing a new service**, and therefore **no CDC, no sync, no divergence.**
- ⭐ **The sizing that licenses it (the staff move — do this math out loud):**
    - 10M businesses × ~1kb = **10GB**
    - 10M businesses × 100 reviews × ~1kb = **1TB**
    - ▸ **Small.** Scaling is exactly what Elasticsearch excels at, and **we don't need it** → Postgres is "a perfectly reasonable solution."
- ⚠ **The honest caveat:** PostGIS is excellent for geospatial, but **may not perform as well as Elasticsearch for full-text search at very large scales.**
- ▹ **The line:** _"I'd reach for PostGIS and pg_trgm first — same index capabilities, no second store, no sync path. I'd move to Elasticsearch when search quality or scale becomes the product requirement rather than the lookup requirement."_

#### ⭐⭐ The variant to prepare — "design it WITHOUT Elasticsearch"

> ⚠ **Interviewers deliberately ban ES because it collapses the problem into "use the product."** HI says they're then looking for exactly three things. **Prepare these three as a unit.**

**(a) The geospatial indexing choice — and a defensible pick**

- ▸ Weigh **geohashing vs quadtrees** (R-trees if you have the familiarity). ▹ All internals → `04a`.
- ⭐ **HI's stated preference here: quadtree.** Two reasons, both properties of _this_ data:
    - **Updates are incredibly infrequent** — businesses don't move. A quadtree's weak point is churn; there is no churn.
    - **Businesses cluster densely** (NYC, SF) → the quadtree's **density-adaptive 4-way split** is exactly the right shape; a uniform grid wastes cells on empty land and overloads them downtown.

> ⚠ **Confusion resolved — why quadtree here when `04a` says "encoded cells for moving points" and Uber uses H3?**
> 
> - ⭐ **Both are correct, because the data shape differs — that's the whole decision rule from `04a`.**
> - **Uber/Swiggy:** millions of **drivers moving continuously** → every position is one integer update → **encoded cells (geohash/S2/H3)** win, because a cell ID is a plain sortable key and updates are cheap.
> - **Yelp:** **10M static businesses**, essentially write-once → nothing to churn → you can afford a **tree** and get density-adaptivity for free.
> - ⭐ **The trigger is _static vs moving_ (and point vs shape), never "which is the better index."** ▹ Saying this distinction out loud is a strong signal; it shows the index choice is derived, not memorized.
> - ⚠ **If pushed on production reality:** a quadtree is pointer-based and **disk-hostile** (`04a`), so real deployments reach for **R-tree via PostGIS/GiST** or **BKD via ES**. ⭐ **Mentioning that the textbook answer and the production answer differ — and why — is the staff flavour.**

**(b) Second-pass filtering (the step candidates skip)**

- ▸ A spatial index **never returns the answer** — it returns a **candidate set**. You then filter by **exact distance**.
- ⭐ **Haversine formula** — "like Pythagoras, but for distances on a sphere." Compute user↔business distance, drop anything outside the requested radius.
- ⭐⭐ **The `04a` closing line applies verbatim: _the index only hands you candidates — you always finish with exact math._** ▹ Also why the **3×3 neighbour-cell trick** exists in cell-based systems: points a metre apart can sit in different cells, so you query your cell plus its 8 neighbours, then post-filter.

**(c) ⭐ Filter sequencing — the cheap point nobody makes**

- ▸ **Goal: shrink the search space as fast as possible.**
- ⭐ **Distance is almost always the most restrictive filter → apply it first.** Then run name/category/rating filters over the **small** surviving set.
- ▹ **The line:** _"Geospatial filter first because it's most selective — it takes 10M businesses to maybe a few hundred. Everything else runs on those few hundred, so the text and category filters stop mattering for performance."_

### 4) How would you support search by named places (cities, neighbourhoods)? ⭐

> ⭐ HI's **staff-level follow-up**, asked when you've moved fast and cleanly. _"Pizza in NYC"_ — and crucially also _"The Mission in San Francisco"_, i.e. **neighbourhoods**, not just zips/cities/states.

- ⚠ **The first realization — say this before anything else:** **a radius from a centre point is insufficient.** Cities and neighbourhoods are **not circular** and have wildly different shapes. You need a **polygon** per place and a containment test.

**Two sub-problems:**

**(1) Name → polygon**

- **A `locations` table:** `name` ("San Francisco") · `type` ("city" / "neighborhood") · `polygon` (the geographic data — a list of lat/long points).
- **Source the data:** publicly available datasets (**GeoJSON** is the standard format and includes polygon handling; Geoapify is one source).
- **Index the `name` column** for fast lookup. ▹ A plain B-tree (`01d`) — this is an exact-match string lookup, nothing exotic.

**(2) Polygon → businesses inside it**

- ▸ Both stores support this natively: **Postgres/PostGIS → Geoshapes** · **Elasticsearch → geo_shape / geo_bounding_box queries.**

```json
{ "query": { "geo_bounding_box": {
    "location": { "top_left":     { "lat": 42, "lon": -72 },
                  "bottom_right": { "lat": 40, "lon": -74 } } } } }
```

- ⚠ **But running a bounding-box/polygon query on every request is wasteful** — the polygons never change and neither do the businesses.

#### ⭐⭐ The optimization — precompute the location arrays

- **Approach:** at **business creation time**, compute every area that contains it and store them as a **list of location identifiers** on the business.

```json
{ "id": "123",
  "name": "Pizza Place",
  "location_names": ["bay_area", "san_francisco", "mission_district"],
  "category": "restaurant" }
```

- ▸ Then all you need is an **inverted index** on `location_names` (a **`keyword`** field in ES; an array/GIN index in Postgres). _"Pizza in The Mission"_ becomes a **term lookup**, not geometry.
- ⭐ **Payoff:** the expensive polygon-containment math runs **once per business, at write time**, instead of on every one of millions of searches. ⭐ **This is the same read-heavy instinct as the denormalized `avgRating` in §5.1 — precompute on the rare write, keep the frequent read trivial.** ▹ **Pointing out that these two deep dives are the _same move_ is a strong closing observation.**
- ▹ Note the hierarchy falls out for free — a business is in `bay_area` **and** `san_francisco` **and** `mission_district`, so nested-place queries need no special handling.
- ⚠ **It does not replace the geospatial index — know this if pushed.** Precomputation only answers **named-place** searches ("pizza in Kanpur"). A **"within 2km of me"** search has no name to look up, so it still needs the **geospatial index + Haversine post-filter** (§5.3). ⭐ **Both paths coexist: name → term lookup; coordinates → spatial index.**
- ⚠ **The cost you're accepting:** the containing areas are frozen at write time. **Add a new neighbourhood, or redraw a boundary, and you must backfill** every affected business. The per-request polygon query never needs a backfill. ⭐ **Acceptable here for the same reason the quadtree was: boundaries essentially never move.** ▹ Say the condition out loud — it's the same "is this data static?" test that drove the index choice.
